# M12: Large solver and worker allocations are never NULL-checked, so memory pressure segfaults the worker instead of failing cleanly

verdict CONFIRMED, severity low, category robustness
locations: sokoban_bfs.c:1018 (256 MiB big table); HashStatePush128 (384 MiB); sokoban_solve_multi ms_lab calloc / ms_arena_tls malloc (3 MB / 24 MB); bq64_push / bq128_push realloc; backsearch.c parent-table pool (only the dedup tables and DFS queue are checked, with exit(1))

## Summary
Several large or long-lived allocations are used without a NULL check. If one fails, for example on a volunteer machine running many 0.5 GB workers, the worker dereferences NULL and dies with SIGSEGV instead of exiting with a clear error. The client then sees a run with no SUMMARY.

## Source report F30 (solver-core)
**Large solver allocations are never NULL-checked, so memory pressure crashes the worker instead of failing cleanly** at /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:1018

*summary*: calloc of 256 MiB (big push table), 384 MiB (HashStatePush128), 3 MB/24 MB (multi-start tables), and realloc in bq64_push/bq128_push are all used without checking for NULL.

*failure_scenario*: On a volunteer machine with many workers and little RAM, the 256 MiB calloc returns NULL. hs->slot becomes NULL, and the next hsp64_update segfaults. The worker dies without a SUMMARY, the job is re-run, and it can crash again on similar machines. It would be cleaner to return -2 (counted, per the silent-prune finding) or exit with a clear 'out of memory' message.

*evidence*: sokoban_bfs.c:1018  if (!hs->slot_big) hs->slot_big = calloc(HTP_SIZE, sizeof(HSlot64));
sokoban_bfs.c:2294  hsp128_tls = calloc(1, sizeof *hsp128_tls);
sokoban_bfs.c:1087  b->items = realloc(b->items, (size_t)b->cap * sizeof(HeapEntry64));

*suggested_fix*: Check each allocation. On failure, print 'OUT OF MEMORY' and exit with a distinct code the client reports as a machine problem, not a job result.

*expected_gain*: Failures under memory pressure become clear and can be diagnosed.

## Source report F39 (worker-io-cli-memory)
**Unchecked allocations (256 MiB solver table, parent-table pool, multi-solve arena) crash with SIGSEGV instead of failing cleanly** at /Users/george/Documents/Claude Projects/project45/sokoban_bfs.c:1018

*summary*: Several large or long-lived allocations are never checked for NULL; a failure means a NULL dereference. Only the dedup tables and the DFS queue are checked (those exit(1)).

*failure_scenario*: On a memory-constrained machine, or under a `ulimit -v`, the lazy 256 MiB `slot_big` calloc returns NULL, and the next probe segfaults. There is no SUMMARY, so the node is re-run elsewhere. That machine keeps crashing on deep jobs until the client backs off after 3 failures. The same applies to `g_ptab = realloc(...)` and the malloc'd buffers in sokoban_ref_build (memset on NULL). This is recoverable, but it is noisy and wastes the partial work.

*evidence*: sokoban_bfs.c:1018 `if (!hs->slot_big) hs->slot_big = calloc(HTP_SIZE, sizeof(HSlot64));` has no check. 1007-1010 hsp64_get calloc/malloc are unchecked. 1410 `t->hk = malloc(sz * sizeof(uint64_t)); t->hc = malloc(...)`, then `memset(t->hk, 0, ...)`. 1844-1845 `ms_lab = calloc(...)` and `ms_arena_tls = malloc(...)`. backsearch.c:543 `g_ptab = realloc(g_ptab, g_ptab_cap * sizeof *g_ptab); memset(g_ptab + g_ptab_n, ...)`. NOTE: the real path of sokoban_bfs.c is /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c.

*suggested_fix*: Check every allocation. On failure, print a distinct status (e.g. `SUMMARY {"status":"oom"}`) or at least a clear stderr message, and exit with a dedicated code, so the client can reduce its worker count instead of retrying blindly.

*expected_gain*: Clean, diagnosable failures under memory pressure.

## Verifier (CONFIRMED, low, refuted=False)
The code defect is real. None of these allocations are checked: sokoban_bfs.c:1007-1010 (hsp64_get struct, 1 MiB slot_small, touched), 1018 (`hs->slot_big = calloc(HTP_SIZE, sizeof(HSlot64))`, 16M x 16 B = 256 MiB), 1087 (`b->items = realloc(b->items, ...)`, which leaks the old block and then writes through NULL), 1410 (`t->hk = malloc(...); t->hc = malloc(...)`, then `memset(t->hk, 0, ...)`), 1844-1845 (ms_lab calloc, 24 MB ms_arena malloc), 2294 (hsp128 struct calloc), and backsearch.c:543 (`g_ptab = realloc(...); memset(g_ptab + g_ptab_n, ...)`). A NULL return means SIGSEGV. Reachability is narrower than the summary suggests. The supported platforms are macOS, Linux and WSL (v2/README.md:8, VOLUNTEERS.md:21). There, large callocs are lazily committed anonymous mmaps and overcommit is on, so memory pressure shows up as the Linux/WSL OOM killer (SIGKILL, rc -9) or as macOS compression/swap, not as NULL. NULL returns realistically need `ulimit -v` / RLIMIT_AS or vm.overcommit_memory=2. Either way the client outcome is the same as any other crash: no SUMMARY, the node is left untouched, and the worker backs off after 3 consecutive failures (volunteer.py:547-558). Diagnosability is the only loss. Related: README says about 200 MB per worker, but the lazy 256 MiB + 384 MiB tables can take a worker well past that, which is the more likely real memory problem at 16 workers. Low.

*fix notes*: Add xmalloc/xcalloc/xrealloc wrappers that print 'OUT OF MEMORY <bytes> at <site>' to stderr and exit with a dedicated code (e.g. 3); keep the old pointer on a failed realloc. In the client, treat that code and rc -9 (SIGKILL, the usual OOM-killer signature) as machine problems, not job failures: log them clearly and reduce the worker count instead of retrying blindly. Also fix the README's per-worker memory figure to state the worst case (small table + lazy 256 MiB big table + 384 MiB 128-bit table + dedup tables).
