## Source report F204 (r2-next-campaign-generalization)
**Champion re-solve has one fixed 30 s / 0.5 GiB attempt, no retry and no offline path; a too_complex champion cannot even be stored at publish** at /Users/george/PathologyRecords/server/lib/v2routes.js:65

*summary*: verifyLater runs once per new per-exit best, with solver6 at 30 s and SOLVER_GIB 0.5, which is about 40M states (radix) or 22M (wide). Failure only logs a warning. No tool re-verifies later with a larger budget, and v2_finish's processSubmission returns needs_solution for a too_complex champion because the worker provides no solution path. For the next campaign's larger levels, verified_moves plausibly stays NULL forever, and the published proof ends up 'unwitnessed' with no stored champion.

*failure_scenario*: In a 6x6 or 5x5 <=4-hole campaign, a 180-move champion needs more than about 22M forward states. measureLevel returns too_complex and the server logs 'level not verified'. It never retries, since only a new best triggers verification. At publish, v2_finish prints '(not re-solved yet)', adds the proof, then calls processSubmission(code, {solverSeconds: 30}); both engines give up and it returns {reason: 'needs_solution'}, so the champion is not stored. The site then shows the proof as 'unwitnessed' with no badge, and addProof's contradiction guard has no verified level of that class. If verification is made a publish gate (as the known finding recommends), such exits can never be published.

*evidence*: v2routes.js:18 `const VERIFY_SECONDS = 30;`; 65-67 `const m = await measureLevel(code, { seconds: VERIFY_SECONDS }); if (m && m.ok && ...) jobs.setVerifiedMoves(jobId, m.moves); else log.warn(...)`; 153 `if (o && o.ok && o.new_best && o.level_code) verifyLater(...)`; pipeline.js:11 `const SOLVER_GIB = Number(process.env.SOLVER_GIB) || 0.5;`; solver6.c:1916-1919 `HSLOTS = (uint64_t)(bytes * TABLE_SHARE / (double)slot_bytes); ... HFILL = (uint64_t)((double)HSLOTS * 0.85);` (10 B / 18 B slots); pipeline.js:111-117 `return { accepted: false, reason: 'needs_solution', ...}`; v2_finish.js:68 `processSubmission(s.best_level.code, { attribution, source: 'upload', solverSeconds: 30, ... })`; no tool calls setVerifiedMoves (tools/: add_proof, finish_chunks, set_chunk_plan, v2_finish, v2_hashes, v2_seed).

*suggested_fix*: Add an owner tool (e.g. tools/v2_verify.js --campaign C --exit E --gib 3 --seconds 3600) that re-solves each exit's champion offline and sets verified_moves, or records a 'too_complex' status so the dashboards show 'not verifiable' instead of pending. Have the worker print the best state's BState.path with LEVEL: the reversed backward path is a forward solution of exactly best moves. Pass it as proposedPath (replay-checked by the site) in v2_finish, so the champion is stored as 'unproven' or 'claimed' rather than dropped.

## Verifier (CONFIRMED, medium, refuted=False)
The code does what the report says. The main trigger it proposes (the solver budget being too small for bigger levels) is weaker than claimed. I found a different trigger in the campaign #1 snapshot that already happens in practice.

What the code shows:
1. There is one attempt and no retry. v2routes.js:18 `const VERIFY_SECONDS = 30;`. Lines 65-67 call `measureLevel(code, { seconds: VERIFY_SECONDS })`. On failure they only run `log.warn(...)`. Line 153 calls verifyLater only when `o.new_best` is set. jobs.js:797 sets newBest only when `bestNode.best > prevBest`, a strict increase. The work is an in-memory async task, so a server restart while it is queued or running loses it for good.
2. Nothing else writes the result. setVerifiedMoves (jobs.js:855) is called only from verifyLater. None of the files in server/tools (add_proof, finish_chunks, set_chunk_plan, v2_finish, v2_hashes, v2_seed) re-solves a champion. seed/verify-claims.js can promote records.db levels with a larger budget, but only levels that are already stored.
3. v2_finish skips its safety check and drops the champion.
   - Line 60 prints '(not re-solved yet)'.
   - Line 61 refuses only when `v != null && v !== best`, so a NULL verified_moves goes straight to addProof (line 64).
   - Line 68 then calls `processSubmission(code, {attribution, source:'upload', solverSeconds:30, note})` with no proposedPath, proposedMoves or claimProven.
   - If the level is too_complex, pipeline.js:113-117 returns `{accepted:false, reason:'needs_solution'}`, so the champion is not stored and proofChampions (db.js:637) shows the proof as 'unwitnessed'.
   - When the champion is solved at publish, v2_finish never compares sub.moves with best.
   - SOLVER_GIB can be raised from the environment, but the 30 s limit is fixed.

A trigger that already happened (new consequence): bestOfExit (jobs.js:301-302) is `ORDER BY j.best DESC, j.id LIMIT 1`, and a report that only ties the best never triggers verification. When a job with a lower id reports the same best later, it becomes the displayed and published champion with verified_moves NULL. The campaign #1 snapshot has two cases:
- Exit 1: job 11613 reported 125 at 1790214577 and was verified (125). Job 11606 (lower id) reported 125 at 1790217340, stayed NULL, and was the displayed champion until a higher best arrived.
- Exit 6: job 5444 reported 134 first and was verified. Job 5236 reported 134 later, stayed NULL, and was the displayed champion.

If either tie had been the final maximum, v2_finish would have printed '(not re-solved yet)' and skipped the solver-disagreement check. Campaign #1 avoided this by luck: every final champion is the verified row (0:60818, 1:27050, 2:9182, 6:17462, 7:3908, 12:621).

Why the budget trigger is weaker than claimed:
- solver6's table uses packed 10 B / 18 B slots (solver6.c:369-372) at 0.88 of the budget with 0.85 fill. At 0.5 GiB that is about 40M states (radix) or 22M (wide). A comment in solver6.c measures 22M states in 14 s.
- The worker's own forward shortcut check has a 16M-slot table (sokoban_bfs.c:932 HTP_SIZE) and a 1M pending cap (HP64_SIZE). Its overflow codes -2/-3/-4 are treated as a prune (backsearch.c:2213-2218), so a level can only be counted valid if its forward search fits in those caps. This is not a strict bound on a fresh solve, because the ptab reference tables let the worker reuse earlier work.
- In campaign #1, every strict new best at exits 0, 1, 2, 6 and 7 was verified at 30 s / 0.5 GiB, including the 149. The two NULL rows at exit 12 are 14- and 32-move levels. They look like an ordering artifact of my replay, not budget failures.
- So a 5x5 campaign with 4 holes probably still verifies within budget. A 6x6 campaign, a slower host, or larger worker caps could still hit too_complex, and then the code above drops the champion.

Nothing is lost for good, since level_code stays in jobs.db. The owner can recover by hand: submit the champion with a proposed length, then run seed/verify-claims.js with the opt engine. The damage is a missing or silently skipped independent check at publish, plus wrong or missing badges. Medium fits.

*fix notes*: 1. jobs.js:301-302. Prefer a verified row among ties: `ORDER BY j.best DESC, (j.verified_moves = j.best) DESC, j.id`. Alternatively, also call verifyLater when a tie arrives and the current champion has verified_moves NULL.
2. v2_finish.js:58-61. When verified_moves is NULL, re-solve the champion there with measureLevel, using new --seconds/--gib flags (offline defaults such as 600 s / 3 GiB). Write the result with setVerifiedMoves, and refuse on disagreement just as for a non-NULL value. If the result is still too_complex, refuse unless --allow-unverified is passed, and print the solver's reason.
3. After processSubmission (line 68), compare sub.moves with best and flag any difference.
4. Add a fallback so a too_complex champion is stored instead of dropped. Pass proposedMoves: best with claimProven: true, attribution 'Collective', so it is stored as 'claimed' and seed/verify-claims.js (opt engine) can promote it later. Better still, have the worker print the reversed BState path with LEVEL and pass it as proposedPath, which the site replay-checks and stores as 'unproven'.
5. Add tools/v2_verify.js (--campaign, --exit, --seconds, --gib). It re-solves every exit champion with NULL verified_moves; this also covers verifications lost to a restart. Or run the same pass once at server start for the active campaign.
6. Record why a verification failed, for example a verify_status column with 'too_complex:timeout' or 'memory'. The dashboards can then say 'not verifiable at budget' instead of looking pending forever.
7. Tests in v2_gates.test.js:
   - A lower-id job that ties a verified best keeps the verified champion displayed.
   - v2_finish with a measureLevel stub that returns too_complex refuses, or stores the champion as 'claimed', instead of silently publishing an unwitnessed proof.
