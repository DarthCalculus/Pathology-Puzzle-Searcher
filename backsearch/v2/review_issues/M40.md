# M40: The PGO training run does not use the campaign's workload (no exit transit, no hole cap, exit 0 only); build has no native-ISA flags

verdict CONFIRMED, severity low, category performance
locations: build_pgo.sh:26 (4 s root search at exit 0 without --allow-exit-transit / --num-holes 3; failures hidden by '|| true'; -O3 without -march/-mcpu=native)

## Summary
The profile comes from 4 s of exit 0 without transit and with unlimited holes. Exit 0 has no block-on-exit states, while exits 1/2/6/7/12 (93.7% of CPU) have 85-95% of them, so exit_block_stuck's fixpoint, the adjflags pull-off checks, variant 3 onto the exit and deep seed replay are all cold in the profile. Unlimited holes exercise the 128-bit solver, which the campaign does not use. A failed training run is hidden, and the build uses no native-ISA flags although every volunteer builds locally. This affects speed only; results and SRC_HASH are unaffected.

## Verifier (CONFIRMED, low, refuted=False)
The premise is true. The gain is probably small (my estimate 0-2%), but the change is essentially free and cannot affect exactness.

What the code shows (/Users/george/Documents/Claude Projects/project45/backsearch/build_pgo.sh):
- Line 26: `TRAIN_ARGS="--grid 5x5 --exit 0 --time 4"`.
- Line 110: `LLVM_PROFILE_FILE="$TMP/w.profraw" "$TMP/worker.gen" $TRAIN_ARGS >/dev/null 2>&1 || true`.
- Line 77: `CFLAGS="-O3 -DGIT_SHA_STR=... -DSRC_HASH_STR=..."`, with no -march or -mcpu.
- Volunteers do build with this script. VOLUNTEERS.md:28/81 and README.md:13 say `./build_pgo.sh -o backsearch_worker_nt --no-torch`, and volunteer.py:294/401/920 tell them to rerun it. So every campaign binary is built from this profile.

1. The training workload differs from the campaign's.
- The training run has no --allow-exit-transit. g_allow_exit_transit defaults to 0 (backsearch.c:70), so lines 1388/1969 never put a block on the exit. As a result, exit_block_stuck (backsearch.c:616-641, called for every state at :2112) always leaves at `if (!on_exit) return 0;`. Its fixpoint loop and the adjflags/pull-off checks get zero counts.
- The training run has no --num-holes. g_max_holes = MAX_HOLES = 64 (backsearch.c:134, sokoban_bfs.h:11).
- It has no --seed-path, so seed replay is cold. That part does not matter: replay runs once per job.
- Snapshot check (jobs_review.db, grouped by exit): exit 0 has accepted == valid (1,443,217,999) and uses 37.7 of 601.8 CPU-hours (6.3%). Exits 1/2/6/7/12 have valid/accepted of 0.152/0.149/0.054/0.071/0.059 and use 93.7% of CPU. The 93.7% figure is right.
- Training on exit 0 would not help even with transit on, because exit 0 accepts no block-on-exit states. The suggestion to train on exit 1 is correct.

2. Minor correction to the reports: "the campaign does not use the 128-bit solver" is not strictly true. With 5 bits per cell on 5x5 and nh = 3, the wide path (sokoban_bfs.c:1842/2674, `g_bits_per_cell*(1+nb)+nh > 64`) is taken for nb >= 12. So it is rare in the campaign but reachable. It is a separate function, so a mis-weighted profile for it barely touches the 64-bit hot path.

3. Size of the gain. solvebench.c's own reference numbers (lines 27-32, Apple M-series, 5x5 corpus) show the whole PGO benefit on the solver as about 5% (11.6 -> 11.0 us/call). The build_pgo.sh comment claims 10-20%. The solver is about 90% of runtime, and its inner BFS loops are profiled by either workload. So the part of that ~5% lost to an unrepresentative profile is a fraction of it: I estimate 0-2% of worker throughput, about 0-12 CPU-hours on a campaign like #1. That is below solvebench's stated ±15% laptop timing noise, so it needs several repeats to measure.

4. Native-ISA flags.
- The owner's binaries are arm64 Mach-O. Apple clang already targets apple-m1 by default on arm64 macOS, so -mcpu=native gains about 0 there.
- On x86-64, __builtin_popcount appears only in mand_setup (sokoban_bfs.c:823/856, once per call, not in the inner loop), and ctz compiles to bsf on the baseline ISA. BMI/POPCNT would give 0-3%, unmeasured.
- Exactness is safe: the DFS path is integer-only. The only double-based scoring is beam_score_handtuned (backsearch.c:1531, beam mode), and the other floats are timing.
- New risk not in the reports: a -march=native binary copied to an older or different CPU (a shared NFS home on a heterogeneous cluster; the 32-worker client may be one) dies with SIGILL on every job. SRC_HASH does not catch this, so it becomes a crash loop with leases re-issued. Native flags should be opt-in (e.g. `--native`), not the default.

5. `|| true` hiding failures: partly true.
- The worker returns 0 on a normal --time cap (backsearch.c:5928), so `|| true` only masks real failures.
- On clang, a run that crashes on a signal writes no profraw. The `llvm-profdata merge` at line 111 then fails, and set -e aborts the build, so the crash is not silently hidden.
- A mistyped custom `--train` string does get through silently. Main returns 1 after writing a profraw that covers only argument parsing, so the whole search is compiled as cold, which can end up slower than plain -O3. On gcc, `-Wno-missing-profile` hides this as well. With the default TRAIN_ARGS this cannot happen.

6. Added consequence: solvebench's documented corpus recipe (solvebench.c:15, `--grid 5x5 --exit 0 --time 5 --harvest`) uses the same unrepresentative workload. So solver speedups were tuned and validated on exit 0 without transit and without a hole cap, while 94% of campaign CPU goes to exits dominated by block-on-exit states. The speed claims may not carry over to the campaign.

Verdict: CONFIRMED, low. It is worth doing before the next campaign as a one-line change with a guard, not as a performance project.
