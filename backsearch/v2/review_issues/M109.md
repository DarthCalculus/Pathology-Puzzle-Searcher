# M109: Ramp policy: a count-based threshold, an absorption budget not scaled to the window, and no real endgame mode

verdict CONFIRMED, severity medium, category algorithmic
locations: jobs.js:582 (120 s ramp window when open jobs < 3 x workers); client absorption budget 120 s

## Summary
The 120 s ramp window switches on whenever there are fewer than 3 open jobs per worker, and the open count is mostly trivial jobs, so from hour 5 onwards most windows were ramp windows. Each still spent the full 120 s absorption budget, which can double the window. In the real endgame every level of a thin, deep subtree costs 120 s of search plus up to 120 s of serial absorption and batching latency, while other workers sit idle.

## Verifier (CONFIRMED, medium, refuted=False)
The premise holds in the code and in the snapshot. The claimed gain is real but smaller than stated, and the proposal leaves out the biggest cause of the tail.

CODE
- jobs.js:580-582: `const open = q.openCount.get(c.id).n; ... const splitAfter = open < 3 * workersActive ? c.ramp_split_after_s : c.split_after_s;`. openCount (jobs.js:276) counts only status='open' rows. Jobs already leased into client queues are not counted. The held cap is 3 x workers + 200 per client (jobs.js:45-46), so clients that lease ahead drain the open count below 213 (3 x 71 workers) long before the real work runs thin.
- volunteer.py:643-644: `probe = max(0.5, self.fparam("absorb_probe_s", 10))`, `absorb_end = time.time() + self.fparam("absorb_total_s", 120)`. This budget does not depend on the window.
- volunteer.py (lease loop): `split_after_s` is fixed when the job is leased, not when it starts, so the window decision lags by however long the job waits in the local queue.
- No other mode exists: 120 s is the only short window, absorption stays on, and reports wait for batch_interval_s (10 s) in sender_loop.

SNAPSHOT (my own queries)
- Ramp splits (elapsed 100-135 s) per hour, hours 5-10: 56, 35, 196, 271, 355, 469. Total 1,385, with 47 CPU-h of window search. Ramp windows began at hour 5, when about 383 CPU-h (about 5.4 h of fleet time) was still left. This is the count threshold misreading hoarded queues as a thin pool.
- The open pool was mostly trivial: 37,212 of 50,920 leased done jobs (73%) ran under 1 s, and 81% ran under 10 s.
- "Each spent the full budget" is overstated:
  - 332 of 1,385 ramp windows (24%) certainly used up the 120 s budget (more than 12 children still open; average 65.9 open).
  - 961 windows left 1-12 children open (average 3.6).
  - 92 windows left none open.
  - On average 63 children were absorbed per window, 22 s of search in total.
- Estimated dropped-probe CPU in ramp windows: 961 x 3.6 x 10 s plus 332 x about 75 s, which is about 12-16.5 CPU-h. That is about 26-35% of the ramp search CPU, and it comes on top of the 602 CPU-h because open nodes carry no summary. This matches the finder's 13.6 h.
- Chain figures confirmed exactly: 166990 was created at 39839 and done at 40044; 167319 at 40044 and 40314 (270 s); 167664 at 40314 and 40514 (200 s). Subtree 165793 has 842 jobs, 0.647 CPU-h of work, and 965 s of wall time (39549 to 40514).
- Correction: the other workers were not idle. After minute 600 there are about 1,090 'dup' reports. Stealing running jobs piled most of the fleet onto the same chain job: 166990 was run about 19 times, 167319 about 22, and 167664 about 40. The CPU was spent on duplicates instead of useful work, so the loss is the same.

HOW MUCH OF THE TAIL THIS EXPLAINS
- Last four levels, 965 s in total: about 485 s of window search, about 370 s of absorption (budget used up at 165793 and 167319; about 60-70 s of probes plus spawn overhead at the other two), and about 110 s of lease and report latency.
- Queueing dominates the full critical chain from 66833 (reported at 35275, 87 minutes before the end). Levels 126770 and 141048 each had a 120 s window but took 1,065 s and 2,077 s from creation to report. The other ramp levels took 357-400 s each.
- These waits come from leasing ahead into FIFO client queues, deepest-first ordering, and windows fixed at lease time. This proposal does not address them.

GAIN (my estimate)
- CPU: about 12-16 CPU-h per campaign of this shape (2-3%). This overlaps the absorption-order finding.
- Wall clock: with absorb_total_s=0 and immediate reports in the endgame, the last four levels would drop from about 965 s to about 550 s with the same 120 s windows. With 30-60 s windows, about 300-450 s. That saves about 7-11 minutes of an 11.25 h campaign (about 1%).
- The finder's "30-40 s per level" is optimistic. Lease spacing (10 s), report batching (10 s), process spawn and the window itself give at least 35-45 s per level, and shorter windows mean more levels.

EXACTNESS
No risk. Window length and absorption only change how the tree is partitioned. A probe that splits is reported open and keeps its level. Shorter windows mean more splits, which relies on the split/REMAINING mechanism that test_split_exact already covers.

WORTH DOING BEFORE THE NEXT CAMPAIGN
Yes. The cheapest part needs no client release: absorb_total_s, absorb_probe_s and batch_interval_s are campaign client_params (jobs.js:54-55) that clients refresh on every heartbeat.

*fix notes*: 1. Zero-code change for the next campaign: set client_params absorb_probe_s to 2 (keep absorb_total_s around 60-120). 73% of leased jobs finish in under 1 s, so short probes still absorb almost all trivial children, and each dropped probe costs 2 s instead of 10 s. This saves about 80% of the dropped-probe CPU.
   - Avoid the finder's min(120, 0.1 x window) budget. At a 12 s budget, ramp windows would return about 87k trivial children (63 per window) to the pool instead of absorbing them.
   - Better client change: scale only the probe with the window, for example probe = min(absorb_probe_s, 0.02 x window), and probe in order of shallowest remaining work rather than deepest first.

2. Ramp threshold: use open + leased-but-not-running jobs, or a work estimate (for example, count only jobs whose parent's absorbed siblings were non-trivial), instead of the open count alone. The current threshold switched to ramp windows 5.4 fleet-hours before the end, because clients hold up to 3 x workers + 200 jobs each.

3. Endgame mode: when a lease returns nothing, or idle workers exceed the non-trivial open jobs:
   - return split_after_s = clamp(estimated work / idle workers, 15, 120) and absorb_total_s = 0 in the lease response (this needs a per-lease absorb override in volunteer.py);
   - have sender_loop flush split reports immediately (not after batch_interval_s);
   - set lease_ahead to about 1 job per worker so critical-path jobs do not sit in FIFO queues.
   This turns the roughly 1,090 duplicate stolen runs into real parallel work.

4. Related, bigger tail cause not covered by this proposal: split_after_s is fixed at lease time (volunteer.py lease loop), and jobs sit in local FIFO queues behind lease-ahead. Critical-chain levels 126770 and 141048 waited 1,065 s and 2,077 s for 120 s windows. Choose the window when the job starts (for example, re-query the server or apply a heartbeat-pushed endgame flag), and cap lease-ahead in the endgame.
