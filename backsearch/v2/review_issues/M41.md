# M41: An empty root seed "" (DESIGN §2) cannot run: the client's SEED_RE rejects it, and the job cycles forever

verdict PLAUSIBLE, severity low, category protocol
locations: volunteer.py:39 (SEED_RE requires >= 1 token); volunteer.py:494 (logs 'ignoring job ... unparsable seed'); worker_argv always passes --seed-path; jobs.js addRootJobs (allowEmpty); DESIGN §2

## Summary
DESIGN §2 defines an exit's root as the empty seed, run by omitting --seed-path, and addRootJobs accepts it. The client's SEED_RE requires at least one token, and worker_argv always passes --seed-path. Such a job is logged as unparsable and dropped locally, released after 120 s, leased again, and never run, so a campaign seeded at the exit root would never finish.

## Verifier (PLAUSIBLE, low, refuted=False)
The client side holds, but the stall scenario as described is not reachable with the production tooling. What holds: SEED_RE (volunteer.py:39) `^(?:[URDL][123])(?:,[URDL][123])*$` rejects ""; the leaser logs 'ignoring job %s with an unparsable seed' and drops it (:494-496); worker_argv always passes `--seed-path`, seed (:423); DESIGN.md:70-71 says 'The exit's root is the empty seed "": a client runs it by omitting --seed-path'; and jobs.js:393 addRootJobs uses `parseSeed(r.seed, { allowEmpty: true })`. What refutes the stall: the only production caller of addRootJobs is tools/v2_seed.js:78. Its readLayer (v2_seed.js:43) calls `parseSeed(f[2])` without allowEmpty, so a layer-0 line `LAYER\t<exit>\t\t0...` gets parseSeed("") -> null. It is counted as 'malformed' in the seed printout and never inserted. There is no admin HTTP route that calls addRootJobs (v2routes.js has none; only the tests call it). An exit seeded that way therefore has 0 roots, not a cycling job. auditExit (jobs.js:1013) requires `roots.length > 0` to be clean, so v2_finish refuses it loudly. No false 'complete' and no silent stall. Splits cannot produce "" either: REMAINING entries extend a non-empty job seed. The residual defect is a contract inconsistency. DESIGN §2 promises layer-0 roots, addRootJobs accepts them, but v2_seed and the client both reject them, and v2_seed calls them 'malformed' instead of 'unsupported'. The owner would find out at seeding time, which matters mainly for a small test campaign. Low severity, but lower than the finders claimed: it is a doc and tooling mismatch, not a stall.

*fix notes*: Pick one contract and make all three places agree. Simplest: forbid empty roots. Change DESIGN §2 to say campaigns are seeded at layer >= 1. Make addRootJobs use plain parseSeed(r.seed), without allowEmpty, so a future tool cannot insert an unrunnable job. Have v2_seed report an empty seed as 'layer-0 roots are not supported; use --list-layer K >= 1' instead of counting it as malformed. Alternatively, support "" end to end: allow it in the client's lease path, omit --seed-path for it, handle the empty prefix in the REMAINING checks, and let v2_seed accept it via allowEmpty. Then add a gate test that seeds a "" root and runs it through the fake client.
