# M65: webbrowser.open can block startup with a console browser on headless Linux

verdict CONFIRMED, severity low, category robustness
locations: volunteer.py:1523 (start_ui calls webbrowser.open synchronously)

## Summary
Over SSH with TERM set, no DISPLAY, and www-browser, lynx, w3m or links installed, Python's webbrowser picks a console browser. GenericBrowser.open waits for it to exit, so run() blocks inside start_ui before any worker starts.

## Source report F71 (client-ui)
**webbrowser.open can block startup with a console browser on headless Linux** at /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py:1523

*summary*: Over SSH with TERM set, no DISPLAY, and www-browser/lynx/w3m/links installed, Python's webbrowser picks a console browser. GenericBrowser.open waits for it to exit, so run() blocks inside start_ui before any worker starts.

*failure_scenario*: A volunteer on a headless box forgets --no-ui. lynx or w3m takes over the terminal showing a page that does nothing without JavaScript, and no workers start. Pressing Ctrl-C to get out sends SIGINT to the client too. With no slots yet, _on_sigint calls os._exit(1) ('interrupted during startup').

*evidence*: volunteer.py:1360-1363 `if not self.args.no_ui: self.start_ui()` runs before `self._reconcile_slots()`; :1521-1525 `if not self.args.no_browser: try: webbrowser.open(url)`; :1432-1435 `if not self.slots: ... os._exit(1)`.

*suggested_fix*: On Linux, skip opening a browser when neither DISPLAY nor WAYLAND_DISPLAY is set, and just print the URL. Otherwise call webbrowser.open from a daemon thread.

## Verifier (CONFIRMED, low, refuted=False)
The issue holds; I checked it against the code and the local stdlib (Python 3.14.3). main() (volunteer.py:1553-1558) registers and checks the hash, then calls run(). run() calls start_ui() at :1359-1360 before _reconcile_slots() and before the leaser thread starts. start_ui() calls `webbrowser.open(url)` synchronously at :1522-1523. In the stdlib's register_standard_browsers, X browsers are registered only `if DISPLAY or WAYLAND_DISPLAY`. Then `if os.environ.get("TERM")` registers www-browser, links, lynx and w3m as GenericBrowser, and elinks as Elinks. GenericBrowser.open does `p = subprocess.Popen(cmdline, close_fds=True); return not p.wait()`, so it blocks until the console browser exits. While it is open, no slots exist and nothing is leased, so no work is lost; only time is. Quitting lynx or w3m (q, then y) returns control and the client continues normally, so in the interactive case the block is not permanent. Ctrl-C reaches both processes because they share the foreground process group. _on_sigint then sees `not self.slots` and calls os._exit(1) ('interrupted during startup'). That is harmless (the token is already stored, no leases are held) but confusing. The worse case is `python3 v2/volunteer.py ... &` over SSH with the terminal still on stdin. The console browser, in a background process group, gets SIGTTIN and stops. p.wait() then never returns, so the client sits forever with the GUI up and zero workers, and the only clue is the last log line 'local GUI at ...'. Mitigations: v2/README.md:39 and collective.html:51 both say 'Headless machine? Add --no-ui'. Under systemd TERM is normally unset, so that path is not affected. Low severity stands.

*fix notes*: In start_ui, do not open a browser when webbrowser would pick a console browser. On Linux with neither DISPLAY nor WAYLAND_DISPLAY set, print the URL instead, but keep WSL working: WSL without WSLg has no DISPLAY, yet Ubuntu-on-WSL maps www-browser to wslview. So either special-case 'microsoft' in platform.release(), or check `webbrowser.get()` and skip only when its basename is lynx/w3m/links/elinks/www-browser resolving to one of those. Also call webbrowser.open from a daemon thread so no browser can hold run() before the workers start. A regression test in test_client.sh can set TERM=xterm, unset DISPLAY and put a fake 'lynx' that sleeps on PATH, then assert that workers start.
