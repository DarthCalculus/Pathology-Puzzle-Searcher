# M87: The split-exactness tests print but never fail on 'extra' levels, which are the evidence of an unsound monolithic dedup

verdict CONFIRMED, severity medium, category test-gap
locations: test_split_exact.py:97 (union_val - full_val only printed); test_chaos.sh (same)

## Summary
Both tests compute union_val - full_val, the levels the split jobs found and the monolithic run did not, and only print it. Split jobs start with empty dedup tables and re-expand twins that the monolithic run skipped. An extra level therefore means the monolithic dedup dropped a real level: its key excludes wh/seg/adjflags, and states are canonicalised and bulk-walked. That breaks the equality DESIGN claims and would mean the published maximum can miss levels, yet the test still passes.

## Verifier (CONFIRMED, medium, refuted=False)
The code does what the report says. The part claiming evidence was thrown away is wrong, and the severity is too high.

Code facts:
- v2/test_split_exact.py:94-98 computes `lost = full_val - union_val` and fails only on `if lost or best != full['best']:`. The reverse set, `union_val - full_val`, is only printed inside the f-string at line 95: `(extra {len(union_val - full_val)})`.
- v2/test_chaos.sh:80-82 is the same: `lost = full - jobs` ... `print(... extra {len(jobs - full)})` / `sys.exit(0 if not lost and jb == fb else 'FAIL')`.
- Both tests check only one direction (full ⊆ union), but the contract asks for equality in both. DESIGN.md §5.1 says the union of jobs "equals the full run's", §5.2 says "== monolithic run", and the test_chaos.sh header says "must equal". So this is a real gap in the only oracle for the core invariant.

Is the report right that an extra means a soundness bug?
- Mostly yes. A valid level is traced only when shortcut_check(s) returns -1 (backsearch.c ~2206-2245). A traced (depth, code) is therefore an optimal-length level with no shortcut, and its depth is fixed by its code.
- An extra is a canonical valid level that a fresh-table job found and the monolithic DFS did not. That means the monolithic search pruned a real level. The report names dedup (the key omits wh/seg/adjflags, plus canonicalisation and bulk walk) as the cause. Other causes are possible: a difference in the conservative -2/-3/-4 caps, or a difference in the parent-reference (ptab) solver path between seed replay and DFS.
- Eviction in the two-table dedup cannot cause an extra, since it only adds re-expansions. So any extra points to a real exactness defect, and the test should fail on it.

Why the high rating does not hold:
- The report says the lead's runs discarded this evidence. Their logs show otherwise: scratchpad/dyn/run_rest.log line 14 (5x5 exit 7, 1803 runs) reads "valid levels lost 0 (extra 0)", and line 18 (4x4 SIGINT) reads the same.
- The lead's stronger fresh-table harness shows "extra 0" too: dyn/roots_l8.log and roots_l8_nobulk.log, 19,680 layer-8 roots each, with and without bulk walk.
- So the gap hides no current defect. It is also only a partial oracle: an extra appears only when a fresh-table job happens to re-expand the one twin whose subtree holds the dropped level. A dedup bug that drops the level in every run shows up in neither direction.
- test_chaos.sh currently stops at "no job was split" before its level-set check (already known), so its extra check never runs today.
- Net: a real but latent test gap in the exactness gate, nothing that affects campaign results directly. Medium (weaker robustness of the gate before campaign #2), not high.

Side notes:
1. Adding a strict extra check to test_chaos.sh as-is would give false FAILs. The SIGKILL of client A orphans its workers. The worker has no SIGPIPE handling (backsearch.c:4866 installs only SIGINT/SIGTERM), and Python's restore_signals gives the child the default SIGPIPE action. So the next STATUS or SUMMARY write kills the worker without flushing the fully buffered g_trace_valid FILE (opened at :4873). The trace file then ends at a buffer boundary, usually mid-line. load() at test_chaos.sh:74-76 then either crashes (ValueError on split, IndexError in canon on a short row) or adds a bogus truncated code that is counted as an extra. This is inferred from reading the code; I did not run it.
2. The same lead logs (dyn/roots_l8.log) show a far more serious signal in the other direction: 9,566 levels lost at depth >= 8 from layer-8 roots with bulk walk, and 0 with --no-bulk-walk. That belongs to whichever finding covers list-layer roots and bulk walk. It also shows that the lead's scratch harness dyn/test_roots_exact.py, which also only prints extras (line 62), is the stronger gate and should be promoted into v2/.

*fix notes*: 1. test_split_exact.py:
   - In run(), keep the trace path instead of discarding it (`path, d, code = ...`), and build a map (d, canon) -> first path.
   - At line 97, set `extra = union_val - full_val` and fail on `lost or extra or best != full['best']`.
   - Print the first 5 extras with the job seed and trace path that found them, and the first 5 lost ones with their monolithic path. That makes a failure debuggable: re-run the full DFS and look at why that twin was skipped.
2. test_chaos.sh load() (lines 70-77): before making extras fatal, make parsing robust against workers killed by SIGPIPE/SIGKILL.
   - Skip lines that do not end in '\n', do not split into exactly 3 fields, or whose code does not have the grid's R rows of C chars.
   - Alternatively, in the worker, open the trace with setvbuf(g_trace_valid, NULL, _IOLBF, 0) at backsearch.c:4873. It is test-only, so the cost does not matter. A partial line is still possible, so keep the parser guard as well.
   - Then use `sys.exit(0 if not lost and not extra and jb == fb else 'FAIL')` and print samples.
