# M100: States wider than 64 bits fall back to a solver with none of the optimisations (matters for 6x6, or 5x5 with more holes)

verdict PLAUSIBLE, severity medium, category performance
locations: sokoban_bfs.c:2681 (sokoban_solve_cutoff dispatch to solve_push128_cutoff); sokoban_solve_multi refuses > 64 bits

## Summary
When bits_per_cell*(1+nb)+nh > 64, the cutoff solve goes to solve_push128_cutoff. That solver has no A* bound, no decision-mode early exit, no walk-depth limit, no small cache-resident table (one 384 MB table) and no parent-table reuse or export, and the bulk multi-solve refuses these states. The threshold is 12+ blocks on 5x5 with up to 4 holes, 11 blocks with 5 holes, and 10 blocks on any 6x6, so a larger next campaign would run much slower.

WHAT THE CODE DOES (all in /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c):
- Dispatch, lines 2679-2685: `if (g_bits_per_cell * (1 + nb) + nh > 64) { hsp64_get()->last_exhaustive = 0; return solve_push128_cutoff(pz, used_dirs, prof, max_cost); }`
- Bits per cell are set at line 134: `g_bits_per_cell = bits_needed(g_ncells + 1)`, with a minimum of 5. That gives 5 bits for 5x5, 4x6 and 5x6, and 6 bits for 6x6.
- The thresholds in the report are correct:
  - 5 bits (5x5, 4x6, 5x6) with nh<=4: nb>=12 (5*13 = 65).
  - 5 bits with nh=5 or 6: nb>=11.
  - 6x6: nb>=10 for any hole count (6*11 = 66), and nb=9 once nh>=5.
- The multi-solve refuses these states at line 1842: `if (g_bits_per_cell * (1 + nb) + nh > 64) return -2;`. The caller (backsearch.c:2414-2433) then solves the starts one at a time, which is exact.
- solve_push128_cutoff (lines 2502-2665) lacks the 64-bit solver's optimisations:
  - no hdist A* prune (the 64-bit version, lines 1549-1556 and 1716-1720, applies it in every mode, not only decision mode);
  - no `if (g_decision_only) goto done` early exit;
  - `walk_dists_from` with no slack limit;
  - no `ref_prunes_at`;
  - one 16M-slot table split into three arrays (lines 2281-2283: htk 256 MB, ht_gen 64 MB, ht_cost 64 MB), so each new state costs about 3 DRAM misses. The 64-bit solver instead uses a 16-byte HSlot64 slot in a 1 MB L2-resident table (lines 974-1023).
- The 384 MB block is calloc'd lazily per thread (line 2294). Because probes land on random pages, resident memory climbs toward 384 MB after roughly 1e5 inserts. README says a worker uses about 200 MB, so memory per worker could roughly triple wherever this path is hot.

HOW OFTEN IT HAPPENED IN CAMPAIGN #1 (snapshot):
- I counted blocks in the per-job best levels: 10 blocks in 639 jobs, 11 blocks in 4 jobs out of about 42k, and none with 12 or more.
- With 3 holes the wide path needs 12 blocks. It is only reached by candidates generated from the rare accepted 11-block states, so it is reachable but its share of solver calls was almost certainly tiny.
- The finder's own estimate of about 0 gain for 5x5 with up to 4 holes therefore holds. The same applies to 4x6 (24 cells, 5 bits, threshold 12), which is the next record target in the project notes.
- For 5x5 with 5 or more holes (threshold 11) the gain is probably small, because 11-block states are rare.
- On 6x6 at campaign #1's best-level densities (7-8 blocks in 25 cells, so about 10-11 in 36), most deep checks would take this path. The claimed gain of more than 2x per affected check is plausible there: A* pruning, the decision-mode exit and a cache-resident table against 3 DRAM misses per insert. I would put it at 2-4x per check, plus several GB of memory saved at 16 workers.
- However, an exhaustive 6x6 campaign is probably out of reach (5x5 with 3 holes already took 602 CPU-hours). Any 6x6 run is likely to use a block cap, and --num-blocks <=9 with nh<=4 never reaches the wide path.
- Verdict: worth doing before a 6x6 campaign or one with 5 or more holes. Not a priority for a 5x5 or 4x6 campaign with up to 4 holes. Hence PLAUSIBLE and medium, not high.

EXACTNESS RISK OF THE PROPOSED FIX:
- The 64-bit table already keys on Zobrist, not on the packed state (USE_ZOBRIST is on unconditionally at line 161, and HSlot64 stores only the key). Keeping 64-bit Zobrist keys for wider states adds no new kind of collision risk.
- But widening HeapEntry64, PushCand and MSSucc to `__uint128_t` in the shared structs would slow the hot 5x5 path. The 16-byte alignment grows HeapEntry64 from about 40 to 64 bytes, and bucket traffic grows with it. Build a second copy of solve_push64_cutoff / sokoban_solve_multi with a 128-bit state type (via a macro template) and choose between them by width instead.
- The interim step of dropping the player field from pack5 looks safe in Zobrist mode. The unpack loops start at `sh = g_bits_per_cell`, pushes overwrite the low field with bpos, and the multi-solve already clears it (line 1909: `pack5(0, ...) & ~g_cell_mask`). It moves every threshold up by one block. It would break the non-Zobrist `HE64_KEY(e) = e.state` build, so that build must be removed or guarded.

AN EXTRA CONSEQUENCE WORTH FIXING BEFORE ANY CAMPAIGN:
- Solver returns -2 (pending entries >= 1M) and -3 (probe limit or heap cap) are pruned silently (backsearch.c:2218 `if (x >= 0 || x == -2 || x == -3 || x == -4)`). Nothing in SUMMARY counts them (backsearch.c:5845 prints only status, states, accepted, valid, best, verify, evict counts, elapsed, solver_calls and src_hash).
- A pruned -2/-3 state is unproven, so any valid levels under it are lost without any sign. The wide solver has no A* prune and no cheap table-to-table retry, so it hits the 1M pending cap (HP128_SIZE, line 2264) more easily.
- On 5x5 this is harmless, because crowded states have tiny forward spaces. On a 6x6 campaign it could quietly break exactness.
- Cheap, zero-risk steps: add counters for wide-path solves and for -2/-3 prunes to SUMMARY, and have the server flag or re-queue jobs where the prune count is not zero. That would also show directly whether this performance issue matters for a given campaign.
