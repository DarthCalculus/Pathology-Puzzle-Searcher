# M11: solve_push64_cutoff returns early for max_cost < 0 without hsp64_clear, so the next export publishes the previous solve's table as this state's reference

verdict CONFIRMED, severity low, category bug
locations: sokoban_bfs.c:1515 (early return before hsp64_clear); sokoban_export_settled; try_successor_x export call

## Summary
For states at depth <= 1, the cutoff solve returns -1 before hsp64_clear runs. last_exhaustive, the touched list and the ref flag therefore still describe the previous, unrelated solve. try_successor_x then calls sokoban_export_settled, which would publish those labels as the new state's parent table. They are not path costs for this state, so reference prunes of its children could be unsound.

## Source report F21 (worker-prune-soundness)
**Early return for max_cost < 0 leaves last_exhaustive stale, so the next export copies the previous solve's table** at /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:1515

*summary*: For depth <= 1 states, solve_push64_cutoff returns -1 before hsp64_clear. sokoban_export_settled then sees last_exhaustive and the touched slots from the previous, unrelated solve, and exports them as this state's own reference table.

*failure_scenario*: In a monolithic run over several exits (no --exit), the second exit's depth-1 children are single-solved with max_cost = -1. They inherit last_exhaustive=1 and the touched list from the first exit's last solve, and export those as depth-1 tables that their descendants then use at k = 1, 2, .... The claims are relative to owner depth 1, so they are almost vacuous (only cost-0 entries claim rest >= 1). The worst outcome is a false accept; a level cannot be lost. Campaign jobs never reach this path because seeds are at depth 4.

*evidence*: sokoban_bfs.c 1515-1518: `if (max_cost < 0) { ... return -1; }` comes before `hsp64_clear(hs);` at 1528, which is where last_exhaustive is reset (1039). Line 1500: `if (!hs->last_exhaustive || hs->slot != hs->slot_small) return -1;`. backsearch.c 2253-2259 exports after every accepted single solve: `int n = sokoban_export_settled(tk, tc, HTP_EXPORT_MAX); if (n > 0) { ns.ptab1 = ptab_alloc(tk, tc, n) + 1; ...`.

*suggested_fix*: Set hsp64_get()->last_exhaustive = 0 before the max_cost < 0 return, or skip the export in try_successor_x when s->depth < 2.

*expected_gain*: Removes a cross-solve state leak in monolithic multi-exit runs.

## Verifier (CONFIRMED, low, refuted=False)
The bug is confirmed but latent and essentially harmless, and it is unreachable in campaign jobs. shortcut_check (backsearch.c:1699-1707) always calls sokoban_solve_cutoff with max_cost = depth - 2. solve_push64_cutoff returns -1 for max_cost < 0 (sokoban_bfs.c:1515-1518) before hsp64_clear, which is where last_exhaustive is reset (1039). try_successor_x then exports (backsearch.c:2253-2259) whatever sokoban_export_settled finds: last_exhaustive, the touched list and last_ref_used from the previous solve (1500-1510). The 128-bit branch already clears it (2682); the 64-bit early return does not. Reachability: last_exhaustive starts at 0 (hsp64_get callocs the struct), and sokoban_solve_multi goes through hsp64_clear. Every campaign or split job is one fresh process with one seed, and its first solve is the seed itself at depth >= 4. Even a depth <= 1 seed in a fresh process exports nothing, and in DFS all depth-1 states come from the root's expansion before any depth-2 solve. The stale export can only happen in a monolithic multi-exit run (the root and depth-1 states of the second and later exits) or in task-seed mode with a depth <= 1 seed after a deeper one. Impact: reference tables only prune forward states, so the worst case is a false accept. It can never lose a level. Near-vacuous as well: a child at chain offset k of an owner at depth d has cut = d-2+k, and ref_prunes_at prunes only when nc > gp+k-2 with nc <= cut, which forces gp < d. A depth-0 owner's stale table can never prune; a depth-1 owner's can only prune through cost-0 entries (the stale solve's start key). For the next campaign its only possible effect is a spurious extra 'valid' level in a monolithic multi-exit reference run, a false alarm in a split-vs-monolithic comparison, not a lost level.

*fix notes*: One line: set `hsp64_get()->last_exhaustive = 0;` in the max_cost < 0 branch of solve_push64_cutoff, or in sokoban_solve_cutoff before dispatching (like the 128-bit branch at sokoban_bfs.c:2682). Optionally also skip the export in try_successor_x when s->depth < 2, since such tables are vacuous anyway. Cross-check runs should use --exit per exit (as test_split_exact does), which avoids the path entirely.
