# M23: A tree report's src_hash is only the first run's SRC_HASH, so a binary rebuilt mid-window gets later runs reported under the old whitelisted hash

verdict CONFIRMED, severity medium, category soundness
locations: volunteer.py:605 (`run_hash = run_hash or h`); binary path resolved again for every run

## Summary
A window runs many worker processes and resolves the binary path again for each run. The report is attributed to the SRC_HASH of the window's first run, and later runs' hashes are never compared with it or with the startup hash. If the volunteer does git pull and a rebuild while the client runs, nodes searched by the new binary are reported under the old whitelisted hash, which bypasses the whitelist.

## Source report F55 (client-core)
**The report's src_hash is the first run's hash; later runs in the same window may use a different binary** at /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py:605

*summary*: The tree is attributed to `run_hash or h`, the SRC_HASH of the window's first run. Runs are never compared with that hash or with the startup hash, so a binary replaced mid-window (git pull plus rebuild while running) produces a mixed tree reported under the old hash.

*failure_scenario*: The volunteer rebuilds while the client runs. The absorption probes and later runs of current windows use hash H2, but the trees are reported as H1. If H2 is not whitelisted, the whitelist is bypassed for those nodes. If H2 is later found buggy and removed with `v2_hashes.js remove H2 --reissue`, the H2-computed nodes filed under H1 are not reissued.

*evidence*: volunteer.py 605 and 657: run_hash = run_hash or h
volunteer.py 680: report = {..., "src_hash": run_hash or self.src_hash, ...}
(no comparison of h with self.src_hash anywhere after read_version)

*suggested_fix*: If a run's SRC_HASH differs from self.src_hash, void that run (node stays open), request_stop('the worker binary changed; restart'), and never mix hashes in one report.

*expected_gain*: Keeps per-job hashes truthful, which `--reissue` depends on.

## Source report F186 (robustness-ops)
**Rebuilding the worker while the client runs gets later runs reported under the first run's hash, bypassing the whitelist** at /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py:605

*summary*: A window runs many worker processes, and the client resolves the binary path again for each run. The tree report's src_hash is only the first run's SRC_HASH (`run_hash = run_hash or h`), and later runs' hashes are ignored. If the binary is replaced mid-window, nodes searched by the new build are reported under the old whitelisted hash.

*failure_scenario*: The owner pushes a new worker to main before whitelisting it, or it has a bug. A volunteer follows updates.json ('git pull and restart the client when convenient') and runs `git pull && ./build_pgo.sh` in another terminal while the client runs. All 16 in-flight windows spawn their remaining runs from the new binary H2 but report under H1, and the server accepts them. If H2 loses levels, those subtrees count as covered under H1, and a later `remove H2 --reissue` does not catch them. Only the next windows (first run H2) are refused with 409.

*evidence*: volunteer.py:605 `run_hash = run_hash or h` (the absorb pass does the same at 657). volunteer.py:680 `"src_hash": run_hash or self.src_hash`. worker_argv (416-425) calls worker_argv_base() on every run, which re-resolves the path (266-280). build_pgo.sh:117 writes `-o "$OUT"` straight over backsearch_worker_nt.

*suggested_fix*: When a run's SRC_HASH differs from run_hash, stop the window: report what came from the first hash and leave the rest open. Alternatively, copy the worker binary into a private temp path at startup, check its --version, and run only that copy for the whole session.

*expected_gain*: The hash whitelist really does bind every searched node to an approved build.

## Verifier (CONFIRMED, medium, refuted=False)
I read the code in /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py and the issue holds as described.

1. The binary path is looked up again on every run. run_worker (line 731) calls worker_argv(), which calls worker_argv_base() (lines 416-425). worker_argv_base (lines 266-280) checks os.path.isfile on args.worker, default ./backsearch_worker_nt, each time. Nothing pins the binary or its inode at startup.

2. Each run's hash is parsed but never checked. run_worker takes SRC_HASH from the worker's stdout (lines 777-780, `run_hash = h`) and returns it. run_window only does `run_hash = run_hash or h` (line 605, and line 657 in the absorb pass), so the first run's hash wins and every later hash is thrown away. The report uses `"src_hash": run_hash or self.src_hash` (line 680). After read_version at startup (line 1550), no code compares a run's hash with self.src_hash.

3. The server stores one hash per tree. jobs.js prepareReport (lines 732-740) checks the whitelist once, against the report's src_hash. insNode (line 278) writes that one src_hash on every node of the tree. reissue (lines 421-429, used by `v2_hashes.js remove H --reissue`) reopens only jobs whose stored src_hash is off the whitelist. Nodes that H2 computed but that were filed under H1 are therefore invisible to both the whitelist and the reissue.

4. The binary can really change under a running client. build_pgo.sh line 117 links straight to -o "$OUT". The macOS linker replaces the file with a rename and GNU ld unlinks and recreates it, so either way the next Popen runs the new build. The docs do not say to stop first. v2/README.md line 37 says only "you will be told to `git pull && ./build_pgo.sh`". updates.json says "git pull and restart the client when convenient", which invites a rebuild in another terminal before the restart. check_dirty runs only at startup, and a pulled checkout is clean anyway.

5. The failure is limited in scope. If a window's first run already uses H2 and H2 is not whitelisted, the server refuses the report with 409 unknown_hash and the client stops itself (lines 919-920 and 941-942). So the leak is bounded: only the windows already running at rebuild time are affected, up to 16 of them, each for its remaining split_after time (up to 1800 s) plus the absorb time (up to 120 s). The heartbeat check at line 1182 compares only the startup hash, so it cannot catch this either.

What goes wrong, concretely:
- (a) The owner pushes a worker that is not yet whitelisted, or is buggy. For the in-flight windows, subtrees searched by H2 are accepted as covered under H1.
- (b) The likelier case: during a transition both H1 and H2 are whitelisted (updates.json has used "results from the previous worker are equally valid"). If H2 later turns out to lose levels, `remove H2 --reissue` reopens only the jobs labelled H2. H2 work labelled H1 stays "done", valid levels may be missed silently, and the per-job audit trail the reissue tool relies on is wrong.

Why not critical: the published result goes wrong only if a volunteer rebuilds mid-run and the new build is also buggy or unapproved. Why not low: when both happen, the loss is silent and defeats the recovery tool built for exactly this case.

Campaign #1 is unaffected: the snapshot has one whitelisted hash (6c531ee6...) and all 167,766 jobs carry it. Any H2 work there would also be labelled H1, so the snapshot cannot rule it out, but this does not bear on the next campaign's fix.

A related effect the finders did not report: if the binary path briefly does not exist, worker_argv_base calls sys.exit(2) inside a slot thread. The file can vanish while GNU ld unlinks and recreates it on Linux, or if a volunteer moves or deletes the binary. Python drops SystemExit silently in a thread, so that slot thread dies. slot.job stays set, and heartbeat keeps listing it in holding/running (lines 1161-1163), so the server renews that job's lease for as long as the client runs. The job stalls and the worker slot is lost without any message (medium/low).

No dynamic run is needed: the static logic is clear and small.

*fix notes*: Preferred fix: pin the binary at startup. In main, after check_dirty, copy the resolved worker binary into a private directory made with tempfile.mkdtemp(), chmod it 0700, and call read_version on the copy. Store self.worker_argv0 once and have worker_argv use it; stop calling worker_argv_base per run. A rebuild then cannot reach running windows, and a missing binary can no longer sys.exit a slot thread. Remove the temp directory on exit.

Defense in depth, whether or not the binary is pinned:
- In run_worker, treat a run as no result (return None, node stays open) when its SRC_HASH is missing or differs from self.src_hash. Log it and call request_stop('the worker binary changed since the client started; restart it').
- Build the report with "src_hash": self.src_hash, since every run has now been checked against it.
- Apply the same check in the absorb pass. The same helper covers it, because the absorb pass also goes through run_worker.
- If sys.exit is left anywhere reachable from slot threads, replace it with an exception that run_window catches. It should release the slot (slot.job = None) and request a stop, so the heartbeat stops renewing a job nobody is running.

Tests:
- Give fake_worker.py an env var (e.g. FAKE_HASH_AFTER=N:H2) that prints a different SRC_HASH from the Nth run on. Against fake_server.py, assert that no report carries nodes computed under H2 labelled as H1, that the H2 runs' nodes stay open, and that the client stops with the 'binary changed' message.
- Run a test that renames the worker binary during a window, and assert that the client neither hangs nor keeps renewing the lease.

Docs: in v2/README.md line 37 and the updates.json action template, say explicitly: stop the client (Ctrl-C) before `git pull && ./build_pgo.sh`, or build to a new -o path.
