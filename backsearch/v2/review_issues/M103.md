# M103: Small-table overflow restarts the solve on a 256 MB table, disables the parent table, and leaves the table resident

verdict CONFIRMED, severity medium, category performance
locations: sokoban_bfs.c:1753 (overflow at 32,768 inserts -> retry from scratch with use_big); sokoban_export_settled (small table only, cap 32,768); sokoban_solve_multi fails at 32K states

## Summary
A cutoff solve that passes 32,768 inserts throws its work away and redoes everything on a 16M-slot table with random probes. Its accepted state then exports no table (export is small-table only), so its children get no reuse. The multi-solve fails outright at 32K states and falls back to per-start single solves. These are exactly the deep checks that dominate cost.

## Source report F160 (algo-worker)
**Small-table overflow restarts the solve on a 256 MB table, disables the parent table, and leaves the table resident** at /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:1753

*summary*: A cutoff solve that passes 32,768 inserts throws its work away and redoes everything on a 16M-slot table with random probes. Its accepted state then exports no table (export is small-table only and capped at 32,768 entries), so its children get no reuse. The multi-solve fails outright at 32K states and falls back to per-start single solves. These are exactly the deep checks that dominate cost.

*failure_scenario*: Cost per call rises from 73 µs to about 2,000 µs with job depth at exit 1. At about 0.7 µs per pop (README: 179M pops in 125 s), deep checks average 1-3K pops with heavy tails. A check needing 40K states pays 32K wasted inserts plus 40K DRAM and TLB misses. The first such solve makes about 220 MB of the big table resident (32K random slots over 16K pages of 16 KB), and it is never freed. With the 160 MB dedup tables that is about 6-7 GB RSS for a 16-worker client.

*evidence*: sokoban_bfs.c:1023 'hs->ht_limit = HTP_SMALL_SIZE / 2;'; 1018 'hs->slot_big = calloc(HTP_SIZE, sizeof(HSlot64));'; 1751-1753 'use_big = 1; goto retry;'; 1500 'if (!hs->last_exhaustive || hs->slot != hs->slot_small) return -1;'; backsearch.c:537 '#define HTP_EXPORT_MAX 32768'; sokoban_bfs.c:1825 'if (hs->ht_count >= MS_SIZE / 2) { hs->overflow = 1; return -1; }' leading to bulk fallback at backsearch.c:2392-2415.

*suggested_fix*: Grow the table in steps (64K, 256K, 1M, 4M, 16M slots). Rehash from the touched list and remap the slot indices already queued, or look up by key on pop. Keep touched lists at every size, raise the export cap (for example 128K entries), and do the same for the MSLab table. Add counters for big-table retries and bulk fallbacks to SUMMARY so the share can be measured before campaign #2.

*expected_gain*: Unmeasured. If 10-30% of solver time is in solves over 32K inserts (plausible from the depth profile), a 2-3x speed-up there gives 5-15% overall, plus parent tables for deep states and about 200 MB less RSS per worker.

## Verifier (CONFIRMED, medium, refuted=False)
PREMISE: TRUE IN CODE.
- sokoban_bfs.c:1023: the small table is 64K slots (1 MB) with `hs->ht_limit = HTP_SMALL_SIZE / 2` (32,768 inserts).
- sokoban_bfs.c:1751-1754: once that limit is hit, `use_big = 1; goto retry;` runs the whole solve again from scratch on `slot_big`. That table is 16M slots x 16 B = 256 MB (calloc at line 1018), probed at `h64(k) & HTP_MASK`.
- The big table is never freed or madvised. `hsp64_clear` only bumps the generation counter.
- sokoban_bfs.c:1500: `if (!hs->last_exhaustive || hs->slot != hs->slot_small) return -1;` means an accepted state whose check used the big table exports no table.
- ms_slot (1825) fails at MS_SIZE/2 = 32K. The caller then solves the starts one by one (backsearch.c:2414-2435).

CORRECTIONS TO THE REPORT.
1. "Children get no reuse" is too strong. At backsearch.c:2262, `ns = *s` keeps the ancestor's ptab1, so the children use the ancestor's table at k+1. The README measures that as a 16-37% pop saving, against 47-49% for their own k=1 table.
2. The multi-solve part is negligible. Every depth-21 WBPROF log in results/ reports "381093 multi-solves ... 3 fallbacks" (13 in the worst log), about 0.001%.
3. The per-pop cost is not 0.7 us. results/wbprof_d21_split.log gives push-type checks 1,056,989 calls, 574M pops, 99.4 s, so about 0.17 us/pop and 540 pops/call. The 0.7 figure divides total run time by pops.
4. The random probes are partly hidden by the pass-1 `__builtin_prefetch`. The main extra cost on the big table is TLB misses: 16K pages of 16 KB, against about 3K L2-TLB entries. There is also the unprefetched stale-slot check on each pop.

MY SPEED ESTIMATE. For an N-insert solve, today's cost is the wasted small-table run plus the full run at roughly 1.3-1.6x the per-pop cost.
- A 1M-slot middle tier (16 MB, 1K pages, fits the TLB) saves about 1.3x on these solves.
- Growing the table in place saves about 1.5-1.9x.
- The finder's 2-3x is optimistic.

HOW MANY SOLVES ARE THIS BIG. The snapshot has no per-call size data. The report JSON carries neither bulk fallbacks nor big-table retries. Deep calls are clearly in this range, though. Exit-1 jobs seeded at depth 60-80 average 1.8-2.3 ms per call, depth 100-110 average 8-10 ms, and exit 6 depth 80 averages 27 ms. At 0.17 us/pop that is at least 10K pops, and inserts are at least pops. But jobs whose average call exceeds 1 ms hold only 3.5% of campaign CPU (21 of 602 h). Overall the campaign averages 97 us/call (22.4B calls, 602 CPU-h). I cannot measure the share of solver time in solves over 32K inserts inside shallow jobs; I put it at 5-30%. That gives an overall gain of about 1-8%, not the claimed 5-15% and 2-3x.

WHAT IS CERTAIN: MEMORY. Apple Silicon uses 16 KB pages, 1,024 slots per page. One overflowing solve touches at least 32K random slots, which faults in 16384 x (1 - e^-2), about 86% of the table: roughly 220 MB. On x86 with 4 KB pages it is about 100 MB at first, rising to 256 MB after a few such solves. That memory stays resident until the job's process exits.
- Per worker: shallow+recent dedup 64+96 = 160 MB, plus about 220-256 MB, plus up to 24 MB of MS arena. That is about 400 MB, against "about 200 MB of RAM" in v2/README.md:23 and "~250 MB" in README.md:255.
- volunteer.py defaults to cores-1 workers, so a 16-worker client needs about 6.5 GB, not 3.2 GB.

EXACTNESS RISK.
- A middle tier with restart has none. Keys are compared in full, so the explored set does not depend on table size. Keeping every tier at 50% load or less keeps the -3 probe-limit exit unreachable.
- In-place rehash has to remap the `e.slot` indices already queued, or re-look-up by key on pop. That is more code and must pass solvebench (exits 3 on mismatch), multitest/BULK_CHECK, REF_CHECK and test_split_exact.
- Raising HTP_EXPORT_MAX is safe. The ptab path builds size-adaptive tables through sokoban_ref_build; REF_SIZE's 32K cap applies only to sokoban_ref_load. Pooled PTab entries never shrink, so memory is at most about 30 live tables x 3 MB at 128K entries.

RELATED FINDING (not new code, found during this check). In a big-table solve, -2 (HP64_SIZE pending cap) and -3 are counted as "shortcut" at backsearch.c:2218. Such a state is pruned without a proof, which could lose a valid level, and no counter exists to show whether this ever happened. The counters proposed here should count these cases separately.

VERDICT: worth doing before the next campaign in its cheap form (counters, a middle tier, a corrected RAM figure in the docs). The large-speedup claim is unproven.

*fix notes*: 1. Measure first. Add SUMMARY lines and report-JSON fields for:
   - small-to-big retries, and pops spent in retried solves;
   - bulk fallbacks (already printed in SUMMARY, not sent in the report);
   - -2 (HP64_SIZE / heap cap) and -3 (probe limit) prunes, counted apart from real shortcuts. These prune a state without proof, which can lose a valid level; today they are counted as 'shortcut' at backsearch.c:2218.
2. Exact low-risk fix: add a middle tier, 1M slots (16 MB, 1K pages of 16 KB, fits the TLB).
   - Small (32K inserts) restarts on middle (512K inserts), which restarts on big.
   - Keep every tier at 50% load or less so -3 stays unreachable.
   - Allocate the tier lazily and keep the gen-stamp clear.
   - The result does not depend on table size, because keys are compared in full.
3. Optional growth in place: rehash from a touched list kept at every tier, then either remap queued e.slot values or look the slot up by key on pop. Gate it on solvebench (exits 3 on mismatch), multitest/BULK_CHECK, REF_CHECK and test_split_exact before any campaign use.
4. Export: record touched slots on the middle tier as well. Let sokoban_export_settled accept it (line 1500 currently requires slot_small). Raise HTP_EXPORT_MAX (for example to 131072) together with the static tk/tc buffers. No REF_SIZE change is needed, because ptab uses the size-adaptive sokoban_ref_build. Cap the PTab pool, since pooled tables never shrink their cap.
5. The same growth could apply to MSLab (MS_SIZE 64K). Low priority: the measured fallback rate is 3 in 381K.
6. Release policy: if the big tier stays, avoid madvise(MADV_FREE) after every big solve (about 14K refaults, tens of ms each time). A middle tier removes most big-tier use anyway.
7. Docs: correct the per-worker RAM figure in v2/README.md:23 ('about 200 MB') and README.md:255 ('~250 MB') from a measured max RSS. It is likely about 400 MB once the 256 MB table has been touched. Consider having volunteer.py cap the default worker count by RAM, not only by cores-1.
8. For a next campaign on another grid or with more blocks: the 128-bit path (g_bits_per_cell*(1+nb)+nh > 64, for example 6x6 with 10 or more blocks) has no small table at all. It probes about 384 MB of parallel arrays on every solve (sokoban_bfs.c:2281-2283), so it needs the same tiering before such a campaign.
