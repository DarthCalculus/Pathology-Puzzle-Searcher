# M71: Unauthenticated register inserts a client row per call, so one IP can fill max_clients and lock out new volunteers

verdict CONFIRMED, severity low, category security
locations: jobs.js:465 (register without token inserts and admits while below max_clients); per-IP cap 600/min; active window 180 s

## Summary
Every register call without a token inserts a clients row and, while below max_clients, admits it. With the 600/min per-IP cap, one host can keep max_clients admitted fake tokens alive (each counts as active for 180 s), which locks out real volunteers, and the clients table grows without bound.

## Source report F91 (server-scheduling)
**Unauthenticated register inserts a client row per call, so a single IP can fill max_clients and lock out new volunteers** at /Users/george/PathologyRecords/server/lib/jobs.js:465

*summary*: Every register call without a token inserts a clients row and, while below max_clients, admits it. With the 600/min per-IP cap, one host can keep max_clients admitted fake tokens alive (each counts as active for 180 s), and the clients table grows without bound.

*failure_scenario*: An abusive host registers 40 names every 3 minutes. active reaches max_clients, so every genuinely new volunteer gets 503 'full'. Existing admitted tokens are unaffected. This is malicious-only, hence low.

*evidence*: 464-465: `const token = cl ? cl.token : crypto.randomBytes(24).toString('base64url'); if (!cl) q.insClient.run(token, c.id, name, workers, t, t, 0);` 468: `if (active + ahead < c.max_clients) { q.touchClient.run(name, workers, t, 1, token); ...`. server.js 30: v2ip limit 600/min.

*suggested_fix*: Cap new registrations per IP per hour (e.g. 10), and count only clients that have leased or reported toward `active`.

## Verifier (CONFIRMED, low, refuted=False)
jobs.js:463-470: a register without a valid reusable token always inserts a new clients row (insClient, admitted=0), then admits it while `active + ahead < c.max_clients`. activeClients (:259) counts admitted clients with last_seen within ACTIVE_S=180 s (:38), and register sets last_seen=t, so one call keeps a slot for 3 minutes. The only limits are the per-IP buckets (server.js: v2ip 600/min, 36,000/h), and the per-token bucket does not apply because the body has no token. Filling max_clients=40 (snapshot) needs about 14 registrations per minute from one IP, far under the cap, after which new volunteers get 503 'full'. Existing admitted tokens keep working, since the admitted branch at :459-461 returns first. The table grows by up to 864k rows per IP per day. Queries stay indexed (idx_clients_seen on campaign_id, admitted, last_seen), so the cost is disk only, not CPU. An honest client does not trigger this: it reuses its stored token, and while queued it re-registers with that token (no new row). Malicious-only, so low under the owner's trust model.

*fix notes*: Cap new-token registrations per IP (e.g. 10 per hour) in v2routes before calling jobs.register. Count toward `active` only clients that have leased or heartbeated after registering. Periodically delete never-used rows (no jobs, admitted=0 or last_seen older than a day). Gate test: 50 tokenless registers from one IP, then assert the 11th gets 429 and the table has at most 10 new rows.
