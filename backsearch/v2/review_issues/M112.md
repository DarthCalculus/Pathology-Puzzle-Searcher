# M112: The v2 server code exists only as untracked files on the laptop and the VPS

verdict CONFIRMED, severity medium, category robustness
locations: PathologyRecords git status: untracked jobs.js, v2routes.js, public v2 pages, tools, test/; uncommitted server.js, db.js, solver.js, pipeline.js; deploy notes (GitHub copy older than the server; rsync deploys, sometimes from Windows)

## Summary
jobs.js, v2routes.js, the v2 public pages, the tools and the gate tests are untracked in the PathologyRecords repo, and the modified server.js and db.js are uncommitted. Deploys go by rsync, sometimes from a Windows machine, and the GitHub copy is older than the server. A disk loss or a bad rsync would destroy the only copies of the scheduling code behind the published proof, with no history to diff or restore.

## Source report F190 (robustness-ops)
**The v2 server code exists only as untracked files on the laptop and on the VPS** at /Users/george/PathologyRecords/server/lib/jobs.js:1

*summary*: jobs.js, v2routes.js, the v2 public pages, the tools and the gate tests are untracked in the PathologyRecords repo, and the modified server.js and db.js are uncommitted. The deploy notes say the GitHub copy is older than the server and deploys go by rsync, sometimes from a Windows machine.

*failure_scenario*: The laptop dies: the only copy of the campaign server code is /opt/pathology/server on the VPS, which has no backup of its own (see the jobs.db finding). Or the owner deploys a small records-site fix from the Windows tree, which lacks v2 (rsync without --delete overwrites server.js with a pre-v2 version). /api/v2/* then returns 404, the running clients' report batches are rejected, a 404 is not transient, so they go to rejected/ and are never retried, and the campaign stalls until someone notices.

*evidence*: gitStatus at session start: `?? server/lib/jobs.js`, `?? server/lib/v2routes.js`, `?? server/public/collective.js`, `?? server/public/hunt.js`, `?? server/test/`, ` M server/server.js`, ` M server/lib/db.js`. deployment_pathology.md line 49 area (2026-09-15 entry): 'The SERVER copy of the site code is newer than GitHub (user deploys from Windows without pushing)'. volunteer.py:915-923: only transient errors or 401 go to the outbox; everything else goes to reject().

*suggested_fix*: Commit and push the v2 server now, and deploy from a git checkout on the server, or rsync only from a clean, tagged tree. Record in each deploy which commit is live, for example a /api/version endpoint.

*expected_gain*: The campaign server survives losing either machine and cannot be silently downgraded.

## Verifier (CONFIRMED, medium, refuted=False)
I checked each claim and all of them hold.

1) Git state (`git status --short` and `git ls-files` in /Users/george/PathologyRecords):
- Untracked: server/lib/jobs.js, server/lib/v2routes.js, all hunt/collective/campaigns pages, updates.json and server/test/.
- Modified but never committed: server.js, db.js, pipeline.js and solver.js. `git diff --stat` shows 1062 insertions, including 596 in db.js (the proofs and derivedProofs code).
- HEAD is only 2 commits deep (894b799, cb23d83), so none of the v2 server has any history.

2) A consequence the source report missed: server/tools cannot be committed as things stand. The .gitignore line 2 pattern `tools/` (meant for the portable Windows toolchain) matches every directory named tools. `git check-ignore -v server/tools/v2_seed.js` returns `.gitignore:2:tools/`. So v2_seed.js, v2_finish.js, v2_hashes.js, add_proof.js, set_chunk_plan.js and finish_chunks.js are ignored. Even the suggested fix ('commit and push the v2 server now') done with `git add -A` would silently leave out the tools that seed campaigns and publish proofs. The deploy recipe also excludes tools/ ('scp them separately'), so the VPS copy of the tools may drift from the laptop copy.

3) Deployment practice (deployment_pathology.md):
- 2026-09-15: 'The SERVER copy of the site code is newer than GitHub (user deploys from Windows without pushing)'.
- 2026-09-23: v2 was deployed with `rsync -az server/ root@...:/opt/pathology/server/` without --delete.
- The only named pre-deploy backup, /opt/pathology/server.bak-20260923, is from before v2.
- The daily cron backup (/var/backups/pathology) sits on the same VPS disk, and I could not verify whether it covers code or jobs.db.
- The worker side is committed and pushed in the backsearch repo (c5bf7d8 through aa7f0bf); the server side is not.

4) The downgrade scenario is concrete:
- server.js:13 requires ./lib/v2routes and server.js:149 routes /api/v2/*. A pre-v2 server.js from the Windows tree would send every /api/v2 request to the generic 404 at server.js:317.
- In the client, volunteer.py:92 treats only status >= 500 or 429 as transient, and volunteer.py:915-923 queues only transient errors or 401 to the outbox. A 404 on /api/v2/reports therefore goes to reject(), which writes rejected/*.json and never retries.
- Leases fail and retry forever (volunteer.py:473-478), and heartbeat failures are only logged (volunteer.py:1171-1175). The campaign stalls quietly.
- Recovery is possible: rejected reports stay on disk, and the jobs are leased out again once their leases expire.

5) Why medium: this is an ops and process gap, not a code bug, and it cannot change a published result. The realistic harm for the next campaign is a silent downgrade or divergence between the laptop and the VPS, or a stall with wasted work. On top of that, the upcoming fixes will overwrite the only copy of the scheduler that produced proof #1, with nothing to diff or bisect against. Losing the code for good would need both machines to fail, so high is not warranted.

*fix notes*: 1) Before any next-campaign edits, commit the current v2 server as-is and tag it campaign1-final, so the code that ran the published proof is preserved.
2) Fix .gitignore:
   - Anchor the toolchain rule to the repo root (`/tools/`) so server/tools/ is no longer ignored.
   - Add `data/jobs.db*` and `data/*.bak*` so runtime databases are never committed.
   Then `git add server/tools server/lib server/public server/test solver/solver6.c`, commit and push.
3) Pull the VPS copy of server/tools back first and diff it against the laptop copy, since tools/ was scp'd separately.
4) Deploy only from a clean, tagged checkout:
   - Either `git pull` on the VPS with a deploy key, or rsync from a tree where `git status --porcelain` is empty.
   - Keep --exclude=data/ always.
   - Refuse to deploy when HEAD is not pushed.
   - Retire deploys from the Windows tree, or require it to be `git pull`ed first.
5) Stamp the live commit: write `git rev-parse HEAD` into a VERSION file at deploy time and expose it via `/api/v2/status` or `/api/version`. The owner can then confirm what is live, and campaign records can store the server commit alongside worker_hash.
6) Client robustness (optional): treat a 404 on /api/v2/* as transient, so reports go to the outbox and retry after a bad deploy instead of landing in rejected/.
7) Keep an off-box copy of jobs.db and the code, for example by pulling nightly to the laptop, since /var/backups is on the same VPS disk.
