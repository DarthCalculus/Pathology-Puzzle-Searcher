# M48: Inherited BS_* debug environment variables make every job 'exhausted' with 0 states (BS_DUMP_SEED) or fill the disk (BS_TRACE_*)

verdict CONFIRMED, severity medium, category robustness
locations: backsearch.c:4394 (BS_DUMP_SEED returns exhausted=1 before searching); BS_TRACE_VISITS / BS_TRACE_VALID (one file per worker PID in the backsearch dir); volunteer.py passes its whole environment to workers; server accepts exhausted with states=0

## Summary
The worker honours debug environment variables in protocol mode, and volunteer.py passes its entire environment to workers. With BS_DUMP_SEED set, every run returns exhausted=1 before searching, and the server accepts that as a covered subtree with states=0, which silently loses coverage. BS_TRACE_VISITS and BS_TRACE_VALID write one ever-growing file per worker PID into the backsearch directory.

## Source report F32 (worker-io-cli-memory)
**Inherited BS_* debug environment variables make every job 'exhausted' with 0 states (BS_DUMP_SEED) or fill the disk (BS_TRACE_*)** at /Users/george/Documents/Claude Projects/project45/backsearch/backsearch.c:4394

*summary*: The worker honours debug environment variables in protocol mode, and volunteer.py passes its whole environment to workers. With BS_DUMP_SEED set, every run returns exhausted=1 before searching, and the server accepts an exhausted summary with states=0. BS_TRACE_VISITS and BS_TRACE_VALID write one file per worker PID into the backsearch directory.

*failure_scenario*: The owner or a volunteer exported BS_DUMP_SEED=1 while debugging, then starts volunteer.py from the same shell. Every leased job prints the seed and `SUMMARY {"status":"exhausted","states":0,...}`. The client marks it done, and sanitizeSummary (jobs.js:640-647) accepts integers >= 0. Whole subtrees count as covered without being searched. Only the 2% duplicate cross-check could flag it, so a few bad jobs have a good chance of reaching a published proof. With BS_TRACE_VISITS exported, each worker writes one path line per expanded node. At the observed ~1.8M accepted states per 120 s window and ~150 B per line, that is ~270 MB per 2 minutes per worker, or ~2 GB/min for 16 workers, filling the volunteer's disk. test_chaos.sh:41 depends on this pass-through (`BS_TRACE_VALID=$T/tv/$1 ... python3 volunteer.py`).

*evidence*: backsearch.c:4394 `if (getenv("BS_DUMP_SEED")) { ... if (out_exhausted) *out_exhausted = 1; ... return 0.0; }` returns before try_successor, so g_states_checked stays 0. 4869-4873 `if (getenv("BS_TRACE_VISITS")) {... g_trace_visits = fopen(tn, "w"); }`, then 4638 writes one line per expanded node. volunteer.py:743 `subprocess.Popen(argv, stdout=subprocess.PIPE, ..., cwd=BACKSEARCH_DIR, ...)` has no env= argument. jobs.js:641 `if (!isInt(s[k], 0, Number.MAX_SAFE_INTEGER)) return null;` accepts states 0.

*suggested_fix*: Worker: ignore BS_DUMP_SEED (or report a non-result status such as `debug`) whenever --split-after or --status-every is given, and gate the BS_TRACE_* variables behind an explicit flag. Client: strip BS_* from the worker environment unless an opt-in such as VOLUNTEER_PASS_TRACE=1 is set, and use that in test_chaos.sh. Server: reject exhausted summaries with states < 1, since a real run always checks at least its seed.

*expected_gain*: Removes an accidental path to false coverage and to disk exhaustion on volunteer machines.

## Verifier (CONFIRMED, medium, refuted=False)
I read the code path end to end and it behaves as described. The trigger is operator error, not a defect in normal runs.

1) Worker. backsearch.c:4394-4399, in the seed-path branch of run_exit_search: `if (getenv("BS_DUMP_SEED")) { ... print_puzzle_for_exit(&seed, g_exit_pos); fflush(stdout); if (out_exhausted) *out_exhausted = 1; if (out_dedup_full) *out_dedup_full = 0; return 0.0; }`. This returns before `try_successor(&seed)`, the only place that increments g_states_checked (line 2082 `g_states_checked++;`, the first statement of try_successor_x). The caller at 5770-5849 then prints `SUMMARY {"status":"exhausted",...,"states":0,"accepted":0,"valid":0,"best":0,...}` with no LEVEL line. Nothing in the worker distinguishes protocol mode (--split-after / --status-every) from a manual run. BS_TRACE_VISITS and BS_TRACE_VALID are opened unconditionally in main (4869-4873) as `<value>.<pid>` in mode "w". Line 4638 writes one path per expanded node and line 2245 one line per valid level. Tracing does not change search results, only disk usage.

2) Client. volunteer.py:743 calls `subprocess.Popen(argv, stdout=subprocess.PIPE, ..., cwd=BACKSEARCH_DIR, ...)` with no env=, so the worker inherits the whole environment. A relative BS_TRACE_* path therefore lands in the backsearch directory (BACKSEARCH_DIR = os.path.dirname(HERE), line 33). The parser at 798-804 accepts any SUMMARY whose status is exhausted or split, and never checks states. In both the main loop (607) and the absorb pass (659), an exhausted summary sets node status to "done".

3) Server. sanitizeSummary (jobs.js:636-649) accepts `isInt(s[k], 0, ...)`, so states=0 passes. applyReport (782) stores the job as done, and a done node has no children, so its whole subtree counts as covered.

Mitigations I checked:
- The 2% duplicate re-issue (jobs.js:812-815) is created only for done jobs and is served only to a *different* client (jobs.js:274).
- A mismatch sets mismatch=1, which makes coverage `clean` false (1005, 1013). So a sustained BS_DUMP_SEED client running next to healthy clients would very likely be caught.
- The cross-check is gone when only one client is active, which is exactly the owner running alone. dupsOfExit (298) ignores open duplicates, so unserved duplicates do not block `clean`.
- The symptoms are loud: states=0, elapsed about 0, and jobs finishing in milliseconds. The damage is also recoverable, because the seeds are kept and the affected rows are identifiable (states=0 AND status='done').

Likelihood:
- BS_DUMP_SEED is documented nowhere except the C comment, so volunteers will essentially never set it.
- BS_TRACE_VISITS appears only in the developer README.md:191 and DESIGN.md:191.
- test_split_exact.py:52 and test_chaos.sh:37/41 set these variables inline for one process, not exported.
- The realistic path is the owner exporting a variable while debugging and then starting volunteer.py from the same shell.

Disk-fill estimate from the snapshot: 9,631 accepted states per worker-second on average. At roughly 150-250 B per path line that is about 1.5-2.5 MB/s per worker, so 16 workers write about 1.5-2.4 GB/min, as the finder said. BS_TRACE_VALID alone is about 1,682 valid levels/s per worker, roughly 0.5 MB/s per worker. That would fill a volunteer's disk within hours.

Is the proposed server guard safe? In the snapshot, the minimum states over all 165,670 done rows (duplicates included) is 1 and over split rows is 1,323, with no NULLs. Since try_successor always counts the seed, rejecting done or exhausted summaries with states < 1 would not have refused any real campaign #1 report.

Severity: I keep medium. If triggered, the consequence is silent coverage loss in an exhaustive proof, or a full disk on a volunteer machine. But the trigger is an operator mistake with an undocumented debug variable, it is usually detectable, and the data can be recovered. The fix is a few lines.

*fix notes*: Defence in depth, all cheap:

(a) Server (most important, since it covers every client): in parseTree/sanitizeSummary, reject a done node whose summary has states < 1, and also a split node with states < 1. A real seed-path run always counts its seed (try_successor_x starts with g_states_checked++). The snapshot shows min states = 1 for done rows and 1,323 for split rows, so no legitimate report is refused. Also consider counting unserved open duplicates as "unchecked" in the coverage panel, so a single-client window is visible.

(b) Client, volunteer.py:743: pass `env={k: v for k, v in os.environ.items() if not k.startswith('BS_')}` unless an opt-in such as VOLUNTEER_PASS_BS_ENV=1 is set. Update test_chaos.sh:41 to set that opt-in, because it relies on BS_TRACE_VALID passing through. test_split_exact.py calls the worker directly and is unaffected. Also have the client drop, and log loudly, any exhausted SUMMARY with states < 1 instead of marking the node done.

(c) Worker: when --split-after or --status-every is given, either ignore BS_DUMP_SEED or print a non-result status (e.g. "debug") so neither the client nor the server treats it as coverage. Optionally, open the BS_TRACE_* files only with an explicit flag, or print a stderr warning when they are active in protocol mode.

(d) Add a gate test in server/test/v2_gates.test.js: a report with nodes[0] = {status: 'done', summary: {status: 'exhausted', states: 0, valid: 0, best: 0}} must get a 400.
