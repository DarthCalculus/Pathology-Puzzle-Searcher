# M19: The client does not dedupe lease grants against queued or running jobs, so one client can run the same job in several slots

verdict CONFIRMED, severity medium, category bug
locations: volunteer.py:508 (leaser_loop appends every granted job)

## Summary
The leaser appends every granted job without checking whether its id is already queued or running locally. With §9 work stealing, a job can pass from X to Z and back to X between two of X's heartbeats (leases every 10 s, heartbeats every 30 s). X's next heartbeat sees the job leased to X, so X never drops the earlier copy, and several of X's slots run the job at once until the first report lands.

## Verifier (CONFIRMED, medium, refuted=False)
**Client, volunteer.py:484-509.** `leaser_loop` builds `good` from the lease response and runs `self.queue.extend(good)` under `self.cond`. Nothing checks the granted ids against `self.queue`, against any `slot.job`, or against `self.pending` (finished reports not yet sent). `take_job` (523-530) pops blindly, so every idle slot starts whatever is queued.

**Server gives a stolen job back to its old holder (jobs.js:601-631).**
- The steal branch runs when the pool is empty (`need > 0 && jobs.length === 0`).
- `leasedOthers` (266-267) only excludes jobs held by the requester right now (`j.client_token != ?`). A job that was just stolen from the requester is a valid candidate.
- The ranking is `rank = j => [runningOf.get(j.client_token).has(j.id) ? 1 : 0, -heldBy.get(...), -j.leased_at]`, which prefers jobs not in the holder's last-heartbeat `running_json`, then newest `leased_at`.
- A job Z has just stolen (`stealJob` sets `leased_at = t`) matches both preferences: it is the newest lease, and Z's `running_json` does not list it until Z's next heartbeat, up to 30 s later. Leases run every 10 s (`batch_interval_s`).
- So when X has an idle slot and the pool is empty, a job Z took from X within the last heartbeat interval is among the first jobs X's next lease steals.

**Heartbeat does not catch the duplicate (jobs.js:525-534).** `for (const id of holding) { if (held.has(id)) continue; ... drop.push(id) }`: J is leased to X again, so X gets no drop. Slot A keeps its copy and slot B starts the second one. Each further steal-back before the first copy reports adds another copy. The extra copies die only after the first report lands and X's next heartbeat returns `drop`. Z's copy dies at Z's next heartbeat.

**Correctness is not affected.** In `applyReport` (744-772) the first report wins, and later ones are stored as 'dup' or 'dup_mismatch'. The cost is wasted CPU only, so this is not critical or high.

**Snapshot data fits the mechanism.**
- Job 167664 was finished (split) by HuO58q at 09:17:09.
- It then received 40 dup reports from 4 tokens up to 09:20:04. HuO58q's own dups have elapsed times of 119, 116, 114, 111, 109, 106 and 103 s, which puts their start times about 10 s apart, one per lease cycle. That is the steal-back pattern.
- Same-second pairs from one token (RtSso4 at 09:17:37, 09:19:36 and 09:19:46) are two local copies that finished within one 10 s send batch.
- 171 dup reports came from the winning token itself, 5.0 CPU-h counting root elapsed only (absorption time not included).

**The campaign #1 figures overstate the waste under current code.** Several copies of 167664 started after 09:17:09 and ran to full completion. The current drop logic would kill those within about 30 s. The client's holding/drop logic went into git at 2026-09-24 03:09 UTC (commit 3829d5c), so some volunteers were probably still on older clients. Treat the 10-14 CPU-h measured as an upper bound for the next campaign.

**Severity: medium.**
- The waste happens only when the pool is empty (the end game, at 10 clients x 16 workers).
- It is mostly capacity that would otherwise sit idle, but it keeps volunteers' machines busy for nothing.
- It uses up steal capacity: the hot-potato job is always the top candidate, so real stragglers are stolen later and the end game runs longer.
- A later copy on the same machine can never finish first, so every extra copy is pure waste.

**Checked and fine.**
- The `reclaimed` path (heartbeat re-lease of a job in `holding`) does not add a local copy.
- The lease branch cannot return one id twice in a response.
- Drop kills every copy, queued or running, once J is finished. A copy between two worker runs (`s.proc` is None) escapes for one heartbeat only, because J stays in `holding` and the next heartbeat drops it again.

**Related consequence.** Release-by-omission (jobs.js:514) can also make a client run the same job again. X finishes J and its report sits in `pending` for up to 10 s. A heartbeat in that gap omits J and reopens it, since `leased_at` is more than 120 s old. X's own leaser can then take J back as the deepest open job and queue it. That copy dies at the next heartbeat after the report lands, so the waste is at most about 30 s. Checking `self.pending` in the same dedupe fixes this as well.

*fix notes*: 1. **Client (volunteer.py `leaser_loop`, just before 506-508).** Under `self.cond`, build `held = {j["id"] for j in self.queue} | {s.job["id"] for s in self.slots if s.job} | {r["job_id"] for r in self.pending}`. Skip and log every granted id that is in `held`, and skip repeats within `good`, before `self.queue.extend(good)`. Skipping is safe: the server records the job as leased to this client, which already holds it, or its pending report is about to land.

2. **Server root cause (jobs.js steal, 610-629).** Do not steal a candidate with `t - j.leased_at < heartbeat_s + margin` (for example 45 s). The holder's `running_json` is stale for such jobs, so the "not running" ranking is wrong for them. Or rank the oldest `leased_at` first among non-running candidates, since a job queued the longest is the true straggler. Optionally also record the previous holder, for example a `prev_token` column, and never hand a job back to the client it was stolen from within a few minutes. This ends the hot-potato ping-pong between all clients, not only duplicates inside one client.

3. **Tests.**
   - a) In the `test_client.sh` style with `fake_server.py`: make the lease response return an id the client is already running. Assert only one slot runs it and a 'skipping duplicate grant' line is logged.
   - b) In `v2_gates.test.js`: A holds J; B steals J (pool empty); A leases again within 30 s with the pool empty. Assert J is not returned to A.
   - c) A `jobs.js` test for the release-by-omission race: a heartbeat without J while J's report is in flight must not let the same client get J again.
