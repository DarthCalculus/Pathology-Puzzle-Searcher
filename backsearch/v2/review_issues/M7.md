# M7: Forward solver identifies states by 64-bit Zobrist key only (HSlot64 and multi-start MSLab): a collision can hide a shortcut or, in the multi solver, invent a win

verdict CONFIRMED, severity low, category soundness
locations: sokoban_bfs.c:1062 (hsp64 insert: `if (s->key == k)` merges states); sokoban_bfs.c:1830 (MSLab lookup `if (sl->key == k) { *is_new = 0; ...}` reuses cached successors/labels); reference-table lookups

## Summary
HSlot64 stores only the Zobrist key, although the exact packed state (at most 64 bits) is carried in the heap entry. A key match merges two different states and drops the second unless it is cheaper, which can hide a shortcut (a false accept); false hits in the reference table can prune. In sokoban_solve_multi, the label slot, with its cached successor list and walk-to-exit distance, is found by key alone. A colliding configuration then replays the first one's successors and win distance, so it can report a false shortcut and lose a valid level. The 128-bit path uses exact keys.

## Source report F19 (worker-prune-soundness)
**Multi-start solver identifies states by 64-bit Zobrist key alone and reuses a cached expansion, so a collision can report a false shortcut** at /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:1830

*summary*: In sokoban_solve_multi a state's label slot, including its cached successor list and walk-to-exit distance, is found by key only. The expansion is computed from the first entry popped for that slot. A second, distinct configuration with the same key then replays the first one's successors and win distance. In the single solver a collision can only drop states (possible false accept). In the multi solver it can invent a win (lost level).

*failure_scenario*: Distinct configurations X and X' collide on the 64-bit key, and X is expanded first. A start i that actually reaches X' is credited with X's walk-to-exit distance. MS_DECIDE_SHORT then sets out[i]=1 and propagates to the starts behind it. Those bulk walk-back children are pruned as if they had shortcuts, even when they are valid levels (and roots of record subtrees). The probability is about n^2/2^65 per multi solve: n = 1e4 gives 2.7e-12, times roughly 1e9 bulk solves is about 3e-3 per campaign.

*evidence*: sokoban_bfs.c 1830: `if (sl->key == k) { *is_new = 0; return (int)idx; }`. 1977-1991: `if (!lb->cached) { ... bp[i] = (int)((e.state >> sh) & g_cell_mask) ... lb->wexit = wdist[exit_pos];`. 2035-2037: `if (lb->wexit >= 0) { int wc = e.prio + lb->wexit; for (...) if (wc <= cut[i]) MS_DECIDE_SHORT(i); }`. By contrast the single solver expands the exact e.state (1615) and uses the key only for cost dedup (1729).

*suggested_fix*: Store the packed e.state (8 bytes) in MSLab and compare it in ms_slot, or check it before replaying a cached expansion. On a mismatch, return -2 so the candidates fall back to single solves.

*expected_gain*: Removes the only path by which a hash collision in the forward checker could discard a valid level.

## Verifier (CONFIRMED, low, refuted=False)
Verified. USE_ZOBRIST is defined (sokoban_bfs.c:161). hsp64_update identifies states by key alone (1062: `if (s->key == k) { if (new_cost < s->cost) ...; return -1; }`), and so do ref_lookup (1450) and ms_slot (1830: `if (sl->key == k) { *is_new = 0; return (int)idx; }`). In the single solver and the reference table, a collision can only drop or prune forward states. That can hide a shortcut (a false accept), which adds explored states and cannot lose a level; the site's re-solve would catch it on a champion. The multi-start solver is worse. The label slot's cached expansion is built once from the first popped e.state (1977-2019), and lb->wexit is set from that state's walk (1991). Every later pop of the same slot replays it (2027-2037: `if (lb->wexit >= 0) { int wc = e.prio + lb->wexit; ... MS_DECIDE_SHORT(i); }`). If distinct X and X' collide, a start that only reaches X' inherits X's labels, successors and exit distance. That can invent a shortcut and prune a valid bulk child together with its whole subtree. This is the only hash-collision path that can lose a valid level. Probability: the MS table overflows to -2 at MS_SIZE/2 = 32768 slots (ms_slot), so a multi solve has at most about 32768^2/2^65 = 2.9e-11 chance of any collision. Campaign #1 made 2.24e10 solver calls in total (snapshot SUM(solver_calls)). Typical n is far below the cap, and a collision only harms when it pairs a cheaply reached X' with an X that has a short walk to the exit or a successor chain to a win within the cutoff. The realistic chance of a lost level is well below 1e-3 per campaign, and the chance it lands in the subtree holding the maximum is far smaller. It scales roughly linearly with campaign size. Correctly rated low.

*fix notes*: The suggested exact-state compare is not a drop-in fix. The Zobrist key deliberately merges permutations of same-mask blocks (sokoban_bfs.c:152-156), and the packed state keeps block identity (`ns = (ns & ~(g_cell_mask << bsh)) | (new_bpos << bsh)`), so equivalent states have different e.state values. Comparing e.state would split legitimate merges; a return of -2 on mismatch would force frequent fallbacks to single solves. Better: compute a second, independent Zobrist key (a second set of z tables, updated by the same XOR deltas) and store and compare it next to key. That costs MSLab 48->56 B, MSSucc 24->32 B (arena 24->32 MB) and HeapEntry64 +8 B. Alternatively, canonicalize by sorting same-mask block cells before packing. At minimum do the multi solver, since it is the only path that can lose a level. Add an assertion test: forcing a tiny key width (e.g. mask keys to 16 bits in a debug build) must make split-vs-monolithic valid-level sets differ, which proves the check catches collisions.
