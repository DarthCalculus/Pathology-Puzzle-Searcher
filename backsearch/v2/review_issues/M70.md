# M70: finishJob overwrites an open probe node's level unconditionally and leaves its verified_moves stale

verdict CONFIRMED, severity low, category bug
locations: jobs.js:287 (finishJob sets best/level_code from the new run, keeps verified_moves)

## Summary
An open node carrying a probe level may already have been verified as a new best. When that node later runs as a job, finishJob replaces best and level_code with the new run's values but keeps the old verified_moves, so a new level can look verified. A re-run with a smaller best, or no level, erases the probe's level from the row.

## Source report F89 (server-scheduling)
**finishJob overwrites an open probe node's level unconditionally and leaves its verified_moves stale** at /Users/george/PathologyRecords/server/lib/jobs.js:287

*summary*: An open node that carries a probe level may already have been verified as a new best. When that node is later run as a job, finishJob replaces best and level_code with the new run's values but keeps the old verified_moves. A re-run with a smaller best, or no level, erases the probe's level.

*failure_scenario*: A probe level L1 (depth d) is the new best and gets verified_moves = d. Later the node is leased and reported with a different level L2 of the same depth. That is not a new best, so there is no re-verification, and the champion row now shows L2 with L1's verification ('solver agrees' in v2_finish). A slower machine that explores less than the probe did would lower best or clear the level.

*evidence*: 287-288: `finishJob: UPDATE jobs SET status = ?, client_token = ?, lease_until = NULL, done_at = ?, src_hash = ?, states = ?, accepted = ?, valid = ?, best = ?, level_code = ?, elapsed_s = ?, solver_calls = ? WHERE id = ?` (verified_moves is not reset). 790-795: open nodes with levels can be the newBest passed to verifyLater.

*suggested_fix*: In finishJob, set verified_moves = NULL whenever level_code changes. Keep the deeper of the old and new level on the same row.

## Verifier (CONFIRMED, low, refuted=False)
jobs.js:287-288 finishJob sets best and level_code from the new run and never touches verified_moves. Open nodes carry a level with best=levelBest (insNode at :789-791; parseTree :701-711, volunteer.py:669-673), and they can be the newBest passed to verifyLater (v2routes.js:153 -> setVerifiedMoves). So both outcomes are reachable: a same-depth different level keeps the old verification, and a shallower run, or none, erases the probe's level from the row. Impact is weaker than it sounds. A probe that splits is reported open and its partial work is dropped, so the node's whole subtree is covered again when it runs as a job. The probe's level L1 therefore reappears in that row or in a descendant, and the final MAX(best) and published result stay exact. In practice the job re-runs the same deterministic DFS from the same seed for at least 120 s, versus the 10 s probe, so it usually re-finds L1 first (L2 == L1). The erase case needs a machine more than 12x slower or an early SIGINT (a client stopping seconds after the job starts). The effect then is a temporary drop of the displayed per-exit best. A stale 'solver agrees' label can only arise from a same-depth tie with a different code. Even then processSubmission re-solves the champion at publish, although addProof runs before it (v2_finish.js:66-70). Snapshot: all 62 verified rows have verified_moves == best and no open rows still hold a level, so no damage was observed. Low, cosmetic.

*fix notes*: In applyReport, when job.level_code is not null and the new first.levelCode is null or shallower (first.levelBest/s0.best < job.best), keep the old level_code and best on the row. Otherwise write the new values and reset verified_moves when the code changes, e.g. `verified_moves = CASE WHEN level_code IS ? THEN verified_moves ELSE NULL END`. Gate test: an open node with a level and verified_moves set, reported with a same-depth different code, gives verified_moves NULL; reported with no level, the old level stays.
