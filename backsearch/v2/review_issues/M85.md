# M85: Campaign 'extra' flags pass unfiltered to the worker, so a compromised server can overwrite volunteers' files

verdict CONFIRMED, severity high, category security
locations: volunteer.py:420 (server extra list appended verbatim to worker argv); backsearch.c flags that open paths at parse time: --harvest (fopen 'wb'), --trace-csv, --bf-dump, --estimate-dump (append)

## Summary
The client appends the server-provided extra list verbatim to the worker's argv. The worker has flags that open arbitrary paths for writing at parse time, before any other validation: --harvest truncates the file and writes argv strings into it, and --trace-csv, --bf-dump and --estimate-dump append. A compromised or misconfigured server (the public site) can therefore truncate or append to any file the volunteer can write, such as ~/.bashrc. The client should whitelist the flags it accepts.

## Source report F125 (e2e-exactness)
**Campaign 'extra' flags pass unfiltered to the worker, so a compromised server can overwrite volunteers' files** at /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py:420

*summary*: The client appends the server-provided extra list verbatim to the worker's argv. The worker has flags that open arbitrary paths for writing at parse time, before any other validation: --harvest (fopen 'wb', which truncates the file and then writes the argv strings into it), --trace-csv, --bf-dump and --estimate-dump (append).

*failure_scenario*: An attacker who can write campaigns.extra_json (a compromised site or DB) sets extra to ["--harvest","../../.zshrc", ...]. Every volunteer who cloned into $HOME, as the README suggests, has ~/.zshrc truncated and replaced with a binary header plus attacker-chosen argv strings on the next job. That is at least destruction of the file, and possibly injection of shell code.

*evidence*: volunteer.py:420 `extra = [str(x) for x in extra if str(x).strip()]`, then `... "--status-every", str(STATUS_EVERY_MS)] + extra`; backsearch.c:5166-5168 `--harvest` then `harvest_open(argv[i], argc, argv)`; 722 `g_harvest_csv = fopen(path, "wb");`; 780 `harvest_write(g_harvest_argv[i], ...)`.

*suggested_fix*: Whitelist the extra flags in the client, and again in createCampaign: --allow-exit-transit, --num-holes N, --num-blocks N and numeric-only values. Refuse any flag that takes a path.

*expected_gain*: Removes a server-compromise-to-volunteer-machine path.

## Verifier (CONFIRMED, high, refuted=False)
I confirmed this by reading the code. There are three corrections to the report, and none of them weakens it.

The client passes the flags through without filtering.
- volunteer.py:416-425 (`worker_argv`) does `extra = self.param("extra", [])`, optionally `shlex.split`, then `extra = [str(x) for x in extra if str(x).strip()]` and appends `+ extra` after the fixed flags.
- `self.campaign` is filled from the server's register and heartbeat responses by `apply_campaign` (volunteer.py:315-318, `self.campaign.update(camp)`). It is refreshed on every heartbeat (around line 1179), so a change to extra_json in the DB reaches every running client within one heartbeat.
- There is no validation anywhere in the client.
- The worker is spawned with `cwd=BACKSEARCH_DIR` (volunteer.py:743-744). BACKSEARCH_DIR is `<clone>/backsearch` (line 33). VOLUNTEERS.md:26-27 tells volunteers to `git clone ...` and then `cd Pathology-Puzzle-Searcher/backsearch`. For a clone made in $HOME, `../../.zshrc` is therefore `~/.zshrc`. `../../.pathology_volunteer.json`, the client's own token store (line 35), is reachable the same way.

The worker opens these files while it parses its arguments.
- backsearch.c:5166-5168: `--harvest` calls `harvest_open(argv[i], argc, argv)`, which does `g_harvest_csv = fopen(path, "wb")` at line 722, or `gzopen(path,"wb1")` for a .gz path. The file is truncated immediately.
- harvest_emit (line 788) writes the header plus the NUL-separated argv blob (lines 777-780). It then writes a 144-byte record per emitted state. Emission is called from the DFS path (lines 1835-2242, 4444, 4504), so a normal campaign job can also write gigabytes and fill the disk.
- Correction 1: `--trace-csv` (5143-5146) and `--bf-dump` (5148-5151) open with `fopen(argv[i], "w")`. That truncates the file; the report says they append.
- Correction 2: only `--estimate-dump` appends (line 4202, `"a"`), and only in estimate mode, so it does nothing in a normal DFS job.
- Unknown arguments exit through print_usage/return 1 at line 5419-5421, but only after the earlier flags have already opened and truncated their files. So even an argv the worker rejects destroys the target file.
- Correction 3 (partial): injecting shell code is not demonstrated. The file starts with the binary "BSH1" header, so bash would refuse to run it as a script. Whether zsh would execute it when sourcing an rc file is untested. `--estimate-dump` does accept any string, so attacker text can sit in the argv blob. Destroying the file is certain.

The server does not filter either.
- jobs.js:347-348 (createCampaign) only checks `extra.length > 40` and each string `length > 100`.
- createCampaign is reached only from tools/v2_seed.js (server-side admin). An attacker therefore needs write access to the server, its DB, or the seed plan, or the owner has to make a mistake (for example copying a debugging `--harvest`/`--trace-csv` into plan.json).

Why this matters: apart from this path, a compromised server has no way to touch volunteer files. The client never downloads code and only checks the hash. This bug turns a single compromise of the public site into truncation, or disk-filling, of arbitrary user-writable files on every volunteer at once. The rubric puts "harm to a volunteer machine" at high; the precondition (server compromise or owner misconfiguration) is the only reason not to go higher. The static reading is conclusive, so no dynamic repro is needed.

*fix notes*: 1. Client (volunteer.py `worker_argv`, or better, one check when the campaign is applied or changes): accept only an explicit whitelist of extra flags.
   - Allowed: `--allow-exit-transit` (no value); `--num-holes N`, `--num-blocks N` and `--max-depth N`, with N matching `^[0-9]{1,3}$`.
   - Reject `--allow-block-on-exit` (owner rule).
   - Reject any flag that repeats a fixed argument (`--grid/--exit/--seed-path/--time/--split-after/--status-every/--two-tables`).
   - Reject everything else, especially path-taking flags (`--harvest`, `--trace-csv`, `--bf-dump`, `--estimate-dump`, `--rollout-bf-target`, `--nn-value-model`, `--list-layer`...).
   - On rejection, stop with a clear message; do not silently drop the flag, because dropping it would change the search space and corrupt results.
   - Also validate `grid` against `^\d{1,2}x\d{1,2}$`.
2. Server (jobs.js createCampaign, around line 347): the same whitelist, and additionally require `--allow-exit-transit` to be present. Also check it in v2_seed.js so a bad plan.json fails before any row is written.
3. Optional defence in depth in the worker: a `--campaign` or `BS_NO_FILE_OUTPUT` mode in which path-opening flags are refused. This changes SRC_HASH, so it would ship with the next campaign's build.
4. Test: in test_client.sh, have fake_server.py serve `extra: ["--harvest","../pwned.bin"]` and assert that the client refuses to start and no file is created. Add a v2_gates.test.js case asserting createCampaign throws for `--harvest`, for `--allow-block-on-exit`, and for a missing `--allow-exit-transit`.
