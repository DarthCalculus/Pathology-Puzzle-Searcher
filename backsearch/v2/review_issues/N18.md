verdict CONFIRMED, severity medium, category test-gap
locations: /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py:503

## Summary
After the solver speedup, every layer-2 root of the chaos configuration finishes in under 1 s. The client clamps both the leased window and each run's split time to 1 s, so lowering split_after_s cannot force a split, and the test stops with 'no job was split'. A timing-based split is also nondeterministic, so the level-set check cannot tell which run's trace the server accepted. Separately, the fake worker prints SRC_HASH (which the client uses as the signal that it may send SIGINT) before installing its handler. A SIGINT in that gap raises KeyboardInterrupt, the process dies with rc -2 and no SUMMARY, and test e logs an error.

## Verifier (CONFIRMED, medium, refuted=False)
Both parts hold. (1) volunteer.py:503 stores 'split_after_s': max(1.0, sa) for every leased job. volunteer.py:592 calls run_worker(slot, job, seed, max(1.0, deadline - now)), and line 438 has the same 1.0 floor. The worker only splits on time (backsearch.c:4646-4650, 'el >= g_split_after_s'; there is no node-count split). So when every layer-2 root finishes in under 1 s, no campaign split_after_s value can produce a split. test_chaos.sh:24-25 already sets split_after_s 1 and ramp 1, and line 58 then exits 3 with 'no job was split'. That matches the lead's run. The file's header comment ('~4 s monolithic ... several jobs exceed split_after = 1 s') is stale since the solver speedup. The title slightly overstates the problem: a heavier worker config (more blocks, layer 1, or the 4x4 ≤3-holes regime the finder suggests) would still split. What cannot force a split is lowering split_after. I also confirmed a second weakness. Even when splits happen, the level-set check (test_chaos.sh:63-82) unions the traces from every worker run in tv/*. That includes orphaned workers of the SIGKILLed client A (Popen with start_new_session=True at volunteer.py:743-745, so they outlive the client and keep tracing) and re-issued duplicates. A subtree the server's accepted tree lost can therefore still look covered, so the check is weaker than a check of accepted work. (2) fake_worker.py:105 prints SRC_HASH, and the handlers are installed only at lines 128-129, after arg and grid parsing and the FAKE_DIE check. The client treats the first output line as permission to send SIGINT (volunteer.py:766-770 sets saw_output, then _send_stop at 1026-1036). A SIGINT in that gap hits Python's default handler, the fake worker dies with rc -2 and prints no SUMMARY, which explains the test e flake. The real worker has no such race: it installs its handlers at backsearch.c:4866 before printing SRC_HASH at 4868. So this part is a harness flake, not a production defect. Severity: no production bug. But this is the only end-to-end test of split, tree reports and audit with the real worker, and today it does not exercise splitting. When it does split, its level check is permissive. That is a real gap before the next campaign, so medium (low if judged purely by production impact).

*fix notes*: Add a deterministic --split-after-nodes N to the worker, checked beside the time check at backsearch.c:4646, and let the client pass it for test campaigns. Or make the 1.0 floors at volunteer.py:438/503/592 a campaign client param (min_window_s, default 1.0). Rebase test_chaos on a config whose roots take more than 1 s (for example the 4x4 ≤3-holes campaign regime). Make the level-set check use only traces from runs whose seed is a node of the server's accepted tree: with deterministic splits, key the traces by seed. Assert that the kill and the SIGINT landed while workers were running. In fake_worker.py, move signal.signal(SIGINT/SIGTERM) to the top of main(), before the first out().
