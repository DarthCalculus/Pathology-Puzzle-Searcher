# M38: The campaign's search definition (grid, rule flags) is never checked when a campaign is created or a report arrives; the proof still claims 'every RxC level under the game rules'

verdict CONFIRMED, severity high, category protocol
locations: jobs.js:347 (createCampaign accepts any extra flags); v2_finish.js:49 (proof class from capsFromExtra: only --num-holes/--num-blocks; 'real rules' hard-coded); backsearch.c:5845 (SUMMARY carries SRC_HASH but no effective flags); v1 campaign.py enforced the owner rules

## Summary
Nothing checks that `extra` contains --allow-exit-transit and lacks --allow-block-on-exit. Nothing rejects flags that narrow the search or override the client's own flags, or requires rows <= cols. SUMMARY echoes the binary hash but not the effective grid, transit, hole cap or dedup mode, so the server cannot confirm that a result came from the campaign's definition. v2_finish still publishes 'every RxC level with at most N holes under the game rules'. The owner's ALWAYS/NEVER rules, which v1 enforced, are unenforced and unverifiable after the fact. (F124 also raises root provenance, covered separately.)

*suggested_fix*: Add a `flags` object or hash to SUMMARY (e.g. grid, allow_exit_transit, allow_block_on_exit, max_blocks, max_holes, two_tables, bulk, exit_block_prune), and have the server compare it with the campaign definition and refuse mismatches.

*expected_gain*: End-to-end provenance: every proof row is tied to both the code and the search definition.

## Verifier (CONFIRMED, high, refuted=False)
I read every cited location and its callers. The issue holds.

1. No validation when a campaign is created. At jobs.js:347-348, `const extra = Array.isArray(p.extra) ? p.extra.map(String) : []; if (extra.some(s => s.length > 100) || extra.length > 40) throw ...` checks lengths only. No code requires '--allow-exit-transit', refuses '--allow-block-on-exit', or rejects flags the client sets itself or flags that narrow the search. parseGrid (jobs.js:93-99) does not require rows <= cols. v2_seed.js passes plan.json straight to createCampaign, and there is no HTTP route for creating campaigns.

2. v1 did enforce these rules, so v2 is a regression. campaign.py:190-192 prepends transit and exits on '--allow-block-on-exit is not a legal Pathology setup; refusing'. run_chunks.py:33-34 also prepends transit.

3. The proof class is built from the caps alone. capsFromExtra (jobs.js:101-109) reads only '--num-blocks' and '--num-holes', using the first occurrence (indexOf). The worker's argv parsing keeps the last occurrence (backsearch.c:5319-5326), so a repeated flag makes the two disagree. v2_finish.js:30,50-51 writes {rows, cols, exitCell, maxBlocks, maxHoles} plus the hard-coded 'backsearch, real rules'. The proofs table comment (db.js:85) says the class is 'under the game's rules (blocks may be pushed over the exit; no level starts with a block on the exit)'.

4. The client does no filtering. volunteer.py:417-425 appends extra after its own flags. The worker's parser is last-wins: '--time' at backsearch.c:4933 simply overwrites g_time_cap_s.

5. SUMMARY (backsearch.c:5845-5849) carries status, seed, exit, states, accepted, valid, best, verify, evict_*, elapsed, solver_calls and src_hash. It has no grid, transit, caps, max-depth or two-tables fields. The server can check the binary but not the search definition.

Some misconfigurations fail loudly (a stall or a loop of rejected reports), not silently:
- '--grid' in extra: validateLevel rejects levels whose dimensions differ from the campaign grid (jobs.js:124-126).
- '--exit' in extra: parseTree rejects a summary.exit that does not match the job.
- '--seed-path' in extra: parseTree rejects a summary.seed that does not match the node.
- '--time N' in extra: jobs end as time_cap and stall.

The silent failures are the dangerous ones:
- Omitting '--allow-exit-transit'.
- Narrowing flags: --max-depth, --fixedholes/--fixedwalls, --place-holes, --holeless, --num-walls, --single-axis-blocks, --dupe-threshold.
- A repeated '--num-holes' whose values differ.
- Roots listed with different flags (the provenance part, tracked separately).
In each of these, every job completes, the audit is clean, and v2_finish publishes a class larger than the one searched. addProof (db.js:663-666) refuses a proof only when a stored verified level of the class has more moves. For campaign #1's classes the stored 149 would catch an under-count at exit 1. A new campaign-#2 class (more holes, another grid) has no stored levels, so there is no backstop.

Grid 5x4 is accepted as well. Its proof is filed with rows=5, cols=4 and exit cells in 5x4 coordinates. Site searches reject rows > cols (server.js:108) and levels are stored canonically with rows <= cols (level.js:120). The proof is wasted, not wrong.

Additional consequence (a volunteer-machine risk not mentioned in the merged issue): because neither server nor client allowlists extra, whoever can write campaigns.extra_json controls part of the worker's argv on every volunteer machine. '--trace-csv PATH' and '--bf-dump PATH' do fopen(argv[i], "w"), which truncates any file the volunteer's user can write (backsearch.c:5143-5152). '--harvest PATH' also writes, and '--argfile PATH' reads local files. The owner is trusted, so this only matters if the site is compromised. It would widen such a compromise to every volunteer machine; the client should refuse unknown extra flags.

Checks that turned out fine:
- Campaign #1's stored extra is exactly ["--allow-exit-transit","--num-holes","3"] (snapshot DB), so this does not affect the published #1 proof.
- No code path updates extra_json after creation (only an INSERT exists). F42's mid-campaign-edit scenario needs a manual sqlite edit.
- volunteer.py builds argv as a list with shlex.split, so there is no shell injection.

Severity: I keep it high, not critical. A wrong published maximum needs an operator slip in a hand-written plan.json (or a stale roots command), not a code path taken on its own. But the next campaign is expected to change exactly these flags (hole count, grid). v1 had a guard, v2 dropped it, and if the slip happens the result is a silently wrong exhaustive claim with a clean audit. Static reading settles this, so no dynamic repro is needed.

*fix notes*: 1. Server, createCampaign (jobs.js:347), with the same check repeated in v2_finish.js before publishing:
- Parse extra against a strict allowlist. Require '--allow-exit-transit' exactly once. Allow '--num-holes N' and '--num-blocks N' at most once each, with integer N. Reject everything else.
- Reject explicitly, with clear messages: '--allow-block-on-exit'; the flags the client sets itself ('--grid', '--exit', '--exitloc', '--seed-path', '--time', '--split-after', '--status-every', '--two-tables', '--no-two-tables'); every narrowing or experimental flag ('--max-depth', '--fixed*', '--place-holes', '--holeless', '--num-walls', '--single-axis-*', '--dupe-threshold', '--mandatory-holes', '--beam', '--rollout*', '--estimate*', '--list-layer', '--list-tasks', '--task-id', '--from', '--until'); and every flag that touches files ('--trace-csv', '--bf-dump', '--harvest', '--argfile', '--nn-*', '--rollout-bf-target', '--estimate-dump').
- Require rows <= cols in parseGrid, or at least in createCampaign.

2. Client, volunteer.py worker_argv: apply the same allowlist and refuse to start, with a clear message, if the server sends an unknown flag. This protects volunteer machines if the site is ever compromised.

3. Worker: add a 'cfg' object, or a hash of it, to SUMMARY. Fields: grid, allow_exit_transit, allow_block_on_exit, max_blocks, max_holes, max_depth, two_tables, bulk, exit_block_prune, holeless, num_walls, any fixed/place restrictions. sanitizeSummary/parseTree should reject a done node whose cfg does not match the one the campaign expects (derived from grid plus extra). This also catches stale client builds that forget to append extra.

4. Have --list-layer print a header with the same cfg, K and SRC_HASH, and have v2_seed refuse a file whose header does not match the plan. This is the provenance part tracked separately.

5. Tests for v2_gates.test.js:
- createCampaign rejects: extra without transit; with '--allow-block-on-exit'; with '--time 3600'; with '--max-depth 50'; with '--num-holes' repeated; grid '5x4'.
- A report whose SUMMARY cfg has allow_exit_transit=0 or a different max_holes is rejected as bad_tree and does not count as done.
- volunteer.py refuses an extra containing '--trace-csv'.
