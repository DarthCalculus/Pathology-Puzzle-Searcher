## Verifier (CONFIRMED, medium, refuted=False)
The gap is real. Every automated exactness test compares the worker with itself, running in its own default mode:
- v2/test_split_exact.py:70 `full, _, full_vis, full_val = run('', 0)` is the only reference.
- test_chaos.sh:37 `BS_TRACE_VALID=$T/full "$WORKER" "${CFG[@]}" --two-tables --time 0` is also the same binary in the same mode.
- None of the v2 tests pass --no-bulk-walk, --no-state-canon, --no-two-tables, --no-parent-table or --no-exit-block-prune (grep finds none).
- No forward or brute-force level enumerator exists in either repo. old_experiments/pathbf.c only replays one given level. multitest.c and the -DREF_CHECK/-DBULK_CHECK builds check solver optimisations against the plain solver, not the backward generator.
- The worker has no dedup-off switch for the main search (only the estimator runs with dedup off).
- DESIGN.md:193-195 ("both dominate the same levels") is asserted, not tested.

I downgraded the severity from high to medium. It is a test gap, not a defect, and several partial guards exist:
1. **Manual A/B checks.** backsearch/README.md:55-57 and :168-172 record by-hand equivalence runs with the prune on and off: `valid levels 473037` / `584050 valid levels either way` across --no-exit-block-prune, and accepted-count equality with --no-bulk-walk on zero-eviction configs. So the alternative modes were used, but only by hand, comparing counts rather than sets, and not repeatably.
2. **Static check of the mechanism the finding names.** The dedup key ignores wh, seg, adjflags and bulk_walk, and each prune driven by those flags only removes states that have a real forward shortcut in their own puzzle, so the result does not depend on the path taken:
   - Walk-segment prune (backsearch.c:2358, 2530): `adist[c] < seg_len + dist[c]` means that walking to the push anchor and following its solution is shorter.
   - adjflags prune (616-640, run before the dedup insert at 2109-2126): the recorded moment M at depth >= 2 exists in the pull-off child's forward replay. The pushed block's mask gains d^2, so a one-move win at M gives a total below depth(C) for any path to C.
   - bulk_walk children: any committed walk-back left out by the dedup'd twin is either the parent's bulk child at the same depth or has a walk-to-parent shortcut.

   So the dedup/flag interaction looks sound, and the finding's example scenario (a prune keyed on an ignored flag) does not hold for the current prunes.
3. **Upper side is covered independently.** Every published level is re-verified by the site's own solvers, so an invalid level or a too-high best cannot be published.
4. **Live falsification check.** db.js:636 (listProofs) and :651-667 (addProof) flag or refuse a proof when a stored verified level of the class is longer. records.db holds 5x5 levels found independently by others (mathmasterzach 108, Allpollo 116, davidspencer6174, the Double2048 bot, and so on); none contradicts. 4x5's stored max of 70 matches the proven 70. This is sparse evidence but independent.

What remains unguarded, and why the gap still matters for the next campaign: a completeness bug in backward move generation is shared by every mode and every split. Examples: a missing move kind (walk, push, new block, un-consume, exit transit), the root direction-orbit reduction (g_canonical_dir_mask at 2497/2805/2946), or the state canonicalisation (apply_sym_to_state and the mask remap at 925-943). Such a bug would pass every current test and would lower the published maximum with nothing to catch it. The next campaign may change the grid, and a non-square grid has a different symmetry subgroup and has never been through split or oracle tests (test_split_exact covers 4x4 and 5x5 only).

Side note, not part of this issue: dedup compares only a 64-bit hash (dedup_check_and_insert ~978, dedup_two_tables 1086-1111, `key == key`, no full-state compare). A false match per lookup is about 2^23/2^64. At campaign #1's roughly 3.6e10 states that is an expected ~0.02 false dedups: negligible, and no test could catch it anyway.

*fix notes*: Suggested tests before the next campaign, all cheap, one CPU, under a minute each:

(1) **Forward oracle on tiny grids.**
- Write a small C enumerator linked with sokoban_bfs.c, or better, the site's solver3.c so the check is truly independent.
- Grids: 2x4, 3x3, 3x4 (include a non-square grid), each canonical exit, at most 2 blocks and at most 2 holes, with exit-transit rules and no block starting on the exit.
- Enumerate "minimal" levels only: unused cells are walls and block masks hold only the directions that are used. Justification: removing unused options never changes the optimal length, so the class maximum is the same.
- Compare the per-exit maximum and the set of canonical maximum-length levels with the worker's BS_TRACE_VALID output under the same caps.

(2) **Mode matrix, comparing sets rather than counts.**
- Configs: 4x4 exit 0 with at most 3 holes, and 5x5 exit 7 with at most 3 blocks.
- Modes: default, --no-bulk-walk, --no-parent-table, --no-exit-block-prune, --no-state-canon and --no-two-tables. Use zero-eviction table sizes (-DSHALLOW_LG2=24 -DRECENT_LG2=24) where needed.
- Require identical canonical valid-level sets and the same best across all modes. This turns the by-hand README checks into a repeatable test.

(3) **Forward-verify levels.** Check every BS_TRACE_VALID level of one small config, or a random sample of a big one, with the site solver. The optimum must equal the traced depth; fail on any mismatch. This catches extras and wrong depths.

(4) **Non-square split test.** Add a 4x5 case to test_split_exact, since a grid change brings a different symmetry subgroup and different canonical exits.

(5) **Nested-class check.** Optionally, have the publish step assert that each new class maximum is at least the maximum of every published subclass for the same exit.

Keep the site's contradiction flag (db.js) as the live backstop.
