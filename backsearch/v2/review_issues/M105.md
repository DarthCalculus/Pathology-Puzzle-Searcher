## Verifier (PLAUSIBLE, low, refuted=False)
Every factual claim checks out against the code. The claimed gains are overstated. None of the changes affects exactness if done as described below.

Premise, point by point:
1. HeapEntry64 is 40 B (sokoban_bfs.c:944-955). The fields are `int prio; int g; int player_pos; uint32_t used; uint32_t slot;` (20 B), then 4 B of padding, `uint64_t state`, and `uint64_t key` (USE_ZOBRIST is defined at :161).
2. `used` is dead. `ne.used = e.used | (1u << cand[ci].dirbit);` (:1740) only feeds best_used -> used_dirs (:1763-1765). Every caller passes NULL: backsearch.c:1707, 2440, 5785, solvebench.c:84, seed_from_level.c:261, multitest.c:50. Dropping it also removes the known UB at :1740, and at :1251 in solve_push64.
3. `key` duplicates the slot key. After `if (hs->slot[e.slot].cost < e.g) continue;` (:1596) the same 16-B HSlot64 holds `key` at offset 0, so reading it there is free. In the multi-start solver the key is only needed on first expansion (:2017 area). Its MSLab is 48 B, so key and lab can sit on different cache lines. That solver should keep its current handling.
4. tail_width is updated on every pop (:1598-1601, and :2549 in the 128-bit solver). shortcut_check always passes &prof, but prof.tail_width is read only under g_use_tailwidth (backsearch.c:1715-1720). bfs_tail_reset also zeroes 256 B per solve.
5. Double hashing is real. `__builtin_prefetch(&hs->slot[h64(nk) & hs->ht_mask], 1, 1);` (:1682) is followed by hsp64_update, which recomputes `uint64_t h = h64(k) & mask;` (:1049) for the same nk. The two passes are separate loops, so no common-subexpression elimination is possible.
6. Two clock_gettime calls per check (backsearch.c:1706-1708). Their only consumer is g_solver_time_by_depth, printed only `if (total_calls > 0 && g_solver_profile)` (:5900).
7. The symmetry copy is real. `*out = *in;` (backsearch.c:931) copies the full BState per non-identity symmetry (:959-962). My arithmetic from the struct at :424-465 gives 448 B.

My own gain estimates:
- Symmetry copy: negligible campaign-wide. Exits 1 and 7 have a trivial stabilizer, so zero copies. Exits 0, 2 and 6 make one copy each. Only exit 12 makes 7. In the snapshot, exit 12 was 3.5 of 347.5 job-hours (1.0%); exit 1 was 191.9 h (55%). The ~0.6 us per state is the cost of the whole canonical_state_key: transform, sorts and a serial splitmix chain in state_key. The fix removes only the memcpy, about 5-10 ns x 7, so roughly 0.3-0.5% of exit-12 time and about 0.005% of the campaign. The "about 4% at centre exits" claim does not hold for this fix.
- clock_gettime: about 40-50 ns per check. The snapshot shows 21.9 us per solver call at exit 12 and 126 us at exit 1, so this is at most 0.2%. It is trivially gateable.
- Per-pop items, against roughly 150-250 ns per expansion (README: 43 s over 200M expansions in the multi bucket):
  - tail_width: about 1 ns, 0.5% or less.
  - 40 B -> 24 B entry: about 0.5-1%, since LIFO buckets stay hot in L1.
  - Single hashing: about 1-2 ns per pass-2 candidate, roughly 1-2%.
- Combined: about 1-3% of solver time, 1-2% of wall time. That is the low end of the claimed 2-6%. It is real but small.

Exactness: none of these changes alters solver decisions or DFS order.
- Pop order depends only on prio and push order, and the slot index does not affect results.
- The runs can therefore be checked for bit-identical states/accepted/best counts on the equivalence configs.
- One real caveat on replacing h64 with raw key bits: the Zobrist values come from xorshift64, which is GF(2)-linear (:170-176), so the raw low bits form a purely linear hash. Clustering would be a performance problem only, except in the big table: there a probe failure returns -3, which try_successor prunes (backsearch.c:2218-2222). That makes it a theoretical exactness hazard. In practice the 64K probe limit against about 1.3K-long clusters at 85% load makes it very unlikely. The small and MS tables cannot fail, because the probe limit equals the table size at load 0.5 or less.

Verdict: PLAUSIBLE, low. Worth bundling into the pre-campaign worker rebuild; dropping `used` is the most valuable piece because it removes known UB. Not a blocker, and the headline numbers should not be expected.

*fix notes*: Changes in order of value and safety:
1. Delete `used` from HeapEntry64 and HeapEntry128 (the 128-bit entry carries a 16-B `__uint128_t used`, relevant if the next grid needs the 128-bit path). Also delete best_used and the used_dirs fill in all four solvers. The used_dirs parameter can stay in the API and be documented as ignored, or be removed. This fixes the known UB at sokoban_bfs.c:1251/1740.
2. Hash once per candidate: compute `uint32_t hidx = h64(nk) & hs->ht_mask` in pass 1, store it in PushCand (which grows 24 -> 32 B), prefetch with it, and pass it to an hsp64_update_at(hs, k, hidx, cost) variant. This keeps the current hash distribution.
   - Do NOT switch to raw Zobrist bits unless zobrist_init also moves from xorshift64 to splitmix64 outputs. If that is done, change hsp64_update, ms_slot, sokoban_ref_build and ref_lookup together.
3. Narrow the cutoff solver's entry to {uint64_t state; uint32_t slot; int16_t g, prio;} plus an int8 player, 24 B total. Read the key as hs->slot[e.slot].key after the cost check at :1596. For the multi-start solver, either keep a separate entry type with the key or read L[e.slot].key only when the successors are not yet cached.
4. Wrap the tail_width increment (:1598-1601, :2549) in a flag set only when g_use_tailwidth, for example a want_tail field in BfsProfile.
5. Gate the two clock_gettime calls and the per-depth time accumulation (backsearch.c:1706-1708, 1731-1732) behind g_solver_profile.
6. Skip the key-only symmetry transform; it is not worth the code. If exit-12-type exits matter on a future grid, a cheaper state_key (a Zobrist-style XOR maintained per symmetry) would be the real win, but it changes the dedup key function and needs its own review.
Verify with bit-identical equivalence-config counts and a solvebench A/B, and bump SRC_HASH as usual.
