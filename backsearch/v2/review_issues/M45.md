# M45: 128-bit state packing silently overflows when bits_per_cell*(1+nb)+nh > 128 (e.g. 6x6 with 20+ blocks)

verdict CONFIRMED, severity high, category soundness
locations: sokoban_bfs.c:2127 (dispatcher sends every >64-bit state to the 128-bit solvers without a fit check); pack/unpack shifts; g_max_blocks default MAX_BLOCKS=32; campaign command has no --num-blocks

## Summary
Nothing checks that a packed state fits in 128 bits. With 6 bits per cell (6x6, 7x7), 20 blocks plus 3 holes need 129 bits. Shifts reach 126-131, so high bits are lost, or the shift count is >= 128, which is UB. Distinct states then alias in the exact-key table, and lost hole bits make open holes look filled after unpacking, so shortcut checks give wrong answers on a larger-grid campaign.

## Source report F24 (solver-core)
**128-bit state packing silently overflows when bits_per_cell*(1+nb)+nh > 128 (for example 6x6 with 20 or more blocks)** at /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:2127

*summary*: The dispatcher sends every puzzle over 64 bits to the 128-bit solvers, but nothing checks that the packed state fits in 128 bits. g_max_blocks defaults to MAX_BLOCKS = 32, and the campaign command has no --num-blocks. With 6 bits per cell (6x6, 7x7), 20 blocks plus 3 holes need 129 bits. Shifts reach 126..131, so high bits are lost, or the shift is >= 128, which is UB. Distinct states then alias in the exact-key table. After unpacking, the lost hole bits make open holes look filled.

*failure_scenario*: Take a future 6x6, 3-hole campaign and a state with 20 blocks. pack128 puts the hole mask at bit 126, so bit 128 (hole #2) is dropped. Two states that differ only in hole #2 share one slot. After unpack, hole #2 reads as filled, so the player may walk over an open hole, and a block pushed onto it is not consumed. The forward optimum comes out wrong in either direction. The state can be pruned as a false shortcut (a valid level lost) or accepted with a wrong depth (an invalid 'record'). Not reachable in the current 5x5 campaign: at most 20 blocks, which is 5*21+3 = 108 bits.

*evidence*: sokoban_bfs.c:2674  if (g_bits_per_cell * (1 + nb) + nh > 64) return solve_push128(pz, used_dirs, prof);
sokoban_bfs.c:2127-2132  static inline __uint128_t pack128(int pl, const int *bp, int nb, int hm) { ... for (int i = 0; i < nb; i++) { s |= ((__uint128_t)bp[i] << sh); sh += g_bits_per_cell; } s |= ((__uint128_t)hm << sh);
sokoban_bfs.c:2554  int hm = (int)(e.state >> sh);
backsearch.c:133  static int g_max_blocks = MAX_BLOCKS;   (MAX_BLOCKS 32, sokoban_bfs.h:10)

*suggested_fix*: At startup, compute the largest nb that fits (b*(1+nb)+nh <= 128) and clamp g_max_blocks to it, with a loud message, or refuse to start. Also add a runtime check in sokoban_solve / sokoban_solve_cutoff that aborts (not prune) if the key cannot hold the state. Alternatively, add a key wider than 128 bits, or store block occupancy as a bitboard per mask.

*expected_gain*: Prevents silent wrong solve lengths once the campaign moves to a larger grid.

## Verifier (CONFIRMED, high, refuted=False)
I confirmed this by reading the code. I did not compile or run anything.

**No fit check anywhere.** There is no check that a packed state fits in 128 bits.
- The dispatcher checks only the 64-bit limit. sokoban_bfs.c:2674 `if (g_bits_per_cell * (1 + nb) + nh > 64) return solve_push128(pz, used_dirs, prof);`. The cutoff variant at :2681 does the same.
- pack128 (:2127-2132) shifts block i to `g_bits_per_cell*(i+1)` and the hole mask to `g_bits_per_cell*(nb+1)`, with no bound.
- All three 128-bit solvers use it and unpack with `int hm = (int)(e.state >> sh);`: solve_hash128 :2155/2166, solve_push128 :2375/2391, and solve_push128_cutoff (about :2525/2554).
- The only fit guard is the 64-bit one at :1842.
- g_bits_per_cell comes from `bits_needed(g_ncells + 1)` (:134). That is 5 bits for up to 31 cells, 6 bits for 32-63 cells, and 7 bits for 64 cells.
- g_max_blocks defaults to MAX_BLOCKS = 32 (backsearch.c:133, sokoban_bfs.h:10). --num-blocks only rejects values above 32 (backsearch.c:5315).
- parse_grid (backsearch.c:4859) accepts any grid up to 64 cells. The header comment at backsearch.c:17 saying "R,C in [1..5]" is stale.
- The server's parseGrid (jobs.js:93-98, MAX_AREA = 64 in level.js:13) also accepts any grid up to 64 cells. Nothing checks a bit budget.
- Campaign #1's extra was `["--allow-exit-transit","--num-holes","3"]`, so no --num-blocks. A copy of that config for another grid would run uncapped.

**What goes wrong.** Take a 6x6 grid with 3 holes and nb = 20.
- The hole mask starts at bit 126, so hole #2's bit (bit 128) is dropped even in the initial state, where ihm = 7.
- Every state in that solve then treats hole #2 as already filled (plain floor). The player can walk over it, and a block pushed onto it is not consumed. The forward solve is therefore for a different puzzle.
- With nb = 21 the hole-mask shift is 132. That is undefined behaviour. With clang's usual lowering of variable i128 shifts it probably acts like a shift by 4, which would OR the hole bits into the player and block-0 fields and scramble the state. Even without that, the hm read at `>>132` is garbage.

**Why a wrong answer loses levels.** shortcut_check (backsearch.c:1697-1706) prunes whenever rc >= 0, and also on -2 and -4. So a falsely short answer from the solver silently removes that state and every valid level below it. This is the critical-class failure: an exact maximum that is wrong with no warning. A falsely long answer would at worst report a wrong level. Server verification of reported levels would likely catch that, but nothing catches a missed one.

**Where it can happen.** In the backward state, blocks sit on board cells with every hole open, so nb <= ncells - 2 - nh (at most 32).

| Grid | Bits | Overflow |
|---|---|---|
| 5x5, any hole count | 5 | never (at most 5*21+3 = 108 bits with 3 holes). Campaign #1 is safe, and a 5x5 "more holes" campaign is safe too. |
| 4x6 | 5 | never |
| 4x7 | 5 | never with nh >= 2; nb >= 25 with nh <= 1 |
| 5x6 / 6x5 | 5 | only nearly full boards: nb = 25 with nh = 3, nb = 24 with nh = 4 |
| 4x8, 5x7, 6x6, 7x7 | 6 | nb >= 20 with nh = 3 |
| 8x8 | 7 | nb >= 17 |

On 5x5 the per-job best levels already reach 11 blocks (snapshot histogram peaks at 7-8, max 11), and the DFS visits denser prefixes than the best levels. So 20+ blocks on 36 cells is well within what a 6x6-class search would visit.

**Severity.** I kept high for the next campaign. The consequence is critical (silent loss of valid levels), but it only happens if the owner picks a grid of 32+ cells, or 5x6 with dense boards. It cannot happen at 5x5, and the fix is trivial. Two side notes:
- `int ihm = (1 << nh) - 1` and `int hm` also cap nh at 30, while g_max_holes defaults to MAX_HOLES = 64. That is UB for nh >= 31. It is harmless while --num-holes is small.
- The 128-bit used-dirs mask (bi*4+d <= 127) fits for nb <= 32, so that part is fine.

*fix notes*: 1. **Worker (backsearch.c main, right after sokoban_set_grid at :5432).**
   - Compute `hb = min(g_max_holes, 30)` and `nb_fit = (128 - hb) / g_bits_per_cell - 1`.
   - If g_max_blocks > nb_fit, refuse to start with a clear error rather than clamping silently. Clamping changes the search space, so the campaign owner has to pass --num-blocks explicitly and accept it.
   - Also reject g_max_holes > 30, or make hm a uint64_t.
2. **Solver (sokoban_solve and sokoban_solve_cutoff, sokoban_bfs.c:2672-2686).** Add a hard runtime check: `if (g_bits_per_cell*(1+nb)+nh > 128) { fprintf(stderr, ...); abort(); }`. Do not return -2 here, because shortcut_check treats -2 as a prune and would drop levels silently.
3. **Server (jobs.js campaign creation, around :346-352).** Compute the same bit budget from the grid (bits = ceil(log2(area+1)), min 5) and the --num-holes / --num-blocks caps. Reject a campaign whose worst case exceeds 128 bits unless --num-blocks is given within budget.
4. **Tests.**
   - A solver unit test on a 6x6 puzzle with 19 blocks and 3 holes: 6*20+3 = 123 bits, which fits, and should match the site solver.
   - A test that 20 blocks on 6x6 is refused at startup.
   - A long-term alternative: a wider key (for example 192 bits) or a block-occupancy bitboard key.
5. **Docs.** Fix the stale comment at backsearch.c:17 ("R,C in [1..5]").
