# M51: Invalid or overlong REMAINING lines are dropped while the node is still reported split with the remaining children (silent coverage gap)

verdict CONFIRMED, severity low, category soundness
locations: volunteer.py:831 (SEED_RE / prefix check drops a line and counts it; lines over MAX_LINE are skipped uncounted); split reported whenever >= 1 valid line remains

## Summary
A REMAINING line that fails SEED_RE or the prefix check is counted as bad and dropped, and a line over MAX_LINE is skipped without being counted. If at least one valid line remains, the run is still reported as split with fewer children, so the dropped subtree never becomes a job. Worker path truncation past 250 tokens is one known trigger. The policy turns any worker glitch into a silent coverage gap instead of a retry.

## Verifier (CONFIRMED, low, refuted=False)
The code does what the issue says. Line 771 (`if len(line) > MAX_LINE: continue`) skips a line without counting it. Lines 783-790 count a REMAINING line as bad and drop it when it fails SEED_RE or the prefix check. Lines 826-834 then still return (summary, remaining, ...) when at least one valid line is left. run_window (628-636) marks the node 'split' with only those children. SUMMARY carries no count of REMAINING lines, so the server cannot detect a missing child, and the dropped subtree would never become a job.

The trigger is purely hypothetical, though. The claimed triggers do not exist in the current worker:
- Every variant pushed is in {1,2,3->2,4}: d_var at backsearch.c 2540/2569/2599/2631, walks use V=1 at 1961/2371/2419/2456, and path_push remaps 3 to 2 at 462-466. So path_text cannot print a digit 0.
- REMAINING lines are at most about 2+249*3 = 749 chars (buffer 4*PATH_TOK_MAX+8 = 1008, PATH_TOK_MAX 250 at 227), far below MAX_LINE = 20000.
- The merged claim that path truncation at 250 tokens triggers this is wrong. A truncated path is still a well-formed prefix that extends the seed, so it passes the check. Or it equals the seed, which sets self_remaining and voids the run, or it duplicates another entry. An exact duplicate is harmless because the truncated path replays an ancestor that covers both entries.
- build_seed_path_seed (2040-2075) pushes the seed tokens exactly as parsed, so every descendant's printed path extends the seed text.
- Seeds are canonical: SEED_RE is checked at lease (495), and campaign #1's longest seed was 128 tokens.
- Partial output from a crash or kill comes without SUMMARY, and such runs are already voided.

This is a real but latent weakness on the path that decides soundness. It is worth hardening because the fix is trivial.

*fix notes*: In run_worker, set a flag whenever a line is over MAX_LINE, and whenever a REMAINING line fails SEED_RE or the seed-prefix/length check. Keep counting exact duplicates separately, since they are harmless. If the flag is set and the status is split, log '!!!' and return None so the node stays untouched and is retried. Consider having the worker print a REMAINING count in SUMMARY (e.g. "remaining":N) and having both client and server require len(children) == N for a split. Test with fake_worker by emitting one malformed REMAINING line among valid ones, and assert that no split is reported.
