# M60: 'Status age' counts from the last fetch attempt, so stale campaign data looks fresh

verdict CONFIRMED, severity low, category robustness
locations: volunteer.py:1386 (campaign_status_at set before GET /api/v2/status; failures keep the old campaign_status)

## Summary
campaign_status_at is set before GET /api/v2/status is attempted, and a failed fetch keeps the old campaign_status. The displayed age therefore cycles between 0 and 30 s even when the data is hours old.

## Source report F66 (client-ui)
**'Status age' counts from the last fetch attempt, so stale campaign data looks fresh** at /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py:1386

*summary*: campaign_status_at is set before the GET /api/v2/status is attempted, and failures leave the old campaign_status in place. The displayed age therefore cycles between 0 and 30 s even when the data is hours old.

*failure_scenario*: /api/v2/status returns 5xx, or the network is down, for hours. 'Active volunteers' still shows the last good value, and 'Status age' shows something like '12 s'.

*evidence*: volunteer.py:1385-1387 `... and now - self.campaign_status_at >= 30:\n    self.campaign_status_at = now\n    threading.Thread(target=self.fetch_campaign_status, ...).start()`; :1223-1225 on ApiError only logs; :1335 `"campaign_status_age": round(now - self.campaign_status_at) if self.campaign_status else None`.

*suggested_fix*: Record a separate campaign_status_ok_at timestamp in fetch_campaign_status on success, base the age on it, and mark the tile as stale after about 90 s.

## Verifier (CONFIRMED, low, refuted=False)
volunteer.py:1385-1387 sets self.campaign_status_at = now before starting the fetch thread. fetch_campaign_status (1216-1224) logs the error and returns on ApiError, and does nothing if the response is not a dict, so the old campaign_status stays. state() (1335) reports campaign_status_age = now - campaign_status_at whenever campaign_status is non-null. While the UI is open, the fetch is retried every 30 s, so the age cycles between 0 and 30 s whether or not any fetch succeeded. Actual impact is smaller than it sounds. Only the 'Active volunteers' tile really depends on campaign_status. The UI reads cs.cpu_hours and cs.active_clients (volunteer_ui.html:342), but /api/v2/status returns {campaign, totals, perExit, clients, ...} (jobs.js:929), with the CPU total in totals.cpu_h and no active_clients field. So 'Total CPU hours' always falls back to the sum over heartbeat exits, and 'Active volunteers' falls back to cs.clients.length, the one stale-able value. The exits table and connection dot come from heartbeats and the Api state, so a full network outage already shows 'unreachable'. The misleading case is /api/v2/status failing while heartbeats succeed. Display only.

*fix notes*: In fetch_campaign_status, set self.campaign_status_ok_at = time.time() on success only, and base campaign_status_age on it. Keep campaign_status_at as the attempt throttle. Show the tile as stale when the age is above about 90 s. While there, fix the field names in volunteer_ui.html:342 to cs.totals.cpu_h and cs.totals.clients.
