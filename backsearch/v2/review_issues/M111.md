# M111: Lease, steal and absorption events are not persisted, so scheduling cannot be measured or tuned afterwards

verdict CONFIRMED, severity low, category performance
locations: jobs.js:268 (leased_at overwritten by steals/reclaims; steal counters in memory only; reports keep only the first node's summary)

## Summary
leased_at is overwritten by steals and reclaims, steal counters live only in process memory, and reports store only the first node's summary. Dropped probe seconds, process spawns, local-queue waits and killed runs are recorded nowhere, so the endgame waste found in this review could only be estimated, and campaign #2 tuning has no data.

## Source report F178 (algo-collab)
**Lease, steal and absorption events are not persisted, so scheduling cannot be measured or tuned afterwards** at /Users/george/PathologyRecords/server/lib/jobs.js:268

*summary*: leased_at is overwritten by steals and reclaims, steal counters live only in process memory, and reports store only the first node's summary. Dropped probe seconds, process spawns, local-queue waits and killed runs are recorded nowhere, so the endgame waste in this review could only be estimated.

*failure_scenario*: After the next campaign, the owner cannot tell how many times a job was leased or stolen, how much work was killed through drop, or how much absorption time was wasted. Tuning split_after, lease_ahead or the absorption settings stays guesswork.

*evidence*: jobs.js:268 `stealJob: ... SET client_token = ?, lease_until = ?, leased_at = ? ...`; :40 `const STEAL_STATS = { empty_leases: 0, stolen: 0 };`; :759 `const summaryJson = JSON.stringify({ nodes: nodes.length, summary: s0 });`. In the snapshot, 125 roots have leased_at NULL after reopening, and no steal count can be recovered.

*suggested_fix*: Add lease_count and steal_count columns, or a small append-only lease-events table. Have the client add window totals to each report: window wall time, absorption wall time, dropped-probe seconds, runs, killed runs and local-queue wait.

*expected_gain*: Lets the next campaign's scheduling be tuned from data, including measuring the effect of the fixes above.

## Verifier (CONFIRMED, low, refuted=False)
The code confirms the premise.
- Leases lose their history. jobs.js:268 `stealJob: UPDATE jobs SET client_token = ?, lease_until = ?, leased_at = ? ...`, the heartbeat reclaim at :528 (`q.leaseJob.run(cl.token, t + c.lease_s, t, id)`) and :284 `reopenJob ... leased_at = NULL` all overwrite or clear leased_at. The jobs schema (:184-207) has no lease or steal counter and there is no events table. The snapshot shows the result: 136 root jobs (128 done, 8 split) finished with leased_at NULL, meaning they were reported after a reopen. That is close to the finder's 125. Nothing records how many times any job was leased, stolen, reclaimed or released.
- Steal counters are not persisted. :40 `const STEAL_STATS = { empty_leases: 0, stolen: 0 };` is a module global. It resets on every server restart, and it is shared by all campaigns: :925 copies it into each campaign's status totals, so campaign #2's totals would start with campaign #1's counts until the next restart. The only per-event traces are console.log lines at :521 and :630. They give a client name and a count, never job ids, and whether they survive depends on how the server's logs are kept. A heartbeat `drop` (:534) is not logged at all.
- Reports keep only the first node's summary. :759 `JSON.stringify({ nodes: nodes.length, summary: s0 })`. For accepted trees this costs nothing, because every other node's summary goes into its own jobs row (insNode). For late duplicate reports (outcome 'dup', :770) the child summaries are thrown away. The snapshot has 1411 dup reports covering 38,818 nodes, and only their root time is kept: 31.6 h, about 5.3% of the 602 CPU-h.
- The client sends no scheduling totals. The heartbeat body (volunteer.py:1168) carries only workers, paused, boards, holding and running. Several kinds of work leave no record on the server: a probe that splits is reported as an open node with no summary (volunteer.py:669-673), so its seconds are counted only in local _account; windows killed through `drop` or on stop produce no report (:634-638, :1207-1209); local-queue wait is not sent either. As a result the server's cpu_h, the sum of jobs.elapsed_s = 601.9 h, understates the CPU actually spent, and the published total is a lower bound.
- The claim is slightly overstated. Some waste can be measured today: duplicate-race CPU from the dup reports (about 5%, as a lower bound), and queue delay from done_at - leased_at where leased_at survived (3318 jobs waited more than 600 s beyond their own elapsed time). What cannot be recovered is the lease and steal count per job, the CPU of killed runs, dropped probe seconds, and absorption wall time.

Gain: no CPU is saved directly. The value is that the next campaign's scheduling knobs (split_after, lease_ahead, absorb_probe_s, absorb_total_s, stealing) can be tuned and checked from data rather than guessed. My estimate is that the unmeasured overhead categories together amount to a few percent up to about 10% of CPU. That is worth measuring at 10 clients x 16 workers, and the fix is cheap: a few columns or a small table, and two numeric fields per report or heartbeat.

Exactness risk: none, provided the new data is append-only and never read by the audit, coverage or first-report-wins logic.

I rank this low because it is observability plus one mildly wrong displayed stat (the global STEAL_STATS). It is still worth doing before campaign #2.

*fix notes*: 1) jobs.js schema and migration, in the same style as the existing ALTER TABLEs at :233-236. Add `lease_count INTEGER NOT NULL DEFAULT 0`, `steal_count INTEGER NOT NULL DEFAULT 0` and `first_leased_at INTEGER` to jobs. In leaseJob (:282) and stealJob (:268), set `lease_count = lease_count + 1` (stealJob also `steal_count = steal_count + 1`) and `first_leased_at = COALESCE(first_leased_at, ?)`. Leave reopenJob and resetJob able to clear leased_at, but never first_leased_at or the counters, except for an explicit admin reset.
   Alternative: an append-only `lease_events(id, campaign_id, job_id, client_token, kind TEXT CHECK(kind IN ('lease','steal','reclaim','release','expire','drop')), t)` table indexed on (campaign_id, kind). That is about 200-400k rows per campaign, which is trivial for sqlite. Log `drop` ids too, because they are the only trace of work that was killed.
2) Replace the module-global STEAL_STATS with per-campaign persisted counters: columns on campaigns, or COUNT(*) over lease_events. That also stops campaign #2's status from showing campaign #1's steals.
3) In applyReport (:759), add up the elapsed, states and solver_calls of all nodes into summary_json (e.g. `{nodes, summary: s0, total_elapsed, total_states}`), so that dup reports (outcome 'dup' / 'dup_mismatch') record the full CPU they wasted. Today only the root's elapsed is kept.
4) Client (volunteer.py run_window): attach an optional top-level `telemetry` object to each report: window_wall_s, absorb_wall_s, probe_runs, probe_split_s (seconds of split probes that were discarded), runs, queue_wait_s (time from grant to start). Add running totals to the heartbeat (killed_runs, killed_cpu_s, idle_worker_s), because killed windows never produce a report. On the server, sanitize with a separate whitelist of bounded numbers. sanitizeSummary (:637) drops unknown keys, so these fields must not be put inside the summary. Store them in reports.summary_json or a client_stats column. Never read them in the audit or coverage paths.
5) Tests: extend server/test/v2_gates.test.js:
   (a) lease, then steal, then reclaim: lease_count = 3, steal_count = 1, first_leased_at unchanged;
   (b) a report carrying telemetry is accepted, oversize or non-numeric telemetry is dropped without rejecting the report, and the audit and coverage results are the same with or without telemetry;
   (c) status totals for a new campaign start at 0 steals.
