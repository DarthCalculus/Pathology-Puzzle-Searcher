# M107: Lease order serves the exit with the most open jobs, and the deepest jobs first, so the largest subtrees start last

verdict CONFIRMED, severity medium, category algorithmic
locations: jobs.js:272 (exit chosen by descending open-job count; deepest-first within an exit)

## Summary
Exits are served in descending order of open-job count and, within an exit, deepest first. Job count runs opposite to work (many trivial roots), and depth runs opposite to subtree size. Heavy shallow jobs wait in the pool for hours behind trivial deep ones and end up forming the campaign's tail, the opposite of largest-first scheduling.

## Source report F171 (algo-collab)
**Lease order serves the exit with the most open JOBS and the deepest jobs first, so the largest subtrees start last** at /Users/george/PathologyRecords/server/lib/jobs.js:272

*summary*: Exits are served in descending order of open-job count and, within an exit, deepest first. Job count runs opposite to work (many trivial roots), and depth runs opposite to subtree size. Heavy shallow jobs wait in the pool for hours behind trivial deep ones and end up forming the campaign's tail. This is the opposite of largest-first scheduling.

*failure_scenario*: In campaign #1, exit 7 (972 roots, 29.4 CPU-h) was served from +31 s. Exit 1 (332 CPU-h, 55% of all work) got only 1.4 CPU-h in the first 2 h. Exit 0 (42 roots, 37.5 CPU-h) finished its first job at +19,998 s. On the critical path of the last job (root 211, 142 CPU-h, first leased at +7,734 s), the split children waited in the open pool 4,353 s (depth 5), 11,107 s (depth 7) and 1,097 s, plus about 2,900 s in a client queue. That is about 16,500 s of waiting on the chain that ended the campaign at +40,514 s.

*evidence*: jobs.js:272 `openByExit: ... GROUP BY exit ORDER BY n DESC, exit`; :275 `ORDER BY j.depth DESC, j.created_at, j.id LIMIT ?`. Snapshot critical path (id created/leased/done): 211 0/7734/10107 -> 11087 10107/14460/18005 -> 23889 18005/29112/29356 -> 66833 29356/30453/35275 -> nine 120 s ramp levels up to 167664 at 40514. Root sizes: 1,909 of 2,761 roots total under 1 s; 54 roots hold 552.9 of 597 CPU-h. From +38,400 s only 15.6 CPU-h remained, yet it took 35 min at under 50% useful utilisation.

*suggested_fix*: Order the pool largest expected job first. As a first proxy, use depth ASC with a matching index on (campaign_id, status, depth, created_at, id), across exits or with exits weighted by estimated remaining work. For roots, run --estimate-dump at seeding, store est_s, and lease by est_s DESC. Once absorption is fixed, trivial deep children stay local, so the pool does not fill with filler.

*expected_gain*: Removes most of the 25-35 min endgame tail (about 4% of wall clock) and delivers the dominant exit's result hours earlier, at no CPU cost. A deeper pool mid-campaign should also trigger fewer ramp windows.

**Simulation** (review/m107_sim2.py)
- Setup:
  - It uses the real job tree: 51,894 leased units, where each unit's work is its own elapsed_s plus that of its locally absorbed descendants, plus 0.03 s per node.
  - Children are released when their parent unit finishes.
  - Worker capacity follows the observed client joins, with one global pool and no client queues.
- The current rule at 64 effective workers gives 40,150 s. That matches the real 40,514 s, so the model is well calibrated.

Makespan by lease order, at 64 workers (71 workers in brackets):

| Lease order | Makespan | Change vs current |
|---|---|---|
| Current: exit by count, deepest first | 40,150 s (37,270) | — |
| Global oldest-first (created_at, id) | 38,172 s (35,133) | -33 min, -4.9% |
| Global depth ASC | 38,802 s (35,968) | -22 min |
| Perfect foresight, largest subtree first | 37,750 s (34,666) | -40 min; this is the capacity lower bound |
| Exit by count + depth ASC inside each exit | 42,674 s (40,371) | worse than today |
| Root estimates + deepest first for children | 41,052 s | worse than today |
| Root estimates + oldest-first | ≈ oldest-first | no extra gain |

- Why the "exit by count + depth ASC" variant is worse: breadth-first order grows that exit's open count, so the rule keeps serving the same exit.
- Why root estimates add nothing: under oldest-first all roots are leased in the first minutes anyway, so `--estimate-dump` at seeding is not needed.

**My estimate of the gain**
- Most of it comes from the exit-count rule, not from depth order.
- Roughly 30-40 minutes, or 5-6% of wall clock, on a campaign like #1. The CPU cost is zero, and the dominant exit's result arrives hours earlier.
- A larger pool mid-campaign (at most about 6k open rows instead of about 2.8k) should also mean fewer ramp windows. The model does not capture this.
- Limits of the model: the split tree is fixed from the real run, and client queues and ramp changes are not modelled.

**Exactness:** none at risk. Lease order only changes when work runs. Coverage is decided by reports and by the tree/proof checks.

*fix notes*: 1. In jobs.js lease(), drop openByExit / the per-exit loop and serve work oldest first across all exits:
   - If an exit preference is set, first run `SELECT ... WHERE campaign_id=? AND status='open' AND exit=? AND <dup_of clause> ORDER BY created_at, id LIMIT ?`.
   - Then, for whatever is still needed, run the same query without the exit filter. The rows leased in the first pass are already 'leased', so they drop out.
   - Keep the `.changes` check.
   - Indexes: add (campaign_id, status, created_at, id), and (campaign_id, status, exit, created_at, id) for the preference pass. Remove idx_jobs_open_order (… exit, depth DESC …).
2. Do NOT use depth ASC inside the current exit-by-count rule. In the simulation that gives 42,674 s against 40,150 s today. Root estimates at seeding are not needed either (they gain about nothing over oldest-first).
3. Update v2_gates.test.js:83-121: it asserts deepest-first and should assert oldest-first across exits, with the preference still working. Fix DESIGN.md:118: keep "oldest open first" and drop "preferring the exit with the most open work", or match whatever is chosen.
4. Pair this with a limit on how far ahead clients lease, so that no heavy job waits behind another heavy job in a client's local queue. That queue cost about 4,700 s on the critical chain (11087 and 66833 above). Work stealing only starts when the pool is empty, so it does not help here.
5. Optional: have v2_finish or an admin tool report the critical chain after a campaign (the recursive parent query used here), so the tail can be tracked in the next campaign.
