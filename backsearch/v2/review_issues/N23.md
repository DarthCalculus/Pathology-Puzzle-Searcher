# N23: v2_finish adds the proof first and then ignores the champion's re-solve: it never compares the solved length with maxMoves, and exits 0 when the champion is not stored or contradicts another proof

verdict CONFIRMED, severity medium, category robustness
locations: /Users/george/PathologyRecords/server/tools/v2_finish.js:64

## Summary
This is distinct from the already-known line-61 gate. addProof commits before the champion is solved. The processSubmission result is only logged: sub.moves is never compared with the proof's maxMoves, and a champion that fails to store does not increment 'failed'. No solverGib is passed, so the solve runs at 0.5 GiB even though the tool runs outside the service cgroup. There is no fallback to storing the reported length. Nothing re-reads listProofs(), so a new champion that contradicts an existing proof goes unnoticed.

## Verifier (CONFIRMED, medium, refuted=False)
I checked every claim against the code and all of them hold.

1. The proof is committed before the champion is solved. v2_finish.js:64 `const r = addProof(proof);` runs first. addProof (db.js:654-676) checks for a contradiction and then does an unconditional INSERT. The champion is solved only afterwards, at line 68 `await processSubmission(s.best_level.code, { attribution, source: 'upload', solverSeconds: 30, note: ... })`.

2. The re-solve result is only logged. processSubmission returns `moves: cand.moves` (pipeline.js:135), but line 69 prints only `sub.accepted ? 'accepted id …' : 'not stored: …'`. The solved length is never compared with `best`. A failed store never increments `failed`. `process.exit(failed ? 1 : 0)` then returns 0.

3. No solverGib or fallback is passed. pipeline.js:61 calls solver6 with `gib: solverGib || SOLVER_GIB`, and SOLVER_GIB defaults to 0.5 when the env var is unset. No proposedMoves or claimProven is passed either, so when both engines give up, pipeline.js:113-117 returns `needs_solution`.

4. Nothing reports the proof's status after the champion is submitted. r.proof comes from listProofs(), but it is computed before the submission and never printed. Nothing compares the new champion with overlapping existing proofs.

Consequences the finder did not mention make this more reachable than it looks. The line-61 gate works only when `verified_moves` is set, and several ordinary paths leave it null:
- verifyLater runs only for a strict new per-exit best (jobs.js:799 `bestNode.best > prevBest`). bestOfExit, however, picks `ORDER BY j.best DESC, j.id` (jobs.js:301). Say job B (id 9000) reports 149 first and gets verified. Job A (a lower-id root, id 5000) reports a 149 tie later and is never verified. exitSummary then returns A with verified_moves NULL. v2_finish prints "(not re-solved yet)", skips the gate, and the post-add solve is the only independent check left, and its result is ignored. Campaign #1 did not hit this (the snapshot shows the champion rows were verified: 60818, 27050, 9182, 17462, 3908, 621), but nothing prevents it.
- verifyLater is fire-and-forget (v2routes.js:62-72) and nothing retries it. server.js:246 retries only v1 chunks, so a server restart during a verification leaves the value NULL for good.
- When the champion cannot be solved at 30 s / SOLVER_GIB, verifyLater only logs a warning.

If the worker's reported length is ever wrong, the proof goes out with the wrong maxMoves. The site shows it only as 'unwitnessed', and the tool exits 0.

Other points:
- Because the proof is added first and addProof has no idempotency check, any throw inside processSubmission (solve() rejects on a missing or failed solver binary, solver.js:61/66) exits 1 after that exit's proof is already committed, and the remaining exits are never processed. Re-running with --publish then inserts duplicate proof rows for exits that were already done.
- Not every non-storage is a failure. 'duplicate' or 'tie' against an existing verified level of the same length is benign, so a fix should key on listProofs() status == 'ok' (plus sub.moves === best), not on sub.accepted.
- The suggested proposedMoves/claimProven fallback would not make the proof witnessed. proofChampions counts only statuses ['verified'], so the fallback just shows the level on the site.
- Scenario (c) is real: a <=3-hole champion from a <=4-hole campaign is stored silently and only flagged in the site's annotateChampions. It can only happen if campaign #1 was not exhaustive, and checking only the champion would miss a <=3-hole level that is longer than 149 but not the overall best.

Rating: medium, because this is a missing safety net. It publishes a wrong best only together with a worker length bug or an engine disagreement. Otherwise it produces an unwitnessed proof and a misleading exit code.

Coverage: I confirmed that nothing else in v2 submits champions to records.db. The only path is v2_finish; the server.js processSubmission call belongs to the public upload route. The local data/records.db has only the older proofs 1-7 (<=4 blocks and <=2 holes) and no campaign #1 proofs, so I could not check campaign #1's witness state locally.

*fix notes*: Fixes for v2_finish.js:
- Change the order to solve, check, add. First run measureLevel(code, { seconds: 300-600, gib: 1.5-2 }). The deploy host has 3.8 GB, no swap and a 2G service cgroup, so 4 GiB is too much there. Refuse unless m.ok && m.moves === best. Also refuse when `s.best_level.best !== best`.
- Only then call addProof, then processSubmission with the same solverGib and solverSeconds.
- Afterwards re-read listProofs(). Require the new proof's status === 'ok' and treat 'unwitnessed' or 'contradicted' as failed++. Print the status of every existing proof whose class overlaps the new one, and fail on any 'contradicted'. Also add a proof-vs-proof monotonicity check: a proof for a superset class must have maxMoves >= that of any subset-class proof with the same size and exit.
- Make it idempotent: skip addProof when an identical (rows, cols, exit, caps, maxMoves) proof already exists, so a re-run after a partial failure does not duplicate rows. Wrap each exit in a try/catch so one exit's solver failure does not abort the rest.

Server side:
- Make bestOfExit prefer a verified row (ORDER BY best DESC, verified_moves IS NULL, id), or verify ties as well.
- Add a startup and periodic sweep that re-verifies per-exit best rows whose verified_moves is NULL.

Test to add to server/test: a v2_finish run against a jobs.db whose champion row has verified_moves NULL and whose level solves to best-2 must exit 1 and must not insert a proof.
