# M26: The local control panel has no Host/Origin check: a DNS-rebinding page can read /state and drive /workers, /pause and /stop

verdict CONFIRMED, severity medium, category security
locations: volunteer.py:1477-1478 (POST routes require only X-Volunteer: 1; Host is never validated); test_client.sh test c (checks only the header)

## Summary
The only protection on the panel's routes is the custom X-Volunteer header, which a foreign origin cannot send without a CORS preflight. After DNS rebinding, though, a page at attacker.tld:8765 that resolves to 127.0.0.1 is same-origin with the panel. It can set the header, read GET /state, and POST any control, including changing the worker count, pausing or stopping. Nothing validates the Host or Origin header, and the test only checks the header.

## Source report F62 (client-ui)
**Control panel has no Host/Origin check: a DNS-rebinding page can read /state and drive /workers, /stop, /pause** at /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py:1478

*summary*: The only protection is the X-Volunteer header. After DNS rebinding, an attacker's page is same-origin with the panel (attacker.tld:8765 resolves to 127.0.0.1), so it can set that header, read /state, and POST any control. Nothing validates the Host or Origin header.

*failure_scenario*: A volunteer with the client running (default port 8765) leaves a malicious page open for about a minute. The page rebinds its hostname to 127.0.0.1 and runs fetch('/state'), which returns the name, log lines, the absolute worker path (revealing the username) and the server URL. It then sends fetch('/workers',{method:'POST',headers:{'X-Volunteer':'1'},body:'{"workers":32}'}). set_workers clamps to campaign workers_max=32 (64 if absent), so a 4-core laptop runs 32 CPU-bound workers of about 200 MB each and becomes unusable. The page can instead loop /stop or /pause to sabotage the contribution. Chrome's Local Network Access checks only partly mitigate this; Safari and Firefox do not.

*evidence*: volunteer.py:1461-1471 do_GET serves `/state` with no Host check. :1476-1479 `# Same-origin pages can set this header; a foreign page cannot without CORS ... if self.headers.get("X-Volunteer") != "1": return self._send(403, ...)`. :1502-1504 `if path == "/workers": n = vol.set_workers(body.get("workers"))`. :1120-1125 clamps to workers_max. Snapshot campaigns.workers_max = 32.

*suggested_fix*: Answer 403 unless Host is exactly 127.0.0.1:PORT or localhost:PORT. For POST, also require the Origin header, when present, to be http://127.0.0.1:PORT or http://localhost:PORT. Optionally inject a random per-run secret into the served HTML and require it as the X-Volunteer value. Add `X-Frame-Options: DENY` so the unconfirmed Pause/Resume buttons cannot be clickjacked.

## Source report F191 (robustness-ops)
**Local control panel accepts DNS-rebound requests: any website can change workers, pause or stop** at /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py:1478

*summary*: The only protection on the panel's control POSTs is a custom X-Volunteer header, and the Host header is never checked. A page served from an attacker domain that re-resolves to 127.0.0.1 is same-origin with the panel, so it can set the header and read /state.

The page sends `POST /workers {"workers":32}` with X-Volunteer: 1. The client clamps to workers_max (32) and starts 32 searches at about 200 MB each on a 4-core 8 GB laptop, which swaps it into the ground. *expected_gain*: A malicious website cannot drive a volunteer's machine.

## Verifier (CONFIRMED, medium, refuted=False)
I read the handler in /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py (start_ui, lines 1439-1520), and the issue holds.

- **No Host or Origin check anywhere.** do_GET (1461-1472) serves `/` and `/state` without looking at any header. do_POST (1474-1510) checks only `if self.headers.get("X-Volunteer") != "1": return self._send(403, ...)`. `_send` sets no X-Frame-Options, and no code reads `Host` or `Origin`. The server binds ("127.0.0.1", port), default 8765 (main line 1531). Binding to loopback does not stop DNS rebinding: after rebinding, the browser treats http://attacker.tld:8765 as its own origin, so it sends the custom header without a preflight and can read the responses. The only thing that would reveal the attack is the Host header, and nothing checks it.
- **Every control is reachable.** The rebinding page can call:
  - `/workers`: set_workers (1115-1133) clamps only to campaign workers_max (64 if absent; 32 in the snapshot), then calls _reconcile_slots at once.
  - `/stop`: request_stop.
  - `/pause` and `/resume`.
  - `/exit`.
  - `/close`: arms ui_close_at, and 1399-1404 stops the client if no /state poll comes within 3 s.
- **What /state (1291-1345) exposes:** the name, server URL, stats, boards and the last 25 log lines. The log ring can hold the startup line "worker <argv> hash ..." with the worker path, and "reusing registration ... (token XXXXXX...)", which shows the first 6 characters of the token. That is not enough to impersonate the client, so the token itself is not leaked.
- **Test gap confirmed.** test_client.sh:162 checks only that a POST without the header gets 403, never a foreign Host.

Refutation attempts that failed:
- The comment's claim that a foreign page needs a CORS preflight is true for cross-origin requests, but rebinding makes the request same-origin.
- Chrome's Private or Local Network Access work only partly mitigates this, and Safari and Firefox are not covered.

Why medium and not high:
- The worst impact is temporary: oversubscribing a laptop's CPU and RAM up to workers_max (32 x ~200 MB, which can swap an 8 GB machine), or silently pausing or stopping a volunteer's contribution, plus a minor information leak.
- There is no code execution and no file read or write. The attack needs someone to target a volunteer who has the client running on a known port and keeps a malicious page open long enough for rebinding.
- It does not endanger the published results or the server's data. Stopped jobs go through the normal SUMMARY or lease path.

It still counts as harm to a volunteer machine that a website can trigger, and the fix is trivial, so it should be fixed before the next campaign.

*fix notes*: In volunteer.py Handler, add a helper that runs first in do_GET and do_POST. It should return 403 unless `self.headers.get('Host')` is exactly one of `127.0.0.1:%d` or `localhost:%d` for args.port. Also accept `[::1]:%d` only if you ever bind IPv6.

On POST, also reject a request whose `Origin` header is present and is not `http://127.0.0.1:PORT` or `http://localhost:PORT`. Keep the X-Volunteer check.

For defence in depth:
- Generate a random per-run secret with `secrets.token_hex(16)` and inject it into the served HTML, for example by replacing a placeholder in volunteer_ui.html. Require it as the X-Volunteer value on POSTs, and optionally as a query parameter or header on /state.
- Add `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'` in `_send`, so the Pause, Resume and Stop buttons cannot be clickjacked.
- Consider dropping the partial token (`self.token[:6]`) from the log line at 337, since the log ring is served by /state.

Tests: extend test_client.sh test c so that GET /state and POST /workers with `-H 'Host: evil.example:PORT'` return 403, and a POST with `Origin: http://evil.example:PORT` returns 403. Keep the existing header-missing check. Also add a case confirming that the real UI still works with Host 127.0.0.1:PORT and with localhost:PORT, because webbrowser.open uses 127.0.0.1 but users may type localhost.
