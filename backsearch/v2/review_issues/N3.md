# N3: The end-of-run champion verify can loop forever when the big table fills (the same bug as the known 1751 hang, at another site), and the client has no watchdog

verdict CONFIRMED, severity low, category robustness
locations: /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:1262

## Summary
Every worker run ends with sokoban_solve() on its best level. That is solve_push64: plain Dijkstra with no cutoff and no reference-table pruning. It has the same 'overflow -> use_big -> goto retry' loop as the known cutoff hang at 1751, so if the big table's 85% limit (14.26M states) is reached, it restarts forever. The verify explores a superset of what the champion's own (A*, parent-table-assisted) shortcut check explored, so it is the most exposed place for this hang on larger levels.

## Source report F202 (r2-next-campaign-generalization)
**The end-of-run champion verify can loop forever when the big table fills (the same bug as the known 1751 hang, at another site), and the client has no watchdog** at /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:1262

*summary*: Every worker run ends with sokoban_solve() on its best level. That is solve_push64: plain Dijkstra with no cutoff and no reference-table pruning. It has the same 'overflow -> use_big -> goto retry' loop as the known cutoff hang at 1751, so if the big table's 85% limit (14.26M states) is reached, it restarts forever. The verify explores a superset of what the champion's own (A*, parent-table-assisted) shortcut check explored, so it is the most exposed place for this hang on larger levels.

*failure_scenario*: The trigger is a job in a 5x5 <=4-hole or 6x6 campaign whose best level's forward space below its length exceeds 14.26M states. The champion's cutoff check passed thanks to A* and the parent reference table, then the run splits. The worker prints REMAINING, enters the final verify and loops forever in retry: select big, clear, rerun, overflow. SUMMARY never appears. The client blocks in proc.wait() with no timeout outside Stop, so the slot is stuck forever while heartbeats list the job as running and keep renewing its lease. The window's REMAINING is never reported, the exit's audit never becomes clean, and the campaign stalls with no error. On Stop, the client SIGKILLs after 90 s and the whole window is lost. A fix applied only at line 1751 (the known finding) leaves this path in place.

*evidence*: sokoban_bfs.c:1262-1265 `} else if (hs->overflow) { /* Small table saturated: rerun this solve on the big one. */ use_big = 1; goto retry; }` inside solve_push64; 1020 `hs->ht_limit = (uint32_t)(HTP_SIZE * 0.85);`; 1054 `if (hs->ht_count >= hs->ht_limit) { hs->overflow = 1; return -1; }`; 1250 `ne.prio = nc; ne.g = nc;` (no heuristic, no cutoff; ref_prunes_at appears only in the cutoff at 1733); backsearch.c:5781-5786 `if (g_best_depth > 0) { ... verify = sokoban_solve(&pz, NULL, NULL); }` runs after every split/stop/exhausted run, before LEVEL/SUMMARY; volunteer.py:808 `rc = proc.wait()` (the only kill timer is STOP_GRACE_S after Stop, line 1393).

*suggested_fix*: Fix both retry sites together: when the big table overflows, return -2 (unknown) instead of retrying. Bound the final verify: use the A* cutoff solver with max_cost = depth, which confirms the length cheaply; skip it when the run was split or stopped; or give it a state/time cap. In the client, add a per-run watchdog (split_after + grace, e.g. 2x) that SIGINTs and then SIGKILLs a silent worker and reports the node open.

## Verifier (CONFIRMED, low, refuted=False)
The code defect is real. The claim that it matters for the next campaign is not.

Mechanism (confirmed by reading the code):
- sokoban_bfs.c:1101-1106: `int use_big = 0; retry: hsp64_select(hs, use_big); hsp64_clear(hs);`
- 1262-1265: `} else if (hs->overflow) { use_big = 1; goto retry; }`
- The big table's limit is 1020 `hs->ht_limit = (uint32_t)(HTP_SIZE * 0.85);`, i.e. 14,260,633 of 16,777,216 slots. Line 1054 sets overflow when the insert count reaches it.
- Once use_big is already 1, the retry re-selects the big table, clears it (generation bump) and re-runs the same deterministic Dijkstra, which overflows again. That is an infinite, CPU-bound loop.
- Nothing inside solve_push64 breaks it. The only exits are the pending-queue cap (1245 `pq_count >= HP64_SIZE` with HP64_SIZE = 1<<20, returns -2) and g_heap_cap. backsearch never calls sokoban_set_heap_cap, so g_heap_cap stays 0.
- The signal handler only sets a flag (backsearch.c:496), and the solver never checks it.
- The cutoff solver has the identical retry at 1751-1754. Those two lines are the only `goto retry` sites. solve_push128 has no retry and returns -3 on probe failure, so the hang is limited to the 64-bit path (5x5 with nb <= 11, 6x6 with nb <= 9).
- The final verify is at backsearch.c:5781-5786: `verify = sokoban_solve(&pz, NULL, NULL)`, i.e. plain Dijkstra with no cutoff, no A* and no reference table. It runs after REMAINING has been printed and flushed (4328-4330) and before LEVEL/SUMMARY (5843-5850).

Client and server side (confirmed):
- volunteer.py:765 blocks in `for line in proc.stdout`, then `proc.wait()` at 808. There is no per-run timeout. The only kill timer is STOP_GRACE_S = 90 s after SIGINT (1393-1397).
- The heartbeat sends running jobs in `holding`, and jobs.js:516-518 pushes each lease out to now + lease_s on every heartbeat, with no cap on run age.
- One consequence the report missed: at the campaign tail, work stealing (jobs.js:607-627) lets an idle client take a running job. The old holder then SIGKILLs its worker via `drop`, and the new holder re-runs the same seed and would hang again. The hang would move from client to client instead of ever resolving.
- The verify value is consumed by nobody. The client does not read it, sanitizeSummary does not keep it, and 0 of the 54,409 snapshot reports contain it. It is pure diagnostic overhead, which makes removing or bounding it free.

Reachability (why severity drops from high to low):
- To hang, a window champion's Dijkstra must insert at least 14.26M distinct push-states while fewer than 1,048,576 entries (stale ones included) are pending. Otherwise the pending cap returns -2 first.
- I counted the reachable forward push-state space of the campaign #1 record level (exit 1, 149 moves, code 53005/0BFB1/0I400/0B8G0/00000) with a small Python BFS in scratchpad/review/fwd_count.py. The key is (exact player cell after push, typed block set, unfilled holes), matching the Zobrist key. The whole space is 367 states: 4-5 orders of magnitude below the limit.
- CHANGES_2026-09-18.md says typical 5x5 checks pop about 1,200 states.
- Campaign #1 ran 166,733 jobs with no hung job; the maximum elapsed was 1797 s, under the split limit.
- A deliberately open synthetic 5x5 level (5 omni blocks, 4 holes) reached more than 90k push-states. But a window champion must have a long optimal solution, and Dijkstra stops at that length.
- So on 5x5 with <=3 or <=4 holes, or grids of similar size (4x6, 5x6), the trigger is not realistic.
- It becomes a real stall risk only on 6x6-or-larger campaigns in the 64-bit path. The HTP_SIZE comment (sokoban_bfs.c:932-937) records 6x6 boards saturating an 8M table.

On the report's details: the relative-exposure argument is correct. The verify explores a superset of the champion's A*/reference-pruned cutoff check (all states with g < L, plus their successors), and a fix applied only at 1751 leaves this site in place. If 1751 is changed to return -2, shortcut_check prunes those states (backsearch.c:1693, 'caller prunes conservatively'), so the verify only sees champions whose cutoff check completed. The report's claim that the client blocks in proc.wait is slightly off: it blocks in the stdout iterator. The effect is the same.

Rating: low for the next campaign as described. The defect is latent, and the consequence (silent permanent stall of one exit, one core spinning on a volunteer machine) would rate high on a 6x6+ grid.

*fix notes*: 1) sokoban_bfs.c:1262-1265 and 1751-1754: make the retry one-shot. Use `else if (hs->overflow) { if (use_big) { /* big table full */ return -5; } use_big = 1; goto retry; }` with a new, distinct return code. Do not reuse -2: shortcut_check treats -2 as 'prune conservatively', which would silently drop a potentially valid level in an exact campaign. In backsearch, count -5 results and emit them in SUMMARY (e.g. "table_full":N). Have the server refuse to treat a job with table_full > 0 as exhaustive evidence, and flag it loudly.
2) backsearch.c:5781-5786: the verify value is unused by the client and the server. Either skip it in campaign mode (--seed-path / --split-after given), or bound it with sokoban_solve_cutoff(&pz, NULL, NULL, g_best_depth), which uses A* and is cheap and only confirms that a solution of length <= depth exists. Or cap it by states and report -5.
3) volunteer.py: add a per-run watchdog. If no STATUS line has arrived for max(3*status_every, 600) s, or the run has lasted longer than split_after + max(600, split_after), send SIGINT, then SIGKILL after STOP_GRACE_S. Log '!!! worker N hung', leave the node untouched and count it in stats. The server could also record runs-without-summary per job and stop re-issuing a job after N consecutive failures, so a deterministic hang cannot move between clients through work stealing.
4) Test: compile-time-overridable HTP_SIZE plus a tiny C or harness test, as in repro_plan, that both solvers return instead of looping when the big table fills. Add a fake_worker mode that hangs after REMAINING, to exercise the client watchdog in test_client.sh.
