## Source report F151 (tests-gaps)
**Gate-test gaps: a comment claims coverage it never asserts, probe levels on open nodes are untested, and server.js limits are bypassed** at /Users/george/PathologyRecords/server/test/v2_gates.test.js:212

*summary*: Gaps in the gate tests:
- The comment 'coverage: J is covered once its open grandchild finishes' is never asserted; there is no audit check after the grandchild's done report.
- No test sends an open node with a {depth, code} level, which the client sends for probes (levelBest taken from level.depth, and the 'needs its depth' error path).

- Registering with a token from a closed campaign is untested.

*failure_scenario*: A regression that fails to mark a split node covered after its last child finishes, or that drops a probe's level (the per-exit best could then come only from a later re-run), passes the gates. So does an XFF-parsing change that uncaps the per-IP limit.

*evidence*: v2_gates.test.js:212-216 `const a1 = jobs.audit(...); assert.ok(!a1.clean); const done = ok(jobs.report(...)); assert.equal(done.status, 'done'); ...` (no audit afterwards); jobs.js:713 `levelBest = summary ? summary.best : (typeof n.level === 'object' && Number.isInteger(n.level.depth) ? n.level.depth : null);`; v2_gates.test.js:399 `ipLimit: () => 0`.

*suggested_fix*: After the grandchild report, assert that J's root is covered (fresh audit on a single-root exit). Add an open-node-with-level case and assert the per-exit best. Add a server.js-level test of clientIP and takeToken.

*expected_gain*: Closes cheap holes in the one suite that runs routinely.

## Verifier (CONFIRMED, low, refuted=False)
I checked each sub-claim. Three of the four hold as stated. The first one is real but matters less than claimed.
(1) v2_gates.test.js:212 has the comment '// coverage: J is covered once its open grandchild finishes'. Lines 213-216 audit only BEFORE the grandchild's report (`assert.ok(!a1.clean)`). After the done report they assert only `done.status === 'done'` and `new_best === null`. No audit follows. However, coverage is not a flag the report sets: auditExit (jobs.js:942-1013) recomputes it from the tree. The hand-built audit test covers this exact shape. At v2_gates.test.js:357-381 a split root r2 has a split child r2b and an open grandchild r2b1. After r2b1 becomes done, line 381 asserts `uncovered_roots == [r3]`, so r2 is covered. The tree report's parent_id wiring for grandchildren is asserted at lines 205-207. So the claimed failure scenario (a regression that 'fails to mark a split node covered' passes the gates) would mostly be caught. What remains is a dangling comment plus a missing end-to-end check. That check cannot be `clean`: exit 12 still has five other roots held by Alice. It would have to be 'J.id not in uncovered_roots'.
(2) This gap is confirmed and matters most. The client does send open nodes with levels. volunteer.py:660-665: 'a probe that splits is reported open ... the server accepts a level on an open node'. _clean_node at :708-709 keeps `level` on open nodes, and levels are `{depth, code}` dicts (:798, :863). On the server, jobs.js:713 takes `levelBest` from `n.level.depth` when there is no summary. jobs.js:714 has the error path 'a level on a node without a summary needs its depth'. jobs.js:791 inserts the open child with `best = n.levelBest`, and jobs.js:795 lets it become the new per-exit best. The best-level queries at jobs.js:302 and :1028 deliberately include open rows with a level. None of this is exercised: no node with `status: 'open'` in the test file carries a `level`. The only `{depth, code}` level in the tests is on a flat report (line 178). A regression here would 400 every client report that contains a probe level (the job goes back to open and is re-run). It could also silently drop the level.
(3) Confirmed. Both HTTP tests (lines 399 and 476) inject `clientIP: () => '127.0.0.1', ipLimit: () => 0`. Nothing in test/ loads server.js, so its clientIP (TRUST_PROXY, last XFF element, server.js:40-55) and takeToken buckets (server.js:57+) have no tests.
(4) Confirmed. No test covers 410 or campaign_closed (grep finds nothing). No test calls register with a token from a closed campaign: the `cl.campaign_id !== c.id` branch at jobs.js:457 is never reached, since line 74 reuses a token from the same campaign. requireClient's 410 at jobs.js:338 is also untested. Campaign #1 is still 'open' in the snapshot, so the next campaign switch will take this path for real.
All of these are test gaps with no production defect in themselves, so low severity stands.

(b) After the grandchild report at line 215, assert that J.id is not in jobs.audit(12, camp.id, {fresh:true}).uncovered_roots, or delete the comment. Add a client-side test that a 410 makes the client re-register instead of looping.
