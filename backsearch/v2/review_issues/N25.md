# N25: A campaign or proof on a non-canonical grid orientation (for example '6x4') is accepted, but its proof can never match any stored level

verdict CONFIRMED, severity low, category robustness
locations: /Users/george/PathologyRecords/server/lib/db.js:655

## Summary
addProof validates only integer-ness, and jobs.createCampaign accepts any RxC with exits that are canonical for that orientation. Stored levels are always canonical (rows <= cols), searchLevels filters rows <= R AND cols <= C, achievableExits(4,6,e,6,4) returns null, and parseFilters rejects rows > cols. A '6x4' proof is therefore unwitnessed forever, never covers a search, and uses exit numbers of the transposed board.

## Verifier (CONFIRMED, low, refuted=False)
I traced the whole path for a grid string with R > C and the gap is real at every stage.

1. Input validation. jobs.js parseGrid (93-99) only checks the regex and `rows*cols <= MAX_AREA`. createCampaign (346-352) then checks exits against `canonicalExitCells(g.rows, g.cols).cells` for that orientation. For '6x4' that is [0,1,4,5,8,9]; for '4x6' it is [0,1,2,6,7,8]. I checked both with node -e on lib/level.js. The worker accepts any RxC (backsearch.c:4929-4931 parse_grid), and build_canonical_exits (backsearch.c:401-414) gives the same row-major D2 representatives. So the layer file, the campaign and the roots all agree on 6x4 numbering. v2_seed --dry only prints the plan and never calls createCampaign, so it validates nothing.

2. During the campaign. validateLevel (jobs.js:124-137) compares the parsed level against the campaign grid as given, 6x4, and does not canonicalize. Everything runs and is accepted.

3. Publish. v2_finish.js:29,50 passes `rows: g.rows, cols: g.cols` (6, 4) and the 6x4 exit numbers straight to addProof. addProof (db.js:653-660) only checks that the values are integers. The champion goes through processSubmission and is stored in canonical form (level.js canonicalize skips transforms with `g.length > g[0].length`), so it is saved as 4x6.

4. Display.
- searchLevels (db.js:268-271) filters `rows <= 6 AND cols <= 4`, which excludes every stored 4x6 level. In any case `achievableExits(4,6,0,6,4)` returns null (level.js:168; checked).
- proofChampions therefore marks the proof 'unwitnessed'.
- proofCovers (db.js:proofCovers) needs `p.rows === f.rows` exactly, and parseFilters (server.js:108) rejects rows > cols, so no search can ever show or cover this proof.
- derivedProofs builds a '6x4 any exit' proof that has the same problem.

Two corrections to the original report:
- (a) "Can never match any stored level" is a little too strong. Smaller padded levels such as a 4x4 level still match (achievableExits(4,4,0,6,4) = {0,4,8}), but the full-size champion never does.
- (b) There is an extra consequence the report missed. addProof's contradiction guard (db.js:661-665) runs the same broken searchLevels, so it never sees stored full-size 4x6 levels. A 6x4 proof whose maximum is lower than an already-stored verified 4x6 record would therefore not be refused.

Why low rather than medium:
- It only happens if the owner writes the grid in the non-canonical orientation (the docs and memory say "4x6").
- Campaign #1 was 5x5, which is square, so it is not affected.
- The search itself is still exact, because the D2 orbits of 6x4 map one-to-one onto those of 4x6 by transposition. Only the labels in the proofs table are wrong.
- Recovery is a manual update of about 6 proof rows (swap rows/cols and remap each exit through the transpose). No job data is lost and no level is missed or counted wrongly.

It is a cheap validation gap worth closing before a non-square campaign.

*fix notes*: 1. In jobs.js createCampaign, after parseGrid, reject `g.rows > g.cols` with a message such as "grid must be written rows<=cols (use 4x6, not 6x4) so exit numbers match the site's canonical numbering". Also reject it in parseGrid's campaign use, or in a new validateCampaignPlan(p) helper.
2. Have v2_seed.js --dry call that same validator. It currently only prints the JSON. It should also print the canonical exits for the grid, so a wrong exit list or orientation shows up before seeding.
3. In db.js addProof:
   - Require `p.rows <= p.cols`.
   - Require `p.rows*p.cols <= MAX_AREA`.
   - When exitCell != null, require `canonicalExitCells(p.rows, p.cols).cells.includes(p.exitCell)`.
   This also protects the contradiction guard, which silently misses full-size levels for a transposed class.
4. Add a gate test in server/test/v2_gates.test.js: createCampaign({grid:'6x4', exits:[0,1,4,5,8,9], ...}) throws; addProof({rows:6, cols:4, ...}) returns ok:false; addProof({rows:4, cols:6, exitCell:3, ...}) (a non-canonical exit) returns ok:false.
5. Optional: if the owner ever wants to run workers in R>C orientation, v2_finish could instead map each exit through the transpose into canonical numbering before calling addProof. Rejecting such grids is simpler and enough.
