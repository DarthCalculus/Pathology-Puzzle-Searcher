# M2: PATH_TOK_MAX=250 truncates paths silently: nodes deeper than 250 moves print wrong REMAINING/CURSOR paths, so subtrees are lost or wrong

verdict CONFIRMED, severity high, category soundness
locations: backsearch.c:462-463 (path_push, BState.path, uint8_t plen); ignored return values in seed replay, try_successor_x, bulk_generate, apply_seed_step; parse_seed_path (accepts 1024 tokens); print_remaining; volunteer.py REMAINING prefix/duplicate check (drops lines, still reports split); jobs.js seed limit of 1024 (stale comment cites g_seed_path[1024])

## Summary
A node's path holds one token per backward move, capped at 250. path_push returns 0 when the path is full and every caller ignores it, so deeper nodes keep a 250-token prefix. REMAINING then names an ancestor or, when the cut falls inside a committed-walk run, a bulk sibling, so a re-run job searches a different subtree. The client drops non-extending or duplicate lines as 'bad' but still reports the split, and the server accepts seeds up to 1024 tokens. Subtrees are therefore lost or searched twice, and deep seeds can livelock splits. This cannot happen on 5x5 (record 149, deepest seed 128 tokens), but any grid whose search passes 250 moves breaks the split protocol.

## Verifier (CONFIRMED, high, refuted=False)
The code does what the merged report says. I found no guard anywhere that stops it.

1. The path is capped at 250 tokens and nothing checks the cap.
- backsearch.c:227 `#define PATH_TOK_MAX 250`.
- BState has `uint8_t plen` and `uint8_t path[PATH_TOK_MAX]` (456-460).
- path_push at 462-466: `if (s->plen >= PATH_TOK_MAX) return 0;`.
- Every call ignores the return value: apply_seed_step 1961/1987/2005/2030, try_successor_x 2250 (`if (g_emit_D >= 0) path_push(&ns, g_emit_D, g_emit_V);`), and bulk_generate 2371 (`for (int k = cn - 1; k >= 0; k--) path_push(&ns, chain[k] ^ 2, 1);`).
- Depth is a separate int32 (433). g_max_depth defaults to INT_MAX (150). No code compares depth or plen with PATH_TOK_MAX. The grep shows every use of PATH_TOK_MAX: buffer sizes, path_parse for --from/--until, and one message.
- So a node deeper than 250 is still queued, and its path is its first 250 tokens.
- print_remaining (4326-4330) and print_cursor (4312-4320) print s->path/plen exactly as stored.
- parse_seed_path accepts up to `sizeof(g_seed_path)/sizeof(*g_seed_path)` = 1024 tokens (1918). jobs.js:32 sets `SEED_MAX_TOKENS = 1024; // the worker's g_seed_path[1024]`. That comment is literally true, but the real cap is 250.
- There is no memory-safety problem. uint8_t plen never passes 250. The path_text buffers are 4*250+8 bytes, and 250 tokens need at most 749 chars.

2. What happens when a split fires with nodes deeper than 250 on the stack. I traced this through the client code.
- (a) If token 250 is the end of an edge, the truncated line names that node's depth-250 ancestor A. Re-running A covers everything below it, including parts already explored. The result is duplicate work, not lost work. The client folds identical strings together (`p not in remaining`, volunteer.py:787); that is harmless because the strings name the same subtree.
- (b) If token 250 falls inside a committed-walk (bulk) chain, build_seed_path_seed (2050-2075) treats the run as one bulk edge. It builds the intermediate cell M with bulk_walk=1, which the comment at 2062-2064 calls "bulk siblings, not ancestors". A bulk child does not walk back again over committed cells, so the real pending node c at the end of the chain is not below M. c's whole subtree, which is exactly where the deepest levels are, is never searched. The parent is still reported as split with M as its child, and nothing in the audit flags it. That is a silent exactness loss, and by the rubric's own definition it is critical impact.
- (c) Any job whose seed is exactly 250 tokens prints its own seed as the cursor and as every child path. volunteer.py:784-785 sets self_remaining, and 821-826 throws the run away. Such a node can only finish by exhausting within split_after; otherwise it is re-run forever, a livelock. Seeds longer than 250 tokens (the reports' case 3) cannot come from the worker, since truncated paths never exceed 250. They would only come from hand-seeding, where every line fails the prefix test (786) and 827-830 returns None, which is also a livelock.

3. A correction to the merged summary: the client dropping non-extending lines is not a second loss path in this scenario. If the seed has 250 tokens or fewer, a truncated child path still starts with the seed, so it either passes the prefix test or equals the seed. The loss comes only from (b). Still, the client logging a warning and reporting a split with dropped children (831-834) is a fragile design in general.

4. Why this cannot happen on 5x5.
- try_successor_x only queues states that pass shortcut_check (2205-2211). A queued state's forward optimum is therefore about its depth, so DFS depth is bounded by the longest optimal solution on the board, about 150 for 5x5 with at most 3 holes.
- In the snapshot, max(jobs.depth) is 128, max seed tokens is 128, and max(best) is 149.
- So campaign #1 was not affected, and a 5x5 or 4x6 (record 160) follow-up would not be either, even with 4 holes. It becomes reachable only on a grid whose search passes 250 moves (plausibly 5x6 or larger).
- That is why I rate it high (latent, with critical impact if the next grid is deep) rather than critical.

5. Two related points for depth above 250.
- The multi-solve's uint8 labels (sokoban_bfs.c:1904 `if (maxcut >= MS_INF - 1) return -2;`) fall back correctly to per-start solves (backsearch.c:2413-2416). That costs speed only.
- backsearch.c:2402 `refk[j] = (uint8_t)(kk > 250 ? 250 : kk);` clamps the reference-table offset. ref_prunes_gp (sokoban_bfs.c:1459-1460) prunes when `nc > gp + k - 2`, so a clamped k prunes the forward search harder than it should. That could hide a shortcut and wrongly accept a state. It needs ptab_k > 250, so it only matters on deep grids. I have not verified it further, but it belongs in the same pre-campaign fix.

*fix notes*: 1. Make overflow fatal in the worker. path_push returning 0 should print an error to stderr and call exit with a nonzero code, before any REMAINING, CURSOR or SUMMARY line is printed. The client already treats a run with no SUMMARY as no result and leaves the node open (volunteer.py:814-820). Also check this once at replay time in build_seed_path_seed.
2. Make the limits match. Cap parse_seed_path at PATH_TOK_MAX, not at the 1024 size of g_seed_path. Set jobs.js SEED_MAX_TOKENS to the worker's real cap and fix the comment at jobs.js:32. Document the cap in DESIGN.md.
3. Before any campaign on a grid that may go past 250 moves, widen plen to uint16_t and make PATH_TOK_MAX a -D knob. Size it per grid, remembering that BState sits in g_queue (realloc at 1181), so a bigger path array raises memory use for every queued state. Keep the path_text buffers and the pb[1100] at 4282 in step. Remove or widen the refk uint8 clamp at 2402, or at least fall back to per-start solves when kk > 250.
4. Harden the client. At volunteer.py:786-790, treat any REMAINING line that does not extend the seed, or is a duplicate, as a failed run (return None) instead of dropping it with only a warning. A correct worker never prints either. Consider adding "remaining": N to SUMMARY and having the client check the count.
5. Add the small-cap regression test from repro_plan so fail-safe behaviour is proven.

- Accepted states have no shortcut, so their depth equals their optimal solve length. Depth therefore stays below about 250 on 5x5, including with a few more holes, and on 4x6 (record 160).
- A grid like 5x6 or 6x6, where optimal lengths can pass 250, triggers it. g_max_depth defaults to INT_MAX, and the solver and depth fields are int32, so nothing else stops the search there.

What happens once depth passes 250:
1. Livelock (the common case). Pending nodes deeper than 250 collapse to the 250-token path of their ancestor A, and the client adds A as a child. When A runs, every child prints exactly A. volunteer.py:783-785 sets self_remaining, 821-825 return None, and run_window 596-601 returns False with the job untouched. The job is re-leased and burns a full split_after window each time, forever, unless A's subtree finishes monolithically inside one window. That is a campaign stall (high). It is loud, so the owner would notice it.
2. Silent loss (the critical case). The cut can fall inside a committed-walk run: a bulk child Y of a node Q with depth(Q) < 250 < depth(Y). Then the 250 tokens replay (2048-2074) to the intermediate cell X with bulk_walk=1. X is a bulk sibling, not an ancestor, as the comment at 2062-2064 says. X's subtree does not contain Y, because bulk_walk=1 suppresses committed walks. Y's pending subtree (the deepest region, where records live) is replaced by X's.
   - If X is also pending, the duplicate line is dropped at volunteer.py:786-790 (`p not in remaining`, counted as bad), with only a warning at 831-833.
   - A second silent drop the sources did not mention: run_window 614-617 (`new = [r for r in remaining if r not in index]`) drops REMAINING lines that equal an existing tree node. The node is still marked split whenever at least one other line survives.
   - When X's job finishes inside its window (likely, since it sits 250 deep near the bottom of the tree), Y's subtree is gone and nothing is ever flagged. That is a wrong exhaustive maximum.
3. Seeds longer than 250 (the server allows up to 1024) print children shorter than the seed. All of them are counted bad, the client logs 'split but no valid REMAINING' and returns None: livelock. In practice such seeds only arise from server seeding, because truncation caps at 250.

The level codes and best depth are computed from the state, not the path, so levels that are found are reported correctly. The damage is limited to coverage and stalls.

Severity: if it fires, the worst case is critical (a silent coverage hole exactly at record depth), mixed with loud stalls. It cannot fire on 5x5 at any hole count likely to be tried, or on 4x6. I rate it high as a latent must-fix before any grid whose optimal lengths can exceed 250, not critical for the next campaign. If the next campaign is 5x6 or 6x6, treat it as critical.

Minor side effects:
- STATUS and trace paths truncate (cosmetic only).
- The multi-solve uint8 labels (sokoban_bfs.c:1807/1904, MS_INF 255) fall back to per-start solving for cutoffs of 254 or more. That costs speed but is still correct.
- seg_len is clamped to 127 at 2363, so it is safe.

No dynamic run is needed: the static chain is unambiguous. An optional fail-safe test belongs to the fix (see fix_notes), not to verification.
