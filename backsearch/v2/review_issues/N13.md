*fix notes*: Corrections and additions to the proposed fix design:

(1) MSLab exact compare: raw pack5 is not the right comparison key. Zobrist keys deliberately merge permutations of blocks that share a pushability mask (sokoban_bfs.c:150-157, zpack64). pack5 depends on block order, so comparing pack5 would stop those merges. That is still sound, but it creates more states, more -2 fallbacks to single solves, and different states/solver_calls fingerprints. Compare a canonical exact pack instead: sort positions within each equal-mask group before packing. Alternatively keep the Zobrist key as the probe index and store that canonical pack for comparison. The reference table cannot use pack5 either, because it looks up across puzzles whose blocks are indexed differently (it needs the g_ref_xor translation), so leave it hash-based.

(2) The "-DZOBRIST_SEED" cross-check would not work with the current generator. zobrist_init (sokoban_bfs.c:170-179) fills every z-value from xorshift64 (13,7,17). That generator is GF(2)-linear with full period, so its characteristic polynomial P is primitive. The z-values are M^i·s0, and the XOR difference over a set S is p_S(M)·s0, which is either zero for every nonzero seed (when P divides p_S) or never zero. So a different seed reproduces exactly the same colliding pairs. A seed knob has to use a nonlinear stream, for example z_i = splitmix64(seed + i).

(3) Generator 128-bit key: take the symmetry minimum lexicographically on (k0, k1), and take the probe index from k0. Account for that in the README/VOLUNTEERS memory figures. With a 32-bit relative clock, the wrap guard matters for runs without a split (--split-after 0, local and test runs) that last several hours.

(4) v2_finish.js:60 currently accepts v == null ("not re-solved yet"). Require v === best. Campaign #1 is unaffected: every champion was verified equal to best.

WHERE THE PROPOSED FIX IS WRONG OR SUBOPTIMAL
(a) The Zobrist tables are xorshift64 outputs (sokoban_bfs.c:170-176), which are linear over GF(2). I computed the characteristic polynomial in Python: degree 64, weight 25, and the relation holds on full words. key(F) = p_F(T)·seed, so two states collide exactly when the primitive characteristic polynomial divides p_{FΔG}. The colliding pairs are therefore THE SAME FOR EVERY SEED.
- The lockstep step "re-run with -DZOBRIST_SEED" would reproduce the same solver collisions.
- A second key table drawn from xorshift64 (a continued stream or a new seed) adds zero protection.
- Tables must come from a non-linear generator, for example splitmix64 of a counter. The generator's splitmix chain is non-linear, so changing its seed does help.
(b) Comparing the MSLab slot against the exact pack5 value is sound, but pack5 depends on block index while Zobrist merges permutations of blocks with the same mask. Example: which of two same-mask blocks fell into a hole. Exact comparison splits those states into separate slots, which means more expansions and more MS_SIZE/2 overflow fallbacks, so "negligible CPU" is unverified. A second, independent, non-linearly generated 64-bit Zobrist key keeps the merging.
(c) A zero-memory option for the generator: ShallowSlot (16 B) and RecentSlot (24 B) each have exactly 4 bytes of tail padding. A 32-bit check hash from an independent chain gives 96-bit keys at no memory cost, P ≈ 1%/2^32 ≈ 2.5e-12 per campaign. The finder's 192/224 MB arithmetic is correct but not needed.
(d) Mandatory verification is right: v2_finish.js:59-61 only refuses when `v != null && v !== best`, so a champion that was never re-solved passes.
