# M20: No poison-job handling: jobs that are rejected deterministically or never produce a SUMMARY are re-leased forever, with no counter or alert

verdict CONFIRMED, severity medium, category robustness
locations: volunteer.py:951 (per-report 400/409 filed to rejected/ and forgotten); volunteer.py:596 (a run without SUMMARY drops the job without telling the server); jobs.js:754 (rejection reopens the job); no per-job attempt/rejection counter or quarantine in jobs.js

## Summary
On a per-report 400 or 409, the client files the report in rejected/ and forgets it, and the server rejects the whole tree and reopens the job. When the job's own run has no SUMMARY, the client drops it silently, and the server releases it after 120 s. Either way the job is re-leased at once (the pool is deepest-first), often to the same client. If the cause is deterministic (the same bad LEVEL or tree, a worker crash, or a hang), the job is re-run for a full window each time, forever, and that exit's audit can never be clean. The server counts no attempts, keeps no quarantine and raises no alert, and no test covers repeated rejection.

## Verifier (CONFIRMED, medium, refuted=False)
The issue holds; I read all the cited code and its callers.

1) Rejection path. When parseTree returns an error, applyReport (jobs.js:750-755) records the report and then reopens the job:
`const giveBack = () => { if (mine && !finished) q.reopenJob.run(job.id); }; if (tree.error) { q.insReport.run(..., tree.levelError ? 'bad_level' : 'bad_tree', t); giveBack(); return fail(400, ...) }`
reopenJob (jobs.js:284) sets status='open' and clears the client. The unknown_hash path (jobs.js:774-777) does the same. The jobs schema (jobs.js:184-208) has no attempts, failure or quarantine column. No query anywhere aggregates reports.outcome: a grep for bad_level, bad_tree and outcome in jobs.js, v2routes.js, the tools and the public JS finds only the insert. The server does not even log the rejection: v2routes.js:146-157 logs only 500s, and jobs.js has no console.warn on this path.
On the client side, reject() (volunteer.py:951-961) only writes outbox/rejected/<t>-<job>-<id>.json and logs '!!! server REJECTED'. It keeps no memory of the job id.
The per-slot backoff does not throttle this loop. run_window returns True as soon as the report is queued (volunteer.py:700), and slot_loop (volunteer.py:547-551) then resets consecutive_failures to 0. The rejection arrives later from the sender thread.
openOfExit (jobs.js:273-275) orders by depth DESC, so the reopened job is among the first handed out again, often to the same client. Each cycle costs a full window plus absorption, about 1800 + 120 s of one core.

2) No-SUMMARY path. volunteer.py:596-599 returns False with `slot.job = None` and tells the server nothing. The job is now in neither `running` nor the queue, so it is missing from `holding` (volunteer.py:1161-1163). The next heartbeat releases it, because leased_at is more than RELEASE_GRACE_S=120 s old (jobs.js:514), and it is re-leased deepest-first. The 3-in-a-row backoff (volunteer.py:552-556) resets on any successful job. One poison job mixed in with good jobs therefore never triggers it.

3) No test covers this. The existing test enshrines unbounded reopening: v2_gates.test.js:169-176 rejects job 1 six times in a row and asserts `row(id).status === 'open'` after each rejection. No test covers quarantine or repeated rejection.

Checked against the snapshot: the reports table has only done, done:match, dup, split and split:incomparable outcomes. There are 0 bad_level, bad_tree or unknown_hash rows, so campaign #1 was unaffected.

Refinements and corrections:
(a) One part of F87 is wrong. A worker that HANGS is not recycled; it is pinned. There is no per-run wall-clock watchdog: STOP_GRACE_S (volunteer.py:1393) applies only after a stop SIGINT, and the client relies on the worker's own --split-after. The hung job stays in `running`, and every heartbeat renews its lease forever (jobs.js:515-519). It moves only when an empty pool triggers stealing, which takes at most one running job per request (jobs.js:612-626). The new holder's worker then hangs too. The effect is still a stalled audit plus one lost core, but through a different mechanism.
(b) The forensic trail is better than 'only a volunteer log line' for rejections: reports.outcome and summary_json.error (first 300 chars) are stored per rejection. The problem is that nothing surfaces them. For no-SUMMARY crashes, however, nothing at all reaches the server.
(c) How likely deterministic triggers are. The caps come from the same `extra` the worker receives (capsFromExtra, jobs.js:101-108; worker_argv, volunteer.py:416-425), and the seed limits (3072 chars) are far above the snapshot's maximum of 383. Deterministic triggers therefore need a real worker/server disagreement, for example exit-orbit or orientation handling on a non-square grid (validateLevel, jobs.js:124-137).
(d) Adjacent defect I found while checking tree-report rejection triggers; it is not M20 and should be tracked separately. volunteer.py:681-684 truncates the tree to `nodes[:MAX_NODES]` (5000) and logs 'the rest stay open on the server'. That log line is false: the dropped REMAINING seeds are never sent. The server has no remaining-count to cross-check (sanitizeSummary keeps no such field), so a root split with more than 4999 REMAINING seeds would silently lose subtrees, which is a coverage hole and potentially critical on a larger grid. If truncation ever cut all children of an inner split node, it would also be a deterministic bad_tree, which feeds exactly this poison loop. It is not reachable for 5x5/h3: the snapshot's largest split has 273 children, and splits normally happen only at the window deadline, so trees are root + REMAINING.

Severity for the next campaign: medium. The loop cannot make a published result wrong. The stuck exit never audits clean, so v2_finish will not publish it. It is also recoverable by hand, since the job id is visible and rejection rows exist. But it turns any deterministic worker/server disagreement or crashing seed into an unbounded CPU sink and a silent stall, and the server gives the owner no signal. A new grid or new level features raise the odds of such a disagreement.

*fix notes*: Server (jobs.js):
- Add migrated columns jobs.attempts INTEGER DEFAULT 0, jobs.fail_count INTEGER DEFAULT 0 and jobs.last_error TEXT.
- Increment attempts in leaseJob, stealJob and the reclaim path. Increment fail_count and set last_error in applyReport on bad_level, bad_tree and unknown_hash.
- After N (e.g. 3) rejections, set status='quarantined' instead of calling reopenJob. openOfExit already filters status='open', so quarantined jobs will not be leased.
- List quarantined jobs, and jobs with attempts > K, in auditExit, /api/v2/status (counts) and v2_finish output, so an exit that has any quarantined job is explicitly 'not clean: N quarantined'.
- console.warn every rejection with the job id and error. Add an owner tool to requeue a quarantined job after a fix.
- Optionally, on levelError, keep the level in a side table for owner review and bound retries, rather than silently rejecting the tree forever.

Client (volunteer.py):
- Keep a session set of job ids the server rejected with 400/409. If a re-lease brings one back, do not run it; hand it back and show a panel banner.
- Report failures to the server: add a 'failed' list to the heartbeat, or a /api/v2/fail endpoint carrying job_id, seed, rc and reason for a root run without a SUMMARY. The server can then count and quarantine crashing seeds.
- Add a per-run wall-clock watchdog: SIGINT at split_after + margin, SIGKILL after STOP_GRACE_S, and count it as a failure. Today a hung worker pins its job and a core forever, because heartbeats renew the lease.

Tests:
- Change v2_gates 'level validation' (test:169), which currently rejects the same job 6 times and expects 'open'. Use a fresh job per case, or assert quarantine after N.
- Add a gate test that sends the same bad level 3 times and expects status 'quarantined', no lease of that job, and the job listed in the audit/status.
- Add a client test where fake_worker exits without a SUMMARY for one specific seed, expecting the failure to be reported and the job quarantined after N.

Adjacent, to track separately: remove the MAX_NODES truncation at volunteer.py:681. Never drop REMAINING children; split them into several reports or raise the cap to REMAINING_MAX+1. Add a remaining_count field to the split summary so the server and audit can verify the child count.
