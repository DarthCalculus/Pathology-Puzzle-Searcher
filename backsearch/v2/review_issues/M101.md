# M101: Children whose new player cell is a dead end provably have no shortcut, but each still gets a full exhaustive solve

verdict PLAUSIBLE, severity low, category algorithmic
locations: backsearch.c:2534 (child shortcut check always run)

## Summary
Take an accepted state s (player at P, no solution of length d-2 or less) and a child c whose newly committed player cell C has P as its only non-wall neighbour, where no block can be pushed from P into C and the forced first move returns to s's configuration. Then c has no shortcut, since any solution is at least d+1 = depth(c) long. This covers walk-backs, push-backs whose mask already had D, un-consumes of committed B, and new blocks frozen by a wall. Today every such child runs a full check that must return -1, and the parent table does not help, because C is always in reach.

## Source report F158 (algo-worker)
**Children whose new player cell is a dead end are provably 'no shortcut', but each still gets a full exhaustive solve** at /Users/george/Documents/Claude Projects/project45/backsearch/backsearch.c:2534

*summary*: Take an accepted state s (player at P, no solution of length d-2 or less) and a child c whose player cell C is newly committed. Suppose (i) C's only non-wall neighbour in c's puzzle is P, (ii) no block can ever be pushed from P into C, and (iii) the forced first forward move returns to s's configuration. Then c has no shortcut. Proof: the first move is forced; later visits to C are removable two-move detours; so the rest of any solution is a solution of s's puzzle, of length at least d, giving at least d+1 = depth(c). Condition (iii) holds for a walk-back, a push-back whose mask already had D, an un-consume whose B was committed in s, and a new block frozen at B because adj[B][D] is a wall. Today every such child runs a full check that must return -1. The parent's table does not help, because the delta cell C is always in reach (README: 0.03% of pops pruned).

*failure_scenario*: Deep states at exit 1 cost 0.2-2 ms per check by job depth. Each dead-end new-cell child spends that exploring the whole cutoff-bounded space and then accepts. Its descendants also get no usable inherited table, because C stays in ptab_delta.

*evidence*: backsearch.c:2534 'd_ref[d_n] = 1;   /* same puzzle up to the newly committed cell C (delta) */'; 2645 'uint64_t delta = s->ptab_delta | (d_bufs[i].committed_empty & ~s->committed_empty);'; 2189 'int x = have_x ? given_x : shortcut_check(s);'; README 118-122: puzzle delta 'prunes 0.03% of those children's pops -- the new cell is where the player starts, so it is always in reach ... effectively get nothing'.

*suggested_fix*: In expand(), test (i) every neighbour of C except P is off-grid or uncommitted in the child; note the exit is committed, so a C next to the exit never qualifies. Test (ii) B=adj[P][D] is off-grid, uncommitted or the exit, or no block's pushable mask has bit D^2 (optionally refined with a relaxed push-closure check for P). Test (iii) per variant as listed above. If all hold, call try_successor_x with have_x=1, given_x=-1. Also, per check, drop from ptab_delta any cell that is still such a dead end in the current puzzle, so descendants use the inherited table at k+1 with full strength; this equals the table the child would have exported. Verify with a check build that still runs the solver and asserts -1, plus the README equivalence configs (accepted counts must match exactly).

*expected_gain*: Unmeasured. Bounded by the solver share of new-cell children (README: two thirds of solver time is in children whose puzzle differs from the parent's). Estimate 3-10% of solver time; a WBPROF run on a campaign root would size it.

## Verifier (PLAUSIBLE, low, refuted=False)
The premise is correct, the shortcut is exact, and the code today spends a full solver call on every such child. On campaign-like search trees, though, these children are a much smaller share than the finder estimated. My estimate is about 2-4% of single-check solver time, against the finder's 3-10%.

CODE FACTS (backsearch.c)
- expand() (2463-2658) sends every non-bulk child through try_successor() -> try_successor_x(s,0,0,0).
- That path always calls `int x = have_x ? given_x : shortcut_check(s);` (2189), and shortcut_check runs sokoban_solve_cutoff with max_cost = depth-2 (1699-1708).
- Nothing in either C file handles dead ends. A grep for dead-end / only-neighbour finds only rollout code.
- The parent table cannot help:
  - The walk child (2534), a push-back whose mask already had D (2560) and an un-consume (2630) get delta = ptab_delta | new cells (2645).
  - ref_prunes_at (sokoban_bfs.c ~1474-1485) refuses to prune while any delta cell c has nc + D(p,c)-1 + D(c,exit)-1 <= cut. C is next to the start cell, so the check always blocks, matching the README's 0.03%.
  - New-block children (variant 3) never get a table.
- Every expanded state has been accepted: the seed goes through try_successor (4401), so the parent's -1 is always established.

PROOF CHECK
I checked the proof against the forward solver's rules (sokoban_bfs.c 1160-1235): pushes need the push-from cell reachable, the landing cell must be free, a hole consumes the block, and the game is won when the player can walk to the exit.
- (i) C's other neighbours are walls or off-grid. Blocks and holes always sit on committed cells, so none can be there, and the first move C->P is forced.
- In variants 2-4, B is free (variants 2/3) or an active hole (variant 4), so the push is always legal.
- Any later visit to C is a P->C->P detour during which nothing moves, so it can be removed.
- (ii) Blocks can enter C only from P, with the player standing on B. The exit is never a push-from cell in a shortest solution, because a win comes first.
- (iii) The state after the forced move equals s in each covered case:
  - walk: yes;
  - variant 2: only if s's mask already had D, since m|D must equal m;
  - variant 3: the new block at B has mask {D}, and adj[B][D] being a wall or off-grid freezes it, which is the same as s's wall at B;
  - variant 4: only if B was committed in s.
- So c's true minimum is at least 1 + d = depth(c), and the exact solver must return -1.
- The shortcut changes a decision only where the solver would have returned -2 or -3 (overflow or cap). There it accepts instead of pruning, which is more correct.
- Accepted sets, valid-level sets, visit sets and the server's fingerprints (states/valid/best) are unchanged.

TABLE-LOSS CONCERN (checked, turned out fine)
Skipping the check means c exports no table of its own. That costs essentially nothing:
- Every child of c commits a new neighbour of C (the new player cell, or the new block's B). The only exception is the move back into P, which is either forbidden by the anti-wiggle rule or blocked by the block on P.
- So every child's check carries a new, reachable delta cell and gets about 0.03% from c's table anyway.
- c's own bulk walk-back set is empty.
The finder's suggestion to drop dead-end cells from the delta per check therefore mostly helps c itself, not its descendants.

RISK
If the predicate is implemented wrongly, the worker accepts states that have shortcuts. That inflates valid-level counts and could produce a false best. The site's own verifier would catch a false best; nothing would catch inflated counts. This risk is controllable with a check build, so it is not a reason to skip the change, but it does require that build.

*fix notes*: Where: in expand(), before the dispatch loop (backsearch.c ~2640), compute a per-child flag deadend[i]. C = the child's player cell and D = the direction.
