# M46: The multi-start chain offset is capped at 250 (uint8_t refk), which makes the reference prune stronger than proven

verdict CONFIRMED, severity low, category soundness
locations: backsearch.c:2402 (`refk[j] = (uint8_t)(kk > 250 ? 250 : kk)`); single-start path passes the uncapped int

## Summary
The reference prune is sound only for the true chain offset k: prune iff nc > gp + k - 2. Capping k down to 250 lowers that threshold, so for chain offsets above 250 the multi-solve can prune states that could still lie on a shortcut. The single-start path passes the uncapped value. This is unreachable on 5x5 but latent for deeper searches.

*summary*: The prune is sound only for the true chain offset k: prune iff nc > gp + k - 2. Capping k down to 250 lowers that threshold, so the prune can fire on states that could still lie on a shortcut. The single-start path passes the uncapped int.

*failure_scenario*: Needs ptab_k + dist > 250 while maxcut <= 253 (otherwise the multi solver falls back). That means an owner table exported at depth < 5, then inherited without re-export for about 250 levels. Then for nc in 249..253 with a small gp, a state is pruned that the true k (251..255) would keep. A shortcut is missed and an invalid level accepted. Practically unreachable on 5x5 (depth <= 149), but it is a real gap in the proof.

*evidence*: backsearch.c:2402  for (int j = 0; j < n; j++) { int kk = s->ptab_k + dist[starts[j]]; refk[j] = (uint8_t)(kk > 250 ? 250 : kk); }

*suggested_fix*: When kk > 250, disable the reference for that start (e.g. refk[j] = 255 as a 'no prune' sentinel, checked in ref_prunes_gp), or widen refk to int16.

*expected_gain*: Makes the prune sound for every input, not just realistic ones.
