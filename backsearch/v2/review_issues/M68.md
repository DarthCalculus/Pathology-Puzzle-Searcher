# M68: The Workers field keeps showing an unapplied value, Enter does nothing, and the clamp to workers_max is silent

verdict CONFIRMED, severity low, category robustness
locations: volunteer_ui.html:229 (workersEdited cleared only by Apply; input max 64 vs campaign max 32)

## Summary
Typing in the Workers field sets workersEdited=true, and only the Apply button clears it. The field then shows the typed number indefinitely although nothing was sent. The input allows up to 64 while the campaign allows 32, and the clamp is not reported.

## Source report F75 (client-ui)
**Workers field keeps showing an unapplied value; Enter does nothing; the clamp to workers_max is silent** at /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer_ui.html:229

*summary*: Typing in the Workers field sets workersEdited=true, and only the Apply button clears it. The field then shows the typed number indefinitely even though nothing was sent. The input's max is 64 while the campaign allows 32, and the clamp is not reported.

*failure_scenario*: A lagging volunteer types 2 and presses Enter, which does nothing because there is no form, then tabs away. The field keeps saying 2 while 8 workers run, and there is no pending flag, so the volunteer believes the load was reduced.

*evidence*: volunteer_ui.html:229 `$('workers').addEventListener('input', () => { workersEdited = true; });`, :230 Apply is the only path that posts and resets the flag, :257 `if (!workersEdited && document.activeElement !== $('workers')) $('workers').value = st.workers;`, :94 `max="64"`.

*suggested_fix*: Apply on Enter or change. Otherwise mark the field as 'not applied' and revert it on blur. Set max from campaign.workers_max and show when the value was clamped.

## Verifier (CONFIRMED, low, refuted=False)
Confirmed by reading volunteer_ui.html. Line 229 `$('workers').addEventListener('input', () => { workersEdited = true; });` sets the flag. Line 230 (the Apply onclick) is the only place that clears it. Line 257 `if (!workersEdited && document.activeElement !== $('workers')) $('workers').value = st.workers;` then stops refreshing the field. The input sits in a plain div with no <form> and no keydown handler (line 94), so Enter does nothing. After a typed value is tabbed away without Apply, the field keeps that value indefinitely. pending_flags() (volunteer.py:1230-1241) only reports retiring or fresh slots, so no 'not applied' hint appears either. The input has max="64" while the campaign has workers_max 32 (snapshot campaigns row 1 = 32; jobs.js:356 default 32). volunteer.py:1115-1132 set_workers clamps with `n = max(1, min(wmax, n))`, and the UI ignores the returned {workers: n}. One part is overstated: the clamp is not fully silent. Once Apply is clicked, focus leaves the input (button, or body in Safari), workersEdited is false, and the next 250 ms render replaces the field with st.workers, i.e. the clamped 32. The client log also records 'workers set to 32'. So the clamp is visible but unexplained. The stale-unapplied-value problem is fully real. It is mitigated because section 2 shows one card per running worker, so an attentive volunteer can count them. No effect on search correctness or on the server.

*fix notes*: Add a keydown handler (Enter calls Apply) or wrap the field in a <form> with a submit handler. On blur without Apply, revert the field or show an 'unapplied' marker next to Apply. Set the input's max from st.campaign.workers_max on render. Show a one-line note when the value returned by /workers differs from the one typed ('limited to 32 by the campaign').
