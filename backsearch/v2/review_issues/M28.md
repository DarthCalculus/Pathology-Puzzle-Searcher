# M28: reopenUnknownHashJobs resets bad-hash jobs but keeps their old subtrees and probe levels: nested re-search (~4.4x) and stale bests

verdict CONFIRMED, severity high, category algorithmic
locations: jobs.js:422-427 (reopenUnknownHashJobs); tools/v2_hashes.js --reissue; exitSummary MAX(best) / bestOfExit

## Summary
Removing a hash with --reissue resets every done or split row under that hash to open, but leaves all parent links, open children and probe rows in place. A reset split node is re-run and creates a new child set that re-covers its whole subtree, while its old children (also reset) must be covered as well. A state at job-tree level k is therefore searched k+1 times, about 4.4x overall. Open probe rows carrying the removed worker's levels and bests stay attached and keep feeding exitSummary MAX(best) and bestOfExit.

## Source report F77 (server-scheduling)
**reopenUnknownHashJobs resets every old-hash node but keeps the old subtree structure: nested re-exploration of about 4.4x** at /Users/george/PathologyRecords/server/lib/jobs.js:427

*summary*: Removing a hash with --reissue resets every done/split row under that hash to open and leaves all parent links in place. A reset split node is re-run and creates new children that re-cover its whole subtree, while its old children (also reset, still its children) must be covered as well. Every level of the old tree gets searched again.

*failure_scenario*: A worker bug is found mid-campaign and the owner follows the documented procedure (DESIGN §1.4, `v2_hashes.js remove H --reissue`). Root R (split, H), child C (split, H) and grandchild G (done, H) all go back to open. R's re-run splits and its new children re-cover subtree(R). C is still R's child and must also be covered, so subtree(C) is searched a second time, and subtree(G) a third. The audit requires all of them. On campaign #1's tree shape, re-issuing everything would cost sum(elapsed x (depth+1)) = 2,605 CPU-h instead of 597 CPU-h.

*evidence*: jobs.js 427-429: `for (const { id } of q.unknownHashJobs.all(campaignId)) { const j = q.jobById.get(id); if (!hs.has(j.src_hash)) { q.resetJob.run(id); ids.push(id); } }`. 313: unknownHashJobs = all done/split non-dup rows. 314: resetJob does not touch parent_id or children. 999: `else ok = (children.get(n.id) || []).every(ch => covered.get(ch.id));` requires the old children too. Snapshot recursive CTE: max depth 15, mean 5.84, weighted rework 2,605 vs 597 CPU-h.

*suggested_fix*: Reset only the topmost old-hash nodes, i.e. those with no reset ancestor. Detach or tombstone all their descendants (e.g. set a 'superseded' status excluded from treeOfExit) so coverage depends only on the new run. A buggy worker's REMAINING partition cannot be trusted anyway.

*expected_gain*: A worker-fix re-issue costs about 1x the affected CPU instead of about 4.4x.

## Source report F96 (server-ingest-routes-tools)
**v2_hashes --reissue resets bad-hash jobs but leaves their subtrees and probe levels in place** at /Users/george/PathologyRecords/server/lib/jobs.js:422

*summary*: reopenUnknownHashJobs resets only finished rows under the removed hash. Open children created from the bad worker's REMAINING, and open probe rows carrying its levels and bests, stay attached. The re-run adds a second child set, and the stale probe rows keep feeding exitSummary MAX(best) and bestOfExit.

*failure_scenario*: Hash H has a bug; the owner runs remove H --reissue. Split job S (under H) is reset but keeps its open children C1..Cn. The fixed worker re-runs S and it splits into D1..Dm, so coverage needs C ∪ D (double work). If some C seed cannot be replayed by the fixed worker (no SUMMARY), S is never covered and the exit can never audit clean, with no tool to repair it. If S re-runs as done, C1..Cn stay open under a done parent forever. An open probe row from an H report with an inflated best (say 150) is not reset, because only done/split rows are selected. It stays in MAX(best) and becomes the champion, and v2_finish then depends solely on that row's verified_moves (null if the 30 s solve failed, in which case it publishes 150).

*evidence*: jobs.js:313 `unknownHashJobs: ... WHERE campaign_id = ? AND status IN ('done','split') AND dup_of IS NULL`; 314-315 resetJob clears only the row itself; 427-430 loop. insNode (790) stores open nodes with `fin ? hashIn : null` as src_hash and `s ? s.best : n.levelBest`, n.levelCode. 1027-1028 exitSummary `MAX(best) ... AND (status IN ('done','split') OR level_code IS NOT NULL)`; 301-302 bestOfExit accepts any status.

*suggested_fix*: When resetting a job, delete (or detach) its whole descendant subtree in the same transaction; the re-run recreates it. Record the reporting hash on open probe rows too, and clear level_code/best of rows created under a removed hash. Add a gate test: split under H, remove H --reissue, re-run, and check only the new children remain.

## Source report F184 (robustness-ops)
**Re-issuing after a hash removal keeps the old children of reset split jobs, so subtrees are searched about 4x over** at /Users/george/PathologyRecords/server/lib/jobs.js:422

*summary*: reopenUnknownHashJobs resets every done/split job whose hash is no longer whitelisted, but leaves each reset split job's children attached. When the reset parent runs again it splits into a new set of children that cover the same states as its old children, which were also reset and are also run. States at job-tree level k get searched k+1 times.

*failure_scenario*: Mid-campaign #2, the owner finds a worker bug and runs `v2_hashes.js remove H1 --reissue`, as DESIGN §1.4 plans ('a worker fix means re-issuing only jobs done under the old hash'). Every H1 split node P returns to open with its old children C1..Cn still pointing at it. P's rerun splits after 30 minutes into D1..Dm, which cover P's subtree minus its first window, while the reset C1..Cn cover the same states again. Recursively, a state at job-tree level k is searched once for each reset ancestor plus itself. On campaign 1's tree (split depth up to 15), the CPU-weighted mean of (level+1) is 4.36, so a full reissue would cost about 2,600 CPU-hours instead of 600. The audit also requires both old and new children to be covered, so none of the redundant work can be skipped. The tool also runs a jobById per row and holds the write lock for the whole loop; on a 2M-row campaign that can exceed the server's 5 s busy_timeout, so heartbeats, leases and reports get 500 until it finishes.

*evidence*: jobs.js:422-432: `for (const { id } of q.unknownHashJobs.all(campaignId)) { const j = q.jobById.get(id); if (!hs.has(j.src_hash)) { q.resetJob.run(id); ids.push(id); } }`. resetJob (314-315) touches only the row itself. applyReport:788-796 inserts the new children with `ids.get(n.parent.seed)` equal to the same job id. auditExit:999 `ok = (children.get(n.id) || []).every(ch => covered.get(ch.id))` covers old and new children alike. Snapshot: WITH RECURSIVE level histogram 0..15; CPU-weighted (level+1) = 4.363.

*suggested_fix*: Reset only the topmost unknown-hash node on each root-to-leaf path. Detach its whole descendant subtree (for example status 'superseded', excluded from lease, audit and steal) instead of resetting it, because the parent's rerun re-covers it exactly. Run the change in chunks of about 5,000 rows per transaction so server writes are not starved. Add a gate test: split tree under H1, remove H1 with reissue, check that no redundant open jobs remain.

*expected_gain*: A mid-campaign worker fix costs about 1x the affected work instead of about 4x.

## Verifier (CONFIRMED, high, refuted=False)
I checked the premise against the code and it holds. The claimed gain holds too, and on campaign #1's tree shape it matches the figure given. The path was never exercised in campaign #1, which used one hash for 167,766 rows. It is still the documented recovery procedure: README.md:49 says `node tools/v2_hashes.js remove <hash> --reissue   # after a correctness fix`, and DESIGN §1.4 says the same.

**What the code does**
- jobs.js:313 selects `status IN ('done','split') AND dup_of IS NULL`. Lines 427-429 then run `if (!hs.has(j.src_hash)) { q.resetJob.run(id); ids.push(id); }` on each row.
- resetJob (314-315) clears only that row's own fields. It leaves parent_id alone, and it does not touch the children, the dup rows, or the `mismatch` column.
- Leasing takes any `status='open'` row (273), so every old child is leased and run again.
- The audit at 999 is `else ok = (children.get(n.id) || []).every(ch => covered.get(ch.id))`. It requires the old children of a re-split node as well as the new children from applyReport:790 (`ids.get(n.parent.seed)` is the same job id).

**Cost model**
- Take a state explored by a node at old tree level k. Each reset ancestor, once re-run, builds a fresh subtree that covers that state again, and the reset node itself is re-run too. So the state is searched k+1 times.
- For a node that had not run when the bug was found, the old run still happens and each reset ancestor adds one more. Its cost is nh+1.
- I checked this on the snapshot with recursive CTEs: 166,733 non-dup rows, max level 15, mean 5.84. A full reissue costs sum(elapsed x (level+1)) = 2,605.3 CPU-h against 597.1 CPU-h, a CPU-weighted factor of 4.363. Weighted by states it is 3.13x.

**Mid-campaign estimate (my own)**
- The more likely case is a bug found partway through. I treated the jobs done before a cutoff as the bad hash H and compared the cost after the reissue: current code sum(elapsed x (#H in the chain + [node not H])) against the proposed fix, which searches every node once (597 h).
- Results:
  - Bug found after 5% of jobs: 738 vs 597 CPU-h.
  - After 10%: 1,212 vs 597.
  - After 25%: 1,890 vs 597.
  - After 50%: 2,272 vs 597.
  - After 100%: 2,605 vs 597.
- So a fix found after a quarter to half of the campaign wastes about 1,300 to 1,700 CPU-h under the current code. At 10 clients x 16 workers that is about 8 to 10 hours of the whole fleet.
- The fresh subtrees get a different split shape (split_after is 1800 s rather than the 120 s ramp), but the multiplier comes from the number of reset ancestors in the old tree, so the estimate holds roughly.

**Exactness**
- The current behaviour is a superset of the needed coverage, so it cannot lose a valid level. The problem is waste and stalls, not wrong results.
- The proposed fix relies only on the design's own trust in the fixed worker's REMAINING. Resetting the topmost bad-hash node on each path and retiring all its descendants covers subtree(T) exactly once through the new run. That includes levels on open probe rows, which the new run finds again. So the fix does not weaken exactness.

**Consequences found beyond the report**
1. **The mismatch flag is never cleared.** setMismatch (291) is the only writer of `mismatch`. Neither resetJob nor finishJob resets it. auditExit pushes `if (n.mismatch)` (1001) for any status, and `if (d.mismatch)` for dup rows (1005). A fingerprint mismatch is exactly how a nondeterminism bug gets noticed (DESIGN §1.5). After `remove H --reissue` and a clean re-run under the fixed hash H2, that exit still can never audit clean, and no tool clears the flag. The owner would need manual SQL. This is a campaign-stall class problem.
2. **Old open children seeds come from the buggy worker's REMAINING.** If the fix changes move validity, the fixed worker rejects such a seed (backsearch.c:2068 `error: --seed-path step %d ... is invalid`) and prints no SUMMARY. If the re-run parent splits again, the audit waits on that child forever.
3. **Old children can be orphaned.** A node that split during the 120 s ramp often re-runs as done under the 1800 s window. Its old children are then left open under a done parent. They are still leased (pure waste), and they are no longer required by the audit, so v2_finish can run while they are open.

**Stale probe levels (weaker than reported)**
Open probe rows keep their H level_code and best (insNode stores `s ? s.best : n.levelBest, n.levelCode`, with src_hash NULL for open rows, so line 313 never selects them). They feed exitSummary MAX(best) (1027-1028) and bestOfExit (301). However, finishJob overwrites best and level_code as soon as such a row runs. So staleness only matters for orphaned open rows (point 3), and only if the bug inflated a probe's claimed depth and the site-solver check (verified_moves or the 30 s re-solve in v2_finish) failed or timed out. That part is real but low severity. A level from a buggy worker is usually still a genuine level.

**Lock time (minor, low to medium)**
The whole loop is one transaction: .all() of every finished id, then a jobById and a resetJob per row. For campaign #1 (~167k rows) that is about 1-2 s. At 1-2M rows it could hold the write lock longer than the server's 5 s busy_timeout (jobs.js:147), so server writes would return 500 until it finishes. That is recoverable through client retry and the outbox.

**Severity**
High. It is conditional on a correctness-driven hash removal, but that is the documented procedure, and when it happens it causes large wasted work (about 3-4.4x of the affected CPU) plus a likely permanent audit stall through the mismatch flag.

**What turned out fine**
The existing gate test (v2_gates.test.js:388) covers only a leaf done job, so it passes. The superset coverage never makes a published result wrong.

*fix notes*: Fix in jobs.js reopenUnknownHashJobs (422-432), plus guards elsewhere.

1. **Reset only the topmost rows.** Per exit, load treeOfExit and walk it in memory. Pick the topmost rows whose hash is off the whitelist, i.e. those with no such ancestor. Reset those with resetJob plus `mismatch = 0`.

2. **Retire every descendant of a reset row.** Set all of them, including good-hash, open, leased and probe rows, to a new status 'superseded' instead of resetting them.

3. **Exclude 'superseded' rows everywhere.** treeOfExit (318) and dupsOfExit (319) need `status <> 'superseded'`. Also exclude them from bestOfExit (301), exitSummary agg (1027), countsByExit and contributors, or keep them in credit stats only as a deliberate choice. openOfExit already filters on 'open'.

4. **Handle dup rows.** Dup rows whose dup_of was reset or superseded must become superseded too, or have mismatch cleared. Otherwise line 1005 blocks the audit forever.

5. **Guard the report path.**
   - applyReport (743+) must treat a superseded job like a finished one: store the report with outcome 'superseded', do not call finishJob, and do not insert children.
   - reopenJob (284) is used by giveBack (750) and has no status guard, so a rejected report on a superseded or finished row can bring it back as 'open'. Guard it with `WHERE id = ? AND status = 'leased'` (or 'leased' OR 'open').

6. **Give the owner a mismatch-clearing tool.** For example, add a `v2_hashes.js clear-mismatch <job>` command, or clear the flag on reset.

7. **Chunk the writes.** Write in transactions of about 5,000 rows. Retire descendants first, then reset the topmost rows, so any intermediate state is still a superset. Optionally pause leasing for the duration. Log the counts: reset N, superseded M, and the CPU-h being redone.

8. **Tests.** Add a gate test covering a nested split under H, the reissue, the re-run under H2, and a clean audit with no redundant open rows. Also test that a superseded job's late report is ignored and does not come back as open.

Estimated gain on the campaign-#1 tree shape: redone work drops from about 3.2-4.4x of the affected CPU to 1x when the bug is found after 25% or more of the campaign; it is 1.24x vs 1x at 5% and 4.36x (2,605 vs 597 CPU-h) for a full reissue. The fix also removes two ways the audit can stall permanently (the mismatch flag and seeds the fixed worker cannot replay). It does not reduce exactness under the design's split invariant.
