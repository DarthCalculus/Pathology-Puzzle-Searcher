# N22: A proven champion that is already stored at a lower tier is never upgraded: it comes back 'duplicate' and the proof stays unwitnessed

verdict CONFIRMED, severity medium, category bug
locations: /Users/george/PathologyRecords/server/lib/db.js:196

## Summary
submitLevel returns 'duplicate' for any existing row with the same canonical data, even when the existing row is 'proposed', 'unproven' or 'claimed' and the candidate was just solved to 'verified'. processSubmission (pipeline.js:139) passes that through. v2_finish therefore publishes a proof whose champion stays unverified. proofChampions and annotateChampions count only 'verified' levels, so the proof reads 'unwitnessed' and the champion never gets a badge.

## Verifier (CONFIRMED, medium, refuted=False)
I read the code and the report holds up. The published maximum is never wrong. The damage is to what the site shows and to whether the proof has a witness.

1. The duplicate check ignores tier. /Users/george/PathologyRecords/server/lib/db.js:184-196, submitLevel: `const dup = selByData.get(cand.data); if (dup) { if (cand.playground) {...} return { accepted: false, reason: 'duplicate', dominatedBy: rowToLevel(dup) }; }`. This runs before `status`/`rank` are computed at line 198-199, so a candidate that was just proven 'verified' is rejected whenever the same canonical data is already stored as 'proposed', 'unproven' or 'claimed'. pipeline.js:139 passes the result straight through (`return { ...submitLevel(cand), ... }`).

2. v2_finish has no fallback. /Users/george/PathologyRecords/server/tools/v2_finish.js:68-69 calls processSubmission with 30 s and then only logs `not stored: ${sub.reason ...}`. It does not increment `failed`, so the tool exits 0 and the owner can easily miss it. It never calls pipeline.verifyLevel. The comment at pipeline.js:167-170 admits the gap ("a resubmission would be rejected as a duplicate"), but grep shows verifyLevel and markVerified have no caller anywhere: no route in server.js, no tool in server/tools. Recovery needs a hand-written node one-off.

3. Only verified levels count as witnesses. db.js:631-638 proofChampions searches `statuses: ['verified']` and returns 'unwitnessed' when nothing matches. db.js:588 annotateChampions skips any level with `lv.status !== 'verified'`, so no star badge. addProof only checks verified levels for contradictions, so the proof itself is still added.

4. The public search shows the mismatch. server.js:174-192 searches the default tiers. The promoted-but-not-promoted champion ends up under `hidden: {count, bestMoves}`, while `proof: proofForFilter(f)` states the maximum. A visitor sees a proven maximum of N, a displayed record below N, and "hidden: best N".

5. How it gets reached. During a campaign the champion code is public: campaigns.js:40 prints it as text, and collective.js:96 and hunt.js:87 render it. /api/submit (server.js:266-280) solves for only 2 s (pipeline.js:44; default engine, then solver6 at the same 2 s). If that times out, the form accepts a bare length ('proposed'), a solution ('unproven') or claimProven ('claimed'). Any visitor or volunteer who pastes the champion before v2_finish runs therefore locks it below 'verified'. A second source is old imports: the local records.db has 56 'unproven' rows, including 5x7, 5x8, 6x6 and 6x7, which matters if the next campaign uses a larger grid.

Campaign #1 was probably not affected. All six champions got verified_moves at 30 s in the snapshot, and the exit-1 149 is already stored as verified (records.db id 1, source thinky). I did not check the live records.db, so I can't rule out an exit-6 or other case there.

6. The suggested fix is incomplete. markVerified/verifyTxnBody (db.js:417-437) never clears the promoted row's own `superseded` flag. A dup row that a same-tier dominator (proposed, unproven or claimed) had superseded would become 'verified' but stay superseded=1, so searchLevels would still hide it. A dominator below the verified tier must not be allowed to supersede a verified row.

Severity: medium. The effect is wrong stats displayed and a proof without a witness, both recoverable. It needs a lower-tier copy to exist first, but nothing prevents that and the exposure is public during every campaign. The published maximum is unaffected, so this is not critical. No dynamic run is needed; the trace through the code is conclusive.

*fix notes*: 1. db.js submitLevel dup branch (line 186). Compute the candidate's status first. When `STATUS_RANK[status] > STATUS_RANK[dup.status]` and status === 'verified', promote the existing row through markVerified(dup.id, { moves: cand.moves, pushesOverExit: cand.pushesOverExit, pushesKnown: cand.pushesKnown !== false }). If dup.path is empty and cand.path is set, also store cand.path so playback returns. Return { accepted: true, upgraded: true, previousStatus, level }. Keep the 'duplicate' reply for equal or lower tiers.

2. In verifyTxnBody, after promotion, clear the row's superseded/superseded_by when the recorded dominator is below the verified tier or no longer dominates. Then re-run the dominated-by-verified check that is already there. Without this a promoted row can stay hidden.

3. v2_finish.js:68-69. If sub.reason === 'duplicate' and sub.dominatedBy.status !== 'verified', call pipeline.verifyLevel(sub.dominatedBy.id, { seconds: 30 }). Count any champion outcome other than 'accepted' or 'duplicate of a verified row' as `failed++`, so the exit code is non-zero. After addProof, re-read listProofs() and fail if the new proof's status is not 'ok'.

4. Add a small tools/verify_level.js CLI around pipeline.verifyLevel, since nothing calls it today.

5. Gate test in server/test/v2_gates.test.js. Store a 'proposed' copy of a level, addProof with its true maximum, resubmit it through processSubmission with a budget that verifies it, then assert status 'verified', superseded 0, proofChampions(...).status === 'ok', and that annotateChampions sets .champion. Add a variant where the proposed row was first superseded by a proposed row with a bogus higher length.
