# M15: The client truncates tree reports at MAX_NODES=5000, silently dropping split children the server cannot detect (subtrees lost, audit clean)

verdict CONFIRMED, severity critical, category soundness
locations: volunteer.py:680-681 (nodes[:MAX_NODES] and log 'the rest stay open on the server'); jobs.js parseTree (split needs only >=1 child); jobs.js audit/coverage

## Summary
When a window's local tree has more than 5,000 nodes, the report sends nodes[:5000]. Children are appended in REMAINING order (cursor, then the stack from the top down), so the cut drops the bottom of the DFS stack, which holds the shallowest and largest pending subtrees, while the node is still reported as split. The server only requires at least one child, creates the listed children, and counts the parent covered once they finish. The dropped subtrees are never searched, the audit can call the exit clean, and the log line saying they 'stay open on the server' is false. Campaign #1 never reached the cap (at most 268 nodes per report and 273 children per split, about 18x headroom), but a bigger grid or a longer window can.

## Verifier (CONFIRMED, critical, refuted=False)
I read the code statically and the claim holds. The dominant scenario is narrower than some of the source reports describe.

1. Client truncation (volunteer.py:680-684). The report is built as `"nodes": [self._clean_node(n) for n in nodes[:MAX_NODES]]` with MAX_NODES = 5000 (line 44). Afterwards it only logs `"... above the %d cap; the rest stay open on the server"`. That message is false: nothing else ever sends the dropped nodes, and no other code path re-queues them.

2. Order of the dropped nodes. Children are appended in REMAINING order (volunteer.py:627-630, `for r in new: ... nodes.append(child)`). The worker prints REMAINING as the cursor first, then the stack from the top down (backsearch.c:4326-4329, `for (long long i = g_q_tail - 1; i >= 0; i--)`). The cut therefore removes the bottom of the DFS stack: the shallowest pending siblings, which root the largest unexplored subtrees.

3. The server cannot detect it. parseTree (jobs.js:656-722) checks only that a split node has at least one listed child: `if (nodes[i].status === 'split' && nodes[i].children === 0)` at line 719. sanitizeSummary (jobs.js:636-649) keeps no remaining or stack count, and the worker's SUMMARY (backsearch.c:5845) has none to offer. applyReport inserts exactly the listed nodes (jobs.js:788-796). auditExit (jobs.js:973-1013, line 999) treats a split as covered when every child in the DB is covered. So J becomes covered once its 4,999 listed children finish, the exit audits clean, and v2_finish could publish a maximum that misses a longer level in the dropped subtrees.

4. The realistic trigger is simpler than the reports suggest. In run_window, J's worker gets `--split-after max(1, deadline-now)`, so J either finishes (no children) or splits at or after the deadline. The loop then breaks on `now >= deadline`. Absorption probes that split are reported open and add no children. Stopping also exits the loop. The local tree is therefore, in practice, always J plus REMAINING(J). Truncation happens exactly when J's pending DFS stack holds 4,999 or more entries. Two variants in the source reports are practically unreachable:
   - the nested one, where a child splits later in the window (F181);
   - the livelock, where a split ends up with zero listed children and is rejected every time. J is node 0 and its first 4,999 children always survive the cut.

5. Interaction with the 4 MB body cap (v2routes.js:15, REPORT_BODY_MAX). One node costs roughly len(seed) + len(parent) + 40 bytes. At campaign-1 depths (longest seed 383 chars), a 5,000-node report is about 4 MB, so a deep J would get HTTP 413 instead. The client treats 413 as non-transient (volunteer.py:92, 915-923) and moves every report in that batch to rejected/. J then waits for its lease to expire and repeats the same result: a stall and poison job, not silent loss. A shallow J has short seeds and fits under 4 MB, and a shallow J is exactly the kind with the deepest remaining search and so the largest stacks. The silent-loss path therefore remains open where it matters most.

6. Reachability. It was not reached in campaign #1. Snapshot: max 273 children per parent, max 268 nodes per report, max job depth 128 tokens, longest seed 383 chars, so about 18x headroom. The worker's queue is unbounded, and the server's own REMAINING_MAX = 20000 (jobs.js:34) shows that splits above 5,000 were anticipated. A campaign with more holes or a bigger grid (deeper trees, larger branching) can realistically approach thousands of stack entries.

7. Test gap. fake_worker.py:171-179 prints only 1-4 REMAINING lines. The gate test only checks that the server refuses more than NODES_MAX nodes. DESIGN.md §7.5 (line 265) states the 5,000 cap but says nothing about what the client does above it.

Coverage: I looked for guards elsewhere and found none. run_worker (volunteer.py:728-834) does not cap REMAINING, and MAX_LINE = 20000 chars per line is far from binding.

**5. Consequences the reviewers did not mention.**
- **REMAINING_MAX = 20000 (jobs.js:34) is dead.** It appears only in the LIMITS export. The legacy summary+remaining shape also passes through `raw.length > NODES_MAX`, so the server cannot accept a split with 5,000 or more REMAINING lines in any shape.
- **So fixing only the client is not enough.** If the client stops cutting, the same split becomes a permanent 400 loop instead: one full window (1,800 s) burned per cycle, and the exit never completes. That is loud, but it is a stall. The server cap has to change, or split nodes must be demotable.
- **The byte cap can hit first.** REPORT_BODY_MAX is 4 MB (v2routes.js:15). Seeds reached 383 characters at depth 128, and each node carries both its seed and its parent's seed, so a report of a few thousand nodes on a deeper grid can exceed 4 MB.
- **A 413 rejects the whole batch.** A 413 is not transient, so volunteer.py:915-923 calls reject() on every report in the batch, including other workers' good reports. The server never saw them, so those jobs stay leased until the lease expires (3,600 s) and are then re-run. The oversized one repeats forever. This wastes work but loses nothing.

**6. How likely it is next time.**
- The trigger is a pending DFS stack of about 5,000 entries at one split. The worker's stack has no bound (backsearch.c:1179-1184).
- A class with roughly 18x the branching times depth of 5x5 with 3 holes would get there, for example a much larger grid or more holes.
- Nothing warns as it approaches: g_q_peak is printed only in the human-readable output (backsearch.c:5837), not in SUMMARY.
- DESIGN §7.2 assumes "a report at most a few hundred nodes", and no test covers the cap. fake_worker prints 1-4 REMAINING lines, and v2_gates only checks that 5,001 nodes are refused.

**Rating.** If it triggers, the result is a wrong exhaustive maximum that passes the audit. That meets the critical definition, so I keep critical and flag it as latent. It should be fixed before any campaign on a larger class. No dynamic run is needed.
