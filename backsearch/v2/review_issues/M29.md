# M29: Batch reports use job rows read before the transaction: the same job twice in one batch is finished twice, or reopened right after finishing

verdict CONFIRMED, severity medium, category bug
locations: jobs.js:844 (reports(): prepareReport for all elements before BEGIN IMMEDIATE); applyReport; finishJob; reopenJob (no status guard)

## Summary
reports() runs prepareReport, which reads the job row, for every element before applying any of them, and applyReport decides finished/mine from that stale row. A second valid element for the same job_id is treated as a first report again: finishJob runs twice and inserts a second child set. If the second element fails validation, it reopens the job the first element just finished, because reopenJob has no status guard.

## Source report F79 (server-scheduling)
**Batch reports use a job snapshot taken before the transaction: the same job twice in one batch is finished twice (second child set), or reopened just after finishing** at /Users/george/PathologyRecords/server/lib/jobs.js:844

*summary*: reports() runs prepareReport, which reads the job row, for every element before applying any of them. applyReport then decides finished/mine from that stale snapshot. A second element for the same job re-runs finishJob and inserts another set of children, or, if it fails validation, reopens a job the first element just finished (reopenJob has no status guard).

*failure_scenario*: A client runs J in two slots (which the steal-back behaviour produces) and both copies finish inside one 10-s batch window. Element 1 turns J from leased to split and inserts children set A. Element 2 still sees 'leased', so it calls finishJob again and inserts children set B under J. The audit then requires A and B, the rest of J's subtree is searched twice, and the published states/jobs totals count it twice. If element 2 has a tree/level error instead, giveBack reopens J and it is re-run from scratch. The snapshot has 15 batches that carried the same job twice; they were harmless only because the job was already finished before those batches arrived.

*evidence*: 844: `const preps = body.reports.map(el => prepareReport(el, c, hashes));` 737: `const job = q.jobById.get(el.job_id);` 746: `const finished = job.status === 'done' || job.status === 'split';` 750: `const giveBack = () => { if (mine && !finished) q.reopenJob.run(job.id); };` 284: `reopenJob: ... WHERE id = ?` (no status condition). Snapshot: `select job_id, client_token, received_at ... having count(*)>1` returns 15 groups, e.g. job 19080 'dup,dup'.

*suggested_fix*: Inside applyReport, re-read the row (q.jobById.get(job.id)) before deciding finished/mine, or dedupe job_ids within a batch. Give reopenJob `AND status IN ('open','leased')` for the giveBack path.

## Verifier (CONFIRMED, medium, refuted=False)
I read the code and checked it against the snapshot. The issue holds as described.

How the code behaves:
- reports() (jobs.js:844) runs `body.reports.map(el => prepareReport(el, c, hashes))` before txn().
- prepareReport reads `const job = q.jobById.get(el.job_id)` (737) and carries that row into the report.
- applyReport then works only from that stale `p.job`:
  - `finished = job.status === 'done' || job.status === 'split'` (746)
  - `mine = job.client_token === cl.token || job.status === 'open'` (749)
  - `giveBack = () => { if (mine && !finished) q.reopenJob.run(job.id); }` (750)
- reopenJob (284) is `UPDATE jobs SET status='open', client_token=NULL, lease_until=NULL, leased_at=NULL WHERE id = ?`, with no status guard.
- finishJob (287) is an unconditional UPDATE, and insNode (790) inserts the child set with parent = job.id.
- Nothing dedupes job_ids inside one batch, on either side. The server does not check, and the client just appends to self.pending (volunteer.py:885) and posts the whole list (913).

So if a batch carries J twice while J is still leased, both elements see 'leased' and both are applied as first reports. Node runs the whole request synchronously, so separate requests never interleave. Only duplicates inside one batch are affected, which matches the claim.

Can this happen in practice? Yes. The snapshot shows one client running the same job in several slots at the end of campaign #1, through steal/re-lease ping-pong:
- Job 19080 got 13 reports from client 8kuK3U within 170 s. Job 167664 got 6 or more from HuO58q.
- There are 15 (job, client, received_at) groups with two reports in the same batch. All are 'dup,dup', because the job was already finished.
- The closest same-client repeat after a job's first accepted report was 10 s later, i.e. the very next batch (jobs 23410, 166456, 166581, 167538).
- No job has two accepted outcomes, so campaign #1 was not hit. It was one batch window away.

Consequences, traced through auditExit (973-1010: a 'done' node is covered no matter what children it has; a 'split' node needs every child covered):
1. split + split: J gets two child sets, R1 and R2. The audit requires both, so J's remaining subtree is searched about twice. Coverage stays correct.
2. split then done: J ends 'done', but R1's open children are still leased and run. That is wasted work; the audit is unaffected.
3. done then split: J's exhausted result is overwritten and R2's subtree is re-run for nothing.
4. The second element fails validation (bad_tree / bad_level): giveBack reopens a job that was just finished and already has children. J is re-run and adds a third child set. This is unlikely, since both copies use the same binary and seed.
5. In all four cases the extra rows count toward exitSummary's SUM(states) / SUM(elapsed_s), which is what the published proof and contributor stats show. So those totals are inflated.
6. finishJob overwrites J's best and level_code with element 2's values. verifyLater (v2routes.js:153) still attaches element 1's verified_moves to J. If J remains the exit's top row with a different best, v2_finish.js:60 falsely refuses ("SOLVER SAYS"). This is recoverable.

No valid level is lost and the best is never wrong: every remaining set is fully covered and the union only grows. Nothing is corrupted beyond repair.

Severity: medium, not critical. The effect is waste bounded by one job's subtree per occurrence, wrong published stats, and a possible false refusal at finish. The trigger is demonstrated reachable while the multi-copy behaviour exists; it becomes latent once the client dedupes its queue.

One more detail: the gate test at v2_gates.test.js:273-274 sends the invalid j3 first and the valid one second. That order happens to work with the stale row, so the harmful order (valid first, then a second valid or invalid copy) is untested.

*fix notes*: 1. At the top of applyReport, re-read the row inside the transaction: `const job = q.jobById.get(p.job.id);`. This is a primary-key lookup, so it costs almost nothing. Derive finished and mine from that row instead of p.job. A repeated job_id then becomes 'dup' automatically, and the fingerprint compare runs against element 1's values.
2. Guard reopenJob with `... WHERE id = ? AND status IN ('open','leased')`. All three current callers intend exactly that: giveBack, the heartbeat release at 514 (myLeases returns only 'leased' rows) and sweepLeases at 1040 (expiredLeases returns only 'leased' rows). So the guard is safe everywhere and makes giveBack harmless even with a stale row.
3. Optionally make finishJob conditional (`AND status IN ('open','leased')`) and skip the child inserts when `.changes === 0`, as defence in depth.
4. Client: in leaser_loop (volunteer.py:508), skip leased jobs whose id is already running or queued. This removes the multi-copy trigger, which the snapshot shows happening a lot at the end of campaign #1.
5. Add the two gate tests from repro_plan.
