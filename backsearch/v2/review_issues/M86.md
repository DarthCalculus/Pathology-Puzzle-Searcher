# M86: SUMMARY elapsed is wall-clock time that includes SIGSTOP pauses and laptop sleep, which inflates the proof's CPU seconds

verdict CONFIRMED, severity low, category bug
locations: backsearch.c:4656 (CLOCK_MONOTONIC elapsed); server sums elapsed_s into cpu_s; v2_finish publishes cpuSeconds

## Summary
run_exit_search measures elapsed time with CLOCK_MONOTONIC, which keeps advancing while the client has SIGSTOPped the worker (Pause) and, on macOS, during sleep. The server sums elapsed_s into cpu_s, and v2_finish publishes that as the proof's cpuSeconds, so paused or sleeping volunteers inflate the published compute.

*summary*: run_exit_search measures elapsed time with CLOCK_MONOTONIC, which advances while the client has SIGSTOP'd the worker (Pause) and, on macOS, during sleep. The server sums elapsed_s into cpu_s, and v2_finish publishes that as cpuSeconds.

*failure_scenario*: A volunteer pauses for 10 h in the middle of a window. On resume the split fires at once, and the job reports elapsed of about 36,000 s for about 1,800 s of CPU. The published CPU-hours and the per-contributor stats are inflated. Campaign #1 was not affected: no job exceeds 1,900 s.

*evidence*: backsearch.c:4652-4653 `clock_gettime(CLOCK_MONOTONIC, &t_now); double el = elapsed_s(t0, t_now);` and SUMMARY "elapsed":%.3f; jobs.js exitSummary `SUM(elapsed_s) AS cpu_s`; v2_finish `cpuSeconds: Math.round(s.cpu_s)`.

*suggested_fix*: Report CPU time (clock_gettime(CLOCK_PROCESS_CPUTIME_ID) or getrusage) as a separate 'cpu' field, sum that instead, and keep wall time only for the split timer.

*expected_gain*: Correct published effort figures.

## Verifier (CONFIRMED, low, refuted=False)
Verified end to end. run_exit_search times with CLOCK_MONOTONIC (backsearch.c:4652-4656, return value elapsed_s(t0, t_now)). That value is exit_elapsed, printed as SUMMARY "elapsed" (backsearch.c ~5845). The macOS clock_gettime(3) man page on this machine says CLOCK_MONOTONIC 'will continue to increment while the system is asleep'. On any OS it keeps counting while the process is SIGSTOPped. The client's Pause SIGSTOPs running workers (volunteer.py:1060-1072) and Resume SIGCONTs them. The server keeps a paused client's leases up to leased_at + lease_s + paused_max_s (jobs.js:517; paused_max_s = 43200 in the snapshot), so one run can absorb up to about 13 h of pause. After resume, el >= split_after at the next check, so the worker splits and reports an elapsed that includes the pause. The server's isNum(s.elapsed, 0, 1e9) (jobs.js:645) accepts it. Node rows store it (jobs.js:783/791), it is summed as cpu_s (jobs.js:299, 306, 309, 870, 877, 1027), and v2_finish.js:52 publishes `cpuSeconds: Math.round(s.cpu_s)`. Example: one 16-worker client paused overnight for 10 h adds about 160 'CPU-hours' (campaign #1 total was 602), and that client's contributor stats inflate by the same amount. Campaign #1 was not affected: no split job exceeds 1824.8 s and no done job exceeds 1797.4 s. The figure is also wall time per worker, so it overstates CPU on oversubscribed or throttled machines. Stats only, no correctness impact. Low.

*fix notes*: Add a "cpu" field to SUMMARY from clock_gettime(CLOCK_PROCESS_CPUTIME_ID); the worker is single-threaded. Have the server validate and store it as cpu_s, and have v2_finish publish that value. Keep the wall-clock elapsed only for the split timer, or move the split timer to CPU time too so a paused window resumes where it left off. This changes SRC_HASH, and the server must accept the new field from old clients (fall back to elapsed when it is missing). The client's job_durations/mean_job_s (used for lease sizing) also include pauses; minor.
