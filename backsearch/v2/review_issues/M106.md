# M106: Cross-job transpositions cost ~0.8% at job roots; an exact dedup on (canonical key, depth, bulk) exists, but a naive shared table would be unsound

verdict PLAUSIBLE, severity low, category algorithmic
locations: backsearch.c:4329 (seed replay / canonicalisation); jobs.js (no dedup of job roots)

## Summary
Replaying every job seed and canonicalising under the exit stabiliser finds 3,107 job roots that duplicate another root, none sharing a parent, costing 4.7 of 597 CPU-hours (0.8%); duplicates below job roots are not visible in the snapshot. Deduping by (canonical key, depth, bulk flag) is exact, because the valid-level set under a node depends only on those. A shared visited table across running jobs or clients would NOT be sound.

## Source report F165 (algo-worker)
**Cross-job transpositions: 0.8% measured at job roots; a sound dedup exists, a naive shared table would be unsound** at /Users/george/Documents/Claude Projects/project45/backsearch/backsearch.c:4329

*summary*: Replaying every job seed and canonicalising under the exit stabiliser, keyed by committed set, player, blocks and masks, holes, depth and bulk flag, finds 3,107 job roots that duplicate another root. None of the pairs share a parent: they are cross-job transpositions. They cost 4.7 of 597 CPU-h (0.8%); duplicates below job roots are not visible in the snapshot. Dedup by (canonical key, depth, bulk) is exact: the valid-level set under a node depends only on those, and an accepted key has a unique depth. A shared visited table across running jobs or clients would NOT be sound.

*failure_scenario*: Now: identical subtrees are explored by 2 or more jobs (exit 1: 2,552; exit 6: 309; exit 0: 211; exit 2: 35). With a naive shared table: job A inserts key K, then is lost (crash, lease expiry, SIGKILL); A's re-run finds K 'already seen' and skips it; K's subtree ends up explored by no reported job, silently losing levels.

*evidence*: backsearch.c:4328-4329 REMAINING prints only paths; canonical_state_key (955-968) is the intrinsic key. Python replay of all 166,733 seeds from jobs_review.db (mirrors build_seed_path_seed, including trailing-run bulk flags): exit 0: 211 dup / 11,451, exit 1: 2,552 / 124,679, exit 2: 35 / 12,878, exit 6: 309 / 13,899, exits 7 and 12: 0.

*suggested_fix*: Print the canonical key (plus depth and bulk flag) on each REMAINING line. When inserting jobs, the server skips a seed whose (exit, key, depth, bulk) already exists as a job; the first copy is a durable job record, so re-runs can never skip it. Any broader shared table may only use entries from server-acknowledged completed jobs.

*expected_gain*: 0.8% measured at root level (a lower bound for cross-job duplication).

## Verifier (PLAUSIBLE, low, refuted=False)
The premise is correct and I reproduced it exactly. The gain is real but small, about 1% of CPU. The idea is sound if built carefully, but it is optional and not a priority before the next campaign.

WHAT I CHECKED IN THE CODE
- backsearch.c:4326-4331: `print_remaining` prints only `REMAINING\t<path>`, with no key.
- backsearch.c:912-925: `state_key` hashes committed_empty, player_pos, nblocks, nholes, the sorted blocks with their masks, and the sorted holes. It does not include depth, wh, seg, adjflags or bulk_walk.
- backsearch.c:955-966: `canonical_state_key` takes the minimum over `g_exit_syms` (`g_state_canon=1` by default).
- backsearch.c:2048-2076: `build_seed_path_seed`. Bulk ends up as 1 only when the path ends in a run of walks over committed cells.
- Why the valid-level set under a node depends only on (canonical key, depth, bulk):
  - The path-dependent prunes are optimality prunes, true of every level below the node:
    - wh (2293-2312): "never in an optimal solution".
    - walk-segment prune (2527-2531).
    - adjflags (613-642): the suffix used for the proof is legal in any descendant level, and equal depth is guaranteed.
  - The only coverage-based prune is bulk_walk: a bulk=1 node skips walks over committed cells because its bulk siblings cover them (2476). So bulk must be part of the dedup key, and a bulk=0 copy covers a bulk=1 copy but not the reverse.
  - Depth is unique for an accepted key. `shortcut_check` rejects any state whose own puzzle has a shorter solution, and in the snapshot no key occurs at more than one depth.
- The in-process dedup (2181-2191) already relies on this same assumption, since it skips second arrivals whatever their wh, seg or adjflags. A server-side merge of job roots is therefore no less sound than the monolithic search.

SNAPSHOT CHECK (my own replay of all 166,733 seeds that are not dup_of copies, mirroring `build_seed_path_seed`, canonicalised under the exit stabiliser, grouped by key, depth and bulk)
- Duplicate job roots per exit: exit 0: 211, exit 1: 2,552, exit 2: 35, exit 6: 309, exits 7 and 12: 0. Total 3,107, in 2,911 groups. No group shares a parent. This matches the report exactly.
  - Exit 1 has a trivial stabiliser, so its 2,552 duplicates are pure transpositions.
  - 2,784 of the 3,107 are bulk=1 copies.
  - 20 keys occur at the same depth with both bulk=0 and bulk=1. For those, only the bulk=1 copy may be skipped.
- Cost: redundant copies cost 5.71 CPU-h of their own. Including the subtrees they split into, they cost 6.45 CPU-h of 597.1 (1.08%). That is a bit more than the reported 4.7 h / 0.8%. By states it is only 0.39% (1.43e8 of 3.64e10).
- Where the cost is: 2,696 of the 3,107 copies ran locally inside a client's tree report (`leased_at` is NULL). They had already run before the server heard of them, but they are cheap: about 0.27 CPU-h in total.
- The part the proposed fix can save: open seeds inserted while a twin job already existed. That is 266 top-level copies with about 6.2 CPU-h of subtree, about 1.0%. So the proposed fix captures nearly all of the measurable gain.
- Duplication below job roots is not measurable from the snapshot. For comparison, earlier single runs in the scratchpad show in-process dedup hits of 3-8% of states checked, and most of those are local transpositions inside one job. My own estimate for total cross-job duplication is 1-3%, not verified.

EVIDENCE FOR EXACTNESS (a free result)
- There are 2,877 twin groups with at least 2 done copies. In every one of them, valid, best and accepted are identical.
- `states` differs in 30 groups. That is the expected "visit sets may differ, valid sets must not" behaviour.
- This is strong empirical support for path-independence, and so for the campaign's exactness invariant. Twin roots are therefore a zero-cost cross-check, and deduping every twin would remove it.

SHARED-TABLE CLAIM: confirmed. Suppose an in-flight job inserts key K into a shared table and is then lost (crash, lease expiry). Its re-run would skip K, and no reported job would ever cover that subtree. Only durable job records, or entries from completed jobs the server has acknowledged, are safe to dedup against.

RISKS IF IMPLEMENTED CARELESSLY
- Using the 64-bit splitmix hash as the cross-job key adds a small collision risk. Use the exact canonical encoding instead.
- Getting the bulk order wrong: merging a bulk=0 seed into a bulk=1 job loses its walk children.
- Merging into dup_of copies or mismatched jobs.
- Coverage and finish checks that do not know about merged nodes.

SIDE NOTE (separate from M106): the in-process dedup itself uses 64-bit hashes. Summing states² / 2^65 over all jobs gives about 0.027 expected false dedup hits across campaign #1, as an upper bound. The chance that one hit a record-length subtree is negligible, but it is not zero.

VERDICT: PLAUSIBLE, low. The idea is correct and exact if built with the safeguards below, but it saves only about 1% for a change to exactness-critical code in the worker, client and server. Do the cross-check first; add the merge later if the next campaign's twin rate turns out higher (for example with more holes).
