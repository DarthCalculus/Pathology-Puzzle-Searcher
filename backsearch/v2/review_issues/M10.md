verdict CONFIRMED, severity low, category docs
locations: DESIGN.md:20 (§1.5); backsearch.c SHALLOW_LG2 / RECENT_LG2 = 22; build_pgo.sh SRC_HASH computation

## Summary
With SHALLOW_LG2 = RECENT_LG2 = 22, eviction starts at about 3.36M inserts. 1,675 of 54,409 reports evicted (up to 179 shallow and 90 recent evictions in one job), and those jobs account for 63% of CPU-hours and 77% of states. Fingerprints still agree because eviction is a deterministic function of the insert sequence. That determinism also depends on compile-time table sizes, which the reviewers say SRC_HASH does not cover. The forced splits justified by the premise also lose dedup sharing: split trees searched about 3.3% more states across 35 natural monolithic-vs-split pairs.

## Verifier (CONFIRMED, low, refuted=False)
The docs premise is false. DESIGN.md:20-22 says jobs are kept small 'so the dedup tables never evict'. In reality two-table dedup is on by default (backsearch.c:79 `g_two_tables = 1`), with SHALLOW_LG2 = RECENT_LG2 = 22 (:884-889), and eviction triggers at 80% full, i.e. 3,355,443 inserts (:1126, :1140).

I re-ran the snapshot numbers from reports.summary_json.summary. They match exactly:
- 1,675 of 54,409 reports have evict_shallow or evict_recent > 0;
- those reports used 390.1 of 621.7 CPU-hours and 28.94 of 37.65 billion states;
- the most evictions in one report were 179 shallow and 90 recent;
- the smallest evicting report had 3,717,975 states.

The fingerprint property still holds in practice. Of 1,033 duplicate jobs, 0 have mismatch > 0. Evicting pairs agree exactly (report 3319 / job 4225: 35,319,535 states; report 12298 / job 8652: 35,703,221), so eviction is deterministic given the insert sequence. Correctness is unaffected, because eviction only causes re-exploration.

The hash gap is real but narrower than claimed:
- SRC_HASH covers only the three source files (build_pgo.sh:41).
- build_pgo.sh hard-codes CFLAGS (:77) and takes no extra -D flags. A volunteer cannot change SHALLOW_LG2 while keeping the hash without editing the unhashed build script, or compiling by hand and copying -DSRC_HASH_STR. A plain manual build gets SRC_HASH_STR "" (backsearch.c:500-501), which the whitelist rejects.
- The HASH_LG2 advice at :851-854 is irrelevant to campaigns: g_visited is allocated only in --no-two-tables mode (:5581-5588).

So a false mismatch needs the owner to deviate on purpose. Even then it only raises an audit flag; the published result is not wrong. I did not re-derive the claimed 3.3% extra states from forced splits (35 pairs). It is plausible, since dedup is per process, and it is waste, not a correctness problem.

*fix notes*: 1. Rewrite DESIGN §1.5. Evictions are routine above about 3.36M inserts: 63% of campaign #1 CPU time, 77% of its states. The (states, valid, best) fingerprint is deterministic because eviction is a deterministic function of the insert sequence and the compiled table sizes.
2. Add a compiled-in config string to --version and to SUMMARY (e.g. "cfg":"S22R22H24"), or fold SHALLOW_LG2/RECENT_LG2 into SRC_HASH_STR in build_pgo.sh.
3. Optional: let the server compare fingerprints only between reports with the same cfg.
4. When sizing the next campaign, weigh the owner's options: keep 1,800 s forced splits (they bound crash loss) or split on demand (saves a few % of states). Either way, stop citing 'no eviction' as the reason.
