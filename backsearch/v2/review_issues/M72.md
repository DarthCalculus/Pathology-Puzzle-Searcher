# M72: v2_finish --publish is not idempotent, and a flag given without a value silently becomes 'true'

verdict CONFIRMED, severity low, category robustness
locations: v2_finish.js:20 (argument parser: a missing value becomes true); addProof (no de-duplication); README ('proofs published only when every exit is clean')

## Summary
Re-running --publish inserts duplicate proof rows (addProof never de-duplicates) and re-submits champions. A flag missing its value evaluates to true: attribution becomes 'true', and campaign or exit becomes Number(true) = 1, which can target the wrong campaign. The README says proofs are published only when every exit is clean, but the tool publishes each clean exit on its own.

## Source report F103 (server-ingest-routes-tools)

*suggested_fix*: Skip an exit that already has a proof of the same class with the same max and campaign id. Error on flags without a value. Drop --attribution or require an explicit value. Align README with the per-exit behaviour.

## Verifier (CONFIRMED, low, refuted=False)
v2_finish.js:20 is `const flag = k => { const i = args.indexOf(k); return i >= 0 ? (args[i + 1] || true) : undefined; };`. A trailing flag with no value evaluates to true. Line 27 is `jobs.getCampaign(Number(flag('--campaign')))`, so `--campaign` with no value gives Number(true) = 1, which is campaign #1. Line 31 does the same for `--exit`, giving exit 1. Line 48 turns a bare trailing `--attribution` into the string 'true'. It is slightly worse than reported: the parser takes the next token even when it is another flag. `--attribution --publish` stores attribution '--publish' and still publishes, because publish is read separately via args.includes at line 21. `--campaign --publish` gives NaN and a harmless 'no campaign'.
Idempotency: addProof (db.js:654-681) checks only the field shapes and whether a stored verified level is longer than the claimed maximum ('contradicted'). It then INSERTs unconditionally. The proofs table has no UNIQUE constraint; the only UNIQUE in db.js is levels.data. Re-running --publish therefore inserts one more stored proof per clean exit. A re-run is realistic. When any exit fails (not clean, not re-solved yet, champion refused), `failed++` makes the tool exit 1. The natural response is to run it again without --exit once the problem is fixed, and that duplicates every exit that already succeeded. The two issues also combine: in the next campaign, `--publish --campaign` with the id forgotten re-publishes all six campaign #1 exits, because they are still clean.
Damage is limited and recoverable. derivedProofs (db.js:525-529) keeps only the newest proof per exit, so the class-level proof's totals and attribution are not double counted. Duplicate stored proofs just show twice on /api/proofs and can be removed with deleteProof. A re-submitted champion comes back as 'already_verified' (pipeline.js:194) and is not stored again. The README point is mostly wording: v2/README.md:59-60 says 'A proof is published only when every exit's audit is clean'. The per-exit proofs are published one exit at a time, but the headline derived proof only appears once every canonical exit has one (db.js:531-533), so the statement holds for the class proof. Low severity is correct.

*fix notes*: Make flag() fail (exit 2) when the next token is missing or starts with '--'. Validate that --campaign and --exit are integers and that the campaign exists. Before addProof, skip an exit that already has a stored proof with the same rows/cols/exit_cell/max_blocks/max_holes/max_moves and a note naming the same campaign. Better, add a campaign_id column, or a UNIQUE index on (class, campaign). Print 'already published #id' in that case. Also skip processSubmission when addProof refused. Reword the README: each exit's proof is published once that exit is clean, and the class proof appears when all exits have one.
