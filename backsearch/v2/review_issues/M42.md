# M42: shallow_evict can free almost nothing: an eviction on every insert, and an endless probe loop if the table fills

verdict CONFIRMED, severity low, category robustness
locations: backsearch.c:1133 (shallow_evict keeps entries with depth <= median); insert `while (key != 0)` probe

## Summary
shallow_evict keeps every entry with depth <= the median depth. When one depth level holds a large share of the entries, it keeps nearly all of them, and the count stays above the 80% trigger. Every later insert then runs another full 4M-slot rehash plus a 64 MB calloc, making the job 100-1000x slower. If inserts at depth <= the threshold keep coming, the table can reach 100%, and the insert's `while (key != 0)` probe never ends. Normally the split timer ends such a job first.

## Source report F7 (worker-dfs-split)
**shallow_evict can free almost nothing: an eviction on every insert, and an unbounded probe loop if the table ever fills** at /Users/george/Documents/Claude Projects/project45/backsearch/backsearch.c:1133

*summary*: shallow_evict keeps every entry with depth <= the median depth. When one depth level holds a large share of the entries, it can keep nearly all of them. The count then stays above the 80% trigger, and every later insert runs another full 4M-slot rehash plus a 64 MB calloc. If inserts at depth <= the threshold keep coming, the table can reach 100%, and the insert's `while (key != 0)` probe never ends. The split timer normally ends such a job first, but at 100-1000x slower speed.

*failure_scenario*: In the heaviest snapshot job (174M states) there were 179 shallow evictions against 90 recent ones. Each shallow eviction therefore freed only about 25% (it kept about 75% of the 3.36M trigger count), already near the no-progress point. In a larger campaign job whose median depth holds more than about half the retained entries, each insert costs about 10-50 ms of eviction. The job crawls until the next 1024-expansion split check. If split_after is long, or checks are sparse, it can end up spinning forever in the insert loop.

*evidence*: 1011-1017: `long long target = g_shallow_count / 2; ... if (acc >= target) { thresh = d; break; }`; 1024: `if (g_shallow[i].depth > thresh) continue;` (keeps all of depth == thresh); 1126-1127: `if (g_shallow_count * 5 >= (long long)SHALLOW_CAP * 4) { shallow_evict(); }`; 1133: `while (stab2[j].key != 0) j = (j + 1) & SHALLOW_MASK;`. Snapshot: `max(evict_shallow)=179, max(evict_recent)=90` in reports.

*suggested_fix*: If the survivors would exceed about 60% of capacity, also evict part of the depth == thresh bucket (e.g. by one key bit), or use thresh-1. Bound the insert probe (if the table is full, skip the insert; skipping is always safe for dedup).

*expected_gain*: Removes a performance cliff that could turn into a hang on larger campaigns.

## Verifier (CONFIRMED, low, refuted=False)
backsearch.c:1004-1033: thresh is the first depth where the cumulative histogram reaches count/2, and every entry with depth <= thresh survives. kept can therefore be as large as count/2 + hist[thresh]. At the fixed point, where the retained set's median bucket stays the same between evictions, each eviction frees only 0.8C - K, which can be close to 0 when one depth bucket holds about 0.4C (1.68M) entries. That is plausible, since jobs hold 1e8+ states over about 100 depths. Once kept >= 80% of the cap, the trigger at 1126 (`g_shallow_count * 5 >= SHALLOW_CAP * 4`) fires on every insert, and each firing is two 4M-slot scans, a 64 MB calloc and a rehash (about 20-50 ms). The insert probe at 1133 (`while (stab2[j].key != 0)`) has no bound, unlike the lookup loop at 1097. Snapshot check: the largest evict_shallow/evict_recent ratio in any report is 179/90 = 1.99 (then 153/80 and 45/28). Recent eviction frees about 50% and both tables receive about the same inserts, so shallow evictions freed about 25% of entries each (kept about 75%). Campaign #1 was far from the cliff but not trivially far. Refutations: (1) The endless loop is effectively unreachable in campaign configuration. The table can grow from 80% to 100% only through zero-progress evictions (about 840k inserts at ~50 ms each, roughly 12 hours), while the split timer is checked every 1024 DFS pops (4646-4650) and fires at split_after (1800 s). That gives at most a few minutes of overrun, and only monolithic --split-after 0 runs could spin forever. (2) Eviction is always safe for dedup, so there is no correctness impact, and the split still produces a valid REMAINING. The real risk for a larger next campaign is a performance cliff that wastes up to one job window per affected job. Low.

*fix notes*: In shallow_evict, if cum(thresh) > 0.6*count, use thresh-1, or split the thresh bucket by a key bit so that kept <= ~55%. Bound the insert probe: if no empty slot is found within SHALLOW_CAP (or a small constant) probes, skip the insert, which is always sound. Do the same for recent_evict and the recent insert at 1141 for symmetry. Add the per-eviction freed fraction (or a minimum) to SUMMARY so that ratios near 1.0 show up in the job DB. Test: a unit harness that feeds 4M keys all at the same depth and asserts that inserts stay O(1) amortised and never hang.
