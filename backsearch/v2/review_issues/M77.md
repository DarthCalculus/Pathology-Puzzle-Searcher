# M77: The retired chunk-tracker write endpoints are still public, and /api/chunks/report multiplies solver work, starving site solves and v2 verification

verdict CONFIRMED, severity medium, category security
locations: server.js:245 (POST /api/chunks/signup, signup-any, release, report still routed); reportChunks (stores any level string; re-solves every NULL-verified level of the reporter, 30 s each, serially); solver semaphore (unbounded FIFO shared with /api/submit, /api/solve, v2 verifyLater); updates.json says the tracker is retired

## Summary
updates.json says the chunk tracker is retired, but its POST endpoints are still live. reportChunks stores any `level` string on a chunk and then re-solves every level of that reporter whose verified_moves is NULL, at up to 30 s each and one after another. A level that times out stays NULL, so each new report queues all of them again. The solver semaphore's unbounded FIFO is shared with /api/submit, /api/solve and v2 verifyLater, so anyone can starve the public site's solves and champion verification.

## Source report F110 (server-web)
**Retired chunk-tracker write endpoints are still public, and /api/chunks/report multiplies solver work, starving site solves and v2 champion verification** at /Users/george/PathologyRecords/server/server.js:245

*summary*: updates.json says the chunk tracker is retired, but POST /api/chunks/signup, signup-any, release and report are still live. reportChunks stores any `level` string on a chunk. After every report, the server re-solves every level of that reporter whose verified_moves is NULL, at 30 s each and one after another. A level that times out stays NULL, so each new report re-queues all of them. The solver semaphore has an unbounded FIFO queue shared with /api/submit, /api/solve and the v2 verifyLater.

*failure_scenario*: The chunk plan and its jobs counts are public (GET /api/chunks/plan). One IP posts up to 30 reports/min (300/h, the 'write' bucket). Each report marks the plan's chunks done under one name, with hard 64-cell levels that time out. Every report starts a chain of about 48 x 30 s solver runs, and the chains re-run because verified_moves is never set. The waiters queue grows without bound. Public submissions and solves then wait hours, and a v2 new-best verification (verifyLater) waits behind the backlog, so hunt, collective and campaigns never show the check mark. The same report can also overwrite reporter and level_code on done chunks when it repeats best_moves.

*evidence*: server.js:236-249 `if (req.method === 'POST' && p === '/api/chunks/report') { ... r = reportChunks(payload.text); ... (async () => { for (const c of db.prepare(`SELECT id, best_moves, level_code FROM chunks WHERE reporter = ? AND status = 'done' AND level_code IS NOT NULL AND verified_moves IS NULL`).all(r.name)) { try { const m = await measureLevel(c.level_code, { seconds: 30 }); if (m.ok) setChunkVerified(c.id, m.moves); } catch {} } })();`
db.js:869-871 `else { setDone.run(best, c.level || null, name, ...`
solver.js:14-17 `const waiters = []; function acquire() { if (running < MAX_CONCURRENT) {...} return new Promise(res => waiters.push(res)); }`
updates.json:24 `The old run_chunks.py no longer works with this server.`

*suggested_fix*: Remove or 410 the /api/chunks POST routes, and the GET routes too if nothing uses them, now that the tracker is retired. At minimum, set verified_moves to a sentinel after a failed attempt so a level is tried once, and cap the solver waiters queue. Give v2 verifyLater its own priority slot so public traffic cannot delay it.

*expected_gain*: Closes an unauthenticated amplification path against the 3-slot solver pool on the public box.

## Verifier (CONFIRMED, medium, refuted=False)
I read the cited code and it holds up. I could not refute it; it depends on one fact about the live database, noted below.

1. The routes are still live. server.js:217-251 routes POST /api/chunks/signup, /signup-any, /release and /report. The only guard is the per-IP 'write' bucket (server.js:24: 30/min, 300/h, shared with improve/claim). No auth, no feature flag. updates.json:22-24 says the tracker is retired and run_chunks.py no longer works. Nothing legitimate uses these POSTs: run_chunks.py only GETs /api/chunks/plan (run_chunks.py:16,28), no public page calls /api/chunks, and reports were always pasted by hand. Removing the POST routes costs nothing.

2. How one report multiplies solver work. Every successful /api/chunks/report starts a new async chain (server.js:245-249):
`for (const c of db.prepare(... WHERE reporter = ? AND status = 'done' AND level_code IS NOT NULL AND verified_moves IS NULL).all(r.name)) { try { const m = await measureLevel(c.level_code, { seconds: 30 }); if (m.ok) setChunkVerified(c.id, m.moves); } catch {} }`
- Nothing marks a level as tried: if the solve is too_complex or unsolvable, verified_moves stays NULL.
- Nothing stops chains from overlapping: every report re-queues every unverified chunk under that name, even while earlier chains are still running.
- measureLevel (pipeline.js:235-250) takes any parseable level up to 64 cells (level.js:13 MAX_AREA = 64) and runs solver6 at 30 s in a fresh process. solver6's memo lives inside the process (solver6.c:1511, TLS calloc), so nothing is cached between calls.

3. What an attacker can write. reportChunks (db.js:850-882) checks only three things: the chunk id, that the exit matches, and that the job count matches n_jobs. All three are public via GET /api/chunks/plan and GET /api/chunks. Beyond that:
- `best` can be any integer.
- `c.level` can be any string.
- A chunk that is not done is simply marked done.
- A done chunk is overwritten (reporter, level_code, stats) when the report repeats its best_moves.

4. The shared queue. solver.js:12-22 caps solves at 3 concurrent (MAX_CONCURRENT), but the `waiters` array is an unbounded FIFO. /api/solve, /api/submit and v2 verifyLater (v2routes.js:62-72, VERIFY_SECONDS = 30) all wait in it. Queued /api/solve work is never cancelled when the HTTP client goes away.

5. Scale. One IP can start 300 chains per hour, each re-solving K levels at up to 30 s (less if solver6 gives up on memory first; SOLVER_GIB is 0.5). The pool delivers 3 solver-hours per hour, so even K = 2 saturates it from a single IP. The number of live chains then grows roughly linearly, and so does the queueing delay for public /api/solve and /api/submit and for v2 new-best checks. For comparison, /api/solve on its own allows only 60 x 30 s per IP per hour, so this path amplifies a single IP by about K x 5.

6. Precondition (not checkable read-only). The attack needs the live chunk plan to still exist, with at least one chunk that can end up with verified_moves NULL. setDone does not reset verified_moves, so chunks already verified cannot be re-armed. Candidates:
- chunks not done when the tracker was retired;
- chunks 11 and 19, which updates.json:29 says came back without a level, so the verify loop skipped them and verified_moves is still NULL;
- chunks whose level failed its first check.

No tool clears the plan except set_chunk_plan.js, which replaces it, so the plan very likely still exists. My local data/records.db has no chunks table, so it says nothing about the live box.

7. Impact on the next campaign is limited. v2 verified_moves only controls the check mark on hunt, collective and campaigns. tools/v2_finish.js:57-60 publishes even when the champion has not been re-solved yet ('not re-solved yet'). It runs as its own process with its own solver semaphore, so the backlog cannot block or corrupt a proof. There is no box-level harm: solver concurrency and memory stay within the designed caps. The damage is availability: the public site's solve/submit and the v2 check marks can be delayed without limit, by one IP.

8. Correction to the source report: it says each report starts 'about 48' re-solves. The real multiplier is only the number of chunks with verified_moves NULL, which is probably smaller. The attack still works from one IP.

Related, low:
- A report that repeats best_moves on an already-verified chunk swaps in its own level_code and reporter but keeps the old verified_moves. So GET /api/chunks would show a check mark next to a level that was never verified. No page renders it any more.
- In the chain, the SELECT runs outside the try and the IIFE has no .catch. server.js has no process.on('unhandledRejection'), so a DB error there would take the whole Node process down. That is unlikely under WAL reads.

Severity: medium. This is not public-site compromise, but it is an unauthenticated, single-IP way to starve the public solver endpoints and the v2 check marks; published results and campaign data are not at risk.

*fix notes*: Before the next campaign:
1. Remove the four POST /api/chunks/* routes, or make them return 410 Gone (server.js:217-251). Keep GET /api/chunks and /api/chunks/plan read-only, or drop them too, since no public page uses them.
2. If any re-verify loop stays:
   - write a sentinel after a failed attempt (e.g. verified_moves = -1, or a verify_attempted_at column) so each level is tried once;
   - verify only the chunk ids this report changed, not every chunk under the name;
   - keep one in-flight verify per chunk (a Set);
   - wrap the whole IIFE body in try/catch, or add .catch.
3. solver.js acquire():
   - cap waiters.length (e.g. 50) and answer 503 with Retry-After when full;
   - add a priority lane, or one reserved slot, for v2 verifyLater and processSubmission, so public /api/solve traffic cannot delay champion checks;
   - optionally drop a queued /api/solve waiter when its request socket closes.
4. Add process.on('unhandledRejection') logging in server.js, so a stray async rejection cannot kill the site.
5. Test: extend server/test with a case that posts two chunk reports carrying a level that times out (stub measureLevel to count calls and return too_complex). Assert the solve count stays at 1 per chunk, and that a full waiters queue returns 503.
