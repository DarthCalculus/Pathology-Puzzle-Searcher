# M8: Every worker process memsets 160 MB of freshly calloc'd dedup tables, which dominates trivial runs

verdict CONFIRMED, severity low, category performance
locations: backsearch.c:4343-4344 (calloc of g_shallow 4M x 16 B and g_recent 4M x 24 B in main; memset at the start of run_exit_search)

## Summary
main() callocs both dedup tables (64 MB + 96 MB), and run_exit_search memsets them before t0, which faults in and zeroes all 160 MB. A campaign run is one exit per process, so every run pays tens of ms and 160 MB resident even when it inserts only a handful of states. About 57% of runs (94k) search for under 10 ms, so this overhead is estimated at 5-10x their search time, and it never shows up in elapsed_s. DESIGN §7 notes trivial jobs run at only about 20 per second per worker.

*suggested_fix*: Skip the memset on the first exit, when the tables come straight from calloc (a static 'fresh' flag), or free and re-calloc them between exits.

*expected_gain*: Faster trivial runs (the most common kind) and less resident memory per worker.

## Verifier (CONFIRMED, low, refuted=False)
The premise matches the code. The gain is real but smaller than the merged "medium" suggests, so I rate it low.

Code facts (backsearch.c):
- Lines 5581-5583 in main: `g_shallow = calloc(SHALLOW_CAP, sizeof *g_shallow); g_recent = calloc(RECENT_CAP, sizeof *g_recent);`. SHALLOW_LG2 and RECENT_LG2 are both 22 (lines 884-893). ShallowSlot is {uint64,int32}, which pads to 16 B; RecentSlot is 24 B. That is 64 MiB + 96 MiB = 160 MiB. Both glibc and macOS serve allocations this large with fresh zero-fill-on-demand mappings.
- Lines 4343-4345 in run_exit_search: `if (g_two_tables) { memset(g_shallow, 0, SHALLOW_CAP * sizeof *g_shallow); memset(g_recent, 0, RECENT_CAP * sizeof *g_recent);`. This writes every page, so the process pays about 10k faults with 16 KiB pages (Apple Silicon) or about 41k with 4 KiB pages (x86 Linux), plus the kernel zero-fill, a second zeroing by memset, and teardown of 160 MiB at exit.
- The t0 timer starts at lines 4512-4513, after both the memset and the seed replay, so elapsed_s never shows this cost.
- A campaign run is one `--exit E` per process. volunteer.py:743 does one subprocess.Popen per seed run, and absorb probes are processes too.
- The --no-two-tables path (g_visited, 256 MiB, lines 4352/5586) has the same pattern.

Exactness risk: none. The only writers to the dedup tables are try_successor_x (2166), bulk_generate (2375) and run_exit_search itself (4428, 4489). All of them run after the memset. Nothing on the campaign path inserts earlier: enumerate_tasks, the --task-id path and --print-seed-key do not touch the tables. Tables from calloc are guaranteed zero, so skipping the first memset leaves dedup behaviour, and therefore the visit and valid-level sets, bit-identical.

Gain, my estimate (not measured):
- Per process: about 20-60 ms. That is page faults plus kernel zeroing (about 15-40 ms), the redundant user memset (about 3-15 ms) and exit teardown (about 5-10 ms). DESIGN §7's "~20/s (process spawn)" means about 50 ms per trivial job, so this is plausibly half or more of a trivial run's wall time. Removing it could make trivial runs roughly 1.5-3x faster.
- Campaign #1 snapshot: 167,766 nodes. 94,257 had elapsed under 10 ms and 67,002 checked fewer than 10 states. But 147,733 nodes with fewer than 30k states hold only 10.6 of 602 CPU-hours; the 20,033 nodes with at least 30k states hold 591 CPU-hours.
- Aggregate saving: about 150-200k processes x ~40 ms ≈ 1.5-2.5 CPU-hours, about 0.3% of the campaign. Campaign wall-clock barely moves.
- Window and absorb budgets are not really limited by this. A window of a few hundred trivial nodes spends about 10-20 s of an 1800 s window on overhead. The absorb budget (120 s) is spent mostly on 10 s probes that do not exhaust, not on trivial ones.

Memory claims are overstated:
- The long jobs that carry 98% of the CPU insert at least 30k keys at random slots. With 1024 slots per 16 KiB page in the shallow table (682 in the recent table), they touch essentially every page anyway.
- So steady-state peak RSS (16 workers x 160 MB ≈ 2.5 GB for these tables) does not change. Only the transient RSS and memory-bandwidth bursts during runs of trivial jobs go down.

Why do it anyway: it is a 3-line change with zero exactness risk and a real latency gain on the most common kind of run. If the next campaign (more holes or a bigger grid) recompiles with larger SHALLOW_LG2/RECENT_LG2, the fixed cost scales linearly. At LG2=24 it would be about 640 MiB and roughly 100-250 ms per trivial process. So CONFIRMED as worth doing before the next campaign, at low severity and low priority.

Other claims in the reports:
- F161's "roughly 2x throughput on trivial jobs" is plausible.
- F176's "50-100 ms per run" is at the high end of plausible.
- "5-10x their search time" is literally true for runs under 10 ms, but the right baseline is total per-process wall time, which includes about 5-15 ms of spawn and dyld.

*fix notes*: Minimal fix in /Users/george/Documents/Claude Projects/project45/backsearch/backsearch.c:
- Add `static int g_dedup_dirty = 0;`.
- In run_exit_search (4343-4352) and run_estimate (4065-4070), wrap the memsets in `if (g_dedup_dirty) { ...memset... }` and set `g_dedup_dirty = 1` right after. Keep the counter resets (g_shallow_count, g_recent_count, g_recent_clock, eviction counters) unconditional.
- Alternatively, free and re-calloc the tables at the start of each exit after the first.
- shallow_evict and recent_evict already calloc fresh tables and swap them in, so they need no change.
- This covers both two-table and --no-two-tables (g_visited) modes.
Tests:
- Run test_split_exact and one ASan run on a few roots to confirm identical SUMMARY fingerprints (states, valid, best).
- Run `/usr/bin/time -l` on a trivial seed to confirm lower wall time and RSS.
Optional, larger change: F161's grow-on-demand tables, or F176's persistent multi-seed worker with generation-stamped tables. The persistent worker would also remove the ~5-15 ms spawn cost per trivial run. Both are more invasive; do not do them just before a campaign. Growing tables would only ever forget entries, which is exactness-safe, but it changes visit sets and eviction timing.
Stats: moving t0 before the table reset would make elapsed_s include this overhead. That is cosmetic and not needed once the memset is gone.
