# M50: An exception in a slot or sender thread kills it silently; a dead slot keeps its job in running/holding, so its lease is renewed forever

verdict CONFIRMED, severity medium, category robustness
locations: volunteer.py:731 (slot_loop / sender_loop have no exception guard); worker_argv_base() sys.exit(2) when the binary is missing, called inside run_worker; outbox_write() OSError on a full disk; log() on a broken stderr pipe

## Summary
A slot thread that dies after run_window has set slot.job leaves that id in every heartbeat's running and holding lists. The server extends the lease indefinitely, and only the end-game steal (one running job per request) can take it back. A dead sender thread stops all report delivery while heartbeats continue. Concrete triggers: a missing binary (sys.exit inside run_worker), a full disk and a broken stderr pipe.

## Source report F49 (client-core)
**An exception in a slot or sender thread kills it silently; a dead slot keeps its job in `running`/`holding`, so the lease is renewed forever** at /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py:731

*summary*: slot_loop and sender_loop have no exception guard.
- A slot thread that dies after run_window has set slot.job leaves that id in every heartbeat's running/holding. The server extends the lease indefinitely, and only the end-game steal (one running job per request) can take it.
- A dead sender stops all report delivery while heartbeats continue.

Concrete raisers: worker_argv_base() calls sys.exit(2) when the binary is missing, and it runs inside run_worker; outbox_write() raises OSError on a full disk; log() raises on a broken stderr pipe.

*failure_scenario*: (a) The volunteer rebuilds or moves the binary while the client runs (`./build_pgo.sh` re-links it in place). Any slot starting a run in that gap raises SystemExit in its thread. The thread dies with slot.job set, and the UI keeps showing it running. The job is held forever. If every slot hits it, the client becomes a heartbeating zombie holding up to 3 x workers + 200 jobs.
(b) The server is unreachable and the disk is full. outbox_write raises in the sender thread, so the batch is lost and the sender is dead. Later reports pile up in memory unsent while their jobs are released by omission and re-run by others. In the main thread's flush_outbox the same error crashes the client after it has already removed the file (os.remove at line 1001).
(c) `volunteer.py 2>&1 | tee log` loses its reader. The next log() raises BrokenPipeError and kills whichever thread was logging.

*evidence*: volunteer.py 274-277: if path is None: sys.stderr.write("Worker binary not found..."); sys.exit(2)
volunteer.py 731: argv = self.worker_argv(job, seed, split_after)   # -> worker_argv_base(), no try
volunteer.py 577-583: with self.lock: slot.job = job ...
volunteer.py 1162: running = [s.job["id"] for s in self.slots if s.job]
volunteer.py 915-916: if e.transient or e.status == 401: path = self.outbox_write(reports, attempts=1)   # OSError propagates
volunteer.py 53: sys.stderr.write(line + "\n")
volunteer.py 533-562 / 887-897: loops without try/except; daemon threads, no excepthook.

*suggested_fix*: Wrap each slot_loop iteration and sender_loop in try/except BaseException that:
- logs the traceback;
- clears slot.job and slot.proc (so the job leaves holding and is released);
- kills any live worker;
- continues after a backoff.

Also:
- After startup, make worker_argv_base raise a normal exception instead of calling sys.exit.
- Make log() swallow OSError.
- Catch OSError around outbox_write and keep the batch in pending for retry.
- Remove the outbox file only after a successful send.

*expected_gain*: No zombie clients holding jobs that nobody runs; reports keep flowing after local I/O errors.

## Verifier (CONFIRMED, medium, refuted=False)
I checked every claim against the code in /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py and /Users/george/PathologyRecords/server/lib/jobs.js. All of them hold.

1. No exception guard anywhere. slot_loop (533-562) and sender_loop (887-897) have no try/except. The threads are daemon threads started at 1142 and 1365, and nothing sets threading.excepthook. The default hook ignores SystemExit silently and prints other exceptions to stderr only, never to the UI log ring.

2. A slot can die holding a job. run_window sets `slot.job = job` at 578 under the lock, and nothing clears it on an exception: there is no try/finally. The same function logs at 585 and calls run_worker at 592. run_worker calls `argv = self.worker_argv(job, seed, split_after)` at 731, and that calls worker_argv_base(), which runs `sys.exit(2)` at 274-277 when the binary is missing. So:
   - SystemExit kills the slot thread silently with slot.job set, slot.proc None and slot.state 'idle'.
   - A BrokenPipeError or OSError from log() at 585 (stderr to a broken pipe, or to a file on a full disk; stderr is line-buffered, so write and flush raise) does the same, and it happens at the start of every window.
   - An exception at 807 would also leave slot.proc set, with an unread pipe.

3. The job is renewed forever. heartbeat() at 1162-1163 puts every slot with s.job into running and holding. The server's heartbeat (jobs.js 509-519) pushes lease_until to t + lease_s for every job in myLeases, so the job is never re-leased by expiry. It gets two more consequences the finder missed:
   - The drop handler (1207) acts only on slots with s.proc, so a dead slot ignores drop.
   - If the job later becomes 'open' again (for example, a stealer's run is released by omission), the zombie's next heartbeat can re-capture it through the reclaim path (jobs.js 531-532).
   - Recovery paths: the end-game steal (jobs.js 608-629; leasedOthers takes any leased job, and running jobs rank last, one per request), a client restart (its new holding list releases the old ids), or a UI worker-count change (set_workers calls _reconcile_slots, which restarts a dead thread whose next run_window overwrites slot.job).

4. A whole client can become a zombie. lease_want (445-446) counts only live idle threads. If every slot dies, the client stops leasing but keeps heartbeating from the main thread, which logs only on failures. It then holds its running jobs plus its queue (the cap is 3 x workers + 200) until the end game.

5. Sender death:
   - send_pending (899-905) swaps self.pending out before send_batch.
   - On a transient error or 401, send_batch calls outbox_write (916). outbox_write does open, json.dump and os.replace with no guard, so ENOSPC raises. The batch is lost and the sender thread dies.
   - Later reports pile up in self.pending. Their slots cleared slot.job, so the jobs leave holding and the server reopens them after RELEASE_GRACE_S (jobs.js 514). Other clients re-run them: all of this client's work is duplicated until it stops, when run() calls send_pending at 1414.
   - A successful batch whose log() at 948 raises (broken stderr) also kills the sender.

6. flush_outbox crash. flush_outbox runs os.remove(path) at 1001 before send_batch at 1004. On a full disk plus a transient failure, the outbox_write inside send_batch raises out of flush_outbox into run()'s main loop. The main thread crashes, the process exits, and that batch is gone from disk. This costs work only, not coverage: reports decide coverage and the jobs are re-run.

7. Additional consequence: state() calls self.worker_argv_base() at 1348. While the binary is missing, every UI poll raises SystemExit in its ThreadingHTTPServer handler thread, and the panel stops updating.

What limits the severity:
- Every trigger is an unusual local condition:
  - the binary deleted or moved mid-run (a rebuild on macOS goes through ld64's temp file and rename, so there is no gap; GNU ld leaves a short one);
  - stderr redirected to a pipe or a file that later breaks or fills (the docs only use a terminal, where stderr writes do not fail);
  - a full disk during a server outage.
- The result stays correct: coverage is decided by reports, and first-report-wins holds.
- The campaign does not stall permanently, because the end-game steal eventually takes the held jobs.
- The real cost is that the held subtrees are pushed to the tail. The client also looks healthy on the server, and an unnoticed sender death duplicates every report the client makes until it stops.

That fits medium (degraded robustness, noticeable waste), not high. The code evidence settles it, so no dynamic repro is needed.

*fix notes*: Fixes for the next campaign, all in volunteer.py:

1. Guard the slot loop. Wrap each slot_loop iteration (take_job + run_window) in try/except BaseException, or Exception plus SystemExit. On an exception:
   - log the traceback through a log() that cannot raise;
   - under the lock, SIGKILL and reap slot.proc if it is still alive;
   - clear slot.job, slot.proc and slot.phase, and set slot.state to 'idle';
   - count a consecutive failure, which reuses the existing backoff;
   - continue.
   Clearing slot.job releases the job on the next heartbeat.
2. Add a watchdog as a backstop. In the main loop, under the lock, find each non-retired slot whose thread is dead: clear slot.job and slot.proc, then restart the thread the way _reconcile_slots does. Build `running`/`holding` in heartbeat() only from slots whose thread is alive. Install threading.excepthook to put the message in self.ring, so the UI shows it.
3. Resolve the worker path once. Do it at startup (read_version already calls worker_argv_base) and cache the absolute path. Remove sys.exit from the per-run path: in run_worker, a missing or non-executable binary should log and return None, like the existing Popen OSError branch at 746. For J that means "job untouched", slot.job is cleared, and the slot backs off. state() at 1348 should print the cached path.
4. Make log() unable to raise. Wrap sys.stderr.write and flush in try/except (OSError, ValueError), and always append to the ring.
5. Harden the sender:
   - In send_batch, catch OSError from outbox_write and put the reports back at the front of self.pending, so they are retried in memory.
   - Wrap sender_loop's body in try/except Exception with a short sleep.
6. Change flush_outbox's order. Do not os.remove the file before sending. On success, remove it. On a transient failure, rewrite the same path with attempts+1 (outbox_write(..., path=path)) instead of creating a new file and patching "newest". Wrap the whole call in run()'s loop in try/except, so a local I/O error cannot kill the main thread.
