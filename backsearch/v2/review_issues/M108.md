# M108: Client lease-ahead is sized by job count at the recent mean window, so heavy jobs pile up in a FIFO local queue with a window fixed at lease time

verdict CONFIRMED, severity medium, category algorithmic
locations: volunteer.py:450 (lease_want = ceil(300 s / mean window of last 20) per idle worker); local FIFO queue; split_after frozen at lease time

## Summary
The mean over the last 20 windows is dragged down by trivial windows, so a client can lease up to 200 jobs at once, multi-hour subtrees included. Those wait behind the rest of the local FIFO queue, and stealing does not rescue them because the pool is not empty. Each job's split_after is frozen when it is leased, not when it starts, so a job leased during the ramp can later run with the wrong window.

## Source report F172 (algo-collab)

*summary*: lease_want asks for ceil(300 s / mean window) jobs per idle worker. Stealing does not rescue them because the pool is not empty. The split_after of each job is frozen when it is leased, not when it starts.

*failure_scenario*: A 200-job batch at about +29,000 s carried 16.55 CPU-h of work into one client. The critical-path job 66833 (a 28.9 CPU-h subtree) was leased at +30,453 but its 1,800 s window only finished at +35,275. Jobs leased while the pool looked deep ran 1,800 s windows during the final hour while other workers were idle: 130054 split at +38,829 after 1,800 s, and 141048 ran 1,792 s.

*evidence*: volunteer.py:450 `per_worker = max(1, int(math.ceil(self.fparam("lease_ahead_s", 300) / self.mean_job_s())))`; :452 `return max(0, min(cap, idle * per_worker) - queued)`; :530 `return self.queue.popleft()`; :503 `"split_after_s": max(1.0, sa)` (stored per job at lease). jobs.js:584 `const cap = 3 * cl.workers + LEASE_HELD_EXTRA;`. Snapshot: 135 of RtSso4's 585 lease batches had 50 or more jobs, and the largest batches had 200. For 1,800 s windows, (done_at - leased_at - elapsed) averaged 1,021 s: 63 of 383 exceeded 1,800 s, and the maximum was 9,118 s.

*suggested_fix*: Lease one job per idle worker plus a small buffer, for example holding at most about 2 x workers, or size requests by expected work so that shallow jobs count as large. Run the local queue shallowest first. Choose split_after when each window starts, from the value carried by the latest heartbeat or lease response, not when the job was leased.

*expected_gain*: Takes the local-queue wait (about 900 s on average, up to 2.5 h) off critical paths. Fewer steals are needed, because queued work stays in the pool where any idle worker can take it.

## Verifier (CONFIRMED, medium, refuted=False)
The finder's premise matches both the code and the snapshot. This behaviour is exactly what DESIGN §7.4 and §7.6 specify, so it is a design weakness, not an implementation slip.

Code:
- volunteer.py:436-438: `mean_job_s` is the mean over the last 20 `run_window` wall times (appended at :688). A trivial leased job's window lasts about one process spawn.
- :450: `per_worker = max(1, ceil(lease_ahead_s(300)/mean))`, and :451-452 caps the request at `min(200, idle*per_worker) - queued`. `lease_want` only fires when a slot is idle, and a slot is only idle when the queue is empty, because `take_job` pops immediately. So `- queued` is roughly 0, and after a run of trivial windows every refill asks for 200 jobs.
- :503 stores `split_after_s` per job at lease time from the response's `split_after_s`. :569 (`deadline = start + job["split_after_s"]`) uses that frozen value whenever the job actually starts.
- :530 `popleft()` is FIFO. The server returns each batch in the order exit-with-most-open, then deepest first (jobs.js openOfExit ORDER BY depth DESC), so the shallow, heavy jobs sit at the back of a 200-job batch.
- jobs.js:584 caps held jobs at `3*workers + 200` (245 for a 15-worker client), so the server does not bound this either.
- jobs.js:607 `if (need > 0 && jobs.length === 0)` steals only when the pool returns nothing, so queued heavy jobs are not rescued while trivial jobs remain open.
- Heartbeats renew every queued lease (the `holding` list), so a job can sit in a queue indefinitely.

Snapshot (campaign 1 started at 1790200915; times below are seconds after that):
- Lease batches of 50 or more jobs: RtSso4 135/585, HuO58q 55/311, MbObJu 42/230. There were 97 batches of exactly 200 across clients.
- Split jobs with 1800-s windows: (done_at - leased_at - elapsed) averaged 1,033 s, 62 of 371 exceeded 1,800 s, and the maximum was 9,118 s.
- The batch of job 66833 went to HuO58q (15 workers) at +30,453. It held 200 jobs carrying 16.55 CPU-h in root nodes (17.09 h including locally-run children), with 17 splits at 1,800 s. That is about 1.1 h of drain on 15 workers.
- Walking the parent chain of the last exit-1 job (167664, done +40,514, where the main phase ends):
  - Local-queue waits were 573 s (batch 200), 1,745 s (batch 197), 124, 3,022 s (66833, batch 200), 88, 262, 668 and 198, about 6,700 s in total.
  - Pool waits were larger, about 27,700 s. They come from the server's deepest-first ordering, which is a separate issue.
- Frozen-window case: MbObJu started job 141048 at about +37,972 with an 1,800-s window leased while the pool was deep (about 330 open at +37,500). By then the pool was about 81, under 3 x ~79 workers, so the ramp window (120 s) would have applied. It ran 1,792 s. Meanwhile the chain waited until RtSso4 took the job over and split it at +39,549, and the remaining chain then took 965 s more. With a window chosen at start, the job would have split around +38,090, saving roughly 20-25 min of makespan. 146160 shows the same pattern (1,698 s started at +38,099).
- The final 1.5 h had about 20 CPU-h of duplicate reports (outcome 'dup'), partly from churn when other clients took over running jobs.

Gain estimate: 0.5-1.5 h off the 11.25 h main phase (about 5-13%), plus fewer takeovers of running jobs and less duplicate work. CPU-hours stay the same. The absolute tail saving should be similar in a larger campaign.

Exactness risk: none. Window length, local execution order and lease sizing only change when and where splits happen. Coverage is decided by tree reports with REMAINING, and split-anywhere exactness is what test_split_exact checks. jobs.js does not check a report's elapsed time against split_after.

Tradeoff: a hard count cap of about 2 x workers can idle workers for up to `batch_interval_s` (10 s) in phases full of trivial jobs, because the pool does hold many never-examined, 0-s jobs (depth 30-48 jobs in the batch above). Mitigate it with an out-of-cycle lease when the queue drains.

Where the finder's numbers differ slightly from mine (383 vs 371 jobs), it is only a matter of how the window classes were bucketed.

*fix notes*: All of these are cheap and have no exactness risk.

1. Choose the window when it starts:
   - volunteer.py:481: record `resp_sa` in `self.split_after_now` on every lease response.
   - jobs.js heartbeat (~489-560): return `split_after_s_now` computed with the rule at jobs.js:580-582, cached for 5-10 s.
   - volunteer.py:569: use `deadline = start + min(job["split_after_s"], self.split_after_now or inf)`, or simply the current value.

2. Run the local queue shallowest first:
   - Keep `depth` in the queued job dict at :503, from `j.get("depth")` or else the seed's token count. The server already sends it.
   - At :529-530, pop the job with the smallest depth instead of `popleft()`. A linear scan is fine for 245 or fewer entries.

3. Bound the queue depth:
   - Server side, so it also applies to old clients: change jobs.js:46 `LEASE_HELD_EXTRA` from 200 to something like `max(4, workers)`, giving a held cap of about 3-4 x workers.
   - Client side: cap `per_worker` at about 2 at :450, or size requests by work, counting jobs at depth 12 or less as a full window.
   - Let the leaser skip `batch_interval_s` once when the queue is empty and a slot is idle, to avoid idling in trivial phases.

4. Optional, server side: at jobs.js:607, also take queued jobs (never running ones) when `jobs.length < need` and the pool is in ramp mode, not only when zero jobs came back. Take them from the holder with the most queued jobs, whose next heartbeat sends it the `drop` list. That drop path already exists.

5. Update DESIGN §7.4 and §7.6 to say the window is chosen when each window starts and the local queue runs shallowest first.

6. Tests: add a fake_server / test_client.sh case that serves a 200-job batch with one shallow job last and asserts it starts first. A second case flips the server to ramp mid-queue and asserts the next window uses 120 s.
