# N12: [fix-design D4] Fail loud end to end: the worker must never print truncated paths; the client must turn a run with any bad REMAINING line into a failure, never a partial split; MAX_NODES truncation becomes a fold-back.

verdict CONFIRMED, severity medium, category protocol
locations: /Users/george/Documents/Claude Projects/project45/backsearch/backsearch.c:462

## Summary
Every layer currently degrades to 'report a split with fewer children', which is a silent coverage gap. The minimal correct rule is that any node whose remaining work cannot be listed completely and exactly is reported open (untouched), or as a failure. The three limits disagree: PATH_TOK_MAX is 250, the worker's g_seed_path holds 1024 tokens, and the server's SEED_MAX_TOKENS is 1024. None of this fired in campaign #1 (longest seed 128 tokens, at most 273 children per split), but 6x6 or deeper records will reach it.

*summary*: Every layer currently degrades to 'report a split with fewer children', which is a silent coverage gap. The minimal correct rule is that any node whose remaining work cannot be listed completely and exactly is reported open (untouched), or as a failure. The three limits disagree: PATH_TOK_MAX is 250, the worker's g_seed_path holds 1024 tokens, and the server's SEED_MAX_TOKENS is 1024. None of this fired in campaign #1 (longest seed 128 tokens, at most 273 children per split), but 6x6 or deeper records will reach it.

*failure_scenario*: Case 1: a node at depth 260 has its path capped at 250 tokens. Its REMAINING line is then an ancestor path, or a path that cuts a bulk edge mid-run and so names a bulk sibling. The replayed subtree is not the pending one.

Case 2: a seed with more than 250 tokens replays, but its descendants' paths do not extend it. The client counts them as bad_remaining, drops them, and still reports the split with the remaining children (or none).

Case 3: a report with more than 5,000 nodes is cut at nodes[:5000]. The children of a split node beyond the cut are never created, and the audit stays clean.

*suggested_fix*: WORKER
- path_push sets g_path_overflow=1 on failure.
- The DFS loop checks it next to g_dedup_full (4644): SUMMARY status path_overflow, no REMAINING, exit code 4.
- apply_seed_step/build_seed_path_seed reject seeds longer than PATH_TOK_MAX with status bad_seed (finding 7).
- --version prints 'LIMITS\tpath_tok_max=250' so the server and tools can cap SEED_MAX_TOKENS to it.
- Guard PATH_TOK_MAX with #ifndef for the B5 test build.

CLIENT
- In run_worker (782-835): any bad_remaining > 0, or a status other than exhausted/split, returns a failure record (reason, rc), never a split.
- In run_window (604-630): a failed child stays open.
- Replace the truncation at 681 with fold-back: while the report exceeds MAX_NODES or about 2 MB, take the last split node other than J. All its descendants are non-split leaves, because it is the last split. Set it to open (drop its summary, keep its level) and remove its children.
- If J alone still has 5,000 or more children, send a failure 'too_many_remaining' instead of a report.
- Cap batches at about 3.5 MB.

SERVER
- parseTree is already strict.
- Keep NODES_MAX equal to the client's MAX_NODES.
- SEED_MAX_TOKENS = min(1024, worker path_tok_max).

DESIGN §2: 'a worker that cannot print a complete, exact REMAINING set must not print status split'.

CONFLICT: fail-loud and fold-back both yield open nodes, never a split node without children, so they compose with the server's 'split needs at least one child' rule (jobs.js:718).

## Verifier (CONFIRMED, medium, refuted=False)
The mechanisms exist as described. One sub-case is overstated. Nothing like this could have fired in campaign #1, and it cannot fire in a 5x5 or 4x6 successor.

WORKER (confirmed)
- backsearch.c:462-463 `static inline int path_push(BState *s, int D, int V) { if (s->plen >= PATH_TOK_MAX) return 0;` with `#define PATH_TOK_MAX 250` (227).
- The return value is ignored at every call site: 1961, 1987, 2005 and 2030 (apply_seed_step), 2250 (`if (g_emit_D >= 0) path_push(&ns, g_emit_D, g_emit_V);`) and 2371 (the bulk chain `for (k...) path_push(&ns, chain[k] ^ 2, 1);`).
- print_remaining (4326-4330) prints `path_text(g_queue[i].path, g_queue[i].plen, ...)` without checking anything.
- Every tree node has plen == depth. A single step adds 1 to both. A bulk child adds dist[c] to depth and pushes dist[c] tokens. The snapshot agrees: max depth 128, longest seed 128 tokens. So a path is truncated exactly when a pending node's depth is over 250.
- If truncation lands on an edge boundary, the 250-token prefix is the node's depth-250 ancestor. Its subtree is a superset, so this only wastes work.
- If token 250 falls inside a bulk walk (2371 pushes the whole chain), build_seed_path_seed (2056-2074) replays the prefix as a bulk child at an intermediate cell of the chain. That is a sibling of the pending node, and its subtree does not contain the pending node. Result: a silent gap.
- A child job with a 250-token seed that later splits prints only its own seed. The client then sets self_remaining (volunteer.py:784-785), run_worker returns None (821-825), and the job is re-leased forever: a stall.

CASE 2 IS OVERSTATED
- Seeds of 251 to 1024 tokens do get through: parse_seed_path has a 1024-entry buffer (229, 1918), and jobs.js:32/66 has SEED_MAX_TOKENS=1024.
- But every REMAINING line from such a seed is 250 tokens, shorter than the seed. So every line fails `len(toks) > len(seed_toks)` (786) and remaining ends up empty. volunteer.py:826-830 then returns None and the node is left untouched. The outcome is a stall or re-lease loop, not a partial split.
- Such seeds cannot come from the worker, which never prints more than 250 tokens. They could only come from the seeding tools.
- With the current worker, the only bad REMAINING lines that can appear next to good ones are duplicates produced by truncation collapse (`p not in remaining` counts them as bad), and those are harmless. So "any bad_remaining means failure" in the client is defence in depth, not a fix for a bug that can fire today.

CASE 3 (confirmed, but only reachable through J's own children)
- volunteer.py:681 `"nodes": [self._clean_node(n) for n in nodes[:MAX_NODES]]` silently drops the tail of the node list.
- The server's parseTree only requires at least one child per split (jobs.js:769), and SUMMARY carries no REMAINING count (backsearch.c:5845). No layer can detect the missing children.
- The log text at 683-684, "the rest stay open on the server", is false: the dropped nodes are never created.
- In the current run_window, J runs with split_after equal to the whole window, and the loop breaks at the deadline (588-590). A report is therefore J plus REMAINING(J), and the cap only matters when a single DFS stack at split time has 4,999 or more entries. Campaign #1's maximum was 273 children per parent. The 203 same-report nested splits in the snapshot come from 120 s ramp windows, probably an older client. The finder's fold-back ("last split other than J") is therefore moot today.

REACHABILITY
- Every tree node passes shortcut_check (2204-2222), so a node's depth is at most its optimal solution length. For 5x5 with 3 holes the best is 149.
- More holes on 5x5, or 4x6 (record 160), stays far below 250.
- A 5x6 or 6x6 campaign, whose records plausibly pass 250, would hit the silent gap. Any campaign whose record could pass about 240 moves makes this critical, so it must be fixed first.
- Rated medium for a next campaign on a similar grid.

UNRELATED OBSERVATION (not part of this issue)
print_remaining prints s itself after expand(&s) has already pushed s's children (2288). REMAINING therefore lists s and each of its children, so those subtrees overlap. That costs work only. The comment at 4324-4325, "These subtrees are disjoint", is wrong.

*fix notes*: WORKER
- Detect truncation where paths are printed, not in the DFS loop. In print_remaining and print_cursor, check every node to be printed: if any has `plen != depth` (or `plen >= PATH_TOK_MAX`), print no REMAINING and print SUMMARY status "path_overflow".
  - The client already treats any status other than exhausted/split as "no SUMMARY", so the node stays untouched.
- Do not abort an exhaustive run on overflow, as the finder's "check g_path_overflow next to g_dedup_full" would. The path is unused there, and aborting would make deep subtrees impossible to finish even without a split.
- Reject --seed-path with more than PATH_TOK_MAX tokens (exit 2, status bad_seed).
- Wrap PATH_TOK_MAX in #ifndef so a test build can shrink it.
- For any grid whose depth can pass about 240, raise PATH_TOK_MAX (plen becomes uint16_t; BState copies get larger, so measure the cost). Fail-loud alone only turns the gap into a stall loop.
- Print `LIMITS path_tok_max=N` in --version.

SERVER
- Set SEED_MAX_TOKENS to min(1024, path_tok_max).
- Make v2_seed.js reject seeds longer than that.

CLIENT
- Treat these as a failure, not a split: bad_remaining > 0, or any REMAINING line with PATH_TOK_MAX or more tokens.
- Remove the nodes[:MAX_NODES] truncation and the false log line.
- Because only J splits in a window, the binding case is J having more than 4,999 children. A plain "too_many_remaining" failure would loop on it. Add a worker option instead, e.g. --split-max-remaining N: when the timer fires but q_tail+1 > N, keep searching until the stack shrinks, then split. This is always exact and always fits a report. Alternatively raise NODES_MAX on both sides, e.g. to REMAINING_MAX = 20000.

TESTS
- fake_worker FAKE_REMAINING_N=6000: expect no truncated report.
- FAKE_BAD_REMAINING: expect a failure, not a split.
- A -DPATH_TOK_MAX=8 build on 4x4 split at depth > 8: expect status path_overflow and no REMAINING lines.

SEPARATELY
Make print_remaining drop s's freshly pushed children (or print s's children instead of s), so the REMAINING subtrees are really disjoint.
