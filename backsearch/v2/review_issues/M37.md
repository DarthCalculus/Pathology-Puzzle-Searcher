# M37: Report batches have no byte cap: a batch over the server's 4 MB limit gets 413 and every report in it is rejected permanently

verdict CONFIRMED, severity medium, category robustness
locations: volunteer.py:907 (send_batch posts all pending reports in one body); v2routes.js:15 (4 MB body cap -> 413)

## Summary
The client posts every pending report in one /api/v2/reports body, and the server caps that body at 4 MB. A 413 is treated as non-transient, so every report in the batch is moved to outbox/rejected/ and never retried, and that finished work is lost. If the server resets the socket instead (the gate test notes EPIPE/ECONNRESET), the batch counts as transient and is retried from the outbox forever, never fitting.

## Source report F100 (server-ingest-routes-tools)
**Report batches have no byte cap on the client; a 413 permanently rejects every report in the batch** at /Users/george/PathologyRecords/server/lib/v2routes.js:15

*summary*: The client posts all pending reports in one /api/v2/reports body. The server caps that body at 4 MB and answers 413, which the client treats as a non-transient rejection of every report.

*failure_scenario*: The largest batch in the snapshot held 32 reports with 2,605 nodes in one POST; seeds reach 383 chars, and each node sends its seed plus its parent's seed. In a deeper or larger campaign, a batch of synchronized windows passes 4 MB. All its reports go to rejected/, the jobs are released and re-run, and the loss repeats whenever windows coincide. A single tree over 4 MB (5,000 nodes × about 810 B at depth 128) is rejected on every client, so that job can never be reported (stall).

*evidence*: v2routes.js:15 `const REPORT_BODY_MAX = 4 * 1024 * 1024;`; 132-134 answers 413. volunteer.py:899-905 send_pending sends the whole `self.pending`; 913 `self.api.post("/api/v2/reports", {"token": self.token, "reports": reports}, timeout=60)`; 92 `transient = status >= 500 or status == 429`; 921-922 `for r in reports: self.reject(r, e.status, e.body)`.

*suggested_fix*: Client: split batches by serialized size (for example ≤ 1 MB) and on 413 retry in halves down to a single report. Server: raise the report body cap, or let children be listed grouped under their parent so the parent seed is not repeated.

## Verifier (CONFIRMED, medium, refuted=False)
I read the code and it confirms the issue. It did not trigger in campaign #1, and it cannot make a published result wrong. It does waste work, and in a campaign with bigger trees it could stall a job.

How the code behaves:
- `send_pending` (volunteer.py:899-905) takes the whole `self.pending` list. `send_batch` (907) posts it as one body at line 913: `self.api.post("/api/v2/reports", {"token": self.token, "reports": reports}, timeout=60)`. Nothing limits the batch by byte size or by count.
- On the server, `REPORT_BODY_MAX = 4 * 1024 * 1024` (v2routes.js:15). `readBody` refuses early when the declared content-length is over the limit. The route then answers 413 with `Connection: close` (lines 131-135).
- The client counts a 413 as not transient (volunteer.py:92: `transient = status >= 500 or status == 429`). So lines 921-922 run `for r in reports: self.reject(r, e.status, e.body)`: every report goes to `outbox/rejected/`, and nothing ever retries from that folder (grep: `rejected/` is only written, never read back).
- If the server resets the socket instead, the error lands in the generic `except Exception` branch, which reports `ApiError(0, ..., True)`. The batch goes to the outbox and `flush_outbox` retries it forever, at most every 300 s, and it never fits. The gate test (v2_gates.test.js:451-455) accepts either outcome.
- Caddy fronts the live site and keeps Go's short wait before closing a connection. Python's `http.client` sends the whole body with `sendall` before it reads the reply. So for a body of 4 MB or more over the internet, the reset branch is the likely one.
- The server's own limits disagree with each other: NODES_MAX=5000 and SEED_MAX_CHARS=3072 allow legitimate tree reports far above 4 MB. The fake server (fake_server.py:426) enforces the same 4 MB and 413, but no test sends a large batch.

How close campaign #1 came (snapshot):
- The `reports` table grouped by (client_token, received_at) shows the largest batch was 32 reports with 2,605 nodes. The next largest was 32 reports with 2,179 nodes, and the third had 549 nodes.
- Jobs created by that largest batch have seeds averaging about 95 characters.
- One done node as Python `json.dumps` writes it is about 632 B at a 95-character seed, 947 B at 200 and 1,496 B at 383. That is seed + parent + status + summary, and the summary repeats the seed and adds a 64-hex src_hash and a `verify` field. An open node is about 227-803 B.
- So the worst batch was about 1.65 MB, roughly 40% of the cap. The failure needs about 2.4 times that.
- Worst cases with campaign #1 limits: 16 workers x 268 nodes (the largest tree) is about 2.7 MB; 32 workers is about 5.4 MB.
- A deeper or larger next campaign (more holes or a bigger grid) makes seeds longer and pending stacks bigger, so this is plausible there.
- A single tree of 5,000 nodes goes over 4 MB alone once seeds average about 160 characters or more. That report would fail on every client, and re-running the job would fail again, so the job stalls. This needs trees about 20 times larger than any seen so far.

Why the results stay correct:
- Heartbeats send `holding = running + queued` (volunteer.py:1163). A job whose report was rejected or parked in the outbox is no longer listed, so the server reopens it after RELEASE_GRACE_S=120 (jobs.js:514). After a Stop, the lease expires instead (3,600 s).
- The re-run is deterministic, so no valid level or best is lost. The cost is wasted CPU, up to a whole client's Stop batch (about 32 windows of up to 1,920 s each, roughly 17 CPU-hours), plus a job that stalls forever if a single report is over the cap.
- Outbox retry order is not a permanent block: a failed file is rewritten under a new timestamp, so it moves to the back of the queue.

Two related things I found while checking; the lead should decide whether they are new:
1. BATCH_MAX=1000 (jobs.js:48, 842) returns one 400 for the whole batch. That also rejects every report, but only a batch of more than 1,000 reports within 10 s triggers it, which is unrealistic.
2. More serious if trees grow: volunteer.py:680-684 cuts the tree to `nodes[:MAX_NODES]` and logs "the rest stay open on the server". That log is wrong. Nodes cut off the end can be children of a split node whose other children were kept, and parseTree (jobs.js:656-720) only requires one child per split node. Those REMAINING subtrees would disappear without any error, which breaks exhaustiveness (critical if a tree ever passes 5,000 nodes; campaign #1's largest was 268). Or a split node whose children were all cut makes the whole report fail with "split without any child", which is a stall. The byte cap and the node cap should be fixed together.

*fix notes*: Client (volunteer.py):
1. In `send_pending`/`send_batch`, cut the pending list into chunks by serialized size (for example 1 MB or less, measured with `len(json.dumps(...))`) and by count (below BATCH_MAX).
2. On a 413, or on a transport error when the body was over 1 MB, split the batch in half and resend, down to a single report. Only reject when a single report still gets 413 or 400.
3. Make the per-node JSON smaller. The server ignores summary.src_hash and summary.verify, and summary.seed is optional (jobs.js:636-648). Drop those three and send with `separators=(',', ':')`. That takes a done node from 638 B to 412 B at a 95-character seed.
4. Also fix the MAX_NODES cut. Never drop some children of a split node while keeping others: stop adding at a whole-subtree boundary, or turn a split node whose children do not fit back into 'open' with no summary. Correct the misleading log line.

Server:
1. Make REPORT_BODY_MAX match NODES_MAX x a realistic node size, or raise it for /reports only (for example 16-32 MB, with Caddy left without a body limit).
2. Optionally accept children grouped under their parent, so the parent seed is not repeated for every child.

Tests:
1. test_client.sh: a fake worker prints several hundred REMAINING lines of 300 characters or more on 4+ workers stopped together, against fake_server's 4 MB/413 check (fake_server.py:426). Assert that every report gets delivered and `rejected/` stays empty.
2. A unit test that a 5,001-node tree never loses any listed child seed.
