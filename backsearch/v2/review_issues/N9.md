1. The prune on capacity codes is real and silent.
- backsearch.c:2218 reads `if (x >= 0 || x == -2 || x == -3 || x == -4) { g_pruned_short++; ... return; }`.
- A state whose shortcut status is UNKNOWN is neither counted nor pushed, so its own validity and its whole subtree are lost.
- The comment calls this "conservatively prune". That is conservative for "never count an invalid level", but unsound for exhaustiveness.
- In the campaign configuration, -2 comes from `if (hs->pq_count >= HP64_SIZE) return -2;` (sokoban_bfs.c:1734-1736, HP64_SIZE = 1<<20 pending entries), or from the 128-bit solver (2641-2642) when 5*(1+nb)+nh > 64.
- -3 is practically dead in the campaign. g_heap_cap is never set: backsearch.c never calls sokoban_set_heap_cap. probe_failed cannot fire on the small table (at most 32K inserts in 64K slots with a 65536-probe limit) and is astronomically unlikely on the big table at 0.85 load.

5. Fix design review.
Correct parts:

## Verifier (CONFIRMED, critical, refuted=False)
Every code fact in the report checks out. Under the campaign flags only one of the three capacity codes, -2, can actually fire.

WHAT THE CODE DOES
- backsearch.c:2218. `if (x >= 0 || x == -2 || x == -3 || x == -4) { g_pruned_short++; ... return; }` returns before q_push. When the check cannot decide a state, its whole subtree is dropped and the run still ends with status "exhausted" (5845).
- The comment at 2210-2217 calls this pruning "conservative". It is conservative only against accepting an unproven level. It is the opposite of conservative for exhaustiveness.
- backsearch.c:4400-4401. The replayed seed goes through `try_successor(&seed)`. The seed has ptab1=0, so a split job re-checks its root with no reference table. That solve is larger than the parent's referenced check of the same state, so split runs can lose states a monolithic run keeps.

WHICH CODES CAN HAPPEN WITH THE CAMPAIGN COMMAND
- -4: only with --shortcut-state-cap (shortcut_check 1739-1742), which the campaign does not pass.
- -3 from the heap cap: impossible. backsearch.c never calls sokoban_set_heap_cap, so g_heap_cap stays 0.
- -3 from the probe limit:
  - Small table: impossible by construction. It takes at most 32,768 inserts into 65,536 slots, so a linear probe finds a free slot within 32,769 steps, below HT_PROBE_LIMIT = 65,536.
  - Big table: practically impossible at ≤85% load.
- -2: live. It fires when one forward solve's pending queue reaches HP64_SIZE = 2^20 (sokoban_bfs.c:1734-1737), or HP128_SIZE for ≥12 blocks on 5x5.

WORSE THAN THE REPORT SAYS
1. Dedup poisoning. The dedup insert (2164-2170) happens before shortcut_check. After a -2 prune, every other path to the same canonical key at the same or greater depth is also discarded, including paths whose referenced solve would have fit.
2. Infinite loop. When the big table itself overflows (ht_count ≥ 0.85·2^24 = 14,260,633 inserts while pending stays under 2^20), sokoban_bfs.c:1751-1754 (and 1262-1265 in solve_push64) runs `use_big = 1; goto retry;` with no check that use_big is already 1. The solve re-runs deterministically forever. The split and time checks (4646) never run, so this is a hang or stall rather than a prune. The proposed -5 has to be returned exactly here, via `if (use_big) return -5;`.
3. Nothing records it.
   - The -2 prunes are folded into g_pruned_short.
   - SUMMARY has no counter for them.
   - sanitizeSummary (jobs.js:638-643) keeps only whitelisted keys, and it rejects any status other than exhausted or split.
   - DESIGN.md never mentions capacity prunes.
   So campaign #1 cannot tell whether any happened.
