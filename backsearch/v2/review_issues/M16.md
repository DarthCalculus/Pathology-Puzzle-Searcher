# M16: Tokens of a closed campaign get HTTP 410 and the client never re-registers: returning volunteers loop forever at startup, and running clients idle

verdict CONFIRMED, severity high, category protocol
locations: volunteer.py:342 (register(): re-registers only on 401/403/404; any other status treated as 'server unreachable', 10 s retry loop); heartbeat (stops only on 401/403); leaser (10 s retry); reports moved to rejected/; jobs.js:338 (requireClient answers 410 campaign_closed)

## Summary
Every route answers a token from a closed campaign with 410 campaign_closed. At startup, register() re-registers only on 401/403/404 and treats 410 as 'cannot reach the server', so it retries every 10 s forever and never calls /register, which would already issue a token for the new campaign. Clients still running when the campaign closes never exit or switch: heartbeat ignores 410, the leaser retries forever, and reports go to rejected/. No existing volunteer can join campaign #2 without deleting ~/.pathology_volunteer.json or passing --reregister, and nothing tells them to.

*expected_gain*: Volunteers carry over to campaign #2 automatically instead of every client silently idling.

## Verifier (CONFIRMED, high, refuted=False)
I read the code and found nothing that refutes the issue.

Server side:
- jobs.js:331-339 requireClient returns `fail(410, 'campaign_closed')` whenever the token's campaign is not 'open'. heartbeat (491), lease (566), report (823) and reports (838) all go through requireClient.
- jobs.js:379 closeCampaign sets status='closed'. v2_seed.js:60-68 refuses to create a new campaign while one is open unless --close-others is passed, and then calls jobs.closeCampaign(open.id).
- In the snapshot, campaign 1 is still 'open' and has 7 clients. Seeding campaign #2 therefore closes #1, and every stored campaign-1 token starts getting 410.

Client side, in volunteer.py:
- Api.post (lines 85-100) raises ApiError(410, {...}, transient=False).
- register(), lines 341-358: `if e.status in (401, 403, 404)` re-registers. Otherwise it logs "cannot reach the server yet" and loops `while not self.stopping: time.sleep(10)`. Inside that loop only `e2.status in (401, 403, 404)` breaks out; 410 just logs "still cannot reach the server" again. The loop never ends and /register is never called. /register would have worked: jobs.js:446-470 registers into the active campaign, and the client does not even send its old token in the register body.
- A returning volunteer who starts the same command against campaign #2 therefore loops forever and leases nothing.

Running clients:
- heartbeat() (1170-1175) calls request_stop only for 401/403, so a 410 is just logged. last_heartbeat_ok is only displayed (line 1312) and never acted on.
- The leaser (472-478) stops only on 403 'revoked'. Everything else is logged and retried every batch_interval_s.
- send_batch (913-923) sends a non-transient, non-401 status to reject(), so reports go to rejected/. That is harmless here because the campaign is closed.
- A campaign-1 client left running idles forever, logging errors. updates.json does tell those volunteers to stop, which softens this part.

Other checks:
- No '410' or 'closed' appears in fake_server.py or test_client.sh, so nothing tests this.
- DESIGN.md, README.md and VOLUNTEERS.md never mention 410 handling or --reregister as the way to join a new campaign.
- collective.js:116 promises "the client will wait for the next campaign". That holds only for tokenless new clients, which get 404 no_campaign and retry.
- Small addition: the obvious workaround, `--reregister` alone, fails too. With --reregister, entry is None, so line 360 takes the name only from --name. Without --name it exits "No registration found ... Pass --name". Volunteers need `--reregister --name "X"`.

Severity: high for the next campaign. Nothing is corrupted and published results are not affected. But campaign #2 would stall at launch, because every experienced volunteer silently idles until told a workaround that no page documents. That is exactly the "campaign stall / large wasted work" class. The owner can soften it by posting instructions in updates.json, which is why it is not critical.

*fix notes*: 1. Client register() (volunteer.py:342 and 356): add 410 to both status tuples. Better still, treat any non-transient 4xx other than 400/429 from the stored-token heartbeat as "stored token is no longer valid; registering again". The name then comes from the stored entry (line 360, since entry is a dict), so no --name is needed.

2. Running client:
- On a 410 from heartbeat, lease, or reports, call request_stop("the campaign has ended; this client will join the next one"). Then either re-run register(), check_hash() and the scheduler loop in-process, or exit with an explicit message.
- In-process re-registration must drop the local queue, clear per-campaign state (exit_pref, no_jobs_until, me/exits stats), re-apply the campaign parameters, and re-run check_hash, since the new campaign may whitelist different hashes.
- Also move the outbox and rejected reports for the old campaign aside, so they are not re-sent under the new token.

3. Optional server change: include the active campaign id (or null) in the 410 body, so the client can tell "wait for the next campaign" (then poll /register, which already waits on 404 no_campaign) from "a new campaign is open".

4. Tests: in fake_server.py, add a close-campaign / open-new-campaign admin hook that answers 410 campaign_closed for old tokens. Add test_client.sh cases for (a) a running client when the campaign closes and (b) a restart with a stored campaign-1 token after campaign 2 opens. Assert that the client registers into campaign 2 and leases jobs without --reregister.

5. Docs: in VOLUNTEERS.md and updates.json, until the fix ships, tell returning volunteers to run `--reregister --name "Your name"` (--reregister alone exits asking for --name).
