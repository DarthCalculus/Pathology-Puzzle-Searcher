# M43: Split, time and status checks run only every 1024 expansions, so window overruns grow with the cost of an expansion

verdict CONFIRMED, severity low, category robustness
locations: backsearch.c:4646 (clock read only when ++iter % 1024 == 0)

## Summary
On 5x5 the worst jobs average about 24 ms per expansion, giving overruns of up to about 25 s (a job ran 1824.8 s against 1800). An expansion can make about 75 solver calls, and solve cost grows quickly with grid size and block count. On a bigger grid, 1024 expansions can exceed the split window, the 3600 s lease, or both, so leases expire and work is duplicated.

**Split, time and status checks run only every 1024 expansions, so overruns grow with the cost of an expansion** at /Users/george/Documents/Claude Projects/project45/backsearch/backsearch.c:4646

*summary*: The clock is read only when ++iter is a multiple of 1024. On 5x5 the worst jobs average about 24 ms per expansion, which gives an observed overrun of up to about 25 s (a split job ran 1824.8 s against 1800). Each expansion can do up to about 75 solver calls (bulk candidates plus 12 single children), and solve cost grows quickly with grid size and block count. On a bigger grid, 1024 expansions can exceed the window, the 3600 s lease, or both. The window then overruns, and leases may expire or duplicate work.

*failure_scenario*: Next campaign on 6x6 with about 1 s expansions: a window with split_after 120 s (ramp) runs about 17 minutes before the first check. With split_after 1800 s the job can pass the 3600 s lease before it hands back, and the server re-leases a job that is still running.

*evidence*: 4646-4650: `if ((!unlimited || g_split_after_s > 0 || g_status_every_ms > 0) && (++iter & 1023) == 0) { clock_gettime(...); ... if (g_split_after_s > 0 && el >= g_split_after_s) { print_remaining(&s); ...`. Snapshot: split jobs `max(elapsed_s)=1824.772`; top elapsed/accepted = 24.2 ms (job 95681).

*suggested_fix*: Read CLOCK_MONOTONIC after every expansion; it costs about 20-50 ns, against millisecond-scale expansions. Or check every N expansions with N adjusted so a check happens at least every second.

*expected_gain*: Keeps windows and leases predictable on larger grids.

## Verifier (CONFIRMED, low, refuted=False)
The mechanism is real, but the lease consequence is refuted. backsearch.c:4646-4651 reads the clock only when `(++iter & 1023) == 0`. The split test (`el >= g_split_after_s`), the --time cap and print_status all sit inside that gate. The SIGINT/stop test on line 4645 (`if (g_stop_requested) ...`) is checked after every expansion, so stops stay prompt. The snapshot matches a 1024-expansion granularity. Split-job elapsed_s: 1249 jobs at 119-121 s, 147 at 121-130 s, 22 at 130-150 s (max 144.7 against the 120 s ramp), and 28 above 1801 s (max 1824.8 against 1800). The worst per-expansion cost is job 95681: 124.4 s over 5137 accepted, about 24 ms, so 1024 expansions take about 25 s. That equals the largest observed overrun. REFUTED PART: the claim that the 3600 s lease can expire under a still-running job. jobs.js:501-519 pushes every held lease to now + lease_s on each heartbeat (`let want = t + c.lease_s; ... q.extendLease.run(until, j.id)`), and volunteer.py:1160-1170 sends `holding` (running + queued) every heartbeat. A running job therefore keeps its lease however long the window overruns, as long as the client heartbeats. Overrun causes no duplicate work. Real remaining consequences: (a) windows are longer than configured, and the client has no hard kill (run_worker waits for the worker). (b) Absorption probes (absorb_probe_s 10, volunteer.py:643) each run at least 1024 expansions, and absorb_total_s is only checked between probes. (c) STATUS lines, meant every 250 ms, only come every 1024 expansions, so control-panel boards go stale. (d) Ramp windows (used when open < 3 x workers, jobs.js:582, i.e. the campaign tail) stretch, which slows fan-out in the tail. If a larger grid reaches about 1 s per expansion, each check comes about 17 minutes apart. That hurts predictability, not correctness. Low.

*fix notes*: Read CLOCK_MONOTONIC after every expansion. On macOS it is a commpage read (tens of ns), against 70 us to 24 ms per expansion on 5x5, which is under 0.1% overhead. If per-expansion reads worry you, use `(++iter & 15) == 0`. Also consider a client-side hard ceiling: SIGINT the worker at window_end + grace. The worker already handles SIGINT by printing CURSOR/REMAINING, and that path is checked every expansion. Add a regression test: a seed with slow expansions and --split-after 1 must return within about 1 s plus one expansion.
