# M54: log() writes stderr synchronously, sometimes under self.lock, so a blocked terminal freezes the scheduler

verdict CONFIRMED, severity low, category robustness
locations: volunteer.py:53 (log() writes directly to stderr); several call sites hold self.lock

## Summary
Every thread writes log lines straight to stderr, and several do so while holding self.lock. If the terminal stops draining, through XOFF (Ctrl-S) or a console selection on WSL/conhost with QuickEdit, slot threads stop reading worker stdout, workers block on full pipes, and a lock holder blocks every other thread, heartbeats included.

## Source report F58 (client-core)

*summary*: Every thread writes log lines straight to stderr, and several call sites do so while holding self.lock. If the terminal stops draining, slot threads stop reading worker stdout (workers then block on the full pipe), and a lock holder blocks every thread, including heartbeats. Triggers include XOFF (Ctrl-S) or a console selection on WSL/conhost with QuickEdit.

*failure_scenario*: A WSL volunteer clicks in the console window, which starts a QuickEdit selection and pauses output, then walks away. Once the pty buffer fills, slot threads block in log() at window boundaries and workers stall on their stdout pipes. If the main thread logs a drop or stop-grace line under the lock, heartbeats stop too. After lease_s, all the client's jobs expire and are re-run by others, and on resume the workers are dropped and killed.

*evidence*: volunteer.py 51-54: line = ...; sys.stderr.write(line + "\n"); sys.stderr.flush()
volunteer.py 1205-1210: with self.lock: for s in self.slots: ... self.log("job %d is held by someone else now ...")
volunteer.py 1277-1285 (handle_wake) and 1388-1397 (stop-grace) also log inside `with self.lock:`.

*suggested_fix*: Push log lines onto a bounded queue drained by a dedicated writer thread that drops lines on overflow. Never write to stderr while holding self.lock. Swallow OSError in the writer.

*expected_gain*: A stalled terminal cannot freeze the search or let leases lapse.

## Verifier (CONFIRMED, low, refuted=False)
The mechanism holds. volunteer.py:51-54 `sys.stderr.write(line + "\n"); sys.stderr.flush()` has no queue and no try/except. CPython's BufferedWriter holds its internal lock while a blocked write(2) is in progress, so once one thread blocks on a stopped tty (Ctrl-S/IXON, or a legacy conhost QuickEdit selection under WSL, which VOLUNTEERS.md:21 recommends for Windows), every other thread that logs blocks as well. Logging under self.lock is real at 1205-1214 (drop), 1276-1290 (handle_wake) and 1388-1394 (stop-grace). When that happens, state() (the UI), heartbeat() and every slot thread block too.

One detail of the finder's scenario needs correcting. In the common case nothing logs under the lock, and the main thread only logs on events, so heartbeats keep running (1377-1379). The server renews every held job on each heartbeat (jobs.js:501-519 `want = t + c.lease_s ... extendLease`), so leases do not lapse.
- A slot frozen at the window-start log (585, after `slot.job = job` at 577-583) stays in `running`, and its lease is renewed indefinitely with no progress. The queue behaves the same way. These jobs come back only through work stealing when the pool is empty (jobs.js:607-630, at most one running job per request), or when the terminal drains. On a lone client the exit stalls.
- A slot frozen at the window-end log (698-700, after `slot.job = None` at 697 and before queue_report at 701) drops out of `holding`. The server releases that job after RELEASE_GRACE_S and it is re-run, so up to split_after_s of work per slot is lost.
- The sender blocks on its 'batch delivered' log line (not under the lock).

The lease-expiry path the finder describes happens only when the main thread itself logs, under the lock or not: a heartbeat failure, a drop, or a wake.

There is also a related consequence the finder did not list. log() does not catch OSError. If stderr is a hung-up tty (for example, the client was started with `&` plus `disown` and the terminal was closed), every log() raises EIO and kills the thread that called it. slot_loop has no try, and dead slot threads are respawned only by set_workers (_reconcile_slots at 1131). If a slot thread dies at the window-start log it leaves slot.job set, so that job is renewed forever.

The effect is recoverable (a stall plus lost window work), and triggers are uncommon, so severity stays low.

*fix notes*: Make log() non-blocking. Append to self.ring, then put the line on a bounded queue.Queue drained by one daemon writer thread. Drop lines when the queue is full (count them), and swallow OSError/ValueError in the writer. Never call sys.stderr from any other thread. With the writer in place, calls made while holding self.lock become harmless, though it is still cleaner to collect messages inside the lock and log them after releasing it. Optionally install SIGHUP -> request_stop. Test: run the client with stderr as a pipe nobody reads (e.g. `2> >(sleep 3600)` or a FIFO opened but never read), then assert that heartbeats continue and reports still arrive at fake_server.
