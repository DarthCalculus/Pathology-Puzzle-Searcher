# M113: Power loss can silently undo owner admin actions, and a lost registration makes the client discard its reports

verdict CONFIRMED, severity low, category robustness
locations: jobs.js:148 (synchronous=NORMAL for all connections, including owner tools); heartbeat 403 unknown_token stops the client; report batch 403 moved to rejected/

## Summary
Every connection, owner tools included, opens with synchronous=NORMAL, so a VPS hard reset can lose the last un-checkpointed commits. For reports that is safe by design, because the jobs return to the pool. A lost hash removal, reissue, campaign creation or registration goes unflagged, though. A client whose registration was lost gets 403 unknown_token: heartbeat stops the client, and a report batch that gets 403 is moved to rejected/ and never resent.

## Source report F193 (robustness-ops)
**Power loss can silently undo owner admin actions; a lost registration makes the client discard its reports** at /Users/george/PathologyRecords/server/lib/jobs.js:148

*summary*: Every connection, including the owner tools, opens with synchronous=NORMAL, so after a VPS hard reset the last un-checkpointed commits are gone. For reports that is safe, as designed: the jobs return to the pool. For a hash removal or reissue, a campaign creation or a registration it is not flagged anywhere. A client whose registration was lost gets 403 unknown_token; heartbeat stops the client, and a report batch that gets 403 is moved to rejected/ and never resent.

*failure_scenario*: The owner runs `v2_hashes.js remove H1 --reissue` after finding a bug, and the host resets seconds later. The removal and the reissue vanish, H1 is accepted again, and the tool had already printed success. Separately, a volunteer registers just before the reset. Its next batch gets 403 unknown_token, and every report in it goes to rejected/ permanently. The client then stops ('server does not recognise this client'), and on restart it re-registers but never resends the rejected batch.

*evidence*: jobs.js:148 `PRAGMA synchronous = NORMAL;   -- §7.9: WAL + NORMAL; a lost commit only leaves jobs leased until expiry`. The tools all call openJobsDB() (v2_hashes.js:27, v2_seed.js:51). volunteer.py:915 `if e.transient or e.status == 401:` -> outbox, otherwise `for r in reports: self.reject(r, e.status, e.body)` (921-922). volunteer.py:1173-1174 `if e.status in (401, 403): self.request_stop(...)`.

*suggested_fix*: In openJobsDB, accept an option the tools set to use synchronous=FULL, or run `PRAGMA wal_checkpoint(FULL)` before a tool exits, so admin changes are durable when the tool prints success. In the client, treat 403 unknown_token on reports as 're-register, then resend the batch' (keep it in the outbox).

## Verifier (CONFIRMED, low, refuted=False)
jobs.js:148 sets `PRAGMA synchronous = NORMAL` under WAL for every connection. The tools use the same openJobsDB (v2_hashes.js:27, v2_seed.js:51, v2_finish.js:24), and no code runs wal_checkpoint anywhere. With WAL+NORMAL a commit is safe against a process crash but not against power loss or OS/hypervisor reset until the WAL pages reach disk. The window is roughly the OS writeback delay (about 30 s on default Linux) or the next autocheckpoint, not every un-checkpointed commit as the summary implies, but the core claim holds. WAL replay stops at the first frame that fails its checksum, so a lost commit takes every later commit with it. Client side confirmed: requireClient returns 403 unknown_token (jobs.js); volunteer.py:915-922 sends only transient or 401 errors to the outbox and rejects on 403, moving reports to rejected/ with no resend; heartbeat 401/403 -> request_stop (volunteer.py:1173-1174). flush_outbox (volunteer.py:1003) also uses send_batch, so batches queued during the outage get rejected once the server is back. Real impact is small. For a lost registration, the client's leases are lost too, so its jobs are open again and are re-run: only a few minutes of CPU are wasted and coverage is unaffected. Resending would even have worked, because first-report-wins accepts reports for open jobs from any client. The only silent dangerous case is a lost `v2_hashes remove` or `--reissue`: an owner action that prints success and vanishes if a hard reset follows within about 30 s. Mitigations exist: v2_finish prints the hash list in the proof note, and campaign or root loss would be obvious. Low.

*fix notes*: openJobsDB(dir, { durable: true }) sets `PRAGMA synchronous = FULL` for the tools (v2_hashes, v2_seed, v2_finish). Alternatively the tools run `PRAGMA wal_checkpoint(FULL)` before printing success. Either way the WAL is fsynced, including the server's earlier frames. In volunteer.py, treat 403 unknown_token on reports as transient: keep the batch in the outbox, call register() to get a new token, then resend. Test: the fake server drops the token and answers 403 once; assert the batch is later delivered, not left in rejected/.
