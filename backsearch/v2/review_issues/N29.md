# N29: solver6 clamps its RAM budget to 80% of MemFree (not MemAvailable), so on a server whose page cache fills RAM, the 0.5 GiB verification budget silently shrinks to as little as 96 MB

verdict CONFIRMED, severity low, category robustness
locations: /Users/george/PathologyRecords/solver/solver6.c:1909

## Summary
avail_phys() uses sysconf(_SC_AVPHYS_PAGES). On Linux glibc derives this from sysinfo().freeram (MemFree), which excludes reclaimable page cache. The requested budget is cut to 0.8×MemFree (floor 96 MB) with no trace in the JSON output, so champions that fit in 0.5 GiB come back too_complex 'memory'. The clamp also ignores the service's 2 GiB cgroup limit, which is what actually governs the process.

## Source report F228 (r2-publish-path-and-verifier)
**solver6 clamps its RAM budget to 80% of MemFree (not MemAvailable), so on a server whose page cache fills RAM, the 0.5 GiB verification budget silently shrinks to as little as 96 MB** at /Users/george/PathologyRecords/solver/solver6.c:1909

*summary*: avail_phys() uses sysconf(_SC_AVPHYS_PAGES). On Linux glibc derives this from sysinfo().freeram (MemFree), which excludes reclaimable page cache. *failure_scenario*: The VPS has run for days; SQLite files and logs have filled the page cache and MemFree is 180 MB. verifyLater and the publish-time processSubmission for a campaign #2 champion get about 144 MB instead of 512 MB, report too_complex(memory), and the champion is left unverified and unstored (see the v2_finish finding). Nothing in the logs reveals the clamp.

*evidence*: solver6.c:158-163:

*suggested_fix*: On Linux, read MemAvailable from /proc/meminfo (and the cgroup's memory.max minus memory.current). Report the effective budget: add it to the too_complex JSON, or use a distinct why such as 'memory_clamped', so a clamp is visible.

## Verifier (CONFIRMED, low, refuted=False)
The mechanism holds. avail_phys (solver6.c:157-164) returns sysconf(_SC_AVPHYS_PAGES)*pagesize. On Linux glibc (Ubuntu 26.04 on the host), __get_avphys_pages is sysinfo().freeram, which is MemFree and excludes reclaimable page cache. solver6.c:1909-1914 clamps `bytes` to 0.8*MemFree with a 96 MiB floor, silently: budgetMB appears only in the verbose stderr line at 2024-2039, and the JSON is just {"status":"too_complex","why":"memory"}. The 0.5 GiB budget is cut whenever MemFree < 640 MiB, which is plausible on a 4 GB VPS after weeks of page-cache growth (daily 14-day backups, journald, SQLite). I could not confirm it on the host because network access is not allowed. The clamp's own rationale ('never push the process into the pagefile', 145-147, 367-368) is about Windows. On a no-swap Linux host, allocating past MemFree just reclaims cache. It also ignores the service cgroup limit, but a single 0.5 GiB process stays under 2 GiB, so that point is minor.

The impact is smaller than the scenario implies, for two reasons:
- processSubmission (used by v2_finish) tries the default hash engine first: 30 s gives memBits 25, and there is no avail_phys clamp in that path. The top 5x5 levels in records.db (149 @ exit 1, and a 4-hole 146 @ exit 6) have full-length paths, which only the default engine produces. So 5x5 champions would still be verified and stored.
- verifyLater (v2routes.js:62-71) goes straight to solver6 via measureLevel, yet all six campaign-#1 champions came back with verified_moves == best.

The realistic effect for a 5x5 follow-up is at most a dashboard check mark missing, plus v2_finish printing 'not re-solved yet'. The clamp matters for larger grids, where only solver6 can verify. Low is correct.

*fix notes*: On Linux, read MemAvailable from /proc/meminfo and fall back to _SC_AVPHYS_PAGES. Optionally, also take min(memory.max - memory.current) from /sys/fs/cgroup/<self cgroup>. Put the effective budget in the too_complex JSON (e.g. "budget_mb":N), or use why 'memory_clamped' when the clamp fired, and have measureLevel/verifyLater log it. As a cheap fallback, the service could pass an env/flag that disables the clamp on the no-swap server.
