# N4: The worker's own reference-free re-solve of each job's best ('verify' in SUMMARY) is dropped by the server

verdict CONFIRMED, severity medium, category soundness
locations: /Users/george/PathologyRecords/server/lib/jobs.js:640

## Summary
The worker prints verify, the result of a full forward solve of the reported level with reference tables off, and the client forwards the whole SUMMARY. sanitizeSummary whitelists fields and drops verify, so a verify/best mismatch, the one cheap signal that a champion was wrongly accepted, is lost. For 6x6 or 4-hole champions the site re-solve may never succeed, which makes this the only re-solve available.

## Source report F203 (r2-next-campaign-generalization)
**The worker's own reference-free re-solve of each job's best ('verify' in SUMMARY) is dropped by the server** at /Users/george/PathologyRecords/server/lib/jobs.js:640

*summary*: The worker prints verify, the result of a full forward solve of the reported level with reference tables off, and the client forwards the whole SUMMARY. sanitizeSummary whitelists fields and drops verify, so a verify/best mismatch, the one cheap signal that a champion was wrongly accepted, is lost. For 6x6 or 4-hole champions the site re-solve may never succeed, which makes this the only re-solve available.

*failure_scenario*: A deep state is wrongly accepted because of a reference-table or multi-start labelling bug (e.g. the known max_cost<0 early return that exports the previous solve's table). Its true optimum is 147, but it is reported as best=149. The worker prints '(verify 147 MISMATCH)' and SUMMARY "verify":147. The client sends summary.verify; sanitizeSummary discards it. The site's 30 s / 0.5 GiB re-solve returns too_complex on a large 6x6 level, so verified_moves stays NULL, and v2_finish publishes 149 as the exhaustive maximum.

*evidence*: jobs.js:636-644 `const out = { status: s.status }; for (const k of ['states', 'accepted', 'valid', 'best', 'evict_shallow', 'evict_recent', 'solver_calls', 'exit']) { ... out[k] = s[k]; }` (verify not kept); backsearch.c:5848 SUMMARY `"verify":%d` and 5838 `printf("  (verify %d %s)", verify, verify == g_best_depth ? "OK" : "MISMATCH");`; volunteer.py:608-609 `node["summary"] = summary` (forwarded whole).

*suggested_fix*: Accept verify as an integer in [-4, MAX] in sanitizeSummary and store it per job. When verify >= 0 and verify != best, mark the node as a mismatch that blocks a clean audit. Show it in the audit and in v2_finish, and refuse to publish when the champion's worker verify disagrees. This depends on making the verify bounded (previous finding).

## Verifier (CONFIRMED, medium, refuted=False)
Every link in the chain checks out, and the campaign #1 snapshot backs it up.

1. The worker computes the value and prints it. At backsearch.c:5781-5785, `int verify = -1; if (g_best_depth > 0) { ... verify = sokoban_solve(&pz, NULL, NULL); }` re-solves the job's best level. It prints `(verify %d %s)` with OK or MISMATCH at 5840 and puts `"verify":%d` in the SUMMARY JSON at 5846-5848. sokoban_solve (sokoban_bfs.c:2672) sends the puzzle to solve_push64 or solve_push128, which are the uncapped solvers. The reference prune (`g_ref_on && ref_prunes_at`) appears only in the cutoff solver at 1733. So verify really is a reference-free, uncapped forward solve.

2. The client passes it through. volunteer.py:799-803 keeps the parsed SUMMARY dict as it is, and :608 does `node["summary"] = summary`. The client never reads verify and never looks at the MISMATCH text; the only 'verify' match in volunteer.py is an unrelated git message at :254.

3. The server drops it. sanitizeSummary (jobs.js:636-648) builds a fresh object from a whitelist: status, states, accepted, valid, best, evict_shallow, evict_recent, solver_calls, exit, elapsed, seed. `verify` is not on the list. What gets stored in reports is the sanitized s0 (jobs.js:759). The jobs table has no verify column. DESIGN.md, README.md and VOLUNTEERS.md never mention verify, which is presumably why it was left off the whitelist.

4. The snapshot confirms it. `select count(*), sum(summary_json like '%verify%') from reports` gives 54409 and 0. The server's own re-solve (verifyLater, v2routes.js:62-71, triggered at :153 only when a report sets a new best for its exit) ran on just 62 of about 166k jobs. All 62 agree (verified_moves = best), including all six exit champions, so campaign #1 shows no sign of a false acceptance. The ~150k per-job worker re-solves were computed and thrown away.

Why it matters for the next campaign:
- The only cross-check the server keeps is verifyLater. It is fire-and-forget: it logs a warning on too_complex, invalid or error, has no retry, and does not survive a server restart. That makes verified_moves NULL a reachable state.
- v2_finish.js:57-61 refuses only when `v != null && v !== best`. With a NULL it prints '(not re-solved yet)' and still calls addProof. The champion goes through processSubmission only after the proof has been added, so the one check addProof makes (a stored verified level contradicting the maximum) cannot catch it.
- The worker verify is therefore the only surviving independent signal on the champion when the site re-solve is missing. It is also the only false-acceptance signal on any non-champion job, and a false acceptance anywhere points to an engine bug that could also cause wrong rejections, meaning missed valid levels.

Where the finding overstates things:
- The claim that the site re-solve 'may never succeed' on 6x6 or 4-hole levels is speculative. solver6 is strong (solver.js notes it proves a 42-cell, 394-move record in 1.2 s), and it re-solved every campaign #1 champion.
- verify comes from the same sokoban_bfs.c codebase, so it is less independent than the site solver.
- It can only catch false acceptances (best above the true optimum). It cannot detect missed valid levels.
- A wrong published maximum needs an engine false-acceptance bug and a missing site verification at the same time. That is why this is medium (a lost defense-in-depth layer plus lost diagnostics), not critical.

For a hard gate on verify, note the values that are not mismatches: -1 means best was 0 (no solve ran) or the level is unsolvable, and -2/-3 are resource failures. Only `verify >= 0 && verify != best` is a real mismatch; a negative verify with best > 0 should be a warning.

*fix notes*: Server, /Users/george/PathologyRecords/server/lib/jobs.js:
- In sanitizeSummary, accept `verify` as an integer in [-3, MAX_SAFE_INTEGER]. Don't reject reports from older workers that lack it.
- Add a `verify INTEGER` column on jobs (plus migration) and keep verify in the reports summary_json.
- In applyReport, when best > 0 and verify >= 0 and verify !== best, set a flag. Either reuse mismatch=1, which already makes audit() unclean at :1001, or add a separate verify_mismatch flag that audit lists under its own key.
- When best > 0 and verify < 0, log it and count it as 'worker could not re-solve'. Do not block on it.

v2_finish.js:
- Show the champion's worker verify next to verified_moves.
- Refuse to publish when the champion's worker verify disagrees.
- Refuse (or re-solve synchronously with a larger budget before addProof) when verified_moves is NULL, instead of publishing with '(not re-solved yet)'.
- Submit and verify the champion before calling addProof, not after.

v2routes.js verifyLater:
- Persist failed or too_complex outcomes (for example verified_moves = -1 plus a reason) and retry them, so a server restart or a transient failure cannot leave a champion unverified without anyone noticing.

Contract and client:
- Document `verify` in the DESIGN.md §7 SUMMARY schema.
- Have volunteer.py log '!!! verify MISMATCH' locally when summary.verify >= 0 and differs from best.

Tests:
- Add a v2_gates test: a done report with best=149 and verify=147 must make the exit's audit unclean and make v2_finish refuse.
- Add a test that a report without verify is still accepted.
- Have fake_worker.py emit verify.
