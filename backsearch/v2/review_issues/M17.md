# M17: Multiple client instances on one machine share one token, and release-by-omission makes each release (and drop) the other's jobs

verdict CONFIRMED, severity high, category protocol
locations: volunteer.py:35 (token file ~/.pathology_volunteer.json); volunteer.py:322 (token keyed only by server URL); v2/README.md ('several clients on one machine' with separate --outbox/--port); jobs.js:514 (heartbeat releases every lease not in `holding` and older than 120 s)

## Summary
Every client process on one machine, or on machines sharing an NFS home, reuses the same stored token. The README even recommends running several clients with separate --outbox and --port. The server keys leases, `running`, release-by-omission and drop by token, so each instance's heartbeat releases the other's running and queued jobs every 30 s. Other clients then lease those jobs and the owning instance gets `drop` and SIGKILLs its workers. workers, boards and running_json also flip between the instances.

*summary*: The token store is keyed only by server URL, so every client process on one machine (or on machines sharing an NFS home) reuses the same token. The README tells volunteers to run 'several clients on one machine' with separate --outbox and --port. The server keys leases, `running`, release-by-omission and drop by token. Each process's heartbeat therefore releases the other process's running and queued jobs every 30 s. Other clients then lease them, and the owning process gets drop and SIGKILLs its workers.

*failure_scenario*: The volunteer starts `volunteer.py --workers 8 --port 8765` and `volunteer.py --workers 8 --port 8766 --outbox o2` as the README suggests. Both load token T.
1. A's heartbeat lists only A's jobs. The server reopens every lease on T older than 120 s that A did not list, which is all of B's running and queued jobs.
2. Those jobs are split children, and the pool is ordered deepest-first, so they sit at the head of the pool. Until B's next heartbeat (up to 30 s later), any lease request can take them, including A's own leaser.
3. If another client takes one, B's next heartbeat returns it in `drop`, and B SIGKILLs the worker, losing up to a full window. If A takes it, both processes run it.
4. Symmetric for A's jobs on every heartbeat from B.

--reregister does not help: it overwrites the single stored entry, so after the next restart both processes share the new token.

*evidence*: volunteer.py 35: TOKEN_FILE = os.path.join(os.path.expanduser("~"), ".pathology_volunteer.json")
volunteer.py 322: entry = store.get(self.api.server) if not self.args.reregister else None
volunteer.py 386: store[self.api.server] = {"token": self.token, ...}
v2/README.md 39-40: "Several clients on one machine: give each its own `--outbox DIR` and `--port`."
jobs.js 514: if (holdingSet && !holdingSet.has(j.id) && t - j.leased_at > RELEASE_GRACE_S) { q.reopenJob.run(j.id); released.push(j.id); continue; }
jobs.js 530-533: a holding id not in this token's leases and not open -> drop.push(id)
jobs.js 500: setRunning overwrites the token's running list on each heartbeat.

*suggested_fix*: Give each client process its own token, for example stored in the outbox directory or keyed by (server, outbox path). Hold an exclusive lock file so two processes never share a token. Alternatively, send a per-process instance id in heartbeats and have the server release by omission only leases granted to that same instance. Fix the README either way.

*expected_gain*: Prevents continuous kill and re-run thrash for any volunteer who follows the README's multi-client advice or has an NFS home directory.

## Verifier (CONFIRMED, high, refuted=False)
Every link in the chain holds when checked against the code.

1. One token per HOME. volunteer.py:35 has `TOKEN_FILE = os.path.join(os.path.expanduser("~"), ".pathology_volunteer.json")`. volunteer.py:322 has `entry = store.get(self.api.server) if not self.args.reregister else None`, so the store is keyed only by server URL. volunteer.py:386 has `store[self.api.server] = {...}`, so --reregister replaces the single entry: after the next restart both instances load the new token again. Nothing makes an instance unique: no lock file, no per-outbox token, no instance id. The token path is not derived from --outbox.

2. The docs invite the setup. v2/README.md:39-40 says "Several clients on one machine: give each its own `--outbox DIR` and `--port`." No doc warns about the shared token.

3. The heartbeat body carries only this process's jobs. volunteer.py:1161-1168 sets `holding = running + [j["id"] for j in self.queue]`, i.e. this process's own slots and queue.

4. The server releases by omission per token. jobs.js:509-514 walks `q.myLeases.all(cl.token)`, which is every lease on the token. It runs `reopenJob` for each lease that is not in `holdingSet` and has `t - j.leased_at > RELEASE_GRACE_S` (120 s). Instance A's heartbeat therefore reopens every job of instance B leased more than 120 s ago, running or queued.

5. Reclaim and drop. On B's next heartbeat, jobs.js:527-534 re-leases any job still open to B with a fresh `leased_at = t`. After another 120 s, A's heartbeat releases it again. Steady state: each job held by either instance sits in the open pool for about (30 - phase) s out of every ~150 s, roughly 10 % of the time on average. If another client leased it during that window, B gets it in `drop`, and volunteer.py:1203-1210 SIGKILLs the worker with no report, losing up to one split window (1800 s) of progress. If the instance's own twin leased it (same token), neither gets a drop: openOfExit excludes only `dup_of` rows of the same token, not the job itself. Both then run the whole job, and the second report is a `dup`.

6. More state flips per heartbeat (jobs.js:499-500). `workers`, `boards` and `running_json` hold only the last heartbeater's values. Consequences:
   - The work-stealing ranking at jobs.js:611-616 sees the other instance's running jobs as queued, so it steals them first. That means SIGKILLs during the campaign tail.
   - The held cap at jobs.js:583-584 (`3*cl.workers + LEASE_HELD_EXTRA`) counts both instances' leases against a single instance's workers value.
   - The public board display flips between the instances.
   - Every heartbeat logs "no longer lists these running jobs as leased to us" and "released N job(s)".

The damage is waste, not correctness. Leases are advisory and first report wins (jobs.js:747-770), so no subtree is lost or double-counted and the exhaustive result is unaffected. That rules out critical.

This is a regression from the 2026-09-24 release-by-omission change, which will be live for the next campaign. Before it, two instances on one token only co-renewed each other's leases, which was harmless.

Campaign #1 evidence: the snapshot shows 7 tokens for 5 names. Panacea has 3 tokens with 2, 8 and 12 workers, i.e. separate registrations per machine, so I found no evidence of a shared token in the finished campaign. The trigger is conditional: two instances under one HOME, or an NFS-shared home. But it is exactly the setup the README recommends. When it fires, it thrashes for as long as both instances run and destroys a large share of that volunteer's output: repeated SIGKILLs of long-running workers, full duplicate runs, and churn for other clients. That fits "large wasted work", so high for the next campaign, conditional on the documented multi-instance setup.

*fix notes*: The client and server both need changes; either one alone helps.

(1) Client: give each process its own identity and lock it.
- Key the token store by (server, os.path.realpath(outbox)), or add a --token-file option that defaults to a file inside the outbox directory.
- Take an exclusive fcntl.flock on a lock file next to the token (for example <outbox>/.lock) for the whole life of the process.
- If the lock is already held, refuse to start with a clear message, or register a fresh token under a new key. Note that flock is unreliable on some NFS mounts, so the server-side fix is the robust one.

(2) Server:
- Have the client generate `instance = uuid4()` per process and send it on heartbeat and lease. Store it on the lease (new column jobs.lease_instance).
- Release by omission only leases whose lease_instance equals the heartbeating instance. Leases with NULL instance, from old clients, keep today's behaviour.
- Scope `drop` the same way: never drop a job held by the same token under a different instance.
- Store running_json, workers and boards per (token, instance) or aggregate them, so the steal ranking, held cap and sumWorkers see both instances.
- When two instance ids heartbeat on one token within 60 s, log a warning and return one in the heartbeat response so the client shows it.

(3) Docs: README lines 39-40 and VOLUNTEERS.md should say each instance gets its own token (or --token-file), until the fix ships.

(4) Test: add a test_client.sh case with two clients under one temporary HOME against fake_server.py. Give fake_server.py the release-by-omission logic. Assert zero cross-instance `released`/`drop` over at least 3 heartbeat cycles, and that both instances' jobs complete exactly once.
