# N10: [fix-design D3] A full big table must return a new code -5 instead of 'goto retry'. The same loop sits in solve_push64, and the end-of-run verify solve can hang after the search has finished.

verdict CONFIRMED, severity high, category bug
locations: /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:1751

## Summary
The minimal correct fix: on overflow, if the big table is already in use, return -5 (UNKNOWN, handled as in finding 1); otherwise switch to the big table once. The same retry loop exists in solve_push64 (used by sokoban_solve). The worker calls sokoban_solve without a cutoff to 'verify' the best level after the search completes. That is the solve most likely to fill 14.26M slots, so today a hang there throws away a finished job. The server discards the verify value anyway.

The same retry loop exists in solve_push64 (used by sokoban_solve). The worker calls sokoban_solve without a cutoff to 'verify' the best level after the search completes. *failure_scenario*: A solve reaches 0.85 x 2^24 = 14.26M distinct states within its cutoff. hsp64_update sets overflow, the code jumps to retry, selects the same big table, clears it and repeats forever. There is no split or stop check, and heartbeats renew the lease for good, so the job and the campaign never finish.

Second case: a run exhausts its subtree, then at backsearch.c:5785 fully solves its best level (no cutoff). On a large 5x5 level with more holes that solve can fill the table, and the finished job is never reported.

Campaign #1 finished, so this never fired there.

*evidence*: sokoban_bfs.c:1751-1754 (cutoff) and 1262-1265 (full solver):

      /* Small table saturated: rerun this solve on the big one. */

- The 128-bit solvers have no fill limit, only the probe limit (-3), so they need no change.

## Verifier (CONFIRMED, high, refuted=False)
The code confirms the infinite loop. It fires only if a single solve gets very large, which campaign #1 never did.

1. The loop. In both /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:1262-1265 (solve_push64) and :1751-1754 (solve_push64_cutoff):
   } else if (hs->overflow) { use_big = 1; goto retry; }
   The retry label (1104 / 1526) calls hsp64_select(hs, use_big) and then hsp64_clear(hs). hsp64_select(big=1) always sets ht_limit = (uint32_t)(HTP_SIZE * 0.85), which is 14,260,633 (line 1020). hsp64_clear resets ht_count and overflow and bumps ht_seq. Nothing else changes: same puzzle, same mand_setup, same reference-table state, and the search is deterministic. So once the big table overflows, every retry repeats the same solve and overflows at the same place, forever. Neither solver checks g_stop_requested or the split timer.
   - The probe limit is not a way out. HT_PROBE_LIMIT is 65536 (line 431), and linear probing at 0.85 load on 16M slots does not reach it.
   - The multi-start solver is different: ms_slot (1825) returns -2 on overflow and falls back. So only the two sites cited loop.

2. What happens when it fires.
   - Worker: STATUS lines come only from the DFS loop (backsearch.c:4646-4651), so a hung worker goes silent. volunteer.py sets slot.last_line_at (line 868) but never checks it, so there is no watchdog.
   - Server: heartbeat() lists the job in 'holding', and jobs.js:514-518 extends its lease to now + lease_s on every heartbeat, so the lease never lapses.
   - Stealing: once the pool is empty, jobs.js work stealing hands the running job to an idle client. That client reruns the same deterministic subtree and hangs at the same solve.
   - Result: the job is never reported and the campaign never completes, while one core per holder spins at 100%. On Ctrl-C the client SIGKILLs the worker after STOP_GRACE_S = 90 s, so the volunteer machine can be stopped. That is a campaign stall, which the rubric rates high.

3. The verify solve. After run_exit_search, backsearch.c:5781-5786 runs a full sokoban_solve (no cutoff, no A*) on g_best_state for every job with best > 0, whether the job was exhausted, split or interrupted. This is the largest solve a job ever runs: it explores every state costing less than L without hdist pruning, a superset of the depth-2 cutoff check. Its value is only printed (5840, 5846). The client ignores it, and sanitizeSummary's whitelist (jobs.js:639) drops it. So it costs one extra full solve per job and exposes finished work to the hang.

4. How likely it is. Both solvers stop with -2 when pending entries reach HP64_SIZE = 1M, so the loop needs at least 14.26M distinct inserts while fewer than 1M are pending. That profile fits long, narrow state spaces, which is what this search looks for.
   - Campaign #1 (5x5, up to 3 holes) finished with all 166,733 jobs reported. Each job ran many cutoff solves plus one verify solve, and a hang would have repeated on every re-lease. So campaign #1's configuration never triggered it, and an identical campaign probably would not either.
   - For "more holes or another grid" it is plausible: solve_push64 covers 5x5 with up to 11 blocks and 4 holes, and 6x6 with up to 9 blocks. The HTP_SIZE comment (line 932) records multi-million-state 6x6 solves.
   - Given a permanent, silent stall with no detection, I keep the rating at high for a larger next campaign.

5. Other claims checked:
   - The 128-bit solvers have no fill limit; they only return -3 on probe failure. True.
   - The server discards verify. True.
   - A dynamic repro is not feasible under the rules: no single-level solve CLI exists, and a small-table build means compiling. The static proof is enough.

*fix notes*: 1. sokoban_bfs.c:1262 and 1751: replace the overflow branch with
     else if (hs->overflow) { if (use_big) { if (prof) { prof->peak_heap_sz = peak_heap; prof->states_popped = n_popped; } return -5; } use_big = 1; goto retry; }
   Document -5 in sokoban_bfs.h:56-63 as "table full: unknown, never a decision". Add a counter for these events (e.g. g_cap_bigfull) and emit it in the SUMMARY. Then add it to the sanitizeSummary whitelist at jobs.js:639, or have the server refuse to call an exit exhaustive while any job reports a nonzero count.

2. Lockstep caller change, required: backsearch.c:2218 only tests `x >= 0 || x == -2 || x == -3 || x == -4`. A new -5 would fall through and be ACCEPTED: it would be counted in g_accepted_valid and could become g_best_depth or a published best. That is critical, worse than today's hang. Handle -5 in the same commit as the other unknown codes (finding 1's UNKNOWN path), or at the very least prune it and count it. The experimental surrogate path at backsearch.c:1840 lacks -3 as well. The beam and harvest callers (3213-3426) test for `== -1`, so they already treat -5 as not valid.

3. Verify at backsearch.c:5781-5786: skip it when --split-after is given, since v2 discards the value, or use sokoban_solve_cutoff(depth-2) and print ok or unknown. This removes the riskiest solve from every job and saves one full solve per job.

4. Test: the macros HTP_SIZE (line 932) and HTP_SMALL_LG2 (line 980) have no #ifndef guards. The proposed build with -DHTP_SMALL_LG2=6 -DHTP_SIZE='(1<<10)' would hit a macro-redefinition warning, the file's own values would win, and the test would silently run with the 16M table. Add #ifndef guards first. Then on 4x4 with up to 3 holes, expect termination with cap_bigfull > 0, under a hard timeout that counts as FAIL.

5. Defense in depth, client side: volunteer.py already records last_line_at (line 868), and a hung solve stops all STATUS output. Add a watchdog: no line for about max(10 x status_every, 600 s) means kill the worker and report the job as failed or quarantined, not silently re-leased. A plain re-lease would hang again deterministically. Also consider a server-side alert for jobs held far beyond split_after + lease_s.
