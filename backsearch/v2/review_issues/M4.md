# M4: The forward solver retries forever when the 16M-slot big hash table reaches its 85% fill limit: the worker hangs with no split/stop check

verdict CONFIRMED, severity high, category robustness
locations: sokoban_bfs.c:1751 (solve_push64_cutoff: `use_big = 1; goto retry;` even when already on the big table); sokoban_bfs.c:1262-1266 (solve_push64, the same pattern, end-of-job verify solve); hsp64_update / hsp64_select(hs,1) (ht_limit = 0.85*16M = 14,260,633)

## Summary
On overflow, both 64-bit solvers set use_big=1 and jump back to retry, even when they are already on the big table. hsp64_select then rebuilds the same 14.26M-insert limit, and the identical solve overflows again, forever. Split and stop checks run only between expansions, so the worker never prints REMAINING or SUMMARY. The client keeps listing the job as running, so its lease is renewed indefinitely, and the worker only ends when the client is stopped and kills it after the 90 s grace. (F155 also restates the separate -2/-3 silent-prune issue.)

## Source report F4 (worker-dfs-split)
**The forward solver retries forever when the 16M big hash table fills: one expansion can hang with no split check** at /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:1751

*summary*: hsp64_update sets overflow when ht_count reaches ht_limit. On the big table that limit is 0.85 x 16M = 14.26M inserts. Both solve_push64 and solve_push64_cutoff handle overflow with `use_big = 1; goto retry;` even when they are already on the big table. The retry repeats the same solve and overflows again, forever. The split and stop checks run only between expansions, so the worker never prints REMAINING or SUMMARY. It only ends when the client kills it: on stop after the 90 s grace (STOP_GRACE_S = 90), or otherwise not at all.

*failure_scenario*: A shortcut check (or the final verify solve) meets a partial puzzle with more than 14.26M reachable push states whose pending frontier never exceeds 1M (a long, narrow search), so the -2 exit never fires first. On 5x5 that means an open board with many blocks; it is more likely on larger grids or with more holes. The worker spins at 100% CPU. The search is deterministic, so every client that leases the job hangs the same way. The job never completes, the campaign cannot finish, and a volunteer core is pinned until someone intervenes.

*evidence*: sokoban_bfs.c 1017-1021: `hs->ht_limit = (uint32_t)(HTP_SIZE * 0.85);` for big. 1054: `if (hs->ht_count >= hs->ht_limit) { hs->overflow = 1; return -1; }`. 1751-1755 (cutoff solver) and 1262-1266 (full solver): `} else if (hs->overflow) { /* Small table saturated: rerun this solve on the big one. */ use_big = 1; goto retry; }` with `retry: hsp64_select(hs, use_big); hsp64_clear(hs);` at 1526/1104.

*suggested_fix*: At both sites: `if (use_big) return -2;` before `goto retry`. Count it with the capacity-prune counter from the previous finding.

*expected_gain*: Removes an unbounded hang that would repeat on every client.

## Source report F17 (worker-prune-soundness)
**When the 16M-slot table saturates, the solver retries forever: worker hangs and its lease is renewed indefinitely** at /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:1751

*summary*: On table overflow both 64-bit solvers jump back to retry with use_big=1, even when they are already on the big table. That table has a fixed limit of 0.85*16M inserts, so the identical solve overflows again, forever.

*failure_scenario*: A shortcut check (or the final verify, which uses the same pattern at 1262-1265) inserts more than 14.26M distinct states while the queue stays below 1M. It overflows on the big table, clears it, reruns identically, and loops. The worker never reaches the between-expansion --split-after or status checks. The client keeps heartbeating, and jobs.js renews every lease the client holds on each heartbeat. So the job is never reissued, the exit's audit never becomes clean (campaign stall), and one volunteer core runs at 100% until the user stops the client. After a restart the same seed is leased again and hangs again. This is not expected at 5x5 with <= 3 holes; it becomes plausible on a larger grid or with more blocks.

*evidence*: sokoban_bfs.c 1751-1755: `} else if (hs->overflow) { /* Small table saturated: rerun this solve on the big one. */ use_big = 1; goto retry; }`. Line 1020: `hs->ht_limit = (uint32_t)(HTP_SIZE * 0.85);`. Line 1054: `if (hs->ht_count >= hs->ht_limit) { hs->overflow = 1; return -1; }`. There is no check that use_big was already 1; the same code appears in solve_push64 at 1262-1265. jobs.js ~501-518: 'Leases therefore expire lease_s after a client's LAST heartbeat, never while it is working' with `if (want > until) { until = want; q.extendLease.run(until, j.id); }`.

*suggested_fix*: `if (use_big) return -2;` before the goto, then handle -2 as in the silent-prune finding. Optionally add a per-solve insert or wall-clock guard, and have the worker check g_stop_requested inside long solves.

*expected_gain*: Turns a potential permanent stall and burned volunteer core into a reported, recoverable event.

## Source report F23 (solver-core)
**Infinite retry loop when the 16M-slot big push table reaches its 85% fill limit** at /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:1751

*summary*: When the table fills, hsp64_update sets hs->overflow, and the solver always jumps back to retry with use_big = 1, including when it is already on the big table. hsp64_select(hs,1) then rebuilds the same 14,260,633-insert limit, and the identical solve overflows again, forever. solve_push64 (lines 1262-1266), which does the end-of-job verify solve, has the same pattern.

*failure_scenario*: A cutoff solve inserts more than 0.85*2^24 = 14.26M distinct keys while fewer than 2^20 entries are pending. This is plausible because Dial's window holds only a few cost levels out of ~150. The worker spins in the retry loop at 100% CPU. It prints no STATUS lines, and --split-after is never checked because that timer lives in the DFS loop. volunteer.py has no wall-clock watchdog: it SIGKILLs only after a SIGINT grace period or a lease drop. The heartbeat's 'holding' list keeps renewing the lease (jobs.js ~502-517), so the job never finishes and the campaign cannot complete. When a volunteer stops, the job goes to the next client and hangs there too, because the solve is deterministic. Campaign #1 finished, so this never fired on 5x5 h3. The HTP_SIZE comment, however, records solves big enough to saturate an 8M table on 11-block 6x6 boards.

*evidence*: sokoban_bfs.c:1016-1020  static void hsp64_select(HashStatePush64 *hs, int big) { if (big) { ... hs->ht_limit = (uint32_t)(HTP_SIZE * 0.85);
sokoban_bfs.c:1054  if (hs->ht_count >= hs->ht_limit) { hs->overflow = 1; return -1; }
sokoban_bfs.c:1751-1755  } else if (hs->overflow) { /* Small table saturated: rerun this solve on the big one. */ use_big = 1; goto retry; }
sokoban_bfs.c:932-937  #define HTP_SIZE (1 << 24) /* ... probe-saturation was observed on 11-block 6x6 boards even at 65K-probe limit ... */

*suggested_fix*: In both solvers: `else if (hs->overflow) { if (use_big) { /* report */ return -2; } use_big = 1; goto retry; }`, counted per the silent-prune finding above. Separately, give volunteer.py a per-run watchdog: if no STATUS line arrives for about 3x status-every plus split_after, send SIGINT and then SIGKILL, and report the job as failed.

*expected_gain*: Removes a way for one job to stall the whole campaign and pin volunteer cores.

## Source report F155 (algo-worker)
**Undecided solver outcomes are pruned silently, and a big-table overflow retries the same solve forever** at /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:1751

*summary*: shortcut_check results -2 (more than 2^20 pending queue entries) and -3 (probe limit) are treated like 'a shortcut exists'. The state and its whole subtree are dropped, nothing counts it, and the job still reports 'exhausted'. Separately, once a solve is already on the 16M-slot big table and hits its 85% insert limit, the overflow branch jumps back to retry on the same big table and repeats forever.

*failure_scenario*: A deep check whose frontier exceeds 1,048,576 pending entries returns -2, and try_successor_x prunes it. If that state had no shortcut, every valid level below it (possibly the record) disappears without any trace in SUMMARY. This is more likely on 6x6, with more blocks, or with more holes. A check that inserts more than 14.2M distinct states while staying under 1M pending loops forever. The split timer is only checked between expansions, so the worker never splits. The lease expires, the job is re-leased, and it hangs again: the campaign stalls on that job. Whether -2 or -3 ever fired in campaign #1 cannot be checked, because nothing records it.

*evidence*: backsearch.c:2218 'if (x >= 0 || x == -2 || x == -3 || x == -4) { g_pruned_short++; ... return; }'; sokoban_bfs.c:1734-1736 'if (hs->pq_count >= HP64_SIZE) { ... return -2; }' (HP64_SIZE = 1<<20, line 939); sokoban_bfs.c:1020 'hs->ht_limit = (uint32_t)(HTP_SIZE * 0.85);' and 1054 'if (hs->ht_count >= hs->ht_limit) { hs->overflow = 1; return -1; }'; sokoban_bfs.c:1751-1753 '} else if (hs->overflow) { /* Small table saturated: rerun this solve on the big one. */ use_big = 1; goto retry; }' (same in solve_push64 at 1262-1264); SUMMARY (backsearch.c:5845-5849) has no counter for these outcomes.

*suggested_fix*: Count -2 and -3 separately and print both in SUMMARY. In campaign mode, treat any undecided check as a job error (non-zero exit or status 'error') so the job is retried or flagged, never reported exhausted. On overflow while already on the big table, return -2 instead of goto retry. Apply the same to solve_push128_cutoff, which returns -3 on its probe limit and -2 at HP128_SIZE.

*expected_gain*: Exactness and stall protection; no speed effect.

## Verifier (CONFIRMED, high, refuted=False)
The loop is real and certain once triggered. Only the trigger's likelihood is uncertain.

1) The code, confirmed in /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:
- hsp64_select (1016-1024): `if (big) { ... hs->ht_limit = (uint32_t)(HTP_SIZE * 0.85); }` with HTP_SIZE = 1<<24 (line 932), so the limit is 14,260,633 inserts.
- hsp64_update (1054): `if (hs->ht_count >= hs->ht_limit) { hs->overflow = 1; return -1; }`
- solve_push64_cutoff (1751-1754) and solve_push64 (1262-1265) both have: `} else if (hs->overflow) { /* Small table saturated: rerun this solve on the big one. */ use_big = 1; goto retry; }`
- Neither site checks whether use_big is already 1. `retry:` (1104-1106 / 1526-1528) calls hsp64_select(hs, 1) and hsp64_clear(hs). That resets ht_count, overflow, the buckets and probe_failed, and re-runs mand_setup(pz). The inputs are unchanged: pz, max_cost, the ref table (g_ref_on) and the thread-local state. So the rerun is bit-for-bit identical and overflows at the same insert, forever. Nothing grows, so it is a pure 100% CPU spin.
- The 128-bit solvers have no ht_limit and no goto retry, so they are not affected. The multi-start solver returns -2 on its own table limit (1825, 1943, 2051, 2060, 2070). But its caller (backsearch.c 2420-2437) falls back to try_successor_x -> shortcut_check -> sokoban_solve_cutoff -> solve_push64_cutoff, so bulk checks can also reach the loop.

2) The trigger is possible, not just theoretical. The loop needs about 14.26M distinct inserts while pq_count stays below HP64_SIZE = 2^20. Otherwise the -2 at 1734/1245 returns first.
- Inserts are roughly pops plus pending. A Dijkstra/A* whose frontier covers only a few cost levels out of ~150 can keep fewer than 1M pending entries while settling more than 13M states.
- ref_prunes_at (1731) inserts labels without enqueuing them, which pushes the ratio further toward overflow.
- The end-of-job verify solve (backsearch.c:5785, `verify = sokoban_solve(&pz, NULL, NULL);`) is a plain Dijkstra with no A*, no cutoff and no decision-mode early exit. It is the largest solve a job does, and it runs at the end of every job that found a level. So it is the most likely site to overflow. If it hangs, the whole job's work (up to split_after) is lost, because SUMMARY is never printed.

3) Nothing interrupts a hung worker:
- The stop and split checks run only between expansions (backsearch.c:4645 checks g_stop_requested; 4646-4650 check split every 1024 iterations). on_stop_signal (496) only sets a flag.
- volunteer.py records slot.last_line_at (868) but never reads it, so there is no no-output watchdog. SIGKILL happens only on stop after STOP_GRACE_S = 90 (1393-1397), on force-quit, or on a lease drop.
- jobs.js ~501-518 extends every lease the client holds on each heartbeat ("Leases therefore expire lease_s after a client's LAST heartbeat, never while it is working").
- Result: the job stays running and leased for as long as the volunteer's client runs, with one core pinned. After a stop or restart the job is released or expires and is re-leased. It hangs again on the next client, because the solve depends only on the state, depth-2 cutoff and ref table, which are nearly always the same. The exit's audit never becomes clean, so the campaign stalls.

4) It did not fire in campaign #1.
- The retry code dates from commit 9488a76, so it was in the campaign worker.
- The snapshot shows all 167,766 jobs done or split. The largest elapsed_s is 1824.8 s (split_after 1800), and the slowest average is about 109 ms per solver call. A permanent hang would have blocked completion, so on 5x5 with at most 3 holes no solve reached 14.26M inserts.
- The next campaign may be larger (more holes on 5x5, or 6x6 with up to 9 blocks, which still uses the 64-bit packing: 6*(1+nb)+nh <= 64). The HTP_SIZE comment at 932-937 records that 6x6 boards already saturated an 8M table. So the trigger is plausible for the next campaign, but I cannot quantify how likely it is.

5) Severity: high. It is a campaign stall plus a pinned volunteer core, silent and repeated on every client that takes the job. It is not critical, because it cannot put a wrong maximum into a published result: the stuck subtree simply never completes.

6) Added consequence, important for the fix: three of the four source reports suggest `if (use_big) return -2;`. With the current worker that is a soundness regression. try_successor_x (backsearch.c:2218) treats -2 and -3 as "prune": `if (x >= 0 || x == -2 || x == -3 || x == -4) { g_pruned_short++; ... return; }`. Nothing counts it, and the job still reports "exhausted". Returning -2 would turn a visible hang into a silently dropped subtree, which could lose a valid level and make a published maximum inexact. That is a critical failure mode. The fix must go together with making undecided outcomes a job error. Likewise, a verify-solve overflow must not hide or alter the SUMMARY result.

*fix notes*: 1) Solver (sokoban_bfs.c, both solve_push64 at 1262 and solve_push64_cutoff at 1751): `} else if (hs->overflow) { if (use_big) { if (prof) {...} return SOK_UNDECIDED_TABLE; /* e.g. -5 */ } use_big = 1; goto retry; }`. Use a distinct code, not -2, so callers can tell it apart. Optionally make the big-table limit a settable parameter, for tests and for an opt-in larger table on big-memory machines. Do not grow the table automatically: 16 workers x 256 MB is already 4 GB on a volunteer machine.

2) Worker (backsearch.c): count every undecided shortcut outcome in its own counter: -2 heap cap, -3 probe or heap cap, the new -5, and the 128-bit -2/-3. Print the counter in SUMMARY. In campaign mode (for example whenever --seed-path or --split-after is given), any undecided outcome must make the job non-exhaustive. Either exit non-zero with a clear "UNDECIDED depth=... state=..." line before any pruning, or finish and report status "undecided" so the server never counts the subtree as done. Do not prune silently at line 2218, and keep -4 (--shortcut-state-cap) disabled in campaigns.

3) Final verify (backsearch.c:5785): an undecided result there must not block or alter the job result. Print "verify: undecided" and keep the job's SUMMARY. Better, skip the verify in campaign mode, since the server re-verifies levels with its own solvers.

4) Client (volunteer.py): add a per-run watchdog. If a worker prints no STATUS or other line for max(3 x status_every, 600 s), send SIGINT, then SIGKILL after STOP_GRACE_S, and report the job as failed with a reason. slot.last_line_at (line 868) is already recorded but never used. The worker's STATUS lines come only from the DFS loop, so a long silence reliably means one solve is stuck.

5) Server (jobs.js): record per-job failure reports. After N failures or undecided reports on the same job, stop re-issuing it and flag it on the campaign page for the owner, so the audit shows why the exit is not complete.

6) Tests: add the solver unit test described in repro_plan with a lowered big limit. Add a fake_worker mode that prints nothing after start, to test the client watchdog. Add a server test that an 'undecided' report neither marks the job done nor lets the exit's audit become clean.
