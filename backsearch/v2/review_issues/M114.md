# M114: Hash rollout order is not enforced, and the refusal message always says 'git pull', even when the build is newer than the whitelist

verdict CONFIRMED, severity low, category protocol
locations: volunteer.py:397 (refusal message); server hash whitelist; GitHub main as the build source

## Summary
The whitelist is the only list of accepted versions, and new volunteers build from GitHub main. If main's worker sources change before the owner whitelists the new hash, every fresh clone, and every volunteer who follows the 'git pull' advice, is refused with instructions that cannot fix it.

## Source report F199 (robustness-ops)
**Hash rollout order is not enforced, and the refusal message always says 'git pull' even when the build is newer than the whitelist** at /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py:397

*summary*: The whitelist is the only accepted-version list, and GitHub main is where new volunteers build from. If main's worker sources change before the owner whitelists the new hash, every fresh clone, and every volunteer who follows the 'git pull' advice, is refused with instructions that cannot fix it.

*failure_scenario*: The owner pushes a worker speed-up to main during campaign #2 and whitelists it an hour later, or forgets. New volunteers from collective.html build it and are refused: 'source hash X is not accepted ... git pull && ./build_pgo.sh'. Pulling changes nothing, and they give up. Volunteers who restart after pulling are locked out the same way.

*evidence*: volunteer.py:397-403: `if self.src_hash not in hashes: sys.stderr.write("\nThe worker's source hash %s is not accepted by the campaign.\n" "Accepted: %s\nUpdate and rebuild in the backsearch directory:\n" "    git pull && ./build_pgo.sh\n...")`. The server exposes only the hashes, not the commits they correspond to (jobs.js:324 publicCampaign).

*suggested_fix*: Store the git commit next to each whitelisted hash (v2_hashes add <hex> --commit <sha>) and return it in the campaign. The client then prints `git checkout <sha> && ./build_pgo.sh` when its hash is unknown. Document the owner rule: whitelist the new hash before pushing to main.

## Verifier (CONFIRMED, low, refuted=False)
The issue holds. check_hash (volunteer.py:392-403) compares the worker's hash only against campaign.hashes. On a miss it always prints 'Update and rebuild in the backsearch directory: git pull && ./build_pgo.sh' and exits 2, with no hint that the build could be newer than the whitelist. The server keeps only hex strings: publicCampaign (jobs.js:321-328) returns `hashes: hashesOf(c)`, and v2_hashes.js takes only `add <hex>`, with no commit or tag. Nothing maps a hash to a git revision, so a volunteer cannot find a build that would be accepted. DESIGN.md:17-19, README 'Owners' and v2_hashes.js document no ordering rule such as 'whitelist the hash before pushing to main'. Setup on collective.html and hunt.html clones the default branch (main), which this checkout confirms is where the v2 work lives (v2 is an ancestor of main; origin/main = aa7f0bf). So if the owner pushes a worker-source change to main before running `v2_hashes add`, every fresh clone is refused with advice that cannot help. The damage is bounded: it lasts only until the owner whitelists the hash, and the refusal happens at startup before any lease, so no work or leases are lost. It is an owner-process gap with an easy procedural fix, so low severity stands. It compounds with M13: even when pulling is the right advice, the printed build command rebuilds the wrong binary.

*fix notes*: (1) Document the owner rule in README 'Owners' and DESIGN §4: compute the new SRC_HASH (the build_pgo.sh line 41 formula), run `v2_hashes add` first, then push. (2) Let v2_hashes add take --commit <sha> (or have the owner tag the commit `worker-<hash8>`). Store it and return it in publicCampaign next to each hash. On a miss the client then prints `git fetch && git checkout <sha> && ./build_pgo.sh -o backsearch_worker_nt --no-torch`. (3) Make the refusal message say that the worker may be newer than what the campaign accepts, and point to the hunt page's hash list. (4) Optionally add a CI or pre-push check that fails when the SRC_HASH of main is not in the live whitelist.
