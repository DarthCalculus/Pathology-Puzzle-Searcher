## Verifier (CONFIRMED, low, refuted=False)
The comment at solver6.c:1026-1029 ('allocated during setup and freed before the main hash table is allocated, so the process peak is max(this, main table), not the sum') is false.

What the code does:
- In the loop at 1940-2022, phase 0 calls alloc_tables() (2015), which mallocs the full table (HSLOTS*10 B, about 0.88*budget) and fully memsets it via ht_touched_reset(1).
- Only a level that exceeds PHASE1_CAP (30,000 states) then enters phase 1, which mallocs rlx_pool (86*713,924 ≈ 61 MB virtual), rlx_ht (2^21*4 = 8 MiB, memset) and rlx_touch (4 MiB) at 1966-1971.
- Phase 1 reuses the same table: alloc_tables sees HSLOTS <= cap_slots_w and does not reallocate.
- Line 2003 says the pool persists, and there is no free(rlx_*) anywhere.
- The main-table touch list ht_touch (2^21*4 = 8 MiB, malloc'd lazily at 413) is also outside `bytes`.

One correction to the finding's number: the pool is indexed with RLX_STRIDE = 22 + ceil(nb/2) (1138, 1205, 1283, 1310), so only that many bytes per state become resident. For a 5x5 level with about 12 blocks that is about 28 B*714k ≈ 20 MB, not 61 MB. rlx_touch is resident only up to about 2.9 MB. The realistic resident overshoot is about 40 MB per hard level (about 82 MB virtual upper bound), roughly 7-15% of a 0.5 GiB budget. Two concurrent escalations then come to about 1.15 GB plus node, still under the 2 GiB cgroup. That roughly matches pipeline.js:7-10's 'near 1.2G', which does not cite the oracle comment. Margins get thinner if SOLVER_MAX_CONCURRENT is 3 (the solver.js default) or if SOLVER_GIB is raised. Documentation and sizing only, so low.

*fix notes*: Fix the comment at 1026-1029. The pool, its index and the touch lists are allocated after the main table and coexist with it. The total overshoot is about 8 MiB index + RLX_STRIDE*states pool + up to 12 MiB of touch lists. Either subtract RLX_BUDGET_MB plus the touch-list sizes from `bytes` before computing HSLOTS (1915-1917), or free rlx_* after the oracle in single-level (non-batch) mode. Update pipeline.js:7-10 to state per-process peak ≈ SOLVER_GIB + ~50-80 MB, and reconcile its SOLVER_MAX_CONCURRENT=2 note with the solver.js default of 3.
