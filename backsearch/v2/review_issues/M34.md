# M34: Champion verification is best-effort and not required at publish: v2_finish publishes a maximum the site solver never re-solved

verdict CONFIRMED, severity medium, category soundness
locations: v2_finish.js:61 (refuses only if verified_moves is non-null and differs); v2routes.js:62 (verifyLater: in-memory, fire-and-forget, only for a strictly new per-exit best, queued behind public solver traffic); finishJob (never clears verified_moves); exitSummary MAX(best) vs champion = best job with level_code; collective.html ('every reported level is re-solved'); no tests for exitSummary/v2_finish/campaignsSummary

## Summary
A level is re-solved only if it was a strictly new per-exit best when reported, by an in-memory job after the commit. A restart, a crash, a 30 s timeout or 'too_complex' leaves verified_moves NULL for good, and later equal reports are not a new best, so nothing retries. finishJob never clears verified_moves when it replaces a level. v2_finish refuses only when a stored verification disagrees, so an unverified (or stale-verified) maximum, taken as MAX(best) over all jobs and possibly differing from the champion row, is published after a printed note. The page claims every reported level is re-solved, and none of this publishing path is tested.

## Source report F97 (server-ingest-routes-tools)
**Champion verification is not enforced at publish time and verified_moves can be stale** at /Users/george/PathologyRecords/server/tools/v2_finish.js:61

*summary*: The champion is chosen when read (ORDER BY best DESC, id), but a level is re-solved only if it was a strictly new per-exit best when reported. finishJob never clears verified_moves. v2_finish publishes when verified_moves is null, and the campaigns page claims the exhaustive result from the audit alone.

*failure_scenario*: (a) Job 50 reports 149 after job 100 already has 149. It is not a new best, so it is never re-solved, but bestOfExit picks id 50; v2_finish prints '(not re-solved yet)' and publishes anyway. (b) An open probe row verified at 140 is later finished with best 149 while another job already holds 149. It keeps verified_moves 140, so the pages show '⚠ 140' and v2_finish refuses with 'SOLVER SAYS 140!' although the level is fine. (c) On a larger grid where solver6 needs more than 30 s or 0.5 GiB, every champion stays null and every proof publishes unverified. (d) If the MAX(best) row has no level_code, a lower row becomes the champion and the refusal message is misleading. Campaign #1 is fine: all six champions are verified and agree.

*evidence*: jobs.js:799 `const newBest = bestNode && bestNode.best != null && (prevBest == null || bestNode.best > prevBest) ? bestNode : null;`. finishJob's column list (287-288) has no verified_moves. 301-302 `ORDER BY j.best DESC, j.id`. v2routes.js:153 verifies only `o.new_best`. v2_finish.js:59-61 `const v = s.best_level.verified_moves; ... if (v != null && v !== best) { ... refused` (null passes). jobs.js:876 campaignsSummary gates only on `x.clean`.

*suggested_fix*: In v2_finish, solve the champion synchronously with a generous budget and refuse unless the result equals MAX(best) and the champion's own best equals MAX(best). Set verified_moves = NULL in finishJob. Break bestOfExit ties in favour of verified rows. Optionally require verified_moves == best in campaignsSummary.

*summary*: The re-solve of a new per-exit best runs in the server process after the transaction commits. ## Verifier (CONFIRMED, medium, refuted=False)
I read the code and every claim holds.

1. The re-solve is fire-and-forget, in memory, and never retried. v2routes.js:62-72 `verifyLater` runs `measureLevel(code, { seconds: VERIFY_SECONDS })` (30 s) in a detached async block. It calls it only for `o.new_best` (v2routes.js:153). jobs.js:799 sets `newBest` only when `bestNode.best > prevBest` (strictly greater). A grep of lib/, tools/ and server.js shows that verifyLater is the only caller of setVerifiedMoves. Nothing re-verifies a NULL row at startup or in the sweeper, where startSweeper only runs sweepLeases. So a restart during the solve, a queue wait behind solver.js's 3-slot FIFO (MAX_CONCURRENT=3, shared with public /api/solve), a timeout, or 'too_complex' at 0.5 GiB leaves verified_moves NULL for good. It is worse than the reports say: when measureLevel returns `{ok:false, reason:'unsolvable'}`, i.e. the site solver definitively disagrees, the code only logs a warning (line 67) and stores nothing. v2_finish then shows it as "(not re-solved yet)" and publishes.

2. v2_finish does not require verification. v2_finish.js:61 is `if (v != null && v !== best) { ... refused }`, so NULL passes. addProof runs at line 64 with `maxMoves: best` = `s.best`, which is exitSummary's MAX(best) (jobs.js:1027). addProof (db.js:654-680) only checks for a stored verified level with more moves. processSubmission then re-solves the champion afterwards (line 68, again with a 30 s budget). If it rejects the champion, the proof has already been written.

3. The tie-break makes an unverified champion likely. bestOfExit (jobs.js:301-302) uses `ORDER BY j.best DESC, j.id`: lowest id, not first reporter. In the campaign #1 snapshot, exit 2 has two 112 rows (9182 verified, 20627 NULL) and exit 6 has two 138 rows (17462 verified, 17765 NULL). So 2 of 6 exits had ties. Both times the lower id happened to be the verified row, so campaign #1's six champions are all verified and agree. In a later campaign, an earlier-created, longer-running job that reports a tying level later becomes the champion with NULL. It shows no check mark and publishes with a note. In that tie case the maximum value was still verified on the other row, so the harm is misleading tooling, not a wrong number.

4. The stale-verification variant is real but rare and fails safe. finishJob (jobs.js:287-288) does not reset verified_moves, and the client does send levels on open probe nodes (volunteer.py:667-672, 708-709). An open probe verified at X keeps X after it finishes with best Y > X, if Y is not a new best. It can then be champion and trigger a spurious "SOLVER SAYS X!" refusal plus a ⚠ on the pages. A variant: the same length with a different level shows "solver agrees" for a level that was never solved.

5. Scenario (d), a MAX(best) row with no level_code, does not occur in practice. In the snapshot, every row with level_code NULL has best 0. It stays a latent edge case.

6. The docs and tests mismatch. collective.html:83-84 says "Every reported level is re-solved by the site", but only 62 of 42,134 level rows in the snapshot are verified (DESIGN §7.8 intends new bests only). The tests never mention exitSummary, v2_finish or campaignsSummary (grep count 0 in test/v2_gates.test.js).

Severity: medium for the next campaign. The site re-solve is the only independent check of the published maximum's move count. It can be skipped silently by a redeploy within about 30 s of the final best (redeploys happened in campaign #1), by a tie, or by a larger grid where solver6 needs more than 30 s or 0.5 GiB (then every champion stays NULL). Even an explicit 'unsolvable' verdict is turned into "not re-solved yet". A wrong published maximum still needs a bug in the worker's own solver as well, and the owner sees the printed note when running v2_finish manually, so this is not critical. Campaign #1's proof is unaffected (all six champions verified and equal to best). Per owner direction, no revocation is proposed.

*fix notes*: For the next campaign:
(1) v2_finish.js: before addProof, re-solve the champion synchronously with a generous budget, e.g. `measureLevel(code, { seconds: 600, gib: 4 })`. Refuse the exit unless m.ok && m.moves === s.best && s.best_level.best === s.best. Do not accept NULL as a pass. Run processSubmission before addProof, or refuse the proof when the champion is not stored.
(2) jobs.js finishJob (287-288): add `verified_moves = NULL` to the UPDATE so a replaced level never keeps an old verification.
(3) jobs.js bestOfExit (301-302): tie-break in favour of verified rows: `ORDER BY j.best DESC, (j.verified_moves = j.best) DESC, j.id`.
(4) v2routes.js verifyLater: store a definitive 'unsolvable' as a sentinel, e.g. verified_moves = -1 or a separate verify_status column, so the pages show a disagreement instead of nothing.
(5) Add a retry: in startSweeper or at server start, check each active exit's champion. If verified_moves is NULL, queue at most one re-solve at a time. Optionally give v2 its own solver slot so public /api/solve traffic cannot starve it.
(6) Fix collective.html:83-84 to say that each exit's longest level is re-solved.
(7) Tests: make db.js honour a DATA_DIR override. Then test exitSummary and v2_finish against temp jobs.db/records.db covering: a NULL-verified champion (must refuse), a tie with a later-reported lower id, a stale verified_moves after finishJob, and an 'unsolvable' result.
