# M58: The exit-preference 'working…' spinner never ends when the preferred exit has no open jobs

verdict CONFIRMED, severity low, category bug
locations: volunteer.py:1241 (exit_applied set only when a leased job has the preferred exit)

## Summary
exit_applied becomes True only when a leased job has the preferred exit. When the server keeps falling back to other exits, the flag 'current jobs finish first; new leases use exit N' spins forever, although no lease will ever use exit N.

## Source report F64 (client-ui)
**Exit-preference 'working…' spinner never ends when the preferred exit has no open jobs** at /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py:1241

*summary*: exit_applied becomes True only when a leased job has the preferred exit. When the server keeps falling back, the pending flag 'current jobs finish first; new leases use exit N' spins forever, although no lease will ever use exit N.

*failure_scenario*: The volunteer prefers an exit whose open pool is empty (for example one that has finished, or one drained near the end of a campaign). Every lease returns other exits with exit_fallback=true. The panel shows both the fallback banner and a permanent spinner promising 'new leases use exit N', which is false.

*evidence*: volunteer.py:510-515 `if any(j["exit"] == pref for j in good): self.exit_applied = True ... self.exit_fallback = fallback`; :1241-1242 `if self.exit_pref is not None and not self.exit_applied and not self.stopping: p["exit"] = "current jobs finish first; new leases use exit %d" % self.exit_pref`.

*suggested_fix*: Do not set the exit pending flag when exit_fallback is True; the banner already explains it. Alternatively, mark the change as applied once any lease response has arrived after set_exit.

## Verifier (CONFIRMED, low, refuted=False)
Confirmed. set_exit (volunteer.py ~1054-1057) sets `exit_applied = ex is None`. The only place that sets it True is the leaser, at lines 510-512 (`if any(j['exit'] == pref for j in good): self.exit_applied = True`). pending_flags (1241-1242) shows 'current jobs finish first; new leases use exit N' whenever the preference is not yet applied. When the preferred exit has no open jobs, every lease falls back (jobs.js ~590-597 sets fallback when j.exit !== pref), so the spinner and the fallback banner (volunteer_ui.html:272) show together, with contradictory messages. There is one more variant. The server's work-stealing path (jobs.js ~608-627) hands out jobs of any exit while `fallback` stays false. The client then records exit_fallback=false and the spinner shows WITHOUT the explanatory banner. The spinner is permanent only while the exit stays drained: if splits by others later add open jobs for exit N, the next lease clears it. For a finished exit it never clears. Cosmetic only; lease behaviour is correct.

*fix notes*: Once a lease response arrives after set_exit whose jobs are all from other exits (exit_fallback true, or stolen jobs), replace the spinner with a static note: 'no open jobs for exit N; using other exits, retried at each lease'. Or suppress p['exit'] while exit_fallback is set. Have the server set exit_fallback on stolen jobs whose exit differs from pref. Optionally mark exits with open == 0 in the selector (the data is already in st.exits).
