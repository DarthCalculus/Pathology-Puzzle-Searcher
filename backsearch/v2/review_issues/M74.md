# M74: A single fingerprint mismatch blocks an exit forever, with no tool to resolve it

verdict CONFIRMED, severity low, category robustness
locations: jobs.js:1001 (mismatch=1 on both rows; exit permanently unclean); reissueJob exported but unused

## Summary
A mismatch sets mismatch=1 on both rows and makes the exit permanently unclean. No tool re-runs the pair or clears the flag (reissueJob is exported but unused), so one flaky dup, for example from a machine fault, blocks that exit's proof until someone edits the DB by hand.

## Source report F105 (server-ingest-routes-tools)

*failure_scenario*: A flaky volunteer machine returns a different states count on a 2% re-check in campaign #2. That exit never audits clean and v2_finish refuses forever; the only way out is hand-written SQL on the live jobs.db.

*evidence*: jobs.js:809 `q.setMismatch.run(job.id); q.setMismatch.run(orig.id);`; 1001 and 1005 push to mismatches, 1013 requires none. reissueJob (434-442) is not used by any tool.

*suggested_fix*: Add a v2 tool that issues independent re-runs of a mismatched pair and clears the flag when a majority agree (or resets the original with its subtree), and document it in README.

## Verifier (CONFIRMED, low, refuted=False)
Confirmed. A dup-check mismatch sets mismatch=1 on both rows (jobs.js:806-811). A late duplicate report sets it on the stored job only (762-768), and the conflicting fingerprint then survives only in reports.summary JSON, with no job row. auditExit adds any row with mismatch=1 to `mismatches` (1001, 1005), clean requires mismatches.length === 0 (1013), and v2_finish.js:41-42 refuses to publish that exit.

No code path ever clears the flag:
- setMismatch only sets it (291).
- resetJob (314-315) resets status and fingerprint columns but not mismatch.
- reissueJob (434-442) only inserts a new dup of the original and cannot clear the original's flag. It is used only in test/v2_gates.test.js:156, and no tool or route calls it.

So one mismatch makes that exit permanently unpublishable without hand-written SQL on the live jobs.db, which is risky. Blocking on a mismatch is the correct conservative default, because a differing 'valid' count means one of the runs is wrong. The gap is the missing resolution tool.

Mismatches are rare. Campaign #1 had 0 in 1,009 dup checks (done:match) and 1,411 late duplicates. A larger campaign on more heterogeneous machines makes one more likely, so severity stays low (operational and recoverable).

*fix notes*: Add tools/v2_mismatch.js with --list and --resolve JOB [--runs 2].
- --list shows each mismatched pair, including late-duplicate fingerprints read from the reports table.
- --resolve issues N fresh dups via reissueJob, preferably leased to different clients.
- When a majority of fingerprints agree with the stored original, clear mismatch on the original and on the agreeing dups, and record the resolution in reports.
- When the majority disagrees with the original, run resetJob on it together with its subtree (delete descendant rows) so it is searched again.

Add a jobs.clearMismatch(id) helper with a test in v2_gates.test.js, and document the tool in README.
