# M104: The sound mandatory-hole prune is off for campaigns, and its eager setup would eat much of its gain

verdict PLAUSIBLE, severity low, category performance
locations: sokoban_bfs.c:805 (mand_setup rebuilds the push-closure table for every mask and cell when walls change); campaign command lacks --mandatory-holes; worker help calls it a sound 'big win on dense/deep walled multi-hole boards'

## Summary
Every shortcut-check puzzle is walled (all uncommitted cells are walls) and has up to 3 holes, which is exactly the case the worker's help calls a big win for --mandatory-holes, but the campaign command does not enable it. Enabled as written, mand_setup would rebuild the push-closure table for every present mask and every cell whenever the walls change, which is nearly every consecutive check, because siblings differ by one committed cell. It needs incremental or cached setup before it pays off.

## Verifier (PLAUSIBLE, low, refuted=False)
The premise holds, the setup-cost half is overstated, and nobody has measured the gain. Worth one cheap A/B before campaign #2, but it may not pay off.

1. The prune is off in campaigns (confirmed).
- backsearch.c:76 has `static int g_mandatory_holes = 0;` and :5519 has `sokoban_set_hole_prune(g_mandatory_holes);`.
- Campaign #1's extra_json in the snapshot is exactly ["--allow-exit-transit","--num-holes","3"].
- The help text at :4677-4683 calls it a "sound speedup ... Big win on dense/deep walled multi-hole boards". That claim was written for the ported solver6 (full level solves). No measurement exists in the backsearch context: I found no results log, no CHANGES entry and no memory note for it. solvebench.c has a `--mand` switch, but it only replays single sokoban_solve_cutoff calls, not the multi-start solver.

2. It looks sound, so it should not risk exactness. I checked the argument against the code.
- Mandatory classification (sokoban_bfs.c:774-781) floods from player_start over walls plus that one hole. The player can never stand on an unfilled hole (walk_dists uses walls|cur_holes|blk_occ). So a hole that cuts start from exit must be filled by a distinct block, since blocks are consumed.
- The block closure (:746) only checks walls, so it is a superset of where a block can go.
- have-need never increases along a path. A push only shrinks a block's closure (the closure-monotonicity comment at :869). Filling a mandatory hole lowers need by 1 and have by at least 1. So a dead state has only dead descendants.
- Multi-start solver (sokoban_solve_multi :1850): mand_setup uses pz->player_start = P. bulk_generate takes every start from P's component over committed & ~blk & ~hol & ~exit (backsearch.c:2320). Those paths avoid walls and holes, so the classification is identical for every start.
- Reference-table export (:1498): pruned states are all dead, and the rest(Y) bounds are facts about the owner's puzzle. The delta check still covers child-only floor cells, so the ptab pruning stays sound.
- Decisions should therefore be unchanged. accepted/valid/states should match exactly, except where a -2 overflow or state-cap path used to fire; there the prune can only avoid a conservative prune.

3. Setup cost is real but about 5-10x smaller than claimed.
- mand_setup (:769-809) already caches on the wall set. It exits early when no hole is mandatory (`if (!mh) return;`). Walls get 0 without a closure call. On a wall change it rebuilds every present mask for every non-wall cell.
- Walls change on new-cell children and when the DFS switches between sibling subtrees. Walk-backs over committed cells (47% of checks per WBPROF, one multi call) and pushes landing on committed cells keep the parent's walls. So "nearly every consecutive check" is an overstatement; I'd guess 30-60% of calls.
- Cost per rebuild: I counted block_closure's inner loop in Python.
  - Random walled 5x5 regions of 10-20 cells with 2-5 masks: median about 860 inner ops (p10 190, p90 2300). At 1-2 ns each that is about 1-4 µs.
  - Worst case, the open 149 board with 5 masks: about 4300 ops, about 6-8 µs.
- Snapshot µs per solver call (total elapsed / solver_calls): e0 80, e1 126, e2 97, e6 73, e7 27, e12 22.
- So amortized overhead is roughly 1-8% at exits 7/12 (together about 7% of the CPU) and under 2-3% at exit 1 (55% of the CPU). It is not "roughly the cost of the check itself", and it would not eat a gain of more than a few %.

4. The gain is unknown, and the only related measurement is a warning sign. The HOLEBOUND comment (:1293-1309, measured 2026-09-18) covers the same situation: the player cannot reach the exit across the unfilled holes. That bound, including its no-qualifying-block death case, cut only 1-2% of pops on the replay corpus. That corpus was probably shallow (a 5 s exit-0 harvest). The mandatory prune is stronger in two ways: it counts (one distinct block per mandatory hole) and its reach test honours walls, which is tight in walled partial puzzles. My estimate is 0-10% less solver time, with low confidence. It could be more on deep 2-3-hole exit-1 subtrees. Only a run can settle it.

Adoption costs almost nothing: add a flag to extra_json. SRC_HASH is unchanged, since flags are not hashed, and the dup cross-check stays consistent because decisions do not change.

Two hazards if it is adopted:
- The parser (:4977) reads a following digit-leading token as a FORCED cell list, which is unsound by design. `--mandatory-holes` must never sit directly before a number in extra; put it last. jobs.js createCampaign does not validate extra at all.
- The PGO training run (build_pgo.sh TRAIN_ARGS "--grid 5x5 --exit 0 --time 4") uses neither --allow-exit-transit, --num-holes nor the prune. Retrain with campaign-like flags.

*fix notes*: 1. Make the closure table cheap before or together with adopting the flag. Replace block_closure's cell-by-cell fixpoint with a bitboard one. Once per wall set, compute S_d = cells whose stand cell (opposite d) and landing cell (d) are both on-board and not walls. Then iterate set |= shift_d(set & S_d) for each d in the mask until it stops changing: about 10-30 ns per closure and well under 1 µs per full rebuild. Alternatively, or as well, keep a small multi-entry cache (4-8 wall sets). The finder's lazy per-(mask,cell) table with a generation stamp also works, but adds a check to every lookup in mand_pop_ctx.
2. A/B as in repro_plan, and also run test_split_exact with the flag. Build once with -DMAND_ASSERT to cross-check the fast and slow death tests on the same roots (needs a compile; do it when the CPU cap allows).
3. If adopting: use extra ["--allow-exit-transit","--num-holes","3","--mandatory-holes"] with the flag last. In jobs.js createCampaign, reject a digit-leading token right after --mandatory-holes, since that is the unsound forced-cell form. Consider rejecting --allow-block-on-exit there too. Retrain PGO with campaign-like TRAIN_ARGS (transit, --num-holes 3, --mandatory-holes); the current training run uses none of them.
4. Correct the worker help text: the "big win" claim was never measured in the backsearch shortcut-check setting.
