## Verifier (PLAUSIBLE, low, refuted=False)
All three code defects exist, but the concrete failure scenario for (a) is refuted, and none of the three can fire in campaign jobs.

(a) The code is as described: sokoban_bfs.c:1515-1518 returns before hsp64_clear, so last_exhaustive stays stale. The multi-exit scenario does not occur, though. After each exit, backsearch.c:5782-5785 calls sokoban_solve on the exit's best state. That goes to solve_push64, whose hsp64_clear (1106) sets last_exhaustive = 0 (1039). g_best_depth is reset per exit (4358) and is always > 0, because depth-1 walk children have no blocks and are always accepted (max_cost < 0 returns -1). So the next exit's depth-1 children see last_exhaustive = 0 and export nothing.

The only remaining trigger is when the previous exit's best needs the 128-bit solver. The sokoban_solve dispatch at 2674-2676 does not reset the flag on that path. That needs 12 or more blocks on 5x5 with 3 holes and is impossible on 4x4, so the finder's 4x4 scenario cannot happen. In that narrow case, if the last cutoff solve used a reference (last_ref_used = 1), the fold loop in sokoban_export_settled (1507-1509) reads g_ref_keys[0]. sokoban_clear_reference (1403, called at backsearch.c:2668) has set that pointer to NULL, so the result is a segfault, not a silent over-count.

Campaign jobs are unaffected: each process runs one exit, and all roots are at depth 4 (snapshot min depth 4; every roots_h3 line has depth 4), so max_cost >= 3. The first solve in a process sees last_exhaustive = 0 from calloc (1007).

(b) ht_seq is uint32. The largest job made 112,449,768 solver calls (snapshot), with at most about 2 clears per call, far below 2^32. Even after a wrap, a stale MSLab entry would also need a slot still holding gen == 2 after 2^32 clears. The code gap is real but negligible.

(c) The multi solver returns -2 when maxcut >= 254 (1904), so depth is at most 255 there. kk > 250 then needs a chain of 251 or more generations without an export. Capping k lowers the prune threshold (nc > gp + k - 2), which prunes more forward states. That can only miss shortcuts, which over-accepts; it never loses a valid level, and the server re-verifies the best. It is impossible on 5x5 (depth <= 149).

The finder's claim that the oracle multi-exit tests would be affected by (a) is mostly wrong: a multi-exit vs per-exit comparison would likely pass without the fix.

*fix notes*: Still apply the three one-liners; they cost nothing:
- Set last_exhaustive = 0 before the early return at 1517. Better: clear it at the top of sokoban_solve_cutoff and sokoban_solve for both widths, so correctness never depends on the incidental verify solve.
- Memset ms_lab in the wrap branch of hsp64_clear.
- Set have_ref = 0 when any kk > 250.

Also guard the fold loop in sokoban_export_settled with `g_ref_keys != NULL` (or record the table pointer in last_ref_used) so a stale flag cannot cause a NULL dereference.
