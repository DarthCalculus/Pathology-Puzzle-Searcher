# M6: Generator dedup treats a 64-bit canonical state hash as identity: a collision silently prunes a distinct state's subtree

verdict CONFIRMED, severity low, category soundness
locations: backsearch.c:1098 (dedup_two_tables key-only match at <= depth); backsearch.c:848 (comment 'negligible at the scales reachable in 60s'); state_key / canonical_state_key

## Summary
The dedup tables store only a 64-bit splitmix hash of the state, the minimum over the exit's stabilizer. A key match at the same or smaller depth prunes the new state and its whole subtree, with no other comparison. Reviewers estimate about 0.005-0.01 expected false prunes over campaign #1 (up to about 1% per campaign), growing linearly with total states times resident table size. No audit or fingerprint can detect such a prune, so the 'exact' result is probabilistic and the code comment is out of date.

## Source report F6 (worker-dfs-split)
**Dedup trusts a 64-bit hash with no check: about a 1% chance per campaign of wrongly pruning a subtree** at /Users/george/Documents/Claude Projects/project45/backsearch/backsearch.c:1098

*summary*: The dedup tables store only a 64-bit splitmix hash of the state; canonical_state_key takes the minimum over the exit's symmetries. A match on key alone (plus depth <=) prunes the state and its whole subtree. Nothing else is compared, so a collision between different states is a silent prune that no audit can see.

*failure_scenario*: Campaign #1 did about 3.7e10 lookups against up to about 6.7M live keys (two tables of 4.19M slots at 80% load): p ~ 6.7e6/2^64 ~ 3.6e-13 per lookup. That is about 0.013 expected false hits, roughly half of them passing the depth test, and more for exit 12 because the minimum over 8 symmetric keys biases hashes low. So there is about a 1% chance that some valid subtree was dropped. The chance grows in proportion to campaign size (10x states means about 10%). Verification of the published level cannot detect it, because the loss is a missing level, not a wrong one.

*evidence*: 912-925: `static uint64_t state_key(const BState *s) { uint64_t h = splitmix64(...); ... return h ? h : 1; }`; 1098-1100: `if (stab[i].key == key) { seen_shallow = 1; if (stab[i].depth <= depth) hit_dup = 1; ...`; slot types at 895-896: `{ uint64_t key; int32_t depth; }` and `{ uint64_t key; int32_t depth; uint64_t clock; }` (4 bytes of padding after depth in both).

*suggested_fix*: Store an independent 32-bit check hash (e.g. a second splitmix of the same fields) in the unused 4 padding bytes of ShallowSlot and RecentSlot, and require both to match. No extra memory, and the per-lookup false-positive rate drops by a further 2^-32.

*expected_gain*: Takes the collision risk from about 1e-2 to about 1e-12 per campaign at no memory cost.

## Source report F20 (worker-prune-soundness)
**Generator dedup treats a 64-bit state hash as identity: about 0.005-0.01 false 'already visited' prunes expected over campaign #1** at /Users/george/Documents/Claude Projects/project45/backsearch/backsearch.c:1098

*summary*: state_key/canonical_state_key produce a 64-bit splitmix hash, and dedup_two_tables treats a matching key at a depth <= the current one as the same state. A collision silently discards the new state's whole subtree.

*failure_scenario*: A new state whose hash equals a stored key from a different state at a depth <= its own is pruned as a duplicate, with no trace. From the snapshot, the sum over jobs of states x min(states, 6.7e6) / 2^64 comes to 0.0053-0.0106 expected false hits in campaign #1. Each drops one subtree, and the published maximum is affected only if that subtree held the exit's record. Very unlikely, but it makes 'exact' probabilistic, and the risk grows with job size.

*evidence*: backsearch.c 912-924: `uint64_t h = splitmix64((uint64_t)s->committed_empty); ... return h ? h : 1;`. 1098-1100: `if (stab[i].key == key) { seen_shallow = 1; if (stab[i].depth <= depth) hit_dup = 1;`. The same test is used for the recent table (1112-1115) and the single table (985-986).

*suggested_fix*: Store a second, independent 64-bit hash in each slot and require both to match (8 more bytes per slot), or store the exact packed state.

*expected_gain*: Removes a small but nonzero chance of silently lost subtrees.

## Source report F128 (e2e-exactness)
**The dedup key is a 64-bit hash; the 'exact' proof is probabilistic, and the code comment is outdated** at /Users/george/Documents/Claude Projects/project45/backsearch/backsearch.c:848

*summary*: Two states with the same 64-bit canonical_state_key are treated as equal, and the second one's subtree is skipped. At campaign scale this is no longer negligible, as the comment claims ('at the scales reachable in 60s').

*failure_scenario*: There are about 3.6e10 lookups against up to about 6.7e6 stored keys (two tables of 2^22 slots, 80% full). The chance of at least one false merge somewhere in campaign #1 is up to about 1%. A false merge drops one subtree. It changes the published max only if that subtree holds every copy of a maximum-depth level, which is far less likely but not excluded by the proof.

*evidence*: backsearch.c:845-849 `Two states with the same hash are treated as equal — collision probability ≈ states_visited / 2^64, negligible at the scales reachable in 60s.`; dedup_two_tables compares only `stab[i].key == key`.

*suggested_fix*: Store a second independent 32-bit check value per slot, or document the residual probability in the proof note.

*expected_gain*: Brings the chance of any false merge below 1e-10, or at least makes the claim honest.

## Verifier (CONFIRMED, low, refuted=False)
I read backsearch.c:912-925 (state_key: chained splitmix64, 0 remapped to 1), 955-965 (canonical_state_key: minimum over g_exit_syms images), 1086-1147 (dedup_two_tables) and 973-994 (single table). In each table the only identity test is `stab[i].key == key` / `rtab[i].key == key` / `tab[i].key == key`, followed by `depth <= depth -> hit_dup/return 1`. A 64-bit collision with a resident key at a depth <= the new state's depth therefore prunes a distinct state: try_successor_x at 2164-2171 returns, and the bulk path at 2373-2376 skips the candidate. The dup is never inserted, and nothing else records it. Two-table mode is the default (line 79, g_two_tables = 1), and g_dupe_threshold defaults to INT_MAX, so every state is looked up. The SUMMARY 'states' field is g_states_checked, which includes dedup-pruned states, so lookups ~ states. I recomputed the estimate on the snapshot (167,766 jobs, sum of states 3.68e10, max 1.74e8): sum over jobs of states*min(states, 2*3,355,443)/2^64 = 0.0106. Weighting each exit by its min-of-k collision factor k^2/(2k-1) (exit 12, k=8: 4.27; exits 0/2/6/7, k=2: 1.33; exit 1: 1) gives 0.014, with a worst single job of 2.7e-4. These are upper bounds, because the resident count grows from 0 during a job. The finders' range of 0.005-0.01 is therefore right. The comment at 845-848 ('negligible at the scales reachable in 60s') is out of date. Mitigation the finders underplay: a false prune drops only the subtree reached through that one edge, and only while the colliding key stays resident. Descendants reachable through other parents, and the same state in other jobs (tables are per job), are still explored. So the published maximum changes only if every path to every representative of the record goes through the pruned edge, which is far less likely than 1e-2. For the next campaign the risk scales with the number of jobs times per-job states times resident size: about 0.1 for a 10x campaign, more if SHALLOW_LG2/RECENT_LG2 are raised. The fix is free in memory, so it is worth doing, but this stays low.

*fix notes*: Add a 32-bit check hash (a different splitmix seed or constant, e.g. splitmix64(h ^ 0x9e3779b97f4a7c15) >> 32) in the 4 padding bytes of ShallowSlot (16 B) and RecentSlot (24 B), and in HashSlot for the single-table path. Require key and check to match in dedup_two_tables, dedup_check_and_insert, both evict rehash loops and the seed-insert calls at 4427-4490. For canonical keys, compute the check on the image that gave the minimum key, or take an independent minimum over the same image set; both are consistent across equivalent states because the image sets are equal. Update the comment at 845-848. A cheap test: build with a deliberately truncated key (e.g. mask to 20 bits) and confirm that test_split_exact then loses levels, and that it stops losing them once the check hash is added.
