# M24: The README says closing the panel does not stop the search (it does, via /close on pagehide), and misstates the default worker count and per-worker memory

verdict CONFIRMED, severity low, category docs
locations: v2/README.md:26; volunteer_ui.html (pagehide posts /close); volunteer.py /close handler + main loop (request_stop after 3 s unless --no-stop-on-close); DESIGN §4; default --workers = cpu_count // 2

## Summary
The panel posts /close on pagehide, and unless --no-stop-on-close is given, the client calls request_stop('browser window closed') after 3 s without a poll. Quitting or relaunching the browser for an update therefore stops the search without the volunteer knowing, while the README says the opposite. The README also gives the default --workers as 'core count minus one', but the code uses cpu_count // 2. It says about 200 MB per worker, while the panel says 'up to several GB each'.

## Verifier (CONFIRMED, low, refuted=False)
All three mismatches hold.

(1) Closing the page. README.md:26-27 says 'Closing the page does not stop the search unless you press **Stop**.' The code does stop:
- volunteer_ui.html:356-357 posts /close on pagehide (commented 'Window close = Stop (DESIGN 4)');
- volunteer.py:1505-1508 records ui_close_at unless --no-stop-on-close;
- volunteer.py:1399-1402 runs request_stop('browser window closed') if no /state poll arrives within 3 s.
DESIGN.md:170 ('Ctrl-C and window close = Stop') and the panel (volunteer_ui.html:141, 'Closing this tab also stops the client.') both agree with the code. Only the README is wrong. The --no-stop-on-close flag (volunteer.py:1540) is not mentioned in the README or in VOLUNTEERS.md.

(2) Default worker count. README.md:22-23 says 'core count minus one'; volunteer.py:1531 uses `max(1, (os.cpu_count() or 2) // 2)`.

(3) Memory. README says 'about 200 MB' per worker; the panel (:100) says 'up to several GB each'. From the code:
- baseline dedup is 64 MB shallow (16 B x 4M) plus 96 MB recent (RecentSlot is 24 B, backsearch.c:896), about 160 MB;
- a lazily allocated 256 MB solver big table (HTP_SIZE 16M x 16 B), a 24 MB multi-start arena and about 4 MB of small tables come on top;
- realistic RSS is therefore about 200-450 MB.
The README figure is low when the big table is used, and 'several GB' looks overstated. I did not measure RSS.

Impact: a volunteer who follows the README, or whose browser relaunches for an update, silently stops contributing. The stop is graceful: splits are handed back, while unstarted leases wait for expiry (already known). This is a docs/default mismatch, so it stays low.

*fix notes*: 1. Choose the behaviour. For a campaign that runs overnight on volunteer machines, the safer default is that closing the tab does NOT stop the client: flip the default to --stop-on-close, or drop the pagehide hook. Otherwise document the current behaviour.
2. Make the README, VOLUNTEERS.md, the panel text (:100, :141) and DESIGN §4 all say the same thing, and mention the flag.
3. Fix the README default to 'half your logical cores'.
4. Replace both memory figures with a measured one, e.g. '~160 MB, up to ~450 MB when the solver's large table is in use'. Measure peak RSS on a 1,800 s campaign job first.
