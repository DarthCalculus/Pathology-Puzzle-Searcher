# M3: Solver capacity results (-2 pending/heap overflow, -3 probe limit/heap cap) are pruned as proven shortcuts and not counted, so 'exhausted' does not mean exact

verdict CONFIRMED, severity critical, category soundness
locations: backsearch.c:2218 (try_successor_x prunes on -2/-3); backsearch.c:2407 (bulk multi-solve decides children); backsearch.c:2647 (solve with the ancestor's reference table); backsearch.c:4401 (fresh solve of a replayed root, no reference); sokoban_bfs.c HP64_SIZE 1<<20 pending cap; sokoban_bfs.h contract ('-2/-3 must be treated as fatal'); SUMMARY has no overflow field

## Summary
shortcut_check returns -2 when the pending queue exceeds 1,048,576 entries and -3 on a probe-limit or heap-cap failure. try_successor_x treats both as a shortcut and drops the state and its subtree. The only trace is g_pruned_short, mixed with real shortcuts (harvest code 'E' is off in campaigns). SUMMARY and the job status still say exhausted, and neither the client, the audit nor the fingerprints can see it, which contradicts the header's rule that callers treat these results as fatal. The state was already dedup-inserted, so later visits at the same or greater depth are suppressed as well. A parent decides its children with the smaller bulk or ref-table solves, while a replayed REMAINING root gets a fresh solve with no reference, so the cap can be hit only in the child job and the result depends on where splits fall. The 1<<20 cap is artificial, since the Dial buckets grow with realloc.

## Source report F3 (worker-dfs-split)
**Solver capacity limits (-2/-3) prune silently: status 'exhausted' does not mean exact, and a split root can hit the cap only in the child job** at /Users/george/Documents/Claude Projects/project45/backsearch/backsearch.c:2218

*summary*: shortcut_check returns -2 when the heap/pending queue overflows (HP64_SIZE = 1M entries) and -3 when the hash probe limit or heap cap is hit. try_successor_x prunes both results as if a shortcut had been proven. The only trace is g_pruned_short++, which is not in SUMMARY. This drops valid states for a capacity reason, not a proof. In a parent job, children are decided by the bulk multi-solve (2407) or by a solve that uses an ancestor's reference table (2647). Both searches are smaller than a fresh one. The replayed REMAINING root is decided by a fresh single solve with no reference (4401), so the cap can be reached only in the child job.

*failure_scenario*: In a parent job, a bulk child is accepted by the multi-solve, or a single child is accepted with an ancestor table that prunes most of the forward search. It is on the stack at the split. The child job re-checks it with a fresh sokoban_solve_cutoff, which reaches 1M pending entries and returns -2. The root is pruned, the stack is empty, and the job reports status 'exhausted' with accepted=0. The monolithic search would have explored that subtree. The same silent prune can happen inside any job, and nobody can tell whether it happened in campaign #1, because no counter reaches the report (the only evidence: no job in the snapshot has accepted=0).

*evidence*: 2218-2223: `if (x >= 0 || x == -2 || x == -3 || x == -4) { g_pruned_short++; ... return; }` with the comment '-3 ... "no shortcut" is unproven. Prune conservatively'. SUMMARY at 5845-5849 has no field for these prunes. sokoban_bfs.c 1245-1247: `if (hs->pq_count >= HP64_SIZE) { ... return -2; }`. 4400-4401: `g_best_state = seed; try_successor(&seed);` (fresh, no reference).

*suggested_fix*: Count -2/-3/-4 prunes in a separate counter (g_pruned_capacity), add it to SUMMARY, and have the server refuse to publish an exact result while any job reports a nonzero count (or re-issue those jobs with bigger solver tables). Also, when the seed-path root itself is rejected, report a distinct status (e.g. 'seed_rejected') instead of 'exhausted'.

*expected_gain*: Makes the exactness claim checkable; turns a possible silent loss into a visible, fixable event.

## Source report F12 (worker-dedup-symmetry)
**Conservative solver outcomes (-2/-3) are unproven prunes, are not counted in SUMMARY, and the dedup entry makes them suppress later visits** at /Users/george/Documents/Claude Projects/project45/backsearch/backsearch.c:2218

*summary*: The depth rule is sound only because every prune is a proof. Heap overflow (-2) and probe-limit/heap-cap (-3) prunes are not proofs, but the state was already dedup-inserted, so every later visit at the same or greater depth in that job is dropped without a re-check (possibly under a different ptab reference). NEW CONSEQUENCE (not in the merged issue): big-table overflow is an infinite loop.
- Where: sokoban_bfs.c:1262-1265 and 1751-1754, `} else if (hs->overflow) { use_big = 1; goto retry; }`.
- Why: the big table sets overflow once ht_count reaches 0.85*16M, about 14.26M inserts (hsp64_select). The code re-selects the big table and hsp64_clear resets the counters. The solve is deterministic, so it overflows the same way again.
- When: a solve with more than 14.26M distinct states whose pending frontier stays under 1M. It spins forever inside expand(), so the split and status checks at 4646 are never reached.
- Effect: the job is never completed, it is re-leased after 3600 s, and it spins again, so the campaign stalls. That is high severity on larger grids.
