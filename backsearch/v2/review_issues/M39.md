# M39: v2_seed cannot check that the root layer is complete and was made with the campaign's flags; the audit only covers the roots it was given

verdict CONFIRMED, severity medium, category soundness
locations: v2_seed.js:37-41 (readLayer keeps LAYER lines, ignores depth/blocks/holes columns, prints skipped/malformed lines and still exits 0); --list-layer output (no grid/exit/flags/SRC_HASH, '[estimate] ... layer = N nodes' header dropped in roots_h3 files); audit (no stored expected root count)

## Summary
v2_seed keeps LAYER lines and ignores everything else. There is no per-exit count check, no check of the depth column against the plan's layer, and no record of the grid, flags or binary the listing used. Malformed lines are only printed, and the tool exits 0. The audit calls an exit clean when every root present in the DB is covered, so a truncated or wrongly flagged listing yields a clean audit and a published proof.

## Verifier (CONFIRMED, medium, refuted=False)
I read the cited code and its callers. The issue holds, with one correction to the scenarios.

1. The seed tool only uses two columns. In v2_seed.js:37-49, readLayer does `if (f[0] !== 'LAYER' || f.length < 3) continue;` and then uses only f[1] (exit) and f[2] (seed). Columns f[3..5] (depth, blocks, holes) are never read. Any line that is not a LAYER line is dropped without being counted. That includes the worker's `[estimate] exit %d: depth-%d layer = %zu nodes` line, which backsearch.c:4124 prints before the LAYER lines at 4134. A malformed seed only increments `skipped.bad`. Line 76 prints the counts, and line 80 exits with `process.exit(r.rejected.length ? 1 : 0)`, so the tool exits 0 even when lines were malformed.

2. Nothing downstream checks either:
- jobs.js:384 addRootJobs stores depth = toks.length and never compares it with c.layer. c.layer is stored at jobs.js:374 and only echoed back by publicCampaign at :323.
- There is no expected root count anywhere in the schema.
- jobs.js:973-1014 auditExit takes as roots whatever parentless rows exist, and returns `clean: roots.length > 0 && uncovered.length === 0 && unknown.length === 0 && mismatches.length === 0`.
- v2_finish.js:37-46 publishes whenever that audit is clean. It takes the proof's caps from capsFromExtra(c.extra), meaning the plan's flags, not from how the roots were made.

So a listing that is a strict subset of the true layer gives a clean audit and a published "exhaustive" maximum. Examples: a listing cut short (it is qsorted in DFS order at 4127, so a cut drops a suffix of the tree), or one made without --allow-exit-transit, or with a tighter --num-holes/--num-blocks. Each is a narrower search, so its seeds still replay fine under the campaign's looser flags, and nothing errors.

3. A concrete extra path: concatenating per-exit files where one lacks a final newline merges two lines, e.g. `...\t1\t1LAYER\t1\tD1,...`. f[0] is still LAYER and f[2] is still a valid seed, so the first root is inserted. The second root is lost without even being counted as malformed.

4. Correction (partly refutes F99): if one exit's file is left out of the concatenation entirely, that exit gets zero roots. The `roots.length > 0` guard then makes its audit not clean, and v2_finish refuses. Only a partial listing within an exit is silent.

5. Campaign #1 is internally consistent:
- The snapshot's campaign row has extra ["--allow-exit-transit","--num-holes","3"] and layer 4.
- DB roots per exit (dup_of null, parent null) are 42/355/233/810/972/349 = 2,761, all at depth 4.
- These equal the line counts of roots_h3/layer4_e*.tsv, which have 0 non-LAYER lines, depth column always 4, and holes at most 3.

The files carry no record of the flags they were made with, so whether --allow-exit-transit was used cannot be proven from them statically. The optional check below settles it.

Severity: this is an operator-error path, not a defect under correct use. But when the error happens, the result is exactly a silent false exhaustive proof, and nothing in the pipeline catches it. Regenerating roots for a new hole count or grid in the next campaign is exactly when a copy-pasted command is likely. That makes medium the right rating: low likelihood, consequence at the critical level, and cheap to fix.

*fix notes*: For the next campaign:

1. Worker, --list-layer: after the LAYER lines of each exit, print a trailer such as `LAYER_END<TAB>grid<TAB>exit<TAB>K<TAB>count<TAB>flags=<normalized search-relevant argv: --allow-exit-transit, --num-holes, --num-blocks, --allow-block-on-exit, ...><TAB>src_hash=<SRC_HASH_STR>`. Keep the existing [estimate] line too.

2. v2_seed.js readLayer: refuse with a nonzero exit and insert nothing when any of these holds:
- a line starting with LAYER has the wrong field count (exactly 6 fields), or a non-integer depth, blocks or holes (this also catches merged lines);
- any malformed line appears at all (bad > 0);
- an exit in plan.exits has no trailer;
- a trailer's count differs from the number of LAYER lines for that exit;
- the trailer's K, grid or normalized flags differ from plan.layer, plan.grid or normalized plan.extra;
- a root's depth differs from plan.layer;
- a root's holes or blocks exceed capsFromExtra(plan.extra);
- the trailer's src_hash is not in plan.hashes. This check could be a warning.

3. Schema: store expected_roots_json (per-exit count) and the trailer text in the campaigns row.

4. Audit and publish:
- auditExit: add `expected_roots` and require `roots === expected` for clean.
- v2_finish: print the expected and actual counts and the trailer provenance in the proof note.
- --append must add to expected counts only through a trailer-checked file.

5. Tests: add v2_gates tests for a truncated file, a merged line with no newline, a flag mismatch, a missing trailer, and a depth other than plan.layer. Each must be refused.

6. Optionally backfill campaign #1's expected counts (42/355/233/810/972/349) so later audits of it show the check, without touching its published proof.
