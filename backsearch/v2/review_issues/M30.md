# M30: status(), the audits and per-token bests are recomputed on the request path at a cost linear in rows; the cache is stamped before compute, so it stops caching at scale

verdict CONFIRMED, severity high, category performance
locations: jobs.js:936 (statusCached sets `at` before calling status()); jobs.js:538 (heartbeat calls statusCached and auditExitCached inside BEGIN IMMEDIATE); jobs.js:899 (status(): countsByExit, contributors JOIN, correlated per-client SUM); bestOfToken (uncached per heartbeat); campaignsSummary (re-audits every campaign, closed ones included, each minute, not rate-limited); hunt.js polling every 3 s

## Summary
status() runs full-campaign GROUP BYs, a join over finished jobs and a correlated SUM per active client, about 0.3 s at 167k rows. It runs about every 2 s whenever a heartbeat or a hunt-page poll arrives, and the heartbeat also runs every exit's full-tree audit once a minute and an uncached per-token best query, all inside its write transaction. Because `at` is stamped before the compute, once a recompute takes about 2 s the cache has already expired when it is stored, and every request recomputes. At about 10x campaign-1 size this blocks the single Node event loop, which also serves the public records site, for seconds. That contradicts §7.8 ('nothing scales with rows on the request path').

## Source report F81 (server-scheduling)
**status(), audit and per-token best are recomputed on the request path at a cost that grows with row count; the cache timestamp is set before the compute** at /Users/george/PathologyRecords/server/lib/jobs.js:936

*summary*: statusCached() stamps `at` before calling status(). status() does full-campaign GROUP BYs and joins, about 0.3 s at 167k rows. It runs about every 2 s whenever a heartbeat arrives or a hunt page is open (polls every 3 s). Once a recompute takes longer than 2 s, every request recomputes. Heartbeats also run the 6 per-exit audits once a minute and an uncached per-token best query every time, all inside BEGIN IMMEDIATE.

*failure_scenario*: The next campaign is 10x larger (about 1.7M rows, within DESIGN §7's 2M-row budget). status() then takes about 3 s, longer than the 2 s TTL, so every heartbeat and every public status poll recomputes and the single Node thread saturates. Each minute one heartbeat also runs about 2-4 s of audits while holding the write lock, so tools with busy_timeout 5 s get SQLITE_BUSY, and heartbeat (20 s client timeout) and report latency climb. This contradicts §7.8 'Nothing scales with rows on the request path'.

*evidence*: 936: `if (!statusCache.body || n - statusCache.at > STATUS_TTL_MS) statusCache = { at: n, body: status() };`. 538: `const st = statusCached();` and 556: `auditExitCached(c, e.exit, false)` both run inside heartbeat's txn(). 542-548: bestOfToken per token per heartbeat. Plan for bestOfToken: 'SEARCH jobs USING INDEX idx_jobs_client ... USE TEMP B-TREE FOR ORDER BY' (Zach: 67,882 rows). Snapshot timings: countsByExit 0.10 s, contributors 0.16 s, clientsActive 0.05 s, treeOfExit exit 1 0.17 s (125k rows, then JS maps). hunt.js 143: `setInterval(load, 3000)`.

*suggested_fix*: Keep incremental aggregates (per exit/status/client counters updated in applyReport, lease and sweep), or at least set `at` after the compute and serve the stale body while recomputing. Compute status and audit outside the heartbeat's write transaction. Add a (campaign_id, exit, dup_of, id) index for treeOfExit. Cache per-token best, or index jobs(client_token, best DESC) WHERE level_code IS NOT NULL.

*suggested_fix*: Stamp the cache after computing (`const body = status(); statusCache = { at: Date.now(), body }`) and make the TTL adaptive, e.g. max(2 s, 10 x the last compute time). *expected_gain*: Removes a linear-in-rows cliff that would stall a 1-2M-row campaign; cuts the current idle CPU spent on unchanged aggregates.

## Source report F188 (robustness-ops)
**status and audit recompute over every campaign row on the request path, blocking Node's single thread** at /Users/george/PathologyRecords/server/lib/jobs.js:899

*summary*: status() runs a group-by over all campaign jobs, a join over all finished jobs and per-client SUM subqueries, and runs again whenever a heartbeat or poll arrives more than 2 s after the last run. hunt.html polls every 3 s. Every heartbeat calls auditExitCached for every exit, which loads every row of the exit into JS objects about once a minute per exit. campaignsSummary re-audits every closed campaign once a minute and is not rate-limited. All of this is synchronous on the one thread that also serves the public records site.

*failure_scenario*: Measured on the campaign-1 snapshot (168k jobs, sqlite3 CLI on the Mac): countsByExit 0.10 s, contributors 0.17 s, clientsActive 0.05 s. The exit-1 tree query returns 124,679 rows in 0.2 s, before building JS objects. On the 2-vCPU CX23, one hunt.html viewer already keeps status recomputing about every 2 s. A campaign 5-10x larger means seconds of event-loop stall every 2 s and one to several seconds per exit per minute, so heartbeats (20 s client timeout) and public-site requests hang. Transient heap per audit is about 0.5 KB per row (a 2M-row exit is about 1 GB on a 4 GB box), which risks a heap OOM, then systemd restarts it, and the next heartbeat triggers the same audit: a crash loop that takes the public site down too.

*evidence*: jobs.js:299-300 countsByExit `... FROM jobs WHERE campaign_id = ? GROUP BY exit, status`. jobs.js:303-307 clientsActive has per-client `(SELECT COALESCE(SUM(elapsed_s), 0) FROM jobs j WHERE j.client_token = cl.token ...)`. jobs.js:308-312 contributors is a full join. jobs.js:555-556 heartbeat does `for (const e of st.perExit || []) { const a = auditExitCached(c, e.exit, false);`. jobs.js:975 `const rows = q.treeOfExit.all(c.id, exit);`. jobs.js:866-871 campaignsSummary loops over all campaigns. v2routes.js:101-104 applies no ipLimit to /api/v2/campaigns. hunt.js:143 `setInterval(load, 3000)`.

*suggested_fix*: Keep per-(campaign, exit, status) and per-client counters in a stats table, updated inside the report, lease and sweep transactions. Maintain a covered flag per job and propagate it upward in applyReport, so the audit becomes a count, with the full recomputation only in v2_finish or a worker_thread. Cache closed campaigns' summaries permanently. Rate-limit /api/v2/campaigns.

*expected_gain*: Server cost per request stays flat as campaigns grow, and the public site is no longer tied to campaign size.

## Verifier (CONFIRMED, high, refuted=False)
The premise matches the code, and the cost is real and grows with rows. What turns a larger campaign from "slow" into "stalled" is where the cache timestamp is set.

CODE (all in /Users/george/PathologyRecords/server/lib/jobs.js)
- 934-937: `const n = Date.now(); if (!statusCache.body || n - statusCache.at > STATUS_TTL_MS) statusCache = { at: n, body: status() };`. The timestamp is taken before status() runs. STATUS_TTL_MS = 2000 (line 50). Writes never invalidate the cache (v2routes.js:150), so the only limit is this TTL.
- status() (892-930) runs these queries:
  - countsByExit (299): scans every row of the campaign.
  - bestOfExit x exits: uses the idx_jobs_best index, so it is cheap.
  - clientsActive (303-307): three correlated subqueries per active client, linear in that client's rows.
  - contributors (308-312): a join over every done/split row, then GROUP BY name.
  All of these are linear in rows.
- heartbeat (497-561) calls statusCached() (538), bestOfToken for each token of the name (546, uncached), and auditExitCached for every exit (556). All of it runs inside txn() = BEGIN IMMEDIATE (243-253).
- The six per-exit audit entries are stamped with the same now() (953-957), so they all expire together. One heartbeat per minute therefore pays for every exit's full treeOfExit load (975) plus the JS tree walk.
- campaignsSummary (863-890) loops over every campaign, closed ones included. It calls auditExitCached plus per-exit aggregates and a contributors join, at most once every 60 s. /api/v2/campaigns has no ipLimit (v2routes.js:101-104). That cost is bounded, because the 60 s cache is stamped after the compute.
- Who asks for status:
  - Heartbeats: every 30 s per client.
  - volunteer.py fetch_campaign_status: /api/v2/status at most every 30 s per client (volunteer.py:230, 1222).
  - hunt.js:143: setInterval(load, 3000), with no in-flight guard and no document.hidden check.
  - collective.js:125: every 10 s.
- The server is a single Node process: server.js mounts the v2 handler on the same event loop as the public records site (server.js:141).

MEASUREMENTS ON THE SNAPSHOT (167,766 rows; sqlite3 CLI, warm cache, this Mac)
- countsByExit 0.090 s, contributors 0.155 s, clientsActive (all 7 clients) 0.039-0.047 s. status() therefore costs about 0.29 s.
- Full audit of all six exits (Python fetch plus tree walk, an upper bound for the JS version): 0.48 s total. Exit 1 alone (124,679 rows): 0.23 s fetch + 0.08 s walk.
- bestOfToken for the largest token (67,882 rows): 0.021 s. Its plan is idx_jobs_client plus a TEMP B-TREE ORDER BY.
- Average seed length is 110 characters.
Every one of these queries is an index range scan plus a row read over all done/split rows, so the cost grows linearly with rows.

LOAD MODEL, MY OWN ESTIMATE
- At 10 clients, status-type requests arrive at about 0.67/s from clients alone (heartbeat plus the status fetch, each every 30 s), plus 0.33/s per open hunt.html tab. The cache is therefore recomputed roughly every 2 s.
- Today that is about 0.3 s per 2 s, roughly 15% of the Node thread on this Mac and probably 25-35% on the 2-vCPU CX23. That is noticeable but works. The audit adds about 0.5 s per minute.
- At about 1.2M rows on the Mac (maybe 0.6-0.9M on the CX23), status() takes longer than the 2 s TTL. Because `at` is set before the compute, the entry is already expired when it is stored, so every heartbeat and every status GET recomputes.
- At 1.7M rows (inside DESIGN §7's 2M-row budget): about 2.9 s per request x 0.67-1 req/s gives utilisation of 2-3. Work arrives faster than it can be done, so the queue grows without bound. Lease and report batches queue behind it and hit the client timeouts (20 s heartbeat, 60 s batch). Batches go to the outbox, leases lapse, the campaign stalls, and the public site hangs.
- With the timestamp set after the compute, the same compute time would give a guaranteed 2 s cached window after each run, so status work is bounded at c/(c+2), about 60%. That is badly degraded but not a collapse.
- The once-a-minute audit grows to about 5 s in one heartbeat, still inside its write transaction. Its transient heap is roughly 350-450 B per row, about 0.5 GB for a 1.25M-row exit on a 4 GB box. That is a heap-pressure risk, not a confirmed OOM.

SEVERITY
- At campaign-1 size this is medium: waste, not failure.
- It is high if the next campaign reaches about 1M rows. The owner says the next campaign will be "similar or larger (more holes)", and the design explicitly budgets 2M rows, so I keep high.
- It cannot make a published result wrong. v2_finish.js:37 always publishes from `jobs.audit(exit, c.id, { fresh: true })`, never from the caches.
- test_load.py starts from a small DB and never polls /api/v2/status, which is why the §7 acceptance test could not catch this.

EXACTNESS RISK OF THE FIXES
- None for caching, timers, counters, indexes or front-end throttling, since they only affect display fields (me, exits, status, campaigns).
- The one caveat is F188's incremental "covered" flag. It may drive display, but the fresh full-tree audit in v2_finish must remain the only gate for publishing.

COVERAGE AND HOUSEKEEPING
- The claim that the heartbeat's write transaction blocks other requests is only partly right. Inside the single Node process everything is serialized anyway, so holding BEGIN IMMEDIATE only hurts external tools (busy_timeout 5000). Moving the compute after COMMIT is a small gain, not the main one.
- bestOfToken is minor today (21 ms) and would be about 0.2 s per heartbeat of the largest contributor at 10x.
- campaignsSummary is bounded at one compute per 60 s per viewer burst. It is waste, not a stall.
- My mistake: a stray `cat` in my first command created an empty /tmp/q_unused and hung until I stopped it. I deleted that file.

*fix notes*: Fixes in priority order. None of them touches exactness.

1. One-line safety valve (do it before the next campaign). In jobs.js:936, set the timestamp after the compute:
   `const body = status(); statusCache = { at: Date.now(), body, cost: Date.now() - n };`
   Then make the TTL adaptive: `ttl = Math.max(STATUS_TTL_MS, 10 * statusCache.cost)`. That caps status work at about 10% of the thread whatever the request rate, and removes the collapse once a compute takes longer than the TTL.

2. Make status() independent of row count. Keep a small stats table (or in-memory counters rebuilt at startup) keyed by (campaign, exit, status). It holds n, dups and cpu_s, plus per-token and per-name finished, splits, done, cpu_s, states, solver_calls and best. Update it inside the existing applyReport, lease, reopen, reset and sweep transactions. Then status() and the heartbeat's `me` become O(exits + active clients).
   If that is too much before launch, recompute status() on a setInterval timer (for example every 5 s, or adaptive) outside any request, and have requests only read the cached, pre-serialized JSON.

3. Heartbeat:
   - Build `me` and `exits` after COMMIT, not inside txn().
   - Take the name's best from the contributors aggregate: it already has MAX(best). Look up the level code only when that best changes, or add the index `jobs(client_token, best DESC) WHERE level_code IS NOT NULL`.
   - Take roots and covered_roots from an audit that runs on a timer and is staggered per exit, not from a synchronous audit triggered by a heartbeat. Otherwise all six exits expire together and one heartbeat per minute pays for the whole tree walk.

4. campaignsSummary: cache the summary of any clean campaign whose status is not 'open' permanently, since it is immutable, keyed by campaign id and invalidated only when the status changes. Add ipLimit to /api/v2/campaigns.

5. Front end:
   - hunt.js and collective.js: skip a poll while one is in flight or while document.hidden is true.
   - Back off, for example to 30 s, when the status shows no open or leased jobs.
   - volunteer.py's 30 s status fetch could be folded into the heartbeat reply, which already carries `exits` and `me`.

6. Test: extend test_load to prefill a DB with about 1.5-2M rows, for example by copying the campaign-1 snapshot's jobs 10x under a new campaign id with remapped ids and parent_ids. Run one hunt poller at 3 s alongside the 10x16 clients. Accept on heartbeat and report p95 < 1 s and status compute < 100 ms.

7. Keep v2_finish's `fresh: true` full audit as the only gate for publishing. Any incremental "covered" flag is for display only.
