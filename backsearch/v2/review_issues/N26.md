## Verifier (CONFIRMED, low, refuted=False)
The mechanism is confirmed from code. The maximal filter at db.js:598 is 'champ.filter(c => !champ.some(o => o !== c && classWithin(c.proof, o.proof) && !classWithin(o.proof, c.proof)))'. Two proofs with identical classes are mutually within each other, so neither is removed, both reach lv.champion, and app.js:126-127 renders one 'longest <label> — <attribution>, <date>' line per entry. addProof (db.js:654-680) inserts with no check for an existing proof of the same class, and v2_finish.js:63-64 calls addProof for every clean exit each time --publish runs. So re-running --publish duplicates every exit's proof. That rerun is a realistic trigger: v2_finish exits 1 if any exit fails (line 76), and an owner who fixes that exit and reruns without --exit re-adds proofs for all the others. derivedProofs (db.js:525-529) already keeps only the newest proof per exit, and its comment explicitly expects 'a class was proven twice for the same exit (e.g. an earlier single-owner run and a later collective campaign)'. So the owner handled this case for derived proofs but not for the badges. I could not verify the specific live '#161 Panacea exit 12 ≤3 holes' row offline. The local records.db and the scratch copies contain only proofs 1-7, where exit 12 is ≤2 holes, strictly within ≤3 holes, and correctly collapsed. The code path that would duplicate it is certain, though. Cosmetic on the public site, and it goes against the owner's 'Collective only' attribution intent, so low.

*fix notes*: Before building maximal in annotateChampions, collapse proofs whose classes are mutually within each other, keeping the newest id (the same rule derivedProofs uses). Better still, apply that collapse once in allProofs()/storedProofs() so proofForFilter and the history views agree. Make v2_finish --publish idempotent: skip or warn when a proof with the same (rows, cols, exit, maxBlocks, maxHoles, maxMoves) already exists. Optionally have addProof refuse an exact duplicate unless forced.
