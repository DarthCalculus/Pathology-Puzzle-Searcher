# M61: poll() has no timeout or staleness indicator: a hung or suspended client leaves a frozen page that looks live

verdict CONFIRMED, severity low, category robustness
locations: volunteer_ui.html:352 (fetch('/state') without timeout; only rejections count as failures; setInterval keeps stacking requests)

## Summary
Only rejected fetches count as failures. If the client accepts connections but never answers, fetch('/state') neither resolves nor rejects. The page keeps its last render ('connected', 'searching', frozen countdowns) with no warning, while setInterval stacks up requests.

## Source report F67 (client-ui)
**poll() has no timeout or staleness indicator: a hung or suspended client leaves a frozen page that looks live** at /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer_ui.html:352

*summary*: Only rejected fetches count as failures. If the client accepts connections but never answers, fetch('/state') neither resolves nor rejects. The page keeps its last render ('connected', 'searching', frozen countdowns) with no warning, and setInterval keeps stacking requests.

*failure_scenario*: The volunteer presses Ctrl-Z instead of Ctrl-C. SIGTSTP stops the Python client, while the workers (start_new_session=True) keep running until their stdout pipes fill. The kernel still accepts TCP connections, so every poll hangs, `failures` stays 0, and the panel shows a healthy state indefinitely. Meanwhile no heartbeats are sent and leases lapse after 1 h. The same happens if a handler thread ever blocks.

*evidence*: volunteer_ui.html:350-355 `try { const r = await fetch('/state', { cache: 'no-store' }); render(await r.json()); failures = 0; } catch (e) { if (++failures === 8) ... }` and `setInterval(poll, 250)`. There is no AbortController, and st.time and server.last_heartbeat_ok are never compared with the browser clock.

*suggested_fix*: Use an AbortController with a timeout of about 2 s and count a timeout as a failure. Skip a poll while the previous one is still in flight. Show 'last update Ns ago' and the heartbeat age, and grey out the page when the data is older than a few seconds.

## Verifier (CONFIRMED, low, refuted=False)
Confirmed. Lines 350-355: `try { const r = await fetch('/state', { cache: 'no-store' }); render(await r.json()); failures = 0; } catch (e) { if (++failures === 8) ... }` and `setInterval(poll, 250)`. There is no AbortController and no in-flight guard, and nothing compares st.time or server.last_heartbeat_ok with the browser clock. The connection 'age' at line 279 is `st.time - st.server.last_ok`, and both values come from the same frozen snapshot. The client installs handlers only for SIGINT and SIGTERM (volunteer.py:1352-1356), not SIGTSTP, so Ctrl-Z stops the Python process. Workers use start_new_session=True (volunteer.py:745), so they keep running until their pipes fill. The ThreadingHTTPServer uses HTTP/1.1 keep-alive. Chrome then reuses its up-to-6 connections, each request hangs with no response timeout, and later fetches queue in the browser. No fetch rejects, failures stays 0, and the page keeps showing 'connected' and 'searching' with frozen countdowns. Firefox gives up after its ~300 s response timeout, and then the page wrongly says the client exited. I also checked the other suggested trigger, a handler blocking on vol.lock: every server call (heartbeat, lease, reports, status) runs outside the lock (volunteer.py:1160-1176, 466-472, 913, 1222), so that path is unlikely. The realistic trigger is a stopped (Ctrl-Z) client, which is rare. Impact is a misleading panel only: leases lapse on the server and recover normally, so this stays low.

*fix notes*: Guard against overlapping polls (skip a tick while one is in flight). Use an AbortController with a ~2 s timeout and count an abort as a failure. Keep lastRenderAt in JS and show or grey out 'last update N s ago' when it exceeds ~3 s. Also show the heartbeat age (st.time - st.server.last_heartbeat_ok). Separately, the client could handle SIGTSTP (log a warning, or treat it like pause by SIGSTOPping the workers) so Ctrl-Z does not leave running workers orphaned behind a stopped controller.
