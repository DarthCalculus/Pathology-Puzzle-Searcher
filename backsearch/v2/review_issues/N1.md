## Source report F200 (r2-next-campaign-generalization)
**A '6x4' campaign is accepted and publishes proofs in a transposed frame that no site level, filter or champion ever matches** at /Users/george/PathologyRecords/server/lib/jobs.js:93

*summary*: parseGrid and createCampaign accept rows > cols. v2_finish writes the proof with the campaign's raw rows, cols and exit cell, but the site stores levels and filters only with rows <= cols. A '6x4' proof is therefore never covered by a filter, never witnessed, and its contradiction guard misses levels that fit only when transposed.

*failure_scenario*: The plan has grid '6x4' and exits [0,1,4,5,8,9]; createCampaign accepts them because they equal canonicalExitCells(6,4).cells. Worker and server agree for the whole campaign. v2_finish then publishes {rows:6, cols:4, exitCell:4, ...}. Consequences: (1) processSubmission stores the champion canonicalised to 4x6, and searchLevels('rows <= 6 AND cols <= 4') never returns it, so proofChampions reports 'unwitnessed' forever. (2) server.js:108 rejects any filter with rows > cols, so proofCovers never matches and the proof never bounds or badges a search. (3) addProof's guard only considers stored levels at most 4 columns wide: 4x5 levels (e.g. the 70-move 4x5 record) fit 6x4 once transposed but fail 'lv.cols > p.cols'. (4) 'exit @ cell 4' in the 6x4 frame is cell 1 in the site's 4x6 frame. (5) A later '4x6' campaign would create a second, disjoint proof set for the same class, and derivedProofs would synthesise a separate '6×4 level' any-exit proof.

*evidence*: jobs.js:93-99 `const m = /^(\d{1,2})x(\d{1,2})$/.exec(...); ... if (rows < 1 || cols < 1 || rows * cols > MAX_AREA) return null; return { rows, cols };` (no rows<=cols check); jobs.js:349-351 `const canon = canonicalExitCells(g.rows, g.cols).cells;`; v2_finish.js:50 `rows: g.rows, cols: g.cols, exitCell: exit, ...`; level.js:120 `if (g.length > g[0].length) continue; // enforce rows <= cols`; db.js:567 `if (lv.rows > p.rows || lv.cols > p.cols) return false;`; db.js:269-270 `cond.push('rows <= ?') ... cond.push('cols <= ?')`; server.js:108 `if (f.rows != null && f.rows > f.cols) throw new Error('size must have rows <= cols');`

*suggested_fix*: In createCampaign (and parseGrid for campaigns), reject rows > cols with a message to enter the grid as CxR. Alternatively, normalise: transpose the grid string and map the exits through the transpose before storing, so the worker runs 4x6. Make addProof reject rows > cols as well, so no tool can store a non-canonical proof.

## Verifier (CONFIRMED, low, refuted=False)
I checked every link in the chain against the code, and each one holds.

1. **The campaign is accepted.** `parseGrid` (jobs.js:92-98) only checks `rows >= 1`, `cols >= 1` and `rows*cols <= MAX_AREA`, so "6x4" passes. `createCampaign` (jobs.js:350-352) checks the exits against `canonicalExitCells(6,4).cells`. For rows != cols that function keeps only the four non-transposing transforms (level.js:140), which gives exits [0,1,4,5,8,9]. `v2_seed.js` passes plan.json straight to `createCampaign`, and v2routes has no other campaign-creation path.

2. **The campaign runs consistently.** The worker's `parse_grid` (backsearch.c:4856-4862) also accepts any RxC within MAX_ROWS/MAX_COLS. `validateLevel` (jobs.js:115-138) uses `parseLevel`, which does not canonicalise, and compares against the raw 6x4 frame. Worker and server therefore agree for the whole campaign, and the published numbers would be correct in the 6x4 frame.

3. **The proof is written in the non-canonical frame.** v2_finish.js:50 writes `rows: g.rows, cols: g.cols, exitCell: exit`, i.e. rows 6, cols 4, with the exit cell in the 6x4 frame. `addProof` (db.js:654-680) validates only that the numbers are positive integers and never checks `rows <= cols`.

4. **Consequences on the site.**
   - **Champion never witnessed.** `processSubmission` canonicalises the champion (pipeline.js:40, then level.js:120 `if (g.length > g[0].length) continue; // enforce rows <= cols`), so it is stored as 4x6. `proofChampions` then runs `searchLevels` with `rows <= 6 AND cols <= 4` (db.js:269-270). A 4x6 level fails that, so the proof stays "unwitnessed" forever.
   - **Proof never covers a search.** `parseFilters` rejects `rows > cols` (server.js:108), so no search filter can match the proof in `proofCovers` (db.js:612), and the proof never bounds or badges a search.
   - **Contradiction guard is weakened.** `addProof`'s guard goes through `proofChampions`, so it only sees stored levels at most 4 columns wide. A stored 4x5 or 4x6 level fits the class once transposed but is excluded by `cols <= 4`. The guard is meant to refuse a proof that a stored verified level contradicts, and here it would miss exactly those levels.
   - **Label is in the wrong frame.** `proofLabel` prints "6×4 level with exit @ cell 4". In the site's canonical 4x6 frame that exit is cell 1.
   - **Duplicate proof sets.** `derivedProofs` groups by the raw `rows x cols` key, so a later "4x6" campaign would produce a separate, disjoint proof set for the same class.

I also checked the docs: DESIGN.md, v2/README.md and VOLUNTEERS.md say nothing about grid orientation.

**Why I rate it low rather than medium:**
- Only the owner can trigger it, by writing rows > cols in plan.json. No volunteer or public input reaches `createCampaign`.
- Campaign #1 (5x5) is not affected.
- The rest of the site uses the rows <= cols convention (the search filter, `/api/exitcells`, and the app's size picker, which swaps r and c when r > c), and so do the owner's own record notes ("4x5", "4x6"). A next campaign on 4x6 or 5x6 would most likely be entered correctly.
- Nothing is lost or corrupted. The job data stays correct in its own frame, and a mis-framed proof row can be deleted with `deleteProof` and re-added with transposed coordinates.
- The worst case, publishing a wrong maximum past the guard, needs a second, independent search bug on top of the input mistake.

The fix is cheap, and it closes a gap in the only automated check that stands between a campaign and a published proof. It should be fixed before a non-square campaign.

*fix notes*: Three changes, in order of importance:

1. **Reject rows > cols at campaign creation.** In `createCampaign` (jobs.js ~348), right after `parseGrid`, add: `if (g.rows > g.cols) throw new Error(`grid must have rows <= cols (enter ${g.cols}x${g.rows}); the site stores every size with rows <= cols`)`.
   - Put the check in `createCampaign` rather than in `parseGrid`, so an existing campaign row that is already non-canonical still parses in `validateLevel` and `v2_finish`.
   - Transposing automatically is not needed, and rejecting is simpler and safer. Automatic transposition would also have to remap every seed path and exit through the transpose, and the roots file from `--list-layer` would then be in the wrong frame.

2. **Make `addProof` refuse non-canonical input.** Return `{ok:false, reason:'invalid'}` when `p.rows > p.cols`, or when `p.exitCell != null` and `canonicalExitCells(p.rows, p.cols).cells` does not include `p.exitCell`. This also guards `finish_chunks.js` and any manual insert.

3. **Add a check to v2_finish.js** that refuses to publish when `g.rows > g.cols`, as a belt-and-braces guard for any legacy campaign.

Tests to add to v2_gates.test.js:
- `createCampaign({grid:'6x4', exits:[0,1,4,5,8,9], ...})` throws.
- `addProof({rows:6, cols:4, exitCell:4, maxMoves:10})` returns `ok:false`.
- A 4x6 proof whose exit is not canonical (e.g. `exitCell:4`, since cell 4 of a 4x6 board belongs to the same orbit as cell 1) is refused.
