# M56: A worker-count change overwrites slot.state with 'retiring', so Pause skips those workers and Resume never unfreezes them

verdict CONFIRMED, severity medium, category bug
locations: volunteer.py:1144 (_reconcile_slots sets 'retiring'); pause() SIGSTOPs only state 'running'; resume() SIGCONTs only state 'paused'

## Summary
_reconcile_slots replaces the process state ('running' or 'paused') of a surplus slot that still has a job with 'retiring'. A retiring worker therefore keeps running while the panel says everything is frozen. A worker that was frozen before it became retiring is never resumed: it stays SIGSTOPped, holds its job's lease and RAM, and never finishes.

## Source report F61 (client-ui)
**Worker-count change overwrites slot.state='retiring', so Pause skips those workers and Resume never un-freezes them** at /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py:1144

*summary*: _reconcile_slots replaces the process state ('running' or 'paused') of a surplus slot that still has a job with 'retiring'. pause() only SIGSTOPs slots in state 'running' and resume() only SIGCONTs slots in state 'paused'. A retiring worker therefore keeps running while the panel says everything is frozen, and a worker that was frozen before it became retiring is never resumed.

*failure_scenario*: (a) The machine lags, so the volunteer lowers workers from 8 to 4, then presses Pause. Slots 4-7 are 'retiring' and are not SIGSTOPped. They keep burning CPU for the rest of their window (up to split_after 1800 s + absorb 120 s) while the banner says 'Paused. Workers are frozen'. No 'freezing…' flag appears, because it counts only state=='running', and the heartbeat tells the server paused:true. (b) The volunteer presses Pause, lowers workers from 8 to 4, then presses Resume. Slots 4-7 stay SIGSTOPped forever. run_window blocks on proc.stdout, the panel spins '4 workers finishing their current job before retiring…' forever, and the cards say 'searching · window, 0 s left'. The heartbeat keeps listing the jobs in running/holding, so their leases are renewed indefinitely. They are recovered only by Stop, or at the campaign tail when §9 steals them (drop, then SIGKILL, and that window's work is lost). Raising the count back to 8 sets retire=False but leaves state='retiring': the workers stay frozen with no spinner. handle_wake has the same gap, since it SIGCONTs only if `s.state == "running"`. Separately, the UI label 'finishing, then retiring' can never show, because the phase check comes first (volunteer_ui.html:295).

*evidence*: volunteer.py:1144-1145 `elif s.retire and s.job is not None:\n    s.state = "retiring"`; pause :1066-1069 `if s.proc and s.state == "running":\n    self._signal(s, signal.SIGSTOP)\n    s.state = "paused"`; resume :1080-1083 `if s.proc and s.state == "paused":\n    self._signal(s, signal.SIGCONT)`; handle_wake :1287 `if s.proc and not self.paused and s.state == "running":`; pending_flags :1243 `running = [s for s in self.slots if s.proc and s.state == "running"]`.

*suggested_fix*: Stop storing retirement in slot.state. Keep the process state and derive 'retiring' from s.retire in snapshot()/pending_flags. In pause(), SIGSTOP every slot with a live proc that is not 'finishing'. In resume(), SIGCONT every slot with a live proc. Record a per-slot 'frozen' boolean rather than reading it from the state string.

## Verifier (CONFIRMED, medium, refuted=False)
Confirmed by reading the code and its callers in /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py.

1. How state gets overwritten. set_workers() (1115-1133) is called from the panel's POST /workers handler (1502-1504). Nothing blocks that call while paused or stopping, and the UI does not disable Apply in those states (volunteer_ui.html:230). set_workers() calls _reconcile_slots(), which runs `elif s.retire and s.job is not None: s.state = "retiring"` (1144-1145). That discards whether the process was 'running', 'paused' (SIGSTOPped) or 'finishing'. Its only other caller is startup (1363), where no slot has a job yet.

2. The consumers key on the state string alone:
- pause(): `if s.proc and s.state == "running": SIGSTOP` (1067)
- resume(): `if s.proc and s.state == "paused": SIGCONT` (1081)
- handle_wake: SIGSTOPs and SIGCONTs only `s.state == "running"` (1263, 1287)
- pending_flags: counts only 'running' when it shows "freezing N" (1243)

Scenario (b) holds exactly as reported: Pause, then lower the worker count, then Resume.
- The surplus workers are still SIGSTOPped and now marked 'retiring', so resume() skips them.
- run_worker blocks on `for line in proc.stdout` (765). The worker's own split timer cannot fire while it is stopped. The client has no wall-clock watchdog except STOP_GRACE_S, which applies only to state 'finishing' (1393).
- heartbeat() keeps listing s.job in running/holding (1162-1163). After Resume it also sends paused:false. The server renews the lease without limit (`want = t + c.lease_s`, jobs.js:516-518, cap applied only when paused).
- So the job, its lease and the worker's RAM are held with no end date.
- Raising the count again sets retire=False but leaves state='retiring', so the worker stays frozen and the spinner disappears.

What recovers it:
- Stop. request_stop -> _send_stop sends SIGCONT and then SIGINT (1035-1036). The stop_pending path at 1390 also covers a worker that never printed its first line. The worker then prints REMAINING, so no work is lost.
- A heartbeat 'drop', which SIGKILLs the worker.
- Tail work-stealing (jobs.js:601-630), but only from a different client. A lone client at the tail therefore stalls until the volunteer presses Stop.

Scenario (a) is real but narrower than reported. Lower the count, then Pause: the retiring worker is not frozen. However, run_worker resets `slot.state = "running"` at the start of every run (741) and SIGSTOPs a new run when self.paused is set (751-753). So only the run in progress escapes Pause. That can still be most of a window: the first run gets split_after = deadline-now, up to 1800 s of CPU while the banner says 'Paused. Workers are frozen', and "freezing N workers" does not count it. The absorb runs and later window runs do get frozen.

Extra consequence the report did not mention: changing the count after Stop turns a 'finishing' slot into 'retiring'. The STOP_GRACE_S kill watchdog (1393) then never fires for it, so a worker that ignores SIGINT would hang the shutdown. This edge case is low on its own.

The UI point also holds: the label 'finishing, then retiring' can never appear, because the phase checks come first at volunteer_ui.html:295.

Correctness of results is not at risk. Nothing is lost or double-counted, and Stop recovers cleanly. The impact is a job held with no end date, a frozen worker holding RAM, a possible stall at the campaign tail, and CPU used on the volunteer's machine against their explicit Pause. "Pause because the machine lags, lower the workers, Resume" is a natural sequence, so medium is the right rating.

*fix notes*: Keep the process state apart from retirement.
(1) Delete the `elif s.retire and s.job is not None: s.state = "retiring"` branch in _reconcile_slots. Take the "retiring" display from s.retire in snapshot() and pending_flags; pending_flags already uses s.retire.
(2) Add a per-slot boolean `frozen`.
- pause() sends SIGSTOP to every slot with a live proc whose state is not 'finishing', and sets frozen=True.
- resume() sends SIGCONT to every slot with frozen=True and clears it.
- run_worker sets frozen=True when it SIGSTOPs a new run while paused.
- _send_stop and request_stop clear frozen, since they already send SIGCONT.
- handle_wake stops and continues based on `s.proc and not s.frozen`.
(3) Make pending_flags count "freezing N" as live procs that are not frozen and not finishing.
(4) Fix volunteer_ui.html:295 so a retiring slot shows its retirement: check s.retire, or a snapshot 'retiring' flag, before the phase checks.
(5) Optionally ignore or reject /workers while stopping, so a 'finishing' slot keeps its STOP_GRACE_S watchdog.
(6) Add a test_client.sh case: Pause, lower workers, Resume, then assert that no worker PID is left in 'T' state. Add the reverse order too: lower workers, Pause, then assert that every live worker is in 'T' state.
