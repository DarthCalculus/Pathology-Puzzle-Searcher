## Summary
In a block-on-exit check, the exit block X has exactly one mask bit D0 and can leave only by the winning push from C0 = adj[exit][D0^2]. A heuristic of 1 + the distance over walls plus the exit cell to the push cells of X's mask is admissible and consistent, and is 2-4 moves stronger for players on the far side of X (exit 1, D0=R: h(2)=1 vs 5, h(3)=2 vs 6). ## Source report F159 (algo-worker)
**The A* bound ignores that the exit is occupied in 85-95% of accepted checks** at /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:1554

*summary*: hdist is the walls-only distance to the exit. In a block-on-exit check, the exit block X has exactly one mask bit D0: blocks reach the exit only at depth 1, since the player stands on the exit only at depth 0. X can move only by the winning push from C0=adj[exit][D0^2]. So h'(c) = 1 + distance over walls plus the exit cell from c to {adj[exit][d^2] : d in mask(X), adj[exit][d] not a wall}, with h'(exit)=0, is admissible and consistent. It is 2 to 4 moves stronger for players on the far side of X. Example, exit 1 with D0=R: h(6)=1 vs h'(6)=3, h(2)=1 vs 5, h(3)=2 vs 6.

*failure_scenario*: Block-on-exit states are 84.8/85.1/94.6/92.9/94.1% of accepted states at exits 1/2/6/7/12, which carry 93.7% of campaign CPU. Their exhaustive checks expand every state with g+h up to the cutoff, including the last 2-4 cost levels on the wrong side of X that can never finish in time. Decision-mode shortcut searches are also pulled toward the blocked exit.

*evidence*: sokoban_bfs.c:1554 'walk_dists_from(walls, exit_pos, g_all_cells, hdist);'; 1722 'int hd = hdist[cand[ci].bpos]; if (hd < 0 || nc + hd > max_cost) continue;'; multi 1860 (same hdist); snapshot: exit 1 accepted 8,356,149,318 vs valid 1,273,389,407; exit 6 4,277,847,725 vs 229,771,852.

*suggested_fix*: When the start state has a block on exit_pos, compute h' once per solve (a multi-source BFS avoiding walls and the exit, plus 1) in solve_push64_cutoff and sokoban_solve_multi, and use it for the root check, the pass-2 filter and prio. Otherwise keep hdist. Decisions are unchanged because h' is admissible; labels remain real path costs, so parent-table export and reference prunes stay sound. Measure pops with solvebench --decision on a harvest from a transit exit.

## Verifier (REFUTED, low, refuted=True)
The premise and the exactness argument hold. The claimed gain does not: it is negligible.

Premise checked against the code:
- apply_seed_step and expand() in backsearch.c reject C == g_exit_pos ('if (C == g_exit_pos) return 0;', ~line 1934). So the player stands on the exit only at depth 0, and a block can land on the exit only through the root pull with P == exit. The header comment at backsearch.c:71-74 says the same: "a block can only land on the exit via a transit backstep at the root".
- Any later pull of that block moves it off the exit, and it can never return. So in every block-on-exit state the exit block X has mask exactly {D0}. build_partial_puzzle passes that mask to the solver, widened only under g_axis_both_ways.
- Forward, X leaves the exit only by a push from adj[exit][d^2] for d in its mask, and that push puts the player on the exit (a win). The walk BFS treats blocks as obstacles (sokoban_bfs.c:1693-1696).
- So h' = 1 + (distance over walls plus the exit to the push cells) is admissible and consistent. It has the same parity as h. The example values are right (exit 1, D0=R: h(2)=1 vs 5).
- Snapshot numbers reproduce exactly. Exit 1 accepted is 8,356,149,318 vs 1,273,389,407 valid, so 84.8% of accepted states have a block on the exit. Exits 1/2/6/7/12 used 564 of 602 CPU-hours (93.7%).

Exactness: the change is safe.
- Solver decisions are unchanged, so the DFS is identical.
- Table labels (sokoban_export_settled) stay real path costs. A key missing from the reference table never prunes (ref_prunes_at returns 0 when gp < 0).
- The multi-solve dominance rule only needs every start's search to stay exhaustive.

Gain: measured with an offline model, not the worker (compiling and running were not allowed).
- I wrote a Python copy of solve_push64_cutoff: same push-macro moves, walk-to-exit win, 'nc + h[bpos] > cut' prune and root check, but no mand_dead pruning. On the 149 level it finds exactly 149.
- For six campaign-best levels I rebuilt the backward block-on-exit states along each optimal solution: committed cells = the player's suffix cells, block end cells, filled holes and the exit; masks = suffix push directions. I then counted pops with h, h' and no heuristic.

The forward searches saturate their small reachable space well before the cutoff, so no bound based on player distance can remove much.

My estimate: under 1% of solver time on exits 1/2/6/7, which carry 92.9% of the CPU. The only noticeable relative gain is at exit 12 (tiny searches, 0.8% of CPU). The finder's 5-20% is not plausible. The "last 2-4 cost levels" it would cut are nearly empty in real checks.
