# M88: No split-exactness test covers the campaign regime (<=3 holes with unbounded blocks, evictions, deep paths)

verdict CONFIRMED, severity medium, category test-gap
locations: test_split_exact.py:8 (configs: 5x5 <=3 blocks, 4x4 <=3 holes); campaign: 5x5 --num-holes 3, unbounded blocks; 2^22-slot dedup tables

## Summary
Every split-exactness run so far uses either at most 3 blocks on 5x5 (holes free) or 4x4 with at most 3 holes. The campaign runs 5x5 --num-holes 3 with unbounded blocks, so 8 or more blocks (the dirbit shift site), big pending stacks and paths of 100-150 tokens are never split-tested. The tables have 2^22 slots, so small tests never evict, although 1,675 campaign-#1 reports did.

## Verifier (CONFIRMED, medium, refuted=False)
The gap is real. I checked it against the code, the docs and the snapshot.

1) No test covers the campaign regime.
- DESIGN.md:188-193 defines split exactness only as `on 4x4 exit 0 and 5x5 exit 12 ≤3 blocks`.
- README.md:65 runs `--grid 5x5 --exit 12 --num-blocks 3 --allow-exit-transit`.
- The lead's own runs were 5x5 exit 7 with ≤3 blocks and 4x4 exit 0 with ≤3 holes.
- test_chaos (DESIGN §5.2) is also 5x5 exit 7 with ≤3 blocks, and the lead reports it no longer splits at all.
- The campaign argv is `--allow-exit-transit --num-holes 3` (campaigns.extra_json) with unbounded blocks, built at volunteer.py:421-425. Nothing tests this regime.

2) The untested regime produced the published results. Snapshot facts:
- 1,675 of 54,409 reports had evict_shallow>0, and every one of them also had evict_recent>0. The smallest such job had 3,717,975 states.
- Those reports hold 28.9 of the 37.6 billion reported states (77%) and 390 of 622 CPU-hours.
- For 5 of the 6 exits, their maximum best equals the published per-exit best (149, 112, 138, 115, 80). Exit 0 is the exception: 124 vs 127.
- Block counts in the jobs' best levels reach 11, and 13,464 jobs have a best level with ≥8 blocks. The published bests for exits 2 and 6 have 8 blocks.
- Seed depth reaches 128.

3) The suggested workaround works as described. test_split_exact.py:48 builds `[a.worker] + cfg + ['--time','0'] + (['--seed-path', seed] if seed else [])`. parse_seed_path (backsearch.c:1899-1901) resets `g_seed_path_n = 0` on each call, so the last `--seed-path` wins. The root run inherits the cfg seed and children override it, so subtree roots can be tested today without code changes. Two defaults match the client: `--two-tables` defaults on (backsearch.c:79), and `--status-every` only changes output plus g_win_state (backsearch.c:2244, 4651).

Why I lowered the severity from high to medium:
- A missing test cannot by itself make a result wrong.
- Eviction is safe by construction. shallow_evict and recent_evict (backsearch.c:998-1080) only copy survivors into a fresh table. dedup_two_tables (1086-1149) re-reads g_shallow/g_recent after an eviction, and no other depth or key is ever written. Eviction can therefore only cause re-expansion and a different visit order. Splitting already changes the visit order, and the small tests cover that.
- Replay (build_seed_path_seed, 2040-2078) is a loop with no branch that depends on depth or block count: g_bulk_min_depth defaults to 0 and MAX_BLOCKS is 32. The small tests run the same code with a different spread of states.
- So the chance of a bug that shows up only in this regime is moderate to low. What makes the gap worth fixing is cost versus benefit: it leaves the core invariant (DESIGN §1/§5) unchecked where most of the work happened, and closing it costs about a CPU-minute per seed. It is the cheapest high-value gate before the next campaign.

A consequence I found that this kind of test should also guard:
- PATH_TOK_MAX is 250 (backsearch.c:227), and `path_push` silently returns 0 once `plen >= PATH_TOK_MAX` (463). All six callers ignore the return value (1961, 1987, 2005, 2030, 2250, 2371).
- Meanwhile `--seed-path` accepts up to 1024 tokens (229, 1918), and g_max_depth defaults to INT_MAX (150).
- Depth equals the token count, so this cannot happen at 5x5 depths (≤~150). But on a larger grid in the next campaign, a state deeper than 250 would print a truncated REMAINING/trace path, and its child job would replay the wrong node. Only a regime test or a hard guard would catch that.

Checked and fine or harmless:
- print_remaining runs after expand(&s) (backsearch.c:4645, 4650). The cursor's children are therefore listed both inside the cursor's own REMAINING line and as separate lines. In the snapshot, 4,103 child jobs extend their sibling cursor. They account for 45M states, about 0.17% of child-job states. This is a superset, so nothing is lost; it is minor waste.
- seg_len saturates at 127 on bulk children and walk segments are short, so this is fine.
- I did not verify whether the 4x4 ≤3-holes run ever reaches 8 blocks, or whether the 5x5 ≤3-blocks reference run itself evicts. The test does not print evict counts. Even if either happens, 5x5 deep, many-block, evicting subtrees remain untested.
