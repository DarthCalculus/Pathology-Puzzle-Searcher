## Verifier (CONFIRMED, low, refuted=False)
I read the code. The mechanism is real, but it only matters once some published proof is already false. Part of the finding also overstates the problem.

What holds:
1. annotateChampions (server/lib/db.js:586-603) never looks at a proof's status. For every covering proof p, a verified level with `lv.moves === p.maxMoves` is pushed into `champ`. A longer level goes into `contra`, but that does not stop other levels from being badged by the same p. listProofs/proofChampions (db.js:631-647) already compute status 'contradicted', but only /api/proofs and tools/add_proof.js --list use it, and no public page renders /api/proofs (grep of public/*.html|js finds nothing).
2. addProof (db.js:654-667) checks only stored verified levels (`proofChampions(probe).longest`). It never compares against other proofs.
3. v2_finish.js:64-67 calls addProof first and then processSubmission of the champion. pipeline.js has no proof-contradiction handling. Nothing warns when a newly stored champion contradicts an existing proof.

The owner's scenario is concrete. Campaign #1 stores proofs of the form (5x5, exit E, maxBlocks null, maxHoles 3) (campaign extra_json = ["--allow-exit-transit","--num-holes","3"]). Suppose campaign #2 (<=4 holes) finds a 3-hole 151-move level at exit 1 and it gets stored verified. A search for 5x5, exit 1, <=3 holes then works like this: proofsCoveringFilter returns proof C1 (<=3h, e1, 149), C2 (<=4h, e1, 151), the derived <=3h any-exit proof (149) and, if complete, the derived <=4h proof. The 151 level is tagged champion (C2 or derived <=4h) and "contradicts proof #C1, #derived". The existing verified 149 level (local records.db id 1, "Capital C", exit 1, 2 holes, verified) still matches C1 and the derived <=3h proof. The maximal-class filter keeps the derived one, so the card shows "★ exhaustively proven champion — longest 5×5 level with ≤ 3 holes — Collective" and the tooltip "none is longer", directly below the 151 card. /api/history behaves the same way.

What is overstated:
(a) proofForFilter's rule `p.maxMoves < best.maxMoves` (db.js:627) is mathematically correct when all proofs are true. The filter class lies inside every covering class, so the minimum is the tightest valid bound. It is wrong only when the chosen proof is contradicted. Also, app.js never reads the `proof` field of /api/search (its only proof-related rendering is lines 119-127), so this value reaches only raw API consumers.
(b) derivedProofs' rule of keeping the newest proof per exit (db.js:529) is a deliberate and internally consistent design.
(c) The addProof gap between proofs is mostly covered in practice by the check against stored levels. Campaign #1's exit-1 champion (149) is stored verified locally. So a buggy <=4h or re-run <=3h proof claiming less than 149 at exit 1 would be refused. The same holds for exit 6 against the verified 146-move 4-hole level id 2, which campaign #2 (<=4h) must reach. A pairwise proof check would not catch the owner's scenario either: C1 (<=3h, 149) and C2 (<=4h, 151) are consistent as a pair. The contradiction appears only once the 151 level is stored, and the status computation already detects that.

Severity: low. It is display-only and needs a false proof, or a wrongly verified level, to exist first. The longer level is already flagged "contradicts proof #N", and the owner's add_proof --list shows CONTRADICTED. It is still worth fixing before campaign #2. The owner has said a possibly false campaign #1 proof stays published until they decide, and in that state the site would keep asserting "none is longer" for a level that a longer displayed level refutes. It would be medium if the owner expects campaign #2 to overturn #1.

*fix notes*: None of these changes delete anything, which respects the owner's direction.
(1) Compute each proof's status once per request and attach it to the proof objects. For example, have allProofs() return proofs decorated with a status taken from proofChampions, cached on (max(levels.id), count(proofs)), since proofChampions runs a searchLevels per proof.
(2) In annotateChampions (db.js:586), keep contradicted proofs out of `champ`. Either drop them or push them into a separate `lv.disputedChampion` list, and have app.js render a 'disputed proof' badge instead of '★ exhaustively proven champion — none is longer'.
(3) In proofForFilter (db.js:625), skip contradicted proofs, or return {proof, status} so API consumers can see the dispute.
(4) In tools/v2_finish.js, after addProof and processSubmission for each exit, call listProofs() and print every proof whose status is 'contradicted', with its longestStored. The owner then learns at publish time that campaign #2 overturned campaign #1, without anything being revoked.
(5) Optional, cheap: in addProof, warn (or refuse unless --supersedes) when classWithin(q, new) && q.maxMoves > new.maxMoves, or when the class is identical with a different maxMoves. This protects the case where the earlier champion was never stored as verified.
(6) Add the regression test from repro_plan to server/test (scratch DB).
