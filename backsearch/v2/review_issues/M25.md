# M25: No client version in register, heartbeat or report: the server cannot refuse old clients that lack holding/running/drop, or tell which client release produced a report

verdict CONFIRMED, severity medium, category protocol
locations: volunteer.py:80 (constant User-Agent, no version field); jobs.js:735 (whitelist covers only worker SRC_HASH); jobs.js:614 (steal logic relies on `running`); collective.html links the stale `v2` branch

## Summary
Coverage depends on client logic: which nodes are done, which children a split has, absorb results, and holding/running/drop, which were added mid-campaign. Yet only the worker source is whitelisted, and the client sends no version. A pre-2026-09-24 client, for example from the stale `v2` branch the site links, is served normally. Stealing treats all its jobs as queued, so the one-running-job cap never applies to it. It ignores `drop`, and release-by-omission never applies, so a restarted old client's abandoned queue is renewed until stolen. The server cannot identify or re-issue reports from a buggy volunteer.py.

## Source report F59 (client-core)
**No client protocol version is sent, so the server cannot detect or refuse clients that lack holding/running/drop behaviour** at /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py:80

*summary*: Correctness of the lease scheme now depends on client cooperation added mid-campaign (holding, running, obeying drop), but register and heartbeat carry no client version and the User-Agent is a constant. A long-running old client process keeps using the old protocol, and the server cannot tell.

*failure_scenario*: A volunteer started before the 2026-09-24 changes keeps running (a clean checkout of an older commit passes the dirty check, and the worker hash may be unchanged). Such a client does not honour drop. In the campaign-#1 end game, 40 duplicate reports for job 167664 kept arriving until 09:20:04 after it split at 09:17:09, each a full ~120 s window. A client honouring drop would have killed those runs within about 30 s, which fits stale clients.

*evidence*: volunteer.py 80 and 116: headers={... "User-Agent": "pathology-volunteer/2"}
volunteer.py 368: self.api.post("/api/v2/register", {"name": name, "workers": self.workers})   # no version
volunteer.py 1168: heartbeat body has no version field
Snapshot: reports for job 167664: first 'split' at 09:17:09, then 40 'dup' up to 09:20:04 with elapsed ~120 s.

*suggested_fix*: Add a client_version (and protocol feature flags) to register and heartbeat. Have the server answer 426 for clients below a minimum, and make the client stop with 'update: git pull'. Record the version on the clients row so the owner can see who runs what.

*expected_gain*: Protocol fixes such as drop and release take effect for everyone instead of only for restarted clients.

## Source report F82 (server-scheduling)

## Source report F187 (robustness-ops)
**No client-version gate: pre-2026-09-24 clients (e.g., from the stale `v2` branch the site links) break stealing and release** at /Users/george/PathologyRecords/server/lib/jobs.js:614

*summary*: The server cannot tell client versions apart: the User-Agent is constant, and the hash whitelist covers only the worker sources. A client without `holding` or `running` is served normally. Stealing treats all of its jobs as queued, so the one-running-job-per-request cap never applies to it, and it ignores `drop`. Release-by-omission never applies to it either, so a restarted old client's abandoned queue is renewed by every heartbeat until stolen. collective.html links the README and DESIGN on the `v2` branch, which is 4 commits behind main and has exactly this old client.

*failure_scenario*: A volunteer checks out the `v2` branch after following the collective.html README link (the worker source is identical there, so the hash check passes), or simply has not pulled since 2026-09-23. At the campaign tail the pool is empty, and each idle client's lease request steals up to n of this client's running jobs, because running_json is '[]'. The old client never handles `drop` and keeps running them, so both machines search the same subtrees and the second result is thrown away. After a restart its previous queue stays leased and is renewed every 30 s until someone steals it.

*evidence*: jobs.js:614 `let r = []; try { r = JSON.parse(j.running_json); } catch {} runningOf.set(j.client_token, new Set(r));`, then 622-627: `const isRunning = runningOf.get(j.client_token).has(j.id); if (isRunning && tookRunning) break;`. jobs.js:500 running_json is updated only `if (Array.isArray(body.running))`. jobs.js:508 `holdingSet = Array.isArray(body.holding) ? ... : null`. volunteer.py:80 `"User-Agent": "pathology-volunteer/2"`. The origin/v2 heartbeat body is `{"token", "workers", "paused", "boards"}` (git diff origin/v2 origin/main). collective.html:54-55 `.../blob/v2/backsearch/v2/README.md`.

*suggested_fix*: Send `client_version` (a protocol integer) in register, heartbeat and lease. The campaign stores min_client_version, and the server answers 426 with an upgrade message, which the client prints before stopping. Until then, treat a heartbeat without `running` as 'every held job is running'. Point the site links to main, and delete or fast-forward the `v2` branch.

*expected_gain*: Protocol fixes like stealing and release actually apply to every connected client.

## Verifier (CONFIRMED, medium, refuted=False)
I confirmed the core claim by reading the code, both on main and on origin/v2.

1. The client never sends a version.
- volunteer.py:80 and :116 send a constant header, "User-Agent": "pathology-volunteer/2".
- volunteer.py:368 registers with only {"name": name, "workers": self.workers}.
- The startup heartbeats at :331/:349 carry {token, workers, paused, boards}.
- The main heartbeat at :1168 adds holding/running but has no version.
- Reports at :913 send {"token", "reports"}.

2. The server gates only on the worker hash.
- jobs.js:735 checks `const hashIn = normHash(el.src_hash)` against the campaign hashes.
- The reports table (jobs.js:218-226) and the jobs table have no column for the client version.
- So after a client bug is found, there is no reliable way to select the reports it produced. Tokens outlive restarts and code updates, so token plus received_at is only an approximation.

3. An old client is served but quietly falls out of the 09-24 protocol.
- jobs.js:500 updates running_json only `if (Array.isArray(body.running))`, so an old client keeps the default '[]'.
- jobs.js:508/514: holdingSet is null, so release-by-omission never happens. Every heartbeat renews all of the token's leases, including a restarted client's abandoned queue, until they are stolen.
- jobs.js:527: `drop` is computed only `if (holding)`, so an old client is never told that a job was stolen or finished. It would ignore the message anyway.
- jobs.js:614-627: `runningOf.get(j.client_token).has(j.id)` is always false for an old client. The rank puts its running jobs first, as if they were queued, and `if (isRunning && tookRunning) break` never fires. At the tail, idle clients can steal any number of an old client's running jobs per request, and it keeps running them.

4. The one existing lever cannot be used mid-campaign.
- Old clients do stop when the worker-hash list changes: origin/v2 volunteer.py:1176 has the "accepted worker hashes changed" request_stop.
- But removing the old hash invalidates finished work. The audit at jobs.js:997 puts every done/split node whose src_hash is no longer listed into `unknown`, and reopenUnknownHashJobs re-runs those jobs.
- So a client-only fix, like the three 09-23/24 commits (3829d5c, 67f612b, aa7f0bf), cannot be enforced or even observed.

5. Evidence from campaign #1 (snapshot): 1,411 'dup' reports, 31.6 CPU-h in total.
- 13.9 CPU-h (about 2.3% of 602) went to runs that started more than 45 s after their job was already finished (received_at - done_at - elapsed > 45).
- With the current client and server this cannot happen: a 30 s heartbeat returns `drop` for a queued job that is already done.
- These late starts cluster at 07-09 UTC on 09-24 and vanish by 12-13 UTC. That fits old clients, or an older server that did not yet send `drop`. Because nothing is versioned, the snapshot cannot say which.
- Job 167664 alone drew 40 dup reports from 5 clients, the last one received 3 minutes after it split.

Parts of the merged report that are weaker than stated:
- Stale `v2` branch. origin/v2 exists, is 4 commits behind main, has worker sources identical to main (0-line diff, so the same SRC_HASH), and carries the old client (heartbeat body without holding/running, no drop handling). collective.html:54-55 links README/DESIGN under blob/v2. However, the clone command at collective.html:34, and the v2 README itself, clone the default branch. Following the link does not by itself put a volunteer on v2. That only happens with a deliberate `git checkout v2`, or if GitHub's default branch is v2, which I cannot check offline. The link itself is a low doc mismatch: DESIGN on v2 has no section 9.
- Correctness. The published result is not endangered. Coverage is decided by reports from whitelisted workers, and first-report-wins keeps duplicates harmless. The cost is wasted CPU, abandoned leases that hold up the audit until the tail steals them, and the loss of targeted remediation. The last one would matter if a client tree-assembly bug (children or absorb) appears: without a version column, the only safe fix is a broad re-run.

Rating for the next campaign: medium. Every client must restart at the next campaign (see the 410 issue below), and a worker-hash bump would force a `git pull`. So the fleet will probably start out uniform. But this review is producing many client-side fixes that will probably land mid-campaign, and today none of them can be enforced or even observed.

Related bug on the same code path, possibly reported separately:
- requireClient returns 410 'campaign_closed' for tokens from a closed campaign (jobs.js:338).
- In register() (volunteer.py:344-360), any status other than 401/403/404 counts as "cannot reach the server" and loops every 10 s forever.
- The running heartbeat (:1171-1175) stops only on 401/403.
- So once campaign #1 is closed and #2 opened, every returning client with a stored token hangs at startup until it is run with --reregister. A running client never moves to the new campaign.
- A new 426 gate would hit this same unhandled-status path.

*fix notes*: Client (volunteer.py):
- Add a constant CLIENT_PROTOCOL (an integer) and CLIENT_SHA (sha256 of volunteer.py, computed once at startup).
- Send both in register, every heartbeat (including the startup heartbeats at :331/:349), lease and reports. Also put them in the User-Agent.
- Handle three statuses explicitly on every endpoint and at startup:
  - 426 'client_too_old': print the server's message ("git pull && ./build_pgo.sh") and stop with exit 2.
  - 410 'campaign_closed': drop the stored token and register again (fixes the infinite startup loop).
  - Unknown 4xx: stop; do not treat it as "unreachable".

Server (jobs.js / v2routes.js):
- Add campaigns.min_client_protocol.
- Treat a missing client_protocol as 0.
- Refuse register, heartbeat and lease below the minimum with 426 {error:'client_too_old', min, message}. This works retroactively: every client deployed today sends nothing, so all of them are refused.
- Keep accepting reports from old clients. They are coverage-valid by worker hash.
- Store client_protocol/client_sha in a new reports column, and on the job row when a report is accepted. Show the version mix per client on the clients row and in /api/v2/status.
- Add a tool that reopens jobs whose accepted report came from a given client_sha, analogous to reopenUnknownHashJobs, so a buggy client release can be remediated without a full re-run.
- Interim, until the gate exists: if a heartbeat has no `running`, set running_json to all of that client's leased ids, so the one-running-job steal cap still applies.

Site and repo:
- Point the collective.html:54-55 links at blob/main.
- Fast-forward or delete the stale `v2` branch.

Tests (v2_gates.test.js):
- A heartbeat or lease without client_protocol, or below the minimum, returns 426.
- A report from an old client is accepted and tagged with its version.
- The reopen-by-client-sha tool resets exactly those jobs.
- A stored token from a closed campaign re-registers into the open one.

Adjacent (probably separate findings): the snapshot shows job 167664 run about 40 times in 3 minutes. Two things together explain that:
- Stealing ping-pong within one heartbeat interval: a freshly stolen job counts as "queued" until the new holder's next heartbeat.
- The client does not deduplicate its queue: volunteer.py:506 `self.queue.extend(good)` never checks the ids it is already running or has queued.

Worth fixing alongside this: dedup the queue by job id, and do not steal jobs that were leased less than about one heartbeat ago.
