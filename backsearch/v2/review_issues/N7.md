verdict CONFIRMED, severity low, category robustness

## Summary
Next campaigns will add nested classes: <=N blocks inside <=3 holes, and <=3 holes inside <=4 holes. A subclass proof whose maximum exceeds a superclass proof, or a superclass proof below a subclass proof, means one of the two searches is wrong. addProof would catch that only if a verified champion level of the offending size is already stored, which fails exactly when verification is too_complex.

## Source report F206 (r2-next-campaign-generalization)
**addProof checks a new proof only against stored verified levels, not against existing proofs of nested classes** at /Users/george/PathologyRecords/server/lib/db.js:654

*summary*: Next campaigns will add nested classes: <=N blocks inside <=3 holes, and <=3 holes inside <=4 holes. A subclass proof whose maximum exceeds a superclass proof, or a superclass proof below a subclass proof, means one of the two searches is wrong. addProof would catch that only if a verified champion level of the offending size is already stored, which fails exactly when verification is too_complex.

*failure_scenario*: A config-E campaign ('5x5, <=3 holes, <=8 blocks') reports exit 1 = 150 because of a bug, while the published '5x5 <=3 holes exit 1' proof says 149. addProof queries stored verified levels in the class with more than 150 moves, finds none, and inserts the proof, because v2_finish calls addProof before submitting the champion. Two mutually contradictory exhaustive proofs are then live. If the 150 champion cannot be verified, neither proof is ever flagged 'contradicted'.

*evidence*: db.js:661-668 `const { longest } = proofChampions(probe); if (longest && longest.moves > p.maxMoves) { return { ok: false, reason: 'contradicted', ... } }` (the only guard); classWithin at db.js:557-563 already implements containment; v2_finish.js:64-68 `const r = addProof(proof); ... processSubmission(...)` (proof first, champion second).

*suggested_fix*: In addProof, also compare against allProofs(). Refuse, or require a --force flag, when some stored proof q has classWithin(new, q) and new.maxMoves > q.maxMoves, or classWithin(q, new) and q.maxMoves > new.maxMoves. Per exit, map exits via achievableExits the same way levelInClass does.

## Verifier (CONFIRMED, low, refuted=False)
The code is as described. addProof (db.js:654-681) validates the fields, builds a probe and calls proofChampions(probe) (db.js:631-639). That runs searchLevels with statuses ['verified'] and refuses only when `longest && longest.moves > p.maxMoves`. Nothing compares the new proof with storedProofs()/allProofs(), even though classWithin (db.js:557-563) exists and is used only for badge filtering in annotateChampions. The tools/add_proof.js header also says the only refusal is 'a stored verified level already contradicts'. v2_finish.js:64-68 calls addProof and then processSubmission without proposedPath/proposedMoves, so a champion that comes back too_complex returns 'needs_solution' and is never stored (pipeline.js:66-117). Same-class disagreement also slips through: derivedProofs (db.js:522-526) silently keeps the newest proof per exit.

Extra consequence: proofForFilter (db.js:625-629) picks the smallest maxMoves among covering proofs. With contradictory nested proofs, a search in the subclass would display the superclass's lower bound, and listProofs would show neither proof as 'contradicted'.

Mitigation for a 5x5 follow-up. All six campaign-#1 champions have verified_moves == best in the snapshot (127/149/112/138/115/80). Locally, the top 5x5 levels (149 @ exit 1, and a 146-move 4-hole level @ exit 6) are stored 'verified' with full-length paths, so the default hash engine handles them. That means a <=4-hole superclass campaign that under-reports an exit below a stored verified level would still be refused by the level check. The gap that remains is real but narrow:
- a subclass (or same-class) proof that over-reports with no real witness (best_level null, or verified_moves null and the solver later measuring it shorter): the result shows only as 'unwitnessed', never as a contradiction;
- grids whose champions are too_complex (4x6/5x6);
- proof-vs-proof inconsistency among existing proofs, e.g. the local 5x5 exit 12 <=2 holes = 80 proof, which happens to be consistent with the <=3 holes = 80 proof.

It is defense in depth rather than a correctness bug, so it stays low.

*fix notes*: In addProof, loop over allProofs(). For each q:
- if classWithin(new, q) and new.maxMoves > q.maxMoves: refuse, reason 'contradicts_proof';
- if classWithin(q, new) and q.maxMoves > new.maxMoves: refuse;
- same class with a different maxMoves: refuse unless --force/--supersede is given.
classWithin needs the same rows/cols. If cross-size proofs should be covered, add an achievableExits-based variant. Add the same check to listProofs as a 'contradicted_by_proof' status so existing rows get flagged. Add a v2_gates test: seed a <=3-hole proof of 149, then addProof a <=3-hole <=8-block proof of 150 and expect a refusal.
