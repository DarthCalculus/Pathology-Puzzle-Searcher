# M47: The multi-start label table is not cleared when the shared generation counter wraps inside a non-multi solve

verdict CONFIRMED, severity low, category robustness
locations: sokoban_bfs.c:1849 (`if (hs->ht_seq == 1) memset(L, ...)`); hsp64_clear (zeroes slot_small/slot_big on wrap, not ms_lab); MSLab liveness `sl->gen == hs->ht_seq`

## Summary
MSLab entries are live when gen == hs->ht_seq, and ht_seq is shared with every cutoff solve. hsp64_clear handles a wrap by zeroing slot_small and slot_big but not ms_lab, and the multi solver clears L only if it happens to see ht_seq == 1. A wrap that lands on a cutoff solve therefore makes stale labels and cached successor lists look live in a later multi solve.

## Source report F29 (solver-core)
**Multi-start label table is not cleared when the shared generation counter wraps inside a non-multi solve** at /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:1849

*summary*: MSLab entries are live when gen == hs->ht_seq, and ht_seq is shared with every cutoff solve. hsp64_clear handles a wrap by zeroing slot_small and slot_big but not ms_lab. The multi solver clears L only if it happens to see ht_seq == 1, so a wrap that lands on a cutoff solve leaves stale labels and cached successor lists that look live again.

*failure_scenario*: A process makes more than 2^32 solves and the wrap happens inside solve_push64_cutoff. The next multi solve sees old MSLab entries whose gen matches the new ht_seq, with stale labels, done bits and cached successors from an unrelated puzzle, and can return wrong out[] decisions. Unreachable in the campaign: split_after 1800 s gives about 2e7 solves per process, but it is latent for long unsplit runs.

*evidence*: sokoban_bfs.c:1028-1031  if (++hs->ht_seq == 0) { memset(hs->slot_small, 0, ...); if (hs->slot_big) memset(hs->slot_big, ...); hs->ht_seq = 1; }
sokoban_bfs.c:1849  if (hs->ht_seq == 1) memset(L, 0, MS_SIZE * sizeof(MSLab));

*suggested_fix*: Also memset hs->ms_lab (if allocated) in hsp64_clear's wrap branch, and drop the ht_seq == 1 special case.

*expected_gain*: Removes a latent wrong-answer path.

## Verifier (CONFIRMED, low, refuted=False)
The code matches the claim. hsp64_clear (sokoban_bfs.c:1027-1031) handles `++hs->ht_seq == 0` by zeroing only slot_small and slot_big; hs->ms_lab (field at :995) is left alone. sokoban_solve_multi calls hsp64_clear itself (:1848) and then clears L only `if (hs->ht_seq == 1)` (:1849). ht_seq is shared with solve_push64 (:1106) and the cutoff solve (:1528). If the wrap happens in either of those, the next multi solve sees ht_seq >= 2 and L is not cleared. ms_slot (:1824) treats `sl->gen == hs->ht_seq` as live, so a matching stale entry brings back its lab/done/cached/soff, and soff points into an arena that is reset every solve.

Why it stays low:
(1) Reachability. The largest per-job solver_calls in the snapshot is 112,449,768 (sqlite max over jobs; max elapsed 1,824 s). g_solver_calls counts one per single or bulk call (backsearch.c:1702, :2413), and each call clears at most twice (small table, then a big-table retry). So a process makes at most about 2.2e8 clears, 19x or more below 2^32. Each job is a fresh process that starts at ht_seq = 1.
(2) Even after a wrap, a wrong answer needs an MSLab slot that no multi solve inserted into for a full cycle of about 2^32 generations. Its stale gen must then equal the current ht_seq and its key must equal a key being looked up. MS_SIZE is 65,536 slots and they are rewritten constantly, so the chance is effectively zero.

What would make it more relevant: dropping forced splits (as M10/F179 suggest). At about 61.6k calls/s, a wrap would take roughly 10-19 h of continuous solving in one process.

*fix notes*: In hsp64_clear's wrap branch, add `if (hs->ms_lab) memset(hs->ms_lab, 0, MS_SIZE * sizeof(MSLab));` (move the MS_* defines above it or pass the size in). Then delete the `if (hs->ht_seq == 1) memset(L, ...)` line at sokoban_bfs.c:1849. The fix costs nothing. To test it, add a debug hook that starts ht_seq at 0xFFFFFFF0 and run test_split_exact on a small grid.
