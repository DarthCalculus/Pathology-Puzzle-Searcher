Clients started inside $(client A 2) are reparented, so cleanup's `pkill -P $$` never reaches them or their real workers. `pkill -9 -f "volunteer.py --name A"` also kills a real client named, say, 'Alice'. `lsof -ti :3199 | xargs kill` kills any process with any socket on that port. lib/db.js ignores JOBS_DATA_DIR, so the test server opens and migrates the owner's data/records.db. The comments also misstate the lease (5 s vs 30) and the one-worker claim.

## Verifier (CONFIRMED, low, refuted=False)
Each mechanism is real. The harm is smaller than the finder suggests.

(1) Leaked clients.
- What happens: `A=$(client A 2)` (test_chaos.sh:48, :50, :52) runs client() in a command-substitution subshell. The `python3 ... &` inside becomes a grandchild and is reparented when the subshell exits, so cleanup's `pkill -P $$` (:19) never matches it.
- Normal runs are fine: :57 sends INT to $A/$B.
- Terminal Ctrl-C also reaches the clients (same process group, and volunteer.py:1355-1356 installs SIGINT/SIGTERM handlers).
- The leak happens only when a SIGTERM/SIGHUP is sent to the script's PID alone.
- The leaked workers finish tiny jobs (split_after 1 s, a campaign of about 1-4 s), so the CPU cost is seconds, not 'full CPU'. What remains is idle clients polling a dead port.

(2) pkill pattern. `pkill -9 -f "volunteer.py --name A"` (:49) is an unanchored regex. It matches, and SIGKILLs, a real `python3 v2/volunteer.py --name Alice ...` on the same machine. That orphans the real client's workers and leaves its leases to expire (3600 s).

(3) Port cleanup. `lsof -ti :$PORT | xargs -r kill` (:32) matches any process with a socket whose local or remote port is 3199, not only the listener. 3199 is an unusual port, so this is rare.

(4) Comments. The header (:4) and DESIGN.md:199 say 'lease 5 s'; the plan sets `"lease_s":30` (:25). README.md:71 says 'Every test runs one worker at a time and finishes in about a minute'. Chaos runs up to 4 real workers (2+2, then 2+1, plus A's orphans), node, and 30 s site-solver verifications (v2routes.js:18, :62-70), with an audit loop of up to 240 s. That matters under the owner's 3-CPU cap.

(5) records.db. server.js:10 requires lib/db.js, whose DATA_DIR is fixed at ../../data (db.js:20-22) and ignores JOBS_DATA_DIR, so the test server opens the owner's local data/records.db. The finder overstates this part:
- the database is the local dev copy, not the live Hetzner DB;
- the load-time statements are guarded, idempotent migrations, the same ones any dev-server start runs;
- nothing in jobs.js or v2routes.js writes to records.db.
So nothing is corrupted. It is a test-isolation smell; test_load.sh:29 has the same issue.

*fix notes*: 1. Start clients without command substitution, e.g. `client A 2; A=$LAST_PID` with `LAST_PID=$!` set inside the function. Keep every PID in an array and kill them all, plus their process trees (`pkill -P $pid`), in cleanup.
2. Replace the pkill -f line with a kill of the recorded PID, or anchor the pattern to the unique outbox (`pkill -f -- "--outbox $T/outbox_A"`).
3. Use `lsof -tiTCP:$PORT -sTCP:LISTEN`.
4. Make db.js honour an env override (e.g. `RECORDS_DATA_DIR || JOBS_DATA_DIR`) and export it in test_chaos.sh and test_load.sh.
5. Fix the header and DESIGN §5.2 lease figure (30 s). Fix README:71: chaos runs up to 4 workers plus node and background site-solver checks, so under the 3-CPU cap run it with --workers 1 per client or taskset/cpulimit.
6. Separately (already known): restore the split exercise. The layer-2 roots now finish under split_after = 1 s; use a bigger config, or split_after 0.2 s, so the level-set check runs again.
