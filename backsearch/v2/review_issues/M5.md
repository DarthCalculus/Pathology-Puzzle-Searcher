# M5: REMAINING re-lists the already-expanded cursor together with its children, so the subtrees overlap and the cursor's subtree is searched twice

verdict REFUTED, severity low, category performance
locations: backsearch.c:4326-4328 (print_remaining prints s, then the whole stack); backsearch.c:4645 (split/stop checks run after expand(&s)); DESIGN.md §1.2 ('those subtrees are disjoint'); volunteer.py cursor==seed handling ('nothing was expanded', self_remaining)

## Summary
The split and stop checks run after expand(&s), so s's children are already on the stack when print_remaining prints s and then the whole stack. The cursor job regenerates every child subtree, and each child also runs as its own job. The result stays exact (overlap only) and the cost was small in campaign #1 (about 25.7k states over 2,072 splits), but it contradicts DESIGN §1.2 and the function comment. For the same reason the client is wrong to read cursor==seed as 'nothing was expanded': it discards a valid split whose root was already expanded.

Every one of those child subtrees is explored twice. The cost is larger when the cursor is shallow, and this also slightly inflates the published state and CPU totals.

## Verifier (REFUTED, low, refuted=True)
The factual claim is correct. As a performance improvement, though, the gain is too small to matter, so it is refuted under the feasibility rubric. The inaccurate docs and comments are a real low-severity mismatch and should be fixed.

Premise, checked in the code:
- In the campaign DFS loop in backsearch.c, the stop check (4645) and the split check (4650) run after `expand(&s);` (4639) has pushed all of s's children.
- expand() has no early return (checked 2463-2720), and g_stop_requested is only tested after expand, so the expansion is always complete.
- print_remaining (4326-4329) prints s and then every g_queue entry, children of s included. So REMAINING = [s, children(s), older stack]. Re-running s regenerates children(s), which also run as their own jobs.
- The comment at 4323-4324 and DESIGN §1.2 (line 13: "Those subtrees are disjoint") are wrong. DESIGN line 70 ("a stack of N entries prints N+1 lines") describes the code accurately.
- volunteer.py:785 says "nothing was expanded" and 822-823 says "interrupted before expanding its root". Both are wrong: print_remaining is only ever reached after the root has been expanded.
- A root cursor can only come from SIGINT (stop). iter starts at 0 (4516), and the split and time checks only fire when (++iter & 1023) == 0. Pause uses SIGSTOP, not SIGINT.

Measured on the snapshot (the first child of each split parent is the cursor; this was checked by the prefix analysis):
- 2,072 cursor jobs, 25,696 states in total (7e-7 of 36.8 billion), 14.3 CPU-seconds (0.004 of 601.9 CPU-hours, about 7e-6), at most 628 states each, and none of them split.
- 2,072 extra job rows out of 167,766 (1.2%). Most are absorbed locally as done nodes in tree reports, so each costs one short probe process spawn.
- Why the cost stays tiny: the cursor is the node popped at an iteration that is a multiple of 1024, so its subtree is typically a few dozen nodes. The share of splits whose cursor subtree is job-sized is about 1e-6. The ratio does not grow with campaign size.
- The "valid"/"states" totals are inflated by the same negligible amount.
- The client's discard on cursor==seed costs one root expansion, in milliseconds. The lease then runs out (at most 3,600 s), which is the stop-lease behaviour you already know about. The discard is safe.
- Side note: the reviewers' prefix counts (510 vs my 1,284) differ because bulk walk-back siblings also extend the cursor's path. It does not affect the conclusion.

Exactness of the proposed change (print only the stack): it is sound. After a complete expand(s), the stack is exactly what a monolithic run would process next. Children of s depend on the same parent-dedup soundness as every other stack entry already does, and adjflags are per path, never merged through dedup hits.

It does add one edge case that must be guarded. When the stack is empty after expand(s), the change would emit status "split" with zero REMAINING lines:
- volunteer.py:826 would log a protocol violation and leave the node untouched, so it gets re-run.
- test_split_exact.py:84 asserts that a split has REMAINING lines.
- The server rejects a split with no children.

Nothing else depends on the cursor-first order beyond the client's pop-order heuristic (volunteer.py:633). The server (jobs.js parseTree) and test_split_exact accept either form.

Net: the behaviour is conservative (overlap, never a gap). Changing the split protocol for a gain of about 1e-5 of CPU is not worth the risk unless the worker is being rebuilt for other fixes anyway, and even then it is optional.
