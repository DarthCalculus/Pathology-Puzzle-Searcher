## Verifier (CONFIRMED, medium, refuted=False)
The gap is real. Nothing in the protocol identifies which client release is talking to the server.
- volunteer.py:80 and :116 send only the fixed User-Agent "pathology-volunteer/2". The register, heartbeat, lease and reports bodies carry no version.
- A grep of jobs.js and v2routes.js for version, user-agent, 426, min_client and release_tag finds no gate of any kind.
- build_pgo.sh:41 computes SRC_HASH as `cat backsearch.c sokoban_bfs.c sokoban_bfs.h | shasum -a 256`. volunteer.py is not part of it, so the hash whitelist (check_hash at volunteer.py:397, heartbeat recheck at :1182, server 409 unknown_hash) can only force a new worker, never a new client.

Mitigations that exist, and limit how likely a mismatch is:
1. check_dirty (volunteer.py:37 and :250-264) refuses to run when v2/volunteer.py or the C files differ from HEAD. A normal `git pull && ./build_pgo.sh` therefore gives a matching pair.
2. If campaign #2 changes the C sources and whitelists only the new hash, every campaign-#1 binary is refused.

An old volunteer.py can still run a new worker binary in these cases:
- The binary was built at one commit and the checkout later moved to another. read_version (:282-295) trusts the compiled-in SRC_HASH and never compares it with a sha256 of the checked-out sources.
- `--worker` points at a binary from another checkout.
- The owner commits the worker change before the matching client change (non-atomic rollout).

The strongest gap applies right now, and not only to hypothetical findings 1, 4 and 7. Client-only fixes planned for the next campaign cannot be enforced at all: releasing unstarted leases, the SIGINT-before-handler race, and the partial-split handling at :831-835. The only way today is to change a C byte artificially so the hash changes.

The old client also mishandles unknown worker output in ways that matter:
- An unknown SUMMARY status (:803) becomes "no SUMMARY". The node is left untouched and re-leased, which wastes work.
- REMAINING lines that fail SEED_RE (`[URDL][123]` tokens, :39) are dropped. The split is still reported as long as one child survives (:831-835). Lines longer than MAX_LINE are skipped at :771 without even counting as bad_remaining.

So any future change to the REMAINING or token format, for example on a larger grid, run under a stale client would silently lose subtrees. That is a critical-class outcome, but it depends on a future format change plus a stale client. That condition is why I rate this medium rather than critical.

Correction to the suggested fix: HTTP 426 does not stop campaign-#1 clients. They loop instead:
- register: any status other than 400 or 503 retries every 30 s forever (:373-378).
- startup heartbeat: a status other than 401/403/404 retries every 10 s forever (:342-358).
- lease: anything but 403 {error:'revoked'} retries (:474-478).
- reports: 426 makes reject() drop the reports (:922).

To turn away clients that predate the gate, the server must use codes old clients already treat as fatal:
- a missing version on /register returns 400 with the upgrade command in the body. The old client prints it and exits (:373-375).
- heartbeat and lease return 403 with error 'revoked' (or plain 403 on heartbeat). The old client calls request_stop (:1173, :474).
New clients can map 426 and client_too_old to a clear message.

Suspected and fine: I found no current mismatch between the campaign-#1 client and worker, and check_dirty does cover volunteer.py.

*fix notes*: CLIENT (volunteer.py)
- Add CLIENT_VERSION and an integer PROTOCOL.
- Send client_version, protocol and client_hash (sha256 of volunteer.py's own file) in register, heartbeat, lease and reports. Put the version in the User-Agent too.
- In read_version, compute the sha256 of the three checked-out C files the same way build_pgo.sh:41 does. Refuse to start if it differs from the binary's SRC_HASH ("binary built from a different checkout; rebuild"). This cheap check alone closes the stale-binary path.
- Require a PROTOCOL line in the worker's --version output.
- Separately, and independent of versioning, make any bad_remaining or over-long skipped line void the whole run (node untouched) instead of reporting a partial split (:771, :831-835).

SERVER (jobs.js)
- Read min_client_version / min_protocol and release_tag from client_params_json. Optionally keep a client_hashes whitelist beside hashes_json.
- For backward compatibility, refuse a missing or old version with codes old clients already treat as fatal:
  - /register: 400 {error:'client_too_old', message:'git fetch && git checkout <tag> && ./build_pgo.sh'}
  - heartbeat and lease: 403 {error:'revoked', reason:'client_too_old'}
  - reports: 409 {error:'unknown_hash'} (the old client stops at :919-920)
- Only new clients need to understand 426.
- Store client_version on the clients and reports rows.

HASH REFUSAL MESSAGE
- Use a retired_hashes list to say "older build" versus "newer or unknown build: check out <release_tag>".

ROLLOUT ORDER
1. Deploy the server gate.
2. Tag the release, committing the client and worker changes atomically.
3. Whitelist the new worker hash and the client hash/version.
4. Create the campaign.
5. Announce.

TESTS
