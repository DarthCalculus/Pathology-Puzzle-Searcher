FEASIBILITY OF THE PROPOSED FIX
Knuth per-root estimates are cheap (my estimate: a few CPU-hours for about 100 probes per root at 60 us per state). They cannot be trusted for an ETA, and the repo's own record says so:
- README.md:227 and :272: the estimator ran 1x-4x, then 6x and ~13x low.
- VOLUNTEERS.md:59-62: "a chunk shown as one hour may take a day". The v1 chunk planning built on these estimates was replaced for that reason.
- The ETA depends almost entirely on the handful of largest roots. Those are the deep-corridor subtrees the probes under-sample most, so a correction ratio fitted on covered roots (which are the small ones) cannot fix that bias.

BETTER WEIGHT SOURCE (tested on data)
The previous class's actual per-root CPU:
- I aggregated results/camp_h2/done.tsv (<=2 holes, layer-8 jobs) by 4-token path prefix and matched it to campaign #1's layer-4 roots.
- 2,303 of the 2,761 roots match. The 458 unmatched roots used 0.0025 CPU-h in total.
- Spearman rank correlation 0.966; 24 of the top 30 roots are the same in both. For the 15 largest roots, the h3/h2 ratio is 3.0-7.3x; the overall ratio is 4.43x.

Simulated forecast using those weights:
- Forecast total = CPU of covered roots + for each uncovered root max(CPU spent so far, s x h2 weight), where s = (CPU of covered roots) / (their h2 weight).
- Forecast vs true done fraction:

| Hours in | Forecast done | True done |
|---|---|---|
| 2 | 10.6% | 5.9% |
| 3 | 25% | 15.8% |
| 4.5 | 45% | 31.3% |
| 6 | 60% | 47.5% |
| 8 | 79% | 69.5% |
| 10 | 97.5% | 91.1% |

- It is biased optimistic by at most about 1.8x, and the bias shrinks as the campaign runs. That is far better than anything shown now.
- A log-log (power-law) calibration was worse (34% forecast vs 15.8% true at 3 h), so keep the plain ratio.

EXACTNESS RISK: none, as long as the weights only drive display and lease order. The job set and the cover/audit logic must stay independent of them.

Worth doing before the next campaign. The display side is cheap, and the same weights enable largest-first root ordering, which attacks the 11-hour tail directly. Severity stays low: this affects display and planning only.

*fix notes*: 1. Add a nullable column `jobs.est_s REAL`. It is metadata only: never read by the audit, cover or finish logic, nor by gates.

2. Change v2_seed.js to accept `--weights FILE` (TSV: exit, seed, est_s):
   - Same grid, larger class (e.g. 5x5 with <=4 holes): produce the file from the campaign-1 jobs DB. Use a recursive CTE summing elapsed_s over all non-dup descendants of each root, keyed by (exit, seed).
   - New grid: produce it from `backsearch --estimate N --estimate-depth 0 --seed-path P --estimate-dump F` per root, or from one `--estimate` run at the root layer. Treat it as a rank signal only, never as an absolute figure.

3. Compute in statusCached, per exit:
   - s = sum(CPU of covered roots) / sum(est_s of covered roots);
   - remaining = sum over uncovered roots of max(0, s * est_s - CPU already spent in that root's subtree), with a floor of the open/leased job count x the median job length;
   - done fraction = CPU spent / (CPU spent + remaining).

   Label it as a rough forecast that runs optimistic: on campaign 1 it read about 1.6x too high early on, and the error shrinks as the campaign runs. Hide it until at least ~5% of the weight is covered.

4. hunt.js:49/59: replace the job-count progress bar with this forecast, or drop the bar. It showed 94% at 3 h when 15.8% of the CPU was done.

5. Optionally, order roots largest est_s first in openOfExit (jobs.js:275). Children inherit the ordering through the existing depth-DESC rule, but untouched roots currently go oldest-first. This is a separate scheduling change and deserves its own review.

6. Tests: a gate test that est_s never changes audit/cover results, plus a unit test of the forecast on a synthetic tree.
