# M94: Server restart mid-campaign and outbox delivery are untested, and the outbox retry bookkeeping updates the wrong file

verdict CONFIRMED, severity low, category test-gap
locations: volunteer.py:1003 (flush_outbox bumps the attempt counter on newest[-1], the lexicographically last file); test_client.sh (in-memory fake server); test_chaos.sh (never restarts node)

## Summary
test_client uses an in-memory fake server, and chaos never restarts node. So transient 5xx and resets during a restart, the outbox write/flush cycle, resends after a commit whose response was lost (which should return dup:true), and migrations on an existing DB are never exercised. flush_outbox also bumps the attempt counter on newest[-1], the lexicographically last outbox file, which with same-second names need not be the file just written, so backoff can be charged to the wrong batch.

## Verifier (CONFIRMED, low, refuted=False)
Both halves hold, but the consequences are milder than 'medium'. Test gap: every test_client.sh test (a-e) runs against the in-memory fake_server.py and calls stop_server only at the end. fake_server has no flag that injects 5xx, resets or timeouts on /reports. test_chaos.sh starts node once (line 33) and only kills or SIGINTs clients (lines 49, 51). So the outbox write/flush cycle and a server restart mid-run are never exercised end to end. Bookkeeping bug (volunteer.py:1004-1011): after any False return, flush_outbox rewrites `newest[-1]` with `entry.get('attempts',0)+1`. That file is the wrong one in three cases. (a) The sender thread's send_batch wrote an outbox file in the same int(time.time()) second. The names then compare on 'batch%d-uuid', which is effectively random. This is rare, because the sender writes only when a window has just finished. (b) Every whole-batch non-transient rejection: 403 unknown_token/revoked/not_admitted, 410 campaign_closed (requireClient, jobs.js:331-339), 400 or 413. There send_batch goes to the reject path and writes no outbox file, yet flush_outbox assumes a re-queue. It overwrites an unrelated, not-yet-tried file's attempts and next_try, then `return`s, so the rest of the outbox waits for the next pass. In the final forced flush at stop, those files are left for the next run. (c) The system clock stepped backwards. In all three cases the damage is retry timing only. The wrong file is rewritten from its own `e2['reports']`, and flush_outbox has a single consumer thread, so no content is lost. One batch backs off up to 300 s too long (which, through M21, lengthens the window in which its job is released and re-run), and another retries every 15 s. The other untested items are low risk. The live snapshot already has all four migrated columns (ramp_split_after_s, client_params_json, running_json, solver_calls; checked with sqlite3), so today's migrations are no-ops on the live DB. dup:true on a resend is unit-tested (v2_gates.test.js:137-148). Scheduling state lives in the DB; only STEAL_STATS and caches are held in memory. Batches are applied in one txn, so a restart cannot half-apply one. It is worth adding a restart test before the next campaign, but no concrete loss or stall path was found. Low.

*fix notes*: Have send_batch take the attempt count and write the outbox file itself with the right attempts and next_try, returning (status, path). On 'rejected', flush_outbox should `continue` to the next file instead of returning. Add a fake_server option such as --fail-reports N / --delay-reports S (502s, or a sleep beyond the 60 s timeout, after committing) so test_client covers outbox write, flush and dup-on-resend. Add a chaos variant that kill -9s node while a batch is in flight and restarts it on the same temp jobs.db. It should then assert that the outbox drains to 0, the audit is clean, and `SELECT parent_id, seed, COUNT(*) FROM jobs GROUP BY 1,2 HAVING COUNT(*)>1` is empty. For any NEW migration added for campaign #2, run openJobsDB on a copy of jobs_review.db as a test.
