# M81: The static file stream has no error handler, so a vanished file or EMFILE crashes the whole server

verdict CONFIRMED, severity low, category robustness
locations: server.js:313 (existsSync/statSync then createReadStream without an 'error' listener)

## Summary
The server checks the file with existsSync and statSync and then opens it asynchronously with createReadStream. If the file vanishes in between (during an rsync deploy, say) or the process hits EMFILE, the unhandled 'error' event becomes an uncaught exception that kills the process and takes down the public site and the v2 API.

## Source report F117 (server-web)
**The static file stream has no error handler, so a vanished file or EMFILE crashes the whole server** at /Users/george/PathologyRecords/server/server.js:313

*summary*: The server checks the file with existsSync and statSync, then opens it asynchronously with createReadStream. An 'error' event with no listener becomes an uncaught exception and kills the process.

*failure_scenario*: The file is deleted between the stat and the open (for example an rsync --delete deploy while a page loads), or the process runs out of file descriptors under a traffic spike. The Node process exits. systemd restarts it, but in-flight v2 requests fail, in-memory rate buckets and STEAL_STATS reset, and any pending verifyLater is lost (see the previous finding).

*evidence*: server.js:311-313 `if (full.startsWith(PUBLIC_DIR) && fs.existsSync(full) && fs.statSync(full).isFile()) { res.writeHead(200, {...}); return fs.createReadStream(full).pipe(res); }`

*suggested_fix*: Use `const s = fs.createReadStream(full); s.on('error', () => { if (!res.headersSent) sendJSON(res, 404, {error:'not found'}); else res.destroy(); }); s.pipe(res);`, or stream.pipeline with a callback.

## Verifier (CONFIRMED, low, refuted=False)
The defect is real, but its triggers are rarer than the report says. server.js:311-313: `if (full.startsWith(PUBLIC_DIR) && fs.existsSync(full) && fs.statSync(full).isFile()) { res.writeHead(200, ...); return fs.createReadStream(full).pipe(res); }`. Readable.pipe() adds an error listener only to the destination, never to the source. The ReadStream opens its file asynchronously, after the handler returns, so an open or read error is emitted outside the surrounding try/catch with no listener. That throws and becomes an uncaughtException. grep finds no process.on('uncaughtException') in server.js or lib/, so the process exits and systemd (Restart=on-failure, per the deployment notes) restarts it. On a restart the in-memory rate buckets, STEAL_STATS and any pending verifyLater re-solve are lost, and in-flight v2 requests fail; the clients retry and queue work in the outbox. Why the triggers are rare: (a) the window between statSync and open is microseconds; (b) the documented deploy is `rsync -az --delete` followed by `systemctl restart`, so a crash there changes nothing; rsync also swaps files atomically by temp-and-rename, and --delete removes only files that are no longer part of the site; (c) Node raises the RLIMIT_NOFILE soft limit to the hard limit at startup, so EMFILE is very unlikely at this scale behind Caddy; (d) EACCES could only appear in the brief gap between rsync and chown, just before the restart. Still, a single-line unhandled error path that can kill the process behind the public site and the v2 API is worth fixing before a larger campaign.

*fix notes*: Use `const s = fs.createReadStream(full); s.on('error', () => { if (!res.headersSent) sendJSON(res, 404, { error: 'not found' }); else res.destroy(); }); s.pipe(res);`, or `stream.pipeline(fs.createReadStream(full), res, err => { if (err) res.destroy(); })`. Optionally add a process-level 'uncaughtException' logger that exits cleanly, so the cause shows up in journalctl.
