# M35: Campaign #1 totals disagree across the campaigns card, its contributors table and updates.json (dup handling, wall clock, dates)

verdict CONFIRMED, severity low, category bug
locations: jobs.js:870-881 (campaignsSummary: header totals use dup_of IS NULL, contributors query and finished_at = MAX(done_at) include dups); status() (includes dups); server/public/updates.json ('four days of wall clock', entries not in date order)

## Summary
campaignsSummary computes the per-exit totals without re-check duplicates, but its contributors table and finished_at (MAX(done_at)) include them, so one card shows two different totals. The live status also includes dups. updates.json mixes both definitions, gives a wall-clock time ('four days') that the DB contradicts, and lists entries out of date order.

## Source report F90 (server-scheduling)
**Completed-campaigns page: finished_at and contributor totals include duplicate runs** at /Users/george/PathologyRecords/server/lib/jobs.js:881

*summary*: campaignsSummary takes finished_at from MAX(done_at) over all jobs, dups included. Its contributors query counts dup jobs, while the per-exit totals exclude them.

*failure_scenario*: Campaign #1 shows finished_at 13:00:26 (the last dup) instead of 09:17:09, the time the tree was actually complete. The contributors' CPU adds up to about 4.8 CPU-h more than the published totals.

*evidence*: 881: `SELECT MAX(done_at) AS t FROM jobs WHERE campaign_id = ?`. 877-879: the contributors query has `WHERE j.campaign_id = ? AND j.status IN ('done','split')` with no dup_of filter, whereas 870-871 use `dup_of IS NULL`. Snapshot: max non-dup done_at 09:17:09 vs 13:00:26.

*suggested_fix*: Add `AND dup_of IS NULL` to both queries.
