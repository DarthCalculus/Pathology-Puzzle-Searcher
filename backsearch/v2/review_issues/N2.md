## Source report F201 (r2-next-campaign-generalization)
**On 6x6, most solver calls would take the 128-bit path, which lacks A*, reference tables and bulk solves and adds up to 384 MB per worker** at /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:2281

*summary*: This extends the known PLAUSIBLE 128-bit-fallback finding with numbers and costs it does not state. At 36 cells, cells take 6 bits, so the 64-bit path holds only nb <= 9. From campaign #1's block counts, an estimated 45-77% of 6x6 solver calls would take the wide path. That path also commits a 384 MB table per worker, disables the bulk multi-start solve (per-start fallback), and gets no PGO profile. For 5x5 <=4 holes nothing changes (5x12+4 = 64 still fits nb <= 11), and 5x6 sends only about 2% of calls down the wide path.

*failure_scenario*: A 6x6 <=3-hole campaign on 10 clients x 16 workers. Every state with 10 or more blocks (6x11 = 66 > 64) goes to solve_push128_cutoff. Campaign #1's level-bearing jobs by level block count: nb >= 7 carries 77.3% of solver calls and nb >= 8 carries 44.6%. Scaling blocks by area (x1.44) puts 45-77% of 6x6 calls on the wide path, and that is a lower bound, since partial puzzles carry at least as many blocks as the finished levels. On that path: plain Dijkstra with no hdist A*; no reference-table prune or export; no 64K small table; every bulk walk-back batch returns -2 at line 1842 and is re-solved start by start; the 1M pending cap (HP128_SIZE) is hit more often, and -2 is pruned (the known exactness class). Each worker that uses the path fills the calloc'd HashStatePush128 (16M x (16+4+4) B = 384 MB) through scattered writes, adding to the known ~0.5-0.6 GB. That is about 1 GB per worker, or about 16 GB for 16 workers, with no memory-aware worker cap in the client (--workers defaults to cpu_count//2). PGO training ('--grid 5x5 --exit 0 --time 4') never runs the wide path, so it is compiled as cold code. Net result: several-fold CPU cost plus swapping or OOM on volunteer machines.

*evidence*: sokoban_bfs.c:133 `g_bits_per_cell = bits_needed(g_ncells + 1);` (6 at 36 cells); 2674 `if (g_bits_per_cell * (1 + nb) + nh > 64) return solve_push128(...)`, 2681 same for the cutoff; 2279-2283 `typedef struct { __uint128_t htk[HT128_SIZE]; /* 256 MB */ uint32_t ht_gen[HT128_SIZE]; /* 64 MB */ int32_t ht_cost[HT128_SIZE]; /* 64 MB */ ...} HashStatePush128;`, 2294 `hsp128_tls = calloc(1, sizeof *hsp128_tls);`; 1842 `if (g_bits_per_cell * (1 + nb) + nh > 64) return -2;` (multi-start), caller backsearch.c:2416 `if (rc < 0) { /* ... decide these candidates one by one */`; 2263 `#define HP128_SIZE (1 << 20)`; build_pgo.sh:26 `TRAIN_ARGS="--grid 5x5 --exit 0 --time 4"`; snapshot block histogram of job levels: nb 6:8866, 7:11850, 8:9008, 9:3813, 10:639, 11:4 (call share nb>=7 77.3%, nb>=8 44.6%, nb>=10 1.7%).

*suggested_fix*: For any 6x6 campaign, either bound blocks (--num-blocks 9 keeps 6x10+4 <= 64) or make the fast solver key-width independent. It already keys its hash by 64-bit Zobrist, so only the unpack payload needs to widen (e.g. two uint64 words in HeapEntry). That would give A*, reference tables and multi-start to wide states. Size the 128-bit table small-first like the 64-bit one. Add a wide-state case to PGO training. Before any 6x6 campaign, measure the real share with a short --estimate plus a solver-call histogram by nb.

## Verifier (PLAUSIBLE, medium, refuted=False)
Checked against the code (read-only) and the snapshot.

What the code confirms:
- Width threshold. sokoban_bfs.c:134 sets `g_bits_per_cell = bits_needed(g_ncells + 1)`, which is 6 bits at 36 cells. The dispatcher at 2674/2681 sends a solve to the 128-bit path when `g_bits_per_cell * (1 + nb) + nh > 64`. So 6x6 with nh <= 3 goes wide at nb >= 10. 5x5 goes wide at nb >= 12 (4 holes) or nb >= 11 (5 holes). 4x6 and 5x6 go wide at nb >= 12.
- The 128-bit cutoff solver (about 2500-2665) is plain Dijkstra: `ne.prio = nc; ne.g = nc`. The 64-bit cutoff solver has several things it lacks:
  - the hdist A* prune (`if (hd < 0 || nc + hd > max_cost) continue;` at 1722-1723);
  - the decision-only early exit (`if (g_decision_only) goto done;` at 1608/1702). Campaign mode turns decision-only on (backsearch.c:5742 `sokoban_set_decision_only(!HARVEST_ACTIVE && ...)`), so on wide states the solver keeps expanding until prio >= best_win instead of stopping at the first win within the cutoff;
  - the slack-0 skip and the slack-bounded walk;
  - the reference-table prune (`g_ref_on && ref_prunes_at(...)`); the dispatcher also clears last_exhaustive, so no table is exported;
  - the 64K L2-resident small table. Every wide probe goes into the 16M-slot table.
- Bulk multi-start. sokoban_solve_multi returns -2 up front for wide states (1842). backsearch.c:2416 then decides the candidates one by one. That is exact, just slower.
- Memory. HashStatePush128 at 2279-2283 is 16M x (16+4+4) B = 384 MB, calloc'd lazily (2294). The header comment at 2257-2260 ('~144 MB per thread', '5 + 5*nb') is stale. Each insert touches about one random page in each array, so a few hundred moderate wide solves make most of the 384 MB resident within one job's lifetime (split_after about 30 min). Resident memory therefore depends on whether wide calls happen at a modest rate, not on their share. That also matters for 4x6, 5x6, or 5x5 with 4-5 holes whenever high-nb states occur.
- PGO. build_pgo.sh:26 trains with `--grid 5x5 --exit 0 --time 4`, which never reaches the wide path.
- Snapshot. I reproduced the finder's histogram exactly: best-level nb 6:8866, 7:11850, 8:9008, 9:3813, 10:639, 11:4. Weighted by solver calls, nb >= 7 carries 77.3%, nb >= 8 44.7%, nb >= 10 1.7%.

Exactness: no risk. The 128-bit path is exact (packed-state keys, no Zobrist). Missing prunes only cost time. The HP128 1M-pending -2 overflow becomes more likely without the hdist prune, but that belongs to the already-known -2 class.

Where the finding overreaches:
1. The 45-77% share for 6x6 is a guess. The histogram is each job's best-level block count, not the nb of solver calls. Calls happen on candidate states at every nb from the seed's up to the subtree's maximum. The best level need not carry the subtree's maximum nb, so the finder's claim that this is a lower bound is not established. The x1.44 area scaling is also an assumption.
2. 'Several-fold' per wide call is plausible but unmeasured. From project history, decision-only plus f-ordering gave about 16% fewer states, bulk walk-back about 17-20%, and the small table was added because big-table probes miss cache. My estimate is roughly 2-4x per wide call.
3. Most important: reach. None of DESIGN/README/VOLUNTEERS mention 6x6 or 5x6. A 6x6 exhaustive class is not realistic at this scale: 5x5 with <=3 holes took 602 CPU-h, and one unconstrained 5x5 exit was estimated at 8000 h or more. For the realistic next campaigns, the wide share is about 0-2%:
   - 5x5 with <=4 holes: campaign #1 had only 4 nb=11 levels, and nb 12 is needed to go wide;
   - 4x6 classes;
   - maybe a 5x6 subclass.
   So the CPU gain there is at most a few percent. The 384 MB memory commit is the part that can still matter.
4. The suggested '--num-blocks 9' is not a neutral fix. It changes the proven class to '<=3 holes, <=9 blocks'.

Overall: the mechanism is real and the cheap parts are worth doing, but the headline 'high' impact only applies to a 6x6 campaign that is unlikely to be the next one. I rate it medium and PLAUSIBLE pending measurement of the actual wide-call share for whichever grid is chosen.

*fix notes*: In priority order for the next campaign. All are exactness-neutral if validated with the existing solvebench/equivalence configs.

1. Measure before choosing the grid.
   - Add g_solver_calls_by_nb[] and a 'wide calls' counter next to g_solver_calls_by_depth (backsearch.c ~1729) and print them in SUMMARY.
   - Record them in reports so the server shows the wide share per campaign.

2. Port the cheap 64-bit prunes into solve_push128_cutoff (sokoban_bfs.c ~2500-2665), about 20-30 lines copied from 1548-1575, 1602-1611 and 1698-1726:
   - hdist computed once per solve;
   - `if (hd < 0 || nc + hd > max_cost) continue;`;
   - f = g + h priority plus `goto done` under g_decision_only;
   - the slack==0 skip.
   These prunes are already validated on the 64-bit path.

3. Make the 128-bit table small-first, like HashStatePush64: a 64K-slot table (about 1.5 MB) with fallback to the 16M table when half full. This removes the 384 MB commit for almost every call. Allocate the big table only on the first fallback.

4. Add a test hook so the 128-bit path is actually exercised: a runtime or compile-time switch that forces the wide dispatcher on 5x5, run on the solvebench equivalence configs. Also add one wide case to the PGO training (e.g. `--train` with a 6x6 or high-nb config). Today the 5x5 campaigns give this path essentially no coverage.

5. Fix the stale comments at sokoban_bfs.c:2257-2260: the table is 384 MB, not 144 MB, and the threshold is bits_per_cell*(1+nb)+nh, not 5+5*nb+nh.

6. Only if 5x6 or 6x6 is really planned: make the 64-bit solver width-independent. It already keys its hash by 64-bit Zobrist (USE_ZOBRIST, HE64_KEY), so only HeapEntry64.state, the unpack code and pack5 need a two-word variant, built as a separate macro instantiation so the 5x5 hot path keeps its entry size. That brings A*, reference tables and multi-start to wide states. Do not use --num-blocks as the fix, because it changes the proven class.

7. Related, already known: the client needs a memory-aware worker cap, since --workers defaults to cpu_count//2 regardless of RAM.
