# M52: flush_outbox deletes the outbox file before sending, and a second Ctrl-C drops in-memory reports

verdict CONFIRMED, severity low, category robustness
locations: volunteer.py:1001 (flush_outbox removes the file, then POSTs with a 60 s timeout); force_quit (SIGKILLs workers and calls os._exit without persisting self.pending or the in-flight batch)

## Summary
flush_outbox removes the outbox file and then POSTs, with a 60 s timeout. force_quit SIGKILLs the workers and calls os._exit without writing self.pending or the in-flight batch anywhere. An exit during that window, from a second Ctrl-C, a crash or a power loss, loses finished reports, and their jobs are re-run.

## Source report F54 (client-core)
**flush_outbox deletes the file before sending, and a second Ctrl-C drops in-memory reports** at /Users/george/Documents/Claude Projects/project45/backsearch/v2/volunteer.py:1001

*summary*: flush_outbox removes the outbox file and then POSTs, with a 60 s timeout. force_quit SIGKILLs the workers and calls os._exit without writing self.pending or the in-flight batch anywhere. Any exit during that window (second Ctrl-C, crash, power loss) loses finished reports.

*failure_scenario*: The volunteer stops while the server is slow, and the final send_pending or flush_outbox sits in a 60 s POST. The volunteer presses Ctrl-C again, and os._exit runs. The batch file is already deleted and pending is discarded, so those windows' work must be redone after release or lease expiry.

*evidence*: volunteer.py 1000-1004: try: os.remove(path) ... if not self.send_batch(reports):
volunteer.py 1107-1113: for s in self.slots: ... SIGKILL; os._exit(1)   # self.pending never persisted

*suggested_fix*: Remove an outbox file only after send_batch returns True; a duplicate is answered dup and is harmless. In force_quit, outbox_write(self.pending) (best effort, in a try) before os._exit.

*expected_gain*: Stops the loss of completed windows on an impatient double Ctrl-C.

## Verifier (CONFIRMED, low, refuted=False)
Confirmed by reading volunteer.py. In flush_outbox, `os.remove(path)` at line 1001 runs before `if not self.send_batch(reports):` at line 1004. send_batch POSTs with `timeout=60` and writes the reports back to disk only in the transient/401 branch (`self.outbox_write(reports, attempts=1)`). So for up to 60 s (connect time included when the server is silently unreachable) the batch exists only in memory. force_quit (1107-1113) SIGKILLs the workers and calls `os._exit(1)`. It never writes self.pending, and it cannot reach the `batch` local that send_pending took out of self.pending. The second Ctrl-C does land during a blocked POST: the handler runs on the main thread, which interrupts the socket wait and retries it afterwards (PEP 475). The main thread itself is blocked in exactly these calls during shutdown: `self.send_pending()` and `self.flush_outbox(force=True)` at the end of run(). One detail makes an impatient second Ctrl-C more likely. During that POST the outbox file is already deleted and pending is empty, so pending_flags shows 'exiting…' rather than 'sending the last report…' (lines 1253-1256). The terminal also shows nothing while it waits. A related path: if outbox_write raises OSError (disk full, unwritable outbox) after the file was removed, the exception is not caught. In the main thread it ends run(). In the sender thread it silently kills the sender, so later reports sit in pending until stop. The loss is bounded: flush returns after its first failure, so at most one outbox file plus the pending or in-flight batch is exposed. The effect is waste only. The lost jobs stay leased to the dead token. They are reopened by expiredLeases (jobs.js:294, 1035) after lease_s, or released at once by release-by-omission when the client restarts with the same token. Coverage and valid-level sets are not affected. README lines 32-33 promise only that running jobs are left to expire on a second Ctrl-C. Losing reports that were already finished goes beyond that, but it costs only CPU. Low.

*fix notes*: Write-ahead: send_pending writes the batch to an outbox file BEFORE the POST and deletes it only after a delivered or rejected outcome. flush_outbox should likewise delete the file only after the outcome. Make send_batch return a tri-state (delivered / queued / rejected) and give it a requeue=False mode for flush callers, so a transient failure does not create a second copy. Resends are safe: applyReport answers dup:true for finished jobs (jobs.js ~755-771; unit-tested in v2_gates.test.js:137-148). In force_quit, add a best-effort `try: self.outbox_write(self.pending, 0)` before os._exit. Catch OSError from outbox_write in send_batch, log it loudly and keep the reports in memory. During the final send, pending_flags should say 'sending the last report…' while a POST is in flight (track an in_flight counter).
