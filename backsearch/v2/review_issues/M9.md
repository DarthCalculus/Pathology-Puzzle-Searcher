# M9: Per-worker memory reaches ~0.5-0.6 GB (solver tables are committed lazily and never freed), far above the documented ~200 MB

verdict CONFIRMED, severity medium, category robustness
locations: sokoban_bfs.c:1018 (256 MiB big push table calloc); HashStatePush128 calloc (256+64+64 = 384 MiB, comment says ~144 MB); backsearch.c:4344 (160 MiB dedup tables); dedup eviction (+96 MiB transient); multi-start arena (24 MiB); heap (up to 1M entries); parent-table pool (keeps its high-water mark); README/VOLUNTEERS '~200 MB per worker'

## Summary
The first 64-bit solve that inserts more than 32,768 states callocs a 256 MiB table, and the first 128-bit solve callocs 384 MiB. Both are hash-indexed, so solves touch random pages, and those pages stay resident because the tables are never freed or trimmed. Add the 160 MiB dedup tables (made resident by the memset), a +96 MiB transient on each eviction, the 24 MiB multi-start arena, up to 1M heap entries and a pool that keeps its high-water mark: one worker can hold about 0.5-0.6 GB, so 16 workers may need about 10 GB, while the docs promise about 200 MB each.

## Source report F25 (solver-core)
**Lazily committed solver tables grow each worker by up to ~640 MB, well past the documented ~200 MB** at /Users/george/Documents/Claude Projects/project45/backsearch/sokoban_bfs.c:1018

*summary*: The first 64-bit solve that inserts more than 32768 states callocs a 256 MiB table (16M x 16 B). The first 128-bit solve (nb >= 12 on 5x5) callocs HashStatePush128, which is 256 + 64 + 64 = 384 MiB; its comment says ~144 MB. Both are indexed by a hash, so each solve touches random pages, and those pages stay resident because the tables are never freed or trimmed. Over a job with millions of solves, most of both tables becomes resident.

*failure_scenario*: A volunteer follows v2/README.md ("each uses about 200 MB of RAM") and runs 16 workers on a 16 GB machine. After some big and some 128-bit shortcut checks, each worker holds 200 MB of baseline plus up to 256 plus 384 MiB of solver tables. That is up to ~13 GB in total, causing swapping or memory-pressure kills of workers (jobs lost and re-run) and a laggy machine.

*evidence*: sokoban_bfs.c:1018  if (!hs->slot_big) hs->slot_big = calloc(HTP_SIZE, sizeof(HSlot64));   (HTP_SIZE = 1<<24, HSlot64 = 16 B)
sokoban_bfs.c:2281-2283  __uint128_t htk[HT128_SIZE]; uint32_t ht_gen[HT128_SIZE]; int32_t ht_cost[HT128_SIZE];   (HT128_SIZE = 1<<24)
sokoban_bfs.c:2261  " * ~144 MB per thread, allocated on first use."
v2/README.md:23  "each uses about 200 MB of RAM"

*suggested_fix*: Grow the big and 128-bit tables on demand (start small, double when needed). Or free them, or madvise(MADV_DONTNEED/FREE) them, after a solve that needed them. At minimum, measure peak RSS on a real campaign job and document it in the README and in the client's default worker count.

*expected_gain*: Protects volunteer machines and makes the published RAM figure accurate.

## Source report F33 (worker-io-cli-memory)
**Per-worker memory is ~160 MB resident at start and can reach ~0.5-0.6 GB; docs say ~200 MB** at /Users/george/Documents/Claude Projects/project45/backsearch/backsearch.c:4344

*summary*: The two-table dedup (64 MiB shallow + 96 MiB recent) is calloc'd and then memset at the start of every run, so all 160 MiB become resident even for jobs that touch a few KB. Dedup evictions allocate a fresh table while the old one is still live (+96 MiB transient). The forward solver lazily allocates a 256 MiB table the first time any check inserts more than 32,768 states. The multi-start arena (24 MiB), up to 1M heap entries, and a parent-table pool that keeps its high-water mark add more.

*failure_scenario*: On a 16 GB laptop running 16 workers (the realistic deployment), baseline RSS is 16 x 160 MiB = 2.5 GiB. Once deep checks trigger slot_big and evictions coincide, 16 x (160 + 96 + 256 + ~50) MiB ≈ 9 GiB, against the documented 16 x 200 MB = 3.2 GB. The machine swaps and becomes laggy, which is the owner's stated concern. Evictions are real: 1,675 of 54,409 report root runs in the snapshot evicted, up to 90 recent and 179 shallow evictions each.

*evidence*: backsearch.c:885-896 `#define SHALLOW_LG2 22`, `#define RECENT_LG2 22`, `typedef struct { uint64_t key; int32_t depth; } ShallowSlot;` (16 B) and `RecentSlot` (24 B). 5582-5583 `g_shallow = calloc(SHALLOW_CAP, ...); g_recent = calloc(RECENT_CAP, ...)`, then 4344-4345 `memset(g_shallow, 0, ...); memset(g_recent, 0, ...)` on the first and only exit. 1019 `ShallowSlot *fresh = calloc(SHALLOW_CAP, ...)` and 1066 `RecentSlot *fresh = calloc(RECENT_CAP, ...)` run before the old table is freed. sokoban_bfs.c:1018 `if (!hs->slot_big) hs->slot_big = calloc(HTP_SIZE, sizeof(HSlot64));` (16M x 16 B), with small-table limit 1023 `HTP_SMALL_SIZE / 2`; 1811 `#define MS_ARENA (1u << 20) /* 24 MB */`. sokoban_bfs.c:1410 keeps each pooled parent table's capacity (`if (t->cap < sz) {...}`). v2/README.md:23 `each uses about 200 MB of RAM`.

*suggested_fix*: Skip the memset when the tables are fresh from calloc (clear only on reuse, or free and calloc again). Document the real peak (~0.5-0.6 GB per worker). Have the client cap the default --workers by physical RAM, for example min(cores/2, RAM_GB/0.6). Optionally release slot_big after a big solve or grow it on demand, and report the parent-table pool's peak MB in SUMMARY so it can be monitored.

*expected_gain*: Predictable memory use on volunteer machines; avoids swapping and lag at 16 workers.

## Verifier (CONFIRMED, medium, refuted=False)
I checked every mechanism the issue lists against the code, and each one is real. The only thing I could not settle statically is how often a 5x5 job with at most 3 holes actually uses the two big solver tables.

1. The 160 MiB dedup baseline is resident from the start of every job. backsearch.c:5582-5583 callocs `g_shallow`: 4M slots x 16 B = 64 MiB. It also callocs `g_recent`: 4M slots x 24 B = 96 MiB. `run_exit_search` at 4343-4345 then runs `memset(g_shallow, 0, ...); memset(g_recent, 0, ...)` unconditionally, which writes every page. `g_two_tables = 1` is the default (line 79).
   - Skipping that memset would only help short jobs. Campaign #1 averaged about 218K states per job (36.4 B states / 166,733 jobs), which is enough random inserts to touch nearly every page of both tables anyway.
   - So the baseline alone roughly matches the README's "about 200 MB" (v2/README.md:23). The excess comes from the items below.

2. Evictions add a transient 64 or 96 MiB. `shallow_evict` (line 1019) and `recent_evict` (line 1066) calloc a fresh full-size table and rehash the survivors into it before they `free()` the old one. The snapshot confirms these run in practice: 1,675 of 54,409 report runs evicted, with up to 179 shallow and 90 recent evictions in a single run.

3. The 64-bit big table (sokoban_bfs.c:1018) is committed lazily and never freed.
   - `if (!hs->slot_big) hs->slot_big = calloc(HTP_SIZE, sizeof(HSlot64));` allocates 16M x 16 B = 256 MiB.
   - It is allocated on the first retry after the small table overflows at `HTP_SMALL_SIZE/2` = 32,768 inserts (lines 1023, 1054, 1751-1754).
   - Slots are picked by `h64(k) & mask`, so writes land on random pages. The gen-stamp clearing never memsets (only when `ht_seq` wraps at 2^32), and nothing frees or madvises the table.
   - One big solve inserts at least 32,768 states, which touches about 65,536 x (1 - e^-0.5), roughly 25.8K pages, or about 100 MiB. A few more push it toward 256 MiB.
   - Each worker process runs one job, for up to 1,824 s and up to 112 M solver calls in the snapshot. So even a rare overflow is likely to happen in long jobs. There is no counter, so I cannot give the rate.
   - Partial puzzles treat unknown cells as walls (`build_partial_puzzle`), which keeps the forward state space small. That argues the overflow is rare on 5x5, but not that it never happens.

4. The 128-bit push table (sokoban_bfs.c:2281-2283) is 256 + 64 + 64 = 384 MiB, calloc'd on first use (line 2294). Its comment at 2261 says "~144 MB", which is wrong.
   - The dispatcher (lines 2674 and 2681) picks it when `5*(1+nb)+nh > 64`, which on 5x5 means 12 or more blocks. Multi-start returns -2 for these (line 1842) and falls back to single `sokoban_solve_cutoff` calls.
   - No block or cell cap applies in campaigns: `g_max_blocks = MAX_BLOCKS = 32`, `g_min_walls = 0`.
   - In campaign #1 the per-job best levels have at most 11 blocks (4 of 42,134 jobs), so 12-block checks are possible but rare on 5x5.
   - When they do happen, the gen and cost arrays hold 1,024 slots per page, so about 30K cumulative inserts already make roughly 200 MB resident.
   - On 6x6 (6 bits per cell, so 128-bit from 10 blocks) and with more blocks, both tables would be common. This matters if the next campaign is larger.

5. Smaller items are also as described:
   - The multi-start arena is up to 24 MiB, touched up to its high-water mark (line 1845), plus `ms_lab` at 3 MiB.
   - The bucket queues grow by `realloc` doubling and never shrink.
   - The parent-table pool (sokoban_bfs.c:1410) keeps each entry's largest capacity, at most 65,536 slots x 12 B = 768 KB per entry. Entries are never freed.
   - The peak live-table figure is printed only in the human-readable output (backsearch.c:5817), not in the SUMMARY JSON.

6. A consequence the reports did not mention: on Linux with transparent huge pages set to "always", scattered touches fault in whole 2 MiB pages. The first big or 128-bit solve would then make almost the whole 256 or 384 MiB resident.

What is refuted or overstated:
- The 160 MiB baseline is not a documentation lie; it is about the documented figure.
- The ~0.5-0.6 GB figure is a plausible worst case per job, not a measured typical value.
- On 5x5 with at most 3 holes, the 128-bit table is likely rarely touched.

Severity for the next campaign: medium.
- There is no correctness impact. A worker killed for memory has its job re-leased, so the failure is recoverable.
- The client default is `max(1, cpu_count//2)` (volunteer.py:1531), which limits exposure. A 16-thread machine gets 8 workers, about 1.3 GB baseline and at most about 5-7 GB worst case.
- Exposure is real for volunteers who pass --workers 16 on a 16 GB machine, and for a larger grid.
- Side mismatch: the README says the default is "core count minus one", but the code uses cpu_count//2.

If only a short dynamic run can settle the frequency question, one process for about 50 s will show whether `slot_big` gets allocated (see repro_plan).

*fix notes*: Fixes, in priority order, for the next campaign:

1. Measure first. Add `ru_maxrss` from `getrusage` to the SUMMARY JSON, plus three counters: 64-bit big-table retries, 128-bit solves, and the parent-table pool's retained MB (the sum of `t->cap` x 12 B). The server and client can then show real per-worker peaks. Set the README figure from that data.

2. Tier the 64-bit table. Keep the 64K small table, add a 1M-slot (16 MiB) middle table, and use the 16M table only as a last resort. The existing overflow-and-retry mechanism already supports this.
   - Alternatively, `free()` `slot_big` and set it to NULL after a solve that used it, so the next calloc is lazily zeroed again. Re-faulting costs tens of milliseconds, which is fine if big solves are rare.
   - If you use madvise instead: Linux `MADV_DONTNEED` zeroes the pages, which is safe because gen 0 never equals `ht_seq` (which is at least 1). macOS `MADV_FREE` may keep stale gens, which is also safe because `ht_seq` only increases.

3. Give the 128-bit solver the same small-table overflow and retry design as the 64-bit one. Crowded boards have tiny state spaces, so a 64K-slot first tier would almost always be enough. Fix the "~144 MB" comment at sokoban_bfs.c:2261 (the real size is 384 MiB). Remove or fix the unused `HashState128` (`solve_hash128`) and its wrong "208 MB" and "64 MB" comments. This matters most if the next campaign is 6x6, where 128-bit starts at 10 blocks.

4. Dedup eviction: compact in place, or keep one spare table allocated for the whole process, to avoid the +64/96 MiB peak from calloc before free. Skipping the initial memset of fresh calloc'd tables and clearing only on reuse is cheap, but it helps only short jobs.

5. Parent-table pool: shrink an entry's `cap` when it is reused for a much smaller n, for example when `cap > 4*sz`.

6. Client and docs:
   - Fix README:23 to state the measured peak, and fix the default-worker text ("core count minus one" versus the code's cpu_count//2).
   - Cap the default and the requested --workers by available RAM, for example `min(cpu//2, avail_RAM / measured_peak)`, and warn when the user asks for more.

7. Tests: add a regression that runs a crowded 12-block 5x5 puzzle and a big-state puzzle through the solver and asserts the solver's peak RSS stays within budget.
