# Solver changes of 2026-09-18

All changes are to the forward shortcut check (`sokoban_bfs.c`) and to how the
backward generator (`backsearch.c`) calls it. Every change is exact: the DFS
accepts the same states and finds the same best depth on every equivalence
config (README "End-to-end equivalence checks"), and each new pruning rule has
a check build that re-runs the pruned solve without the rule and compares
decisions. Nothing in the rule set changed (`--allow-exit-transit` on,
`--allow-block-on-exit` off).

Benchmark used throughout: the depth-21 precursor of the 149 (`--exit 1
--num-holes 3 --seed-path <first 21 tokens of the 149>`), which exhausts with
1,858,193 accepted states and best depth 149. A smaller depth-36 precursor
(185,569 accepted, ~35 s) was used for pop counts in the afternoon.

| state of the code | depth-21 wall time |
|---|---|
| start of day (decision mode, walk-segment prune, small L2 table) | 212 s |
| + bulk walk-back with expansion caching | 191 s |
| + nearest-first ordering, slot cache | 171 s |
| + ancestor dominance in the multi solve | ~155 s |
| + nearest-parent reference tables | 141 s |
| + review of the tables (below), final production worker | 125 s |

The last row is the median of three interleaved runs against the previous
production worker (135 s) and the same worker with tables disabled (168 s);
load average was 3.5-5 during the series, so single runs vary by ~5%.

## 1. Bulk walk-back: one forward solve per player component

**Observation (WBPROF build).** Walk-back children over already-committed cells
were 47% of shortcut checks and 43% of solver time, and only 5% of them were
pruned. Every such child has the *same forward puzzle* as its parent (walls,
blocks, masks, holes) and differs only in the player's start cell.

**Change.** `sokoban_solve_multi()` runs one lockstep Dijkstra for up to 24
start cells at once. Every forward state carries a vector of labels (one per
start); the *expansion* of a state (unpack, walk BFS, push candidates) is done
once and its successor list is cached in an arena, so later pops of the same
state at other labels only replay the list. `bulk_generate()` in `backsearch.c`
collects the whole walk component of an accepted state (BFS over committed
cells), applies the shortest-walk-segment prune and the dedup insert to each
cell first, and decides all survivors in one call. Children produced this way
carry `bulk_walk = 1` so their own expansion skips committed walk-backs (already
covered). Default on; `--no-bulk-walk` disables, `--bulk-min-depth D` restricts.

**Soundness.** Per start i the answer is exactly "does a solution of length
<= cut[i] exist from start i", identical to the single solve. Positive edge
weights make the lockstep pop order valid: a popped entry at prio p finalises
exactly the starts whose label equals p.

**Pitfalls met.** First pushes need one queue entry per *distinct* label, not
one per start; push children of bulk children must reset `bulk_walk = 0` (a
depth-58 branch was lost before that fix); dedup must run *before* the multi
solve or cells visited from another branch are solved again.

**Measured.** Harness (`multitest.c`): multi solve costs 0.59x the sum of the
single solves. Benchmark 214 s -> 191 s. Earlier, without expansion caching, it
was a wash: "one call" is not "shared work" -- the check is expansions per
state, not calls.

## 2. Shortcut propagation, ordering, dominance in the multi solve

* **Predecessor masks.** `pred[i]` = starts one step closer to the parent cell
  and adjacent to start i. A shortcut at such a predecessor implies one at i
  (walk one step, then the predecessor's shortcut), so starts behind a decided
  shortcut are decided without search.
* **Nearest cells pushed last.** The DFS pops them first; their subtrees reach
  shared states at the lowest depth, so the two-table dedup sees keys at their
  final depth first and re-explores less. 191 s -> 171 s.
* **Ancestor dominance.** Let j be a chain ancestor of i at chain distance k
  (cut[i] = cut[j] + k). If i reaches state X at cost g_i and j at g_j with
  g_i - g_j >= k - 1, then i need not explore X: a solution for i through X of
  length <= cut[i] gives j one of length <= cut[j] + 1, hence <= cut[j] by
  parity (all solutions from one start share a parity), so j has a shortcut
  and i is decided by propagation. The first version applied the k = 1 rule to
  all ancestors and was **unsound** (harness caught 6 mismatches); the chain
  distance `kd[i][j]` fixed it. Label pops in the harness 0.79 -> 0.56.
* **Slot cache.** Successor entries remember their hash slot; slots never move
  within a solve. Small gain, kept.
* A depth threshold for enabling bulk never beat always-on.

## 3. Rejected: hole-crossing lower bound

When the player cannot reach the exit with the unfilled holes treated as walls,
every solution must first bring some block to some hole; the minimum over
(block, hole) pairs of walk + pushes + walk is an admissible bound. Exact, but
it prunes 1-2% of pops on 5x5 and costs ~25% per solve. Compiled out; opt in
with `-DHOLEBOUND`.

## 4. Ancestor-table reuse ("parent tables")

**Idea (the user's: rule out re-solving the parent while solving the child).**
An accepted state P's shortcut check ran to exhaustion with cutoff depth-2, so
for every forward state Y it reached at cost g(Y), any solution through Y has
length >= depth (no solution <= depth-2, and depth-1 is excluded by parity):
rest(Y) >= depth - g(Y). A child C at chain offset k (cutoff depth-2+k) whose
forward search reaches Y at cost nc can skip Y iff
nc + depth - g(Y) > depth - 2 + k, i.e. **nc > g(Y) + k - 2**. For k = 1 this is
"only states the child reaches strictly cheaper than the parent" -- the states
closer to the child's start than to the parent's, about half of them.

**Mechanics.** After an exhaustive check on the small table, the settled
(key, cost) pairs are exported (`sokoban_export_settled`) into a pool entry
(`g_ptab`, reference-counted while the state waits in the DFS queue) and every
child that may use it carries `ptab1 / ptab_k / ptab_delta / ptab_xor`. Keys
are Zobrist over (player, blocks with masks, unfilled holes) and independent of
the walls, so a lookup is direct. Default on; `--no-parent-table` disables.

**Who may use the parent's table** (the forward puzzle must be the parent's, or
the parent's proof says nothing):

* walk-backs over committed cells (the bulk solve; k = walk distance, one
  lookup per candidate shared by all starts);
* push-backs of an existing block along a direction already in its mask;
* **un-consumes** (added in the review): once the new block is consumed into
  the new hole the board is the parent's exactly, so the child's keys for that
  part of its search equal the parent's up to a constant XOR (the consumed
  block's Zobrist term). This required keying hole Zobrist terms by *cell*
  rather than by hole index, so an extra filled hole contributes nothing.
  Un-consume checks lost 61% of their pops (42M -> 16M on the depth-36 seed).
* Children whose puzzle gained floor cells (a newly committed cell) may use it
  only with a **puzzle delta**: prune additionally requires every new cell to
  be too far to be used within the budget. Measured: prunes 0.03% of those
  children's pops -- the new cell is where the player starts, so it is always
  in reach. Kept for soundness only.
* New-block children and push-backs that add a direction change the puzzle in
  ways the proof does not cover (the new block / new direction can be used
  later) and never use a table.

**Completed tables (review).** A child solved with a reference has an
incomplete hash (pruned states are missing). Its labels are costs of real paths
and the reference's entries at +k are also upper bounds on its distances (the
child reaches the owner's start in k moves), so their union is a complete table
of upper bounds and the child's own children can reference *it* at k = 1
instead of inheriting the owner's at k + 1. Exact; gained under 1% of pops.
Kept because it gives un-consume children's descendants proper tables.

**Verification.** `-DREF_CHECK` re-runs every check made with a reference on
without it and compares decisions: 0 mismatches on 2.2M re-run checks across
the benchmark configs. `-DBULK_CHECK` does the same for the multi solve.

## 5. Review of the table code (afternoon)

Why the tables were sound but gave only -14%:

1. **Only a third of solver time was eligible.** Two thirds is spent on
   children whose puzzle differs from the parent's (new block, new direction,
   new cell). Within the eligible third the saving is the predicted half:
   k = 1 references remove 47-49% of a check's pops, inherited references at
   k >= 3 only 16-37% (they prune "nc > g + k - 2", which shrinks as k grows).
2. **The delta rule is dead weight** (0.03%, above).
3. **Per-check rebuilding cost as much as it saved.** Each referenced check
   rebuilt a fixed 64K-slot table (768 KB, cache-hostile) from ~1200 entries --
   about as many hash operations as the check popped -- and the multi solve
   repeated every lookup once per start.

Changes made:

* Tables are built **once at export** as right-sized open-addressing hashes
  (`SokRefTable`, `sokoban_ref_build`) and **attached by pointer**
  (`sokoban_ref_attach`) for the whole expansion of a state; per-child state is
  just k, delta and xor (`sokoban_ref_set_k/_set_xor/_set_reference_delta`),
  and ineligible children run with the table suspended. Builds on the depth-36
  seed: 148M inserted entries -> 83M; peak 29 live tables, 11 MB.
* Lookups happen only for new or improved labels (after the hash update) and
  are hoisted out of the per-start loop in the multi solve: 251M -> 201M.
* Un-consume children and completed tables (section 4).
* Bugs: the 128-bit solver path left the "exhaustive" flag stale and could
  export the previous solve's table for a different state (unreachable on
  5x5 -- needs >= 12 blocks -- fixed); the bulk check harness ran its
  comparison solves with the reference on and reported false mismatches; the
  bulk fallback singles were solved without a reference yet tagged as
  inheriting one (now solved with it at their own offset); during the rework
  the reference was briefly left active after the bulk solve for ineligible
  children -- caught by widening `REF_CHECK` to *every* check made with a
  reference on.

Deterministic counts on the depth-36 seed: 275M solver pops without tables,
207M before the review, 179M after (hash operations 444M -> 367M).

## Addendum 2026-09-21: DFS-order ranges and checkpoints

Every state now carries its path from the root (one byte per backward step;
bulk walk-back children carry the BFS-parent chain of their walk).  Because
children are generated in a fixed order and popped in reverse, the path is the
node's position in the DFS visiting order, which gives one-line checkpoints
(`CURSOR` on Ctrl-C / time cap, resume with `--from`), exact ranges
(`--from`/`--until`), layer listings in visiting order, and contiguous chunks
for the collective proof.  Exactness was checked by comparing visit traces of
full runs against their ranges and against interrupted-plus-resumed runs.  The
seed-path replay now reproduces the generated state exactly (walk history,
bulk-edge marking), and the redundant push-off-exit root seeds were removed
(equivalence counts +3 / +1, see README).
